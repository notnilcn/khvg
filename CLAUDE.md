# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Instructions

1. Do NOT read any of the module bindings in <./client/Scripts/module_bindings>. The code in this folder is automatically generated by SpacetimeDB, so you don't need to know the underlying logic. If you need to look at this code, ask for permission first and provide a reason.
2. Do NOT run 'spacetime publish' or 'spacetime generate'. If it needs to be done, then just say so.
3. Do NOT try to do large tasks all in one go. Break the large task up into smaller tasks and create a CLAUDE.md file in the appropiate folder (e.g. if you're changing the LocalPlayer.cs, then create a CLAUDE.md file in the <./client/Scripts/Characters> folder).
4. Do NOT use Bash. Use Powershell.

## Project Overview

This is a **bullet-hell MMO roguelike** built in **Godot 4.6.3 mono**. Combat is dodge-focused: enemies fire telegraphed parametric bullet patterns, players evade. Exported to Web/HTML5.

The codebase started as a Vampire Survivors-style template and has been rearchitected toward the above vision. **The client is now 100% C# — no GDScript remains.**

**Networking status:** SpacetimeDB multiplayer is working. Multi-profile lobby/world flow, remote player sync with dead-reckoning extrapolation, enemy state sync, AoI via server-filtered view tables, bullet pattern system, texture registry, and torus world wrapping are all implemented. The scene is 2.5D: 2D physics/collision on the main scene with a 3D SubViewport (World3D) overlaid for visuals.

## Scale Target

- **Player cap:** 2048–4096 players per server (powers of 2, not yet decided)
- **World design:** One large persistent torus map — no realm instancing. All players share the same tables. AoI via SpacetimeDB chunk subscriptions prevents clients from receiving every player's data.
- **Single-node is fine** at this scale — horizontal scaling escape hatch is spinning up additional server instances with shared persistence, not built-in clustering
- **Estimated server cost** at 4096 players: ~$300–500/month (financially sound at any reasonable monetization)

## SpacetimeDB Backend

SpacetimeDB is a relational database that is also a server: tables + reducers, clients subscribe to row subsets, scheduled reducers act as game ticks. Deployed on SpacetimeDB maincloud (registered via GitHub account).

**Database name:** `bullethell` on maincloud. Dashboard: `https://spacetimedb.com/@<username>/bullethell`

**Module language: Rust.** Server module lives at `server/spacetimedb/src/` organized into domain modules. Publish with `spacetime publish bullethell --module-path ./spacetimedb` from `server/`. After publishing, regenerate client bindings with `spacetime generate --lang csharp --out-dir ../client/Scripts/module_bindings --module-path ./spacetimedb` from `server/`.

**Key architectural decision: clients connect to SpacetimeDB only.** No separate Godot listen-server. All server authority runs inside SpacetimeDB Rust reducers.

#### Player lifecycle flow

```
client_connected
  └─ inserts LoggedOutPlayer (lobby) + default PlayerProfile ("Knight")

create_profile(name, texture_id)   → adds a profile (max 3 per account)
delete_profile(profile_id)         → removes a profile + associated data
join_world(profile_id)             → moves LoggedOutPlayer → LoggedInPlayer;
                                      scaffolds PlayerData/Stats/Inventory if missing;
                                      inserts PlayerPosition at (0,0)
leave_world()                      → moves LoggedInPlayer → LoggedOutPlayer
client_disconnected
  └─ moves LoggedInPlayer → LoggedOutPlayer
```

#### Player reducers (`server/spacetimedb/src/player/reducers.rs`)

- `set_username(username)` — sets display name (works in lobby or world)
- `create_profile(profile_name, texture_id)` — creates a profile (lobby only, max 3)
- `delete_profile(profile_id)` — deletes profile + data (lobby only)
- `join_world(profile_id)` — enters world with selected profile
- `leave_world()` — returns to lobby
- `report_movement(x, y, rotation)` — updates position; **wraps coordinates for torus world** server-side
- `gain_xp(amount)` — grants XP; max 500 per call; triggers level-up and stat recompute
- `update_inventory(slots)` — replaces inventory slots with validation; triggers stat recompute
- `pickup_drop(drop_id)` — adds loot drop to backpack; deletes drop row

#### Admin / misc reducers (`server/spacetimedb/src/main/admin.rs`)

- `claim_admin` — grants is_admin to caller (works in lobby or world); fails if any admin already exists
- `release_admin` — revokes is_admin from caller
- `change_stats(target_username, profile_name, ...)` — admin: overrides player stats
- `give_item(target_username, profile_name, item_id)` — admin: adds item to inventory

- `place_building(hex_q, hex_r, building_type)` — any logged-in player; places a building on an empty tile

#### Server init (`server/spacetimedb/src/main/lifecycle.rs` / `seeds.rs`)

On first publish (`init` reducer), the server automatically:
1. Starts `EnemyBehaviorSchedule` (100 ms interval) and `EnemySpawnSchedule` (2 s interval)
2. Seeds default textures: Enemy, Archer, Knight (player), Bullet, Arrow
3. Seeds default enemy templates: Enemy (wander/straight), Archer (wander/fast-straight), TestBoss (stationary/multi-pattern spiral+ring)
4. Calls `internal_add_chunks` with defaults (chunk_hex_radius=5, chunk_cols=10, chunk_rows=20, hex_outer_radius=32.0)

#### Torus world wrapping

`report_movement` calls `wrap_world_pos(x, y, ...)` before storing the position. The world is a finite torus: coordinates that go out of bounds on one side wrap to the other. `surrounding_chunk_indices` also wraps chunk coords for AoI computation.

World defaults (in `server/spacetimedb/src/world/methods.rs`):
- `DEFAULT_CHUNK_HEX_RADIUS = 5`
- `DEFAULT_CHUNK_COLS = 10`
- `DEFAULT_CHUNK_ROWS = 20`
- `DEFAULT_HEX_OUTER_RADIUS = 32.0`
- `DEFAULT_AOI_CHUNK_RADIUS = 3` (surrounds 37 chunks)
- `ENEMY_SIMULATION_RANGE = 640.0` (enemies only tick when a player is within this range)

#### Enemy attack system

`AttackDef` uses an `AttackSequence` (list of `SequenceStep`s) instead of a flat pattern/target pair. Each step is either:
- `SequenceSingle` — fires once, then optionally waits
- `SequenceRepeat` — fires N times at an interval, then optionally waits

`BulletPatternEvent` now carries `origin_offset_x/y`, `base_angle_offset`, and `texture_id` per event. The client reads these when spawning bullets.

### AoI (partially wired)

`PlayerPosition`, `Enemy`, `LootDrop`, `BulletPatternEvent` each carry a `chunk_index: i64` column (btree indexed) computed from the entity's chunk axial coords using the hex spiral formula.

**AoI is enforced server-side** via view tables (`NearbyRemotePlayers`, `NearbyEnemies`). The server filters each client's subscription to rows whose `chunk_index` falls within the player's surrounding `DEFAULT_AOI_CHUNK_RADIUS` (3) rings of chunks — approximately 37 chunks.

**Not yet wired:** the client does not re-subscribe when the player crosses a chunk boundary, so the AoI window is fixed at `join_world` time.

**Chunk index formula (hex spiral) — same on server and client:**

1. Convert axial (cq, cr) → cube: `x = cq`, `z = cr`, `y = −cq − cr`
2. Ring radius: `ρ = max(|x|, |y|, |z|)`
3. If ρ = 0: index = 0
4. Otherwise: `index = 3ρ(ρ−1)+1 + arm×ρ + step`, where arm/step are determined by which face of the ring (see `spiral_chunk_index` in `methods.rs` and `HexSpiralIndex` in `HexGridOverlay2D.cs`)

### Position reporting and validation

Clients send `ReportMovement(float x, float y, float rotation)` at 10 Hz. The server wraps the coordinates (torus), recomputes `chunk_index`, and updates `PlayerPosition`.

Other clients receive updates via `NearbyRemotePlayers.OnUpdate` and extrapolate using dead-reckoning (velocity = `Speed * SpeedPerStat` in direction of `rotation`). A `WrapSnapThreshold` (50 units) detects torus teleportation and snaps immediately.

### Enemy position sync strategy

Enemy positions are server-authoritative. `tick_enemy_behavior` (100 ms) updates movement and fires `BulletPatternEvent` rows. Clients lerp toward server positions.

**Enemy targeting — `EnemyTarget` enum:**

```
Idle              — no target; enemy does not move
NearestPlayer     — client computes nearest player independently each frame
NearestCluster    — client computes centroid of nearest player cluster independently
SpecificPlayer(Identity) — all clients chase the same named player; no divergence
```

**Enemy phase system:**
- `EnemyTemplate.phases` → `Vec<PhaseDef>` — static: `phase_index`, `hp_threshold`, `movement`, `attacks` (Vec<AttackDef>)
- `AttackDef.attack` → `AttackSequence` with `steps: Vec<SequenceStep>` (Single | Repeat) and `loop_sequence: bool`
- `EnemyBehavior.phases` → `Vec<PhaseInstance>` — runtime state with `Vec<AttackInstance>` tracking per-attack fire timers

### Bullet system (completed)

The server writes a `BulletPatternEvent` row when an enemy fires. `BulletManager.Spawn(evt)` applies the origin offset, resolves the base angle (from `target` identity → player position), adds `BaseAngleOffset`, loads the texture via `GetResPath(evt.TextureId)`, then dispatches:

| PatternType | Spawner | Key params |
|-------------|---------|-----------|
| `Straight` | `SpawnStraight` | speed, count |
| `Ring` | `SpawnRing` | speed, count (360° distributed) |
| `Sine` | `SpawnSine` | speed, count, amplitude, frequency |
| `Burst` | `SpawnBurst` | speed, count, spread (radians) |
| `Spiral` | `SpawnSpiral` | speed, count, arms, rotation_speed |
| `Homing` | `SpawnHoming` | speed, count, turn_rate |

All bullets use `DirectionalBulletsData2D` → `BulletFactory2D.spawn_directional_bullets`. Collision layer 3 (Enemy), mask layer 2 (Player), size 8×8 px, lifetime 8 s.

## Hex Grid

**Continuous grid** — player/enemy/bullet positions as `Vector2`. All physics, movement, and collision operate here.

**Hex grid** — buildings and terrain as axial coordinates `(q, r)` integers. Pointy-top hex math:
```
x = R * sqrt(3) * (q + r/2)
y = R * 1.5 * r
```
Hex size `R` = `hex_outer_radius` in MapConfig (default 32.0). Must be chosen once and never changed — it invalidates all stored coordinates.

### What is implemented

- **`BuildingTile` table** — all hex tiles generated by `add_chunks`/`init`. Auto-seeded on first publish.
- **`MapConfig` singleton** — written by `add_chunks`, read by all reducers. Fallback constants in `world/methods.rs`.
- **`HexGridOverlay2D.cs`** — C# debug overlay; draws hex grid with chunk coloring, coordinates, spiral indices, out-of-bounds shading, torus seam highlighting.
- **Server hex math** — `world/methods.rs` wraps the `hexx` crate: `world_to_hex`, `hex_to_world`, `small_to_big`, `hexmod`, `inv_hexmod`, `chunk_center_hex`, `world_to_chunk`, `spiral_chunk_index`, `surrounding_chunk_indices`, `wrap_world_pos`, `wrap_chunk_coords`.
- **Torus wrapping** — `report_movement` wraps positions server-side. AoI queries wrap chunk indices.

### What is NOT yet implemented

- Building placement / mutation client UI
- Tile claiming system
- Enemy-vs-structure combat

## Anti-Cheat System

### Authority model

**Stats:** Server authority always. `PlayerStats` are recomputed server-side from level + gear — never accepted from clients.

**Combat:** Client authority by default. Clients self-report bullet hits on enemies. The server calculates damage from reports. Because this is PvE, combat cheating only harms the cheater — delayed detection and banning is acceptable.

**Economy:** Server authority always. Drops, trades, purchases, and inventory mutations are validated server-side.

### Swarm anti-cheat

Honest clients report bullet collisions for other players in their AoI. If a cheater fails to self-report being hit, other clients' reports raise their `suspicion_score`.

### Movement history logging

Position history is only written to `PlayerPositionHistory` for players above a `suspicion_score` threshold. Below the threshold, `PlayerPosition` alone is sufficient.

### Batch audits

Audits run non-live, once per day:
1. Reconstruct player positions from `PlayerPositionHistory` snapshots
2. Reconstruct bullet positions from `BulletPatternEvent` rows (deterministic parametric math)
3. Check for statistically implausible bullet evasion
4. Check for implausible damage reports (exceeds weapon stats or out of range)
5. Adjust `suspicion_score`

### Wave banning

Bans from audit findings are queued and released in periodic waves to prevent reverse-engineering of detection methods.
