## Project Overview

This is a **bullet-hell MMO roguelike** built in **Godot 4.6.1 mono**. Combat is dodge-focused: enemies fire telegraphed parametric bullet patterns, players evade. Exported to Web/HTML5. The client is 100% C# — no GDScript remains.

**Backend:** SpacetimeDB (Rust module). Clients connect to SpacetimeDB only — no separate Godot listen-server. All server authority runs inside SpacetimeDB Rust reducers. Database name `bullethell` on maincloud, dashboard at `https://spacetimedb.com/@<username>/bullethell`.

## Running and Developing

- **Engine:** Godot 4.6.1 mono (`Godot_v4.6.1-stable_mono_win64.exe`) — the mono build is required for C# and SpacetimeDB
- **Run game:** Press F5 in Godot editor (main scene: `Scenes/main.tscn`)
- **Export:** Web/HTML5 preset configured in `export_presets.cfg`
- **No build system** — Godot handles compilation internally
- **⚠️ NuGet warning:** Never use **Project → Tools → C# → Create C# solution** — it regenerates the `.csproj` from scratch and wipes the `SpacetimeDB.ClientSDK` package reference. The solution already exists. If the package reference is ever lost, run `dotnet add package SpacetimeDB.ClientSDK --version 2.1.0` while Godot is closed.

## Scale Target

- **Player cap:** 2048–4096 players per server (powers of 2, not yet decided)
- **World design:** One large persistent map — no realm instancing. All players share the same tables. AoI via SpacetimeDB chunk subscriptions is what prevents clients from receiving every player's data.
- **Single-node is fine** at this scale — horizontal scaling escape hatch is spinning up additional server instances with shared persistence, not built-in clustering
- **Estimated server cost** at 4096 players: ~$300–500/month (financially sound at any reasonable monetization)

## Hex Grid

BitCraft-style dual coordinate system. Two grids coexist independently:

**Continuous grid** — player/enemy/bullet positions as `Vector2`. All physics, movement, and bullet hit detection operate here.

**Hex grid** — buildings and terrain as axial coordinates `(q, r)` integers. Pointy-top hex math:
```
x = R * sqrt(3) * (q + r/2)
y = R * 1.5 * r
```
Hex size `R` (`hex_outer_radius` in `MapConfig`, default 32.0) must be chosen once and never changed — it invalidates all stored coordinates.

### Chunk index formula (hex spiral) — must match on server and all clients

Implemented in `world/methods.rs` (`spiral_chunk_index`, `surrounding_chunk_indices`):

1. Convert axial (cq, cr) → cube: `x = cq`, `z = cr`, `y = −cq − cr`
2. Ring radius: `ρ = max(|x|, |y|, |z|)`
3. If ρ = 0: index = 0
4. Otherwise: `index = 3ρ(ρ−1)+1 + arm×ρ + step`, where arm/step are determined by which face of the ring cube (cq, cr) lies on

This bijection is unique for all integer (cq, cr) including negative values.

### Architectural rules

- All collision math is in continuous `Vector2` space — never in hex coordinate space. Building positions are converted to world space via `hex_to_world` before any collision check. The hex grid and the spatial hash grid (for AoI/hit detection) are different things at different granularities. Don't conflate them.
- **Bullets can hit buildings.** Enemy bullets interact with player structures; building damage is handled by the elevated client (which already owns enemy bullet trajectories) calling a `DamageBuilding` reducer. Other clients react to the building's HP changing via subscription — no client-side determinism required for building damage.
- **Building placement requires a claimed zone.** Players can only place buildings in tiles they have claimed. Enemies can enter and attack structures in claimed zones (raids are intentional). Bullet patterns are always fired in unclaimed territory, so buildings cannot appear mid-pattern in the area the audit reconstructs for player-evasion checks.
- `BuildingTile` needs a `destroyed_at` timestamp (nullable) so the batch audit can reconstruct which buildings existed during a given audit window.

## Anti-Cheat System (target design)

### Authority model

**Stats:** Server authority always. `RpgStats` (STR/WIS/DEX/DEF/VIT/SPD) are written only by the elevated client or admin reducers — never accepted from regular clients.

**Combat:** Client authority by default. Clients self-report both getting hit by bullets and landing hits on enemies. The server calculates damage from those hit reports, but relies on clients to report hits in the first place. Because this is PvE, combat cheating only harms the cheater — delayed detection and banning is acceptable. This is intentional; it means zero server overhead for honest players and gives a lever to tighten enforcement if abuse becomes a real problem.

**Economy:** Server authority always. Drops, trades, purchases, and inventory mutations are validated server-side. Economy cheating has cross-player impact so it is never deferred to auditing.

### Swarm anti-cheat

Honest clients will be able to tell the server when another player is cheating. For bullet collisions, players perform those collisions for all other players within their AoI and report them to the server. If a player cheats by not reporting that they were hit, other players will still tell the server, and the cheater's `suspicion_score` will increase.

### Movement history logging

SpacetimeDB advises against high-frequency logging for all players. Position history is therefore only written to a `PlayerPositionHistory` table for players whose `suspicion_score` is above a threshold. Below the threshold, `PlayerPosition` alone is sufficient for live gameplay.

### Batch audits & wave banning

Audits run non-live, once per day, via an external script (not a STDB reducer): reconstruct player positions from `PlayerPositionHistory`, reconstruct bullet positions from `BulletPatternEvent` rows, check for implausible bullet evasion or implausible outgoing damage, and adjust `suspicion_score`. Bans from audit findings are queued and released in periodic waves — not applied immediately — so cheaters can't correlate ban timing to a specific action.
