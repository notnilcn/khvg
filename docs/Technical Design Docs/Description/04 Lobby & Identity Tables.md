## The 30-second version

Three tables carry *who you are* and *whether you're in the world*. `LoggedOutPlayer` and `LoggedInPlayer` are one row per connection, keyed by the SpacetimeDB `Identity`, and the pair acts as a two-state login machine: lifecycle hooks (`client_connected`/`client_disconnected`) and the lobby reducers (`join_world`/`leave_world`, plus the combat death cleanup) move the row between the two tables — it is never in both. `PlayerProfile` is the character roster: up to three rows per identity, created at first connect and by `create_profile`, chosen by `join_world`, deleted by `delete_profile`. The client reads all three through per-caller views (`local_lobby_player` and `local_player_profiles` in the `LobbyTables` wave; `local_player` and `local_player_active_profile` in `GameTables`), and the lobby UI lives in `LobbyComponent`, which calls the reducers and shows/hides itself off the `LocalPlayer` row's arrival.

## Main body

### Why identity is two tables instead of a flag

A SpacetimeDB *reducer* is a transactional server function the client calls by name; *lifecycle hooks* (`#[reducer(client_connected)]` etc.) are reducers the runtime invokes itself on connect/disconnect. The module splits login state into `LoggedInPlayer` (public, carrying the chosen `profile_id`) and `LoggedOutPlayer` (not public, no `profile_id`) — [[server/spacetimedb/src/player/tables.rs#LoggedInPlayer|definitions]] — *because* the split gives the two most common server questions one-row answers: every gameplay reducer opens with [[server/spacetimedb/src/player/methods.rs#require_in_world|require_in_world]] (find the `LoggedInPlayer` row by `ctx.sender()` or fail), and the lobby reducers open with [[server/spacetimedb/src/player/methods.rs#require_in_lobby|require_in_lobby]] (find the `LoggedOutPlayer` row or fail). A reducer therefore cannot accidentally run for a player in the wrong state — `create_profile`, `delete_profile`, and `join_world` are lobby-only; `report_movement`, `report_hit`, and friends are world-only. The guards live in `player/methods.rs` alongside [[server/spacetimedb/src/player/methods.rs#require_logged_in|require_logged_in]] (same check as `require_in_world`, discarding the row) and [[server/spacetimedb/src/player/methods.rs#is_admin|is_admin]], which reads `is_admin` from whichever of the two tables currently holds the caller's row.

`username` and `is_admin` are duplicated onto both tables *because* a transition deletes one row and inserts the other, and both fields must survive the move — every transition copies them across (`leave_world` in [[server/spacetimedb/src/player/reducers.rs#leave_world|player/reducers.rs]] is the clearest example). `profile_id` lives only on `LoggedInPlayer`, as a `#[unique]` column: one identity drives at most one profile in the world, and the value is what every per-caller game view (`local_player_data`, `local_player_position`, …) resolves the caller's rows through — see [[03 Connection, Subscriptions & Views]] for that pattern.

### The lifecycle, state by state

**First connect.** [[server/spacetimedb/src/main/lifecycle.rs#client_connected|client_connected]] finds no row in either table, so it inserts a `LoggedOutPlayer` row with an empty username *and* a default `PlayerProfile` named "Knight" with `texture_id` "Knight" — a brand-new identity lands in the lobby with one playable character already, so the character-select screen is never empty on first run. **Reconnect while in the lobby** hits the `else if !in_lobby` guard and does nothing — the existing row is kept. **Disconnect from the world** is [[server/spacetimedb/src/main/lifecycle.rs#client_disconnected|client_disconnected]]: it purges the profile's statuses and zones first (no status may tick a logged-out player, and a caster's zones die with them), then deletes the `LoggedInPlayer` row and inserts the matching `LoggedOutPlayer` row. A disconnect *from the lobby* deletes nothing — the `LoggedOutPlayer` row persists across sessions, which is what makes "reconnect while in the lobby" a no-op.

**Joining.** [[server/spacetimedb/src/player/reducers.rs#join_world|join_world]] is the lobby→world transition: `require_in_lobby` proves the caller is in the lobby and yields the row to copy from; the profile must exist and belong to the caller; then the `LoggedOutPlayer` row is deleted, the `LoggedInPlayer` row is inserted with the chosen `profile_id`, and [[server/spacetimedb/src/player/methods.rs#try_scaffold_profile|try_scaffold_profile]] builds the profile's gameplay rows (data, inventory, position at the world origin, …). **Leaving** is [[server/spacetimedb/src/player/reducers.rs#leave_world|leave_world]]: purge statuses/zones, delete the `LoggedInPlayer` row, insert the `LoggedOutPlayer` row. **Death** takes the same exit — [[server/spacetimedb/src/combat/mod.rs#deal_damage_to_player_opts|deal_damage_to_player_opts]] runs the shared [[server/spacetimedb/src/player/methods.rs#teardown_profile|teardown_profile]] cleanup (which *does* delete position/inventory rows, unlike `leave_world`) and moves the player to `LoggedOutPlayer`. Death is a full character reset; leaving is a pause.

Two reducers update the identity rows in place. [[server/spacetimedb/src/player/reducers.rs#set_username|set_username]] (1–20 non-whitespace chars) updates whichever of the two tables holds the caller — it has no lobby/world guard *because* renaming is legal in both states. [[server/spacetimedb/src/main/admin.rs#claim_admin|claim_admin]] / [[server/spacetimedb/src/main/admin.rs#release_admin|release_admin]] flip `is_admin` the same way, enforcing the single global admin slot: `claim_admin` fails if *any* row in either table already has `is_admin`. No first-party client code calls `set_username` today (only the generated bindings expose it), so `Username` stays empty unless set through the `spacetime` CLI — see Known gaps.

### PlayerProfile: the character roster

`PlayerProfile` ([[server/spacetimedb/src/player/tables.rs#PlayerProfile|definition]]) is one row per character: auto-increment `profile_id` primary key, `player_id` back-pointer (btree — the per-caller views filter on it), `profile_name`, `texture_id`, and the `aim_assist`/`lock_on` toggles. Writers are few and simple: [[server/spacetimedb/src/player/reducers.rs#create_profile|create_profile]] is lobby-only, caps the roster at three, and rejects case-insensitive duplicate names within the caller's own roster (it collects the caller's rows via the `player_id` btree and compares in memory; the composite `by_player_profile_name` index is declared but nothing queries it yet). The admin give/remove flows look profiles up through [[server/spacetimedb/src/player/methods.rs#find_profile_by_name|find_profile_by_name]], the same ownership-scoped case-insensitive match. [[server/spacetimedb/src/player/reducers.rs#delete_profile|delete_profile]] is lobby-only, verifies ownership, then runs `teardown_profile` before deleting the row *because* the profile's gameplay rows must not orphan — a deleted character leaves nothing behind. The row is **never updated**: there is no rename/edit-profile reducer, so `aim_assist`/`lock_on` stay at the `false` defaults every insert stamps.

One quirk of the default profile: `try_scaffold_profile` ([[server/spacetimedb/src/player/methods.rs#try_scaffold_profile|player/methods.rs]]) checks whether the joining profile is literally named "Knight" and, if so, seeds its stat allocation with 999 points per stat — the auto-created first profile starts maxed for testing, while `create_profile` characters start at zero. The name check, not any flag on the row, is the discriminator.

### The client: two scenes, one login machine

The client is a Godot scene tree: `main_menu.tscn` is the entry scene, and its root script [[client/Scripts/Game/LobbyGui.cs|LobbyGui]] is menu navigation only — `CharSlotsPressed` swaps the whole scene to `game.tscn`, and the ServerList/Settings buttons just show/hide panels. Everything table-driven happens in `game.tscn`.

The `DatabaseConnector` autoload ([[client/sstdbsdk/DatabaseConnector.cs|sstdbsdk]]) owns the connection and pumps `FrameTick()` every frame. On connect it does two lobby-relevant things: it hooks `conn.Db.LocalLobbyPlayer.OnInsert/OnUpdate` internally ([[client/sstdbsdk/DatabaseConnector.cs#OnConnected|DatabaseConnector.OnConnected]]) to mirror the row's `username` into its `Username` property — one of only two places outside the binder pattern that touches table callbacks directly (the other is `TableSubscriber`'s `MapConfig` lap vectors) — and fires its `Connected` signal, on which `TableSubscriber` subscribes the `BaseTables` wave and then `SubscribeLobby()` ([[client/sstdbsdk/TableSubscriber.cs#OnConnected|TableSubscriber]]): the `LobbyTables` wave is exactly `LocalLobbyPlayer` + `LocalPlayerProfiles`.

The lobby UI itself is `LobbyComponent`, declared under `UI` in [[client/Scenes/game.tscn|game.tscn]] as an instance of `lobby_component.tscn` — that scene is the **live wiring site** for its child `LocalPlayerProfilesBinder` (`TableName = "LocalPlayerProfiles"`, `ReplayExistingRows = true`, `RowInserted` → `OnProfileRowInserted`). Replay matters here *because* the binder node is created when `game.tscn` loads, potentially after the lobby subscription already delivered the profile rows: replay re-fires the cached rows through `RowInserted` so the panels appear without a separate catch-up read. Each insert instantiates one `profile_panel.tscn` (a plain `Panel` with Name/ID labels, an Icon sprite, and Join/Delete buttons — no script of its own; [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnProfileRowInserted|LobbyComponent]] fills the labels and hooks the buttons in code) and tracks it in a `Dictionary<ulong, Control>` keyed by `ProfileId`, so replayed inserts can't duplicate a panel and deletion goes straight to the panel.

The join flow ([[client/Scripts/Components/Lobby/LobbyComponent.cs#OnJoinPressed|LobbyComponent.OnJoinPressed]]) is deliberately pessimistic: it sets `joinPending`, hooks the `OnJoinWorld` reducer event, calls `JoinWorld(profileId)`, despawns any live entities, and swaps subscription waves (`SubscribeGame` + `UnsubscribeLobby`) — but the lobby **stays visible** until proof of success. Success proof is not the reducer callback (a reducer returns nothing; "committed" only means the transaction didn't fail) but the arrival of the `LocalPlayer` view row: EntitySpawnerComponent's `LocalPlayerBinder` in `game.tscn` fires `OnLocalPlayerInsert`, which spawns the local-player puppet and calls `LobbyComponent.HideLobby()` ([[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerInsert|EntitySpawnerComponent]]). The failure paths are the reducer event reporting `Failed`/`OutOfEnergy` ([[client/Scripts/Components/Lobby/LobbyComponent.cs#OnJoinWorldResult|OnJoinWorldResult]]) or a `JoinTimeoutSeconds` (5 s) timer firing first — both route to `FailJoin`, which swaps the waves back (`UnsubscribeGame` + `SubscribeLobby`) and shows the reason in the `JoinError` label. `HideLobby`/`ShowLobby` also drive the menu `PhantomCamera2D` priority (60 in the lobby, 0 in the world) *because* the phantom_camera addon picks the highest-priority camera, so the same toggle controls both UI and viewpoint.

The reverse transition needs no UI code: when the `LocalPlayer` row disappears (death, `leave_world`, disconnect-and-reconnect), `OnLocalPlayerDelete` despawns everything, re-shows the lobby, and swaps back to the lobby wave ([[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerDelete|EntitySpawnerComponent]]) — the row delete *is* the "back to character select" signal.

### The profile row in the live world

Once in the world, `PlayerProfile` reaches the client two more ways. The local player's own active profile streams through `local_player_active_profile` ([[server/spacetimedb/src/player/views.rs#local_player_active_profile|player/views.rs]] — resolves `profile_id` from the caller's `LoggedInPlayer` row, with a `u64::MAX` sentinel so a logged-out caller matches nothing) in the `GameTables` wave. The consumer is `LocalPlayerProfileComponent` with its child `LocalPlayerActiveProfileBinder`, both declared inline in [[client/Scenes/local_player.tscn|local_player.tscn]] (replay on; `RowInserted`/`RowUpdated` wired there): insert sets `ProfileName`, resolves `texture_id` through the catalog's `GetResPath`, swaps the sprite's `SpriteFrames`, and raises `AimSettingsChanged` on the `LocalPlayer` entity so `CombatComponent` re-reads `aim_assist`/`lock_on` ([[client/Scripts/Components/Visual/LocalPlayerProfileComponent.cs|LocalPlayerProfileComponent]]). `LocalPlayerProfiles` is also in the `GameTables` wave (it appears in both waves), so the roster survives the lobby→game wave swap.

Remote players' profiles arrive AOI-filtered through `nearby_remote_players_profiles` ([[server/spacetimedb/src/player/views.rs#nearby_remote_players_profiles|player/views.rs]] — a right semijoin of `PlayerProfile` over the same chunk-filtered `PlayerPosition` scan as `nearby_remote_players`, *because* the query builder can't filter the right side of a left semijoin). No binder consumes it: [[client/Scripts/Players/Remote/RemotePlayer.cs|RemotePlayer]] does a one-shot `Iter()` lookup by `ProfileId` at spawn to pick its sprite texture — fine *because* profile rows change rarely (never updated server-side) and the spawn-time read is the only consumer.

## Known gaps / stubs

- **`client_connected` mishandles the already-in-world case.** When an identity connects while it already has a `LoggedInPlayer` row, the hook logs `log::error!("Player ... connected while already in world — this is a bug.")` but then *recovers destructively*: it purges the player's statuses/zones, deletes the `LoggedInPlayer` row, and inserts a `LoggedOutPlayer` row — bouncing the player back to the lobby instead of rejecting the duplicate connection. Flagged as a bug only inside the log message itself, not in a comment ([[server/spacetimedb/src/main/lifecycle.rs#client_connected|main/lifecycle.rs]]).
- **`LobbyGui` is scene navigation only** — `main_menu.tscn`'s menu is not wired to any reducer; the `create_profile`/`join_world`/`delete_profile` calls all live in `LobbyComponent` inside `game.tscn`. Its ServerList and Settings panels are show/hide shells with no behavior ([[client/Scripts/Game/LobbyGui.cs|LobbyGui]]).
- **No client UI calls `set_username`.** Only the generated bindings expose it; `DatabaseConnector.Username` mirrors whatever the `local_lobby_player` row holds, which stays `""` unless the reducer is called from the CLI.
- **Leftover debug `GD.Print`** in [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnProfileRowInserted|LobbyComponent.OnProfileRowInserted]] ("Successfully synced a profile …") fires on every profile row insert/replay.
