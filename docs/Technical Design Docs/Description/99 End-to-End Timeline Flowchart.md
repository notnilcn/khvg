# 99 End-to-End Timeline Flowchart

The single chronological narrative all the system docs (01–09) transclude their steps from — see [[00 Roadmap|00's conventions section]] for the sync-embed and anchor syntax. Read top to bottom for the full story of a player's session; read a system doc for the "why" behind any one section.

## 01 Server bootstrap

The server module boots once, when it's first published (or republished after `--clear-database -y`) — before any client ever connects. Full detail: [[01 Architecture & Sync Model|01]].

1. Publishing the module runs SpacetimeDB's `init` lifecycle reducer exactly once. `init` first inserts one row into each of three scheduled tables — `EnemyBehaviorSchedule` (100ms interval), `EnemySpawnSchedule` (2s interval), `ConsumableEffectSchedule` (`CONSUMABLE_EFFECT_TICK_SECONDS`, 1s by default). A scheduled table is a normal table whose rows carry a `ScheduleAt` time or interval; SpacetimeDB automatically invokes the paired reducer when a row's time comes due, which is how this project runs its always-on ticks (enemy behavior in [[06 Enemy AI & Bullet Patterns|06]], enemy spawning also 06, consumable buff/DoT ticks in [[05 Item, Equipment & Enchantment System|05]]) without any client driving them. [[lifecycle.rs##pub fn init|init]] ^boot-1
2. `init` then seeds static content in a fixed order: default textures, terrain layering rules, adjacency rules, decor-ground rules, default enemy templates plus five hand-authored test-boss phase progressions, world item and enchantment catalogs, and world-generation defs (biomes, regions). These are the `seed_*` helpers in `main/seeds.rs` and `item/seeds.rs` — each just inserts rows the way any reducer would; there's nothing magic about "seeding" beyond it happening inside `init`. Enemy template shape: [[06 Enemy AI & Bullet Patterns|06]]. Item/enchantment shape: [[05 Item, Equipment & Enchantment System|05]]. World-gen rule tables: [[03 World & Hex Grid|03]]. ^boot-2
3. `init` lays out the chunk grid — `internal_add_chunks(ctx, DEFAULT_CHUNK_HEX_RADIUS, DEFAULT_CHUNK_COLS, DEFAULT_CHUNK_ROWS, DEFAULT_HEX_OUTER_RADIUS)` — using the tunables from `main/global.rs`, the single file every subsystem's constants live in (chunk/hex sizing, AOI radii, player stat baselines, inventory layout, enemy tick rate, world timers). [[global.rs##pub const DEFAULT_CHUNK_HEX_RADIUS|global.rs]] ^boot-3
4. `init` generates the starting world's terrain onto that chunk grid — `internal_generate_world_proc(ctx, "Earth", 0)`, a fixed seed so every fresh publish produces the same map. This is the same generation entry point the admin `generate_world_proc` reducer calls later ([[09 Admin, Debug & World Lifecycle|09]]); full pipeline detail is [[03 World & Hex Grid|03]]. [[lib.rs##mod world;|lib.rs module list]] ^boot-4
5. Once `init` returns, the module is idle — tables populated, three scheduled ticks already running against an empty player base — and sits waiting for a client to connect. That's `02 A client connects`, next. ^boot-5

## 02 A client connects

1. The client's `main.tscn` scene loads with `GameManager` (`Node2D, IEntity`) as its root ("Main"); `GameManager._Ready` stashes a static `instance` reference so the static facade (`GameManager.Conn`, `.Username`, `.GetItem(...)`, etc.) has something to delegate to. Full entity/component boot order is [[02 Entity & Component Framework|02]]'s concern — the relevant part here is that `ConnectionComponent`, a child of Main, registers itself during this same tree-entry pass. [[GameManager.cs##public override void _Ready|_Ready]] ^conn-1
2. `ConnectionComponent.OnRegistered` fires immediately on registration and calls `Connect(Host, DbName)` — default `http://127.0.0.1:3000`, database `"bullethell"` — which builds a `DbConnection` via SpacetimeDB's builder pattern (`WithUri`/`WithDatabaseName`/`WithToken(null)`/`OnConnect`/`OnConnectError`/`OnDisconnect`) and returns immediately; the actual handshake happens asynchronously. `WithToken(null)` means every connection today is anonymous — the commented-out `AuthToken.Init`/`SaveToken` calls are a stubbed-out persistent-login path, not yet wired up (see Known gaps). [[ConnectionComponent.cs##protected override void OnRegistered|OnRegistered]] · [[ConnectionComponent.cs##public void Connect|Connect]] ^conn-2
3. Server-side, SpacetimeDB fires the `client_connected` lifecycle reducer for the new identity. The common case — this identity has never connected before — falls into neither `logged_in_player` nor `logged_out_player`, so the reducer inserts a blank `LoggedOutPlayer` row (empty username) and a default `PlayerProfile` row (`profile_name`/`texture_id` both `"Knight"`). If the identity is found already `in_world` (a `LoggedInPlayer` row exists), that's logged as a bug — a reconnect while a prior session's cleanup never ran — and the reducer force-moves that row to `LoggedOutPlayer` rather than leaving two live rows for one identity. [[lifecycle.rs##pub fn client_connected|client_connected]] ^conn-3
4. Once SpacetimeDB acknowledges the connection, `ConnectionComponent.OnConnected` runs client-side: stores `LocalIdentity`, wires `LocalLobbyPlayer`'s `OnInsert`/`OnUpdate` to keep `Username` current, then emits the `Connected` Godot signal. Every sibling component that needs the connection (`SubscriptionComponent`, `CatalogComponent`, and others per [[02 Entity & Component Framework|02]]) hooked `Connected` during its own `OnRegistered` and reacts now, not before — the connection genuinely doesn't exist until this point. [[ConnectionComponent.cs##private void OnConnected|OnConnected]] ^conn-4
5. `SubscriptionComponent.OnConnected` opens the **base wave**: a subscription (a live query SpacetimeDB keeps continuously in sync, pushing inserts/updates/deletes as they happen — not a one-shot fetch) over `AllTextures`, `AllItems`, `AllEnchantments`. These three are unfiltered, whole-table views — static catalog data every screen needs regardless of lobby/in-world state — so they're subscribed once, up front, and never torn down for the life of the connection. [[SubscriptionComponent.cs##private void OnConnected|OnConnected]] ^conn-5
6. In the same call, `SubscriptionComponent` invokes `SubscribeLobby()`, opening the **lobby wave** — `LocalLobbyPlayer`, `LocalPlayerProfiles` — with an `OnApplied` callback. This is a second, separate subscription handle (`lobbySub`) so it can be torn down independently via `UnsubscribeLobby()` once the player joins the world and the **game wave** (`SubscribeGame()`) takes over; that hand-off, and everything the lobby UI does with these two tables, is [[04 Player System|04]]'s `lobby-N` steps. [[SubscriptionComponent.cs##public void SubscribeLobby|SubscribeLobby]] ^conn-6
7. In parallel, `CatalogComponent.OnConnected` (also hooked to `Connected`) wires `OnInsert`/`OnUpdate`/`OnDelete` for the same `AllTextures`/`AllItems`/`AllEnchantments` base-wave rows into three local dictionaries (`textureCache`/`itemCache`/`enchantmentCache`). This is the cache `GameManager`'s static facade reads from (`GetItem`, `GetEnchantment(s)`, `GetResPath`) — by the time any UI calls one of those, the base wave has already been open since `conn-5`, so the cache is warm well before it's needed for lobby profile textures or inventory rendering. [[CatalogComponent.cs##private void OnConnected|OnConnected]] ^conn-7

## 03 Lobby and profile creation

1. Once the base and lobby subscriptions from [[01 Architecture & Sync Model|01]]'s `conn-5`/`conn-6` are open, `LobbyComponent.OnRegistered` — which runs synchronously during `Main`'s own `_Ready` pass, before any subscription has necessarily applied — calls `ShowLobby()` (raises the lobby UI's `PhantomCamera2D` priority so it's the active camera) and wires `LocalPlayerProfiles.OnInsert` to `OnProfileInsert`. Every player has at least one `PlayerProfile` row already: `client_connected` (`conn-3`) inserts a default `"Knight"`/`"Knight"` profile for a never-before-seen identity, so the moment the lobby subscription's rows land, `OnProfileInsert` fires once for that default profile alone — a first-time player sees one character-select panel without ever calling `create_profile`. [[LobbyComponent.cs##protected override void OnRegistered|OnRegistered]] · [[LobbyComponent.cs##private void OnProfileInsert|OnProfileInsert]] ^lobby-1
2. `OnProfileInsert` builds one panel per row (name label, id label, Join/Delete buttons wired to that specific `PlayerProfile` by closure) — this is the only place panels are created, so a player-authored profile arrives through the exact same path as the seeded default one: `create_profile` (`player/reducers.rs`) validates the name (1-20 non-whitespace characters), enforces a 3-profile cap and case-insensitive uniqueness per player, then inserts a new `PlayerProfile` row with a hardcoded `texture_id: "Knight"` — the create panel's `LineEdit` never offers a texture choice even though the column exists, so every profile a player creates today looks identical to the default one. [[player/reducers.rs##pub fn create_profile|create_profile]] ^lobby-2
3. `delete_profile` requires the caller to be in the lobby and to own the profile, then calls `teardown_profile` (the archetype helper `try_scaffold_profile`'s inverse — full mechanism in [[02 Entity & Component Framework|02]]) before deleting the `PlayerProfile` row itself; for a profile that never joined the world, `teardown_profile`'s five deletes are all no-ops, since nothing was ever scaffolded for it. Client-side, `OnDeletePressed` doesn't wait for a row-delete event to confirm the reducer succeeded — it fires `DeleteProfile` and, in the same call, scans the panel container for a child whose `ID` label text-converts to the deleted profile's id and frees it directly, an optimistic removal that would leave a stale panel on screen if the reducer were ever rejected server-side (today it can only fail on an ownership check a well-behaved client can't trigger against its own panel). [[player/reducers.rs##pub fn delete_profile|delete_profile]] · [[LobbyComponent.cs##private void OnDeletePressed|OnDeletePressed]] ^lobby-3

## 04 Joining the world

1. Clicking Join (`OnJoinPressed`, guarded against firing while the create panel is open) hides the lobby UI immediately, fires the `JoinWorld` reducer, and in the same call switches subscription waves — `SubscribeGame()` then `UnsubscribeLobby()` — without waiting for any acknowledgment that `join_world` actually succeeded server-side; reducers don't return data to callers ([[00 Roadmap|conventions]]), so the client's only real signal that joining worked is rows starting to arrive on the new game-wave subscription, not this call itself. [[LobbyComponent.cs##private void OnJoinPressed|OnJoinPressed]] ^join-1
2. Server-side, `join_world` requires the caller to be in the lobby and to own the requested profile, deletes the `LoggedOutPlayer` row, inserts a `LoggedInPlayer` row carrying that `profile_id`, then calls `try_scaffold_profile` — the same idempotent archetype helper from [[02 Entity & Component Framework|02]]. For a profile's first-ever join, this is where its `PlayerData` (level 1, `xp` 0, hp/max_hp at `BASE_MAX_HP`), `PlayerStats`, `PlayerInventory` (the starter loadout — Bow equipped, Bread/Hat/Helmet/Skull/Bag placed in their type-matched slots, detailed in [[05 Item, Equipment & Enchantment System|05]]), `PlayerPosition`, and `PlayerChunk` rows are first created; for a profile rejoining after only a `client_disconnected` (never a death — [[01 Architecture & Sync Model|01]]'s `end-3`), every one of those five `is_none()` checks is already false, so the call is a no-op and the player resumes exactly where they left off. [[player/reducers.rs##pub fn join_world|join_world]] · [[player/methods.rs##pub fn try_scaffold_profile|try_scaffold_profile]] ^join-2
3. The `LoggedInPlayer` row lands back on the client through the game wave's `LocalPlayer` view (the same subscription `join-1` opened), and `EntitySpawnerComponent.OnLocalPlayerInsert` — the client's "archetype helper" per [[02 Entity & Component Framework|02]] — instantiates `local_player.tscn` and `bullet_manager.tscn` in one `AddChild` each. `LocalPlayer._Ready` then reads `LocalPlayerData`/`LocalPlayerStats`/`LocalPlayerInventory`/`LocalPlayerPosition`/`LocalPlayerActiveProfile` by iterating each table's `.Iter()` directly rather than reacting to insert events — since the game wave subscribes to all of them together, there's no guaranteed order in which their rows arrive, so reading the already-landed snapshot in one pass at `_Ready` sidesteps having to sequence six different `OnInsert` callbacks. [[EntitySpawnerComponent.cs##private void OnLocalPlayerInsert|OnLocalPlayerInsert]] · [[LocalPlayer.cs##public override void _Ready|_Ready]] ^join-3

## 05 The parallel in-world loop

Everything from here to `06 Session end` is independent systems running at once, not a sequence — a player who has joined the world is simultaneously moving, fighting, looting, and being rendered, and none of those subsystems wait on each other. The subsections below group steps by subsystem for readability; they don't imply subsystem B starts only after subsystem A finishes.

### Movement and AOI

The world-side half of "what's near me" — chunk-ring resolution, torus wrap, the terrain subscription's own render loop — was written in the [[03 World & Hex Grid]] session (`move-1` through `move-3`); the player-side half — `report_movement`, `PlayerChunk` updates, remote-player/enemy interpolation — continues the same numbering in the [[04 Player System]] session.

1. Once the client is in-world and `SubscriptionComponent.SubscribeGame()` opens (the transition itself is [[04 Player System|04]]'s `join-N`), most of that subscription's rows aren't plain per-table subscriptions but SpacetimeDB **views** — `#[spacetimedb::view(...)]` functions taking a `ViewContext` whose body can read `ctx.sender()` — so unlike a subscribed table (identical rows for every connection), a view's result set is computed per-subscriber. `nearby_terrain_tiles`/`nearby_hex_decor` (`world/views.rs`) share their "what's near me" resolution with `nearby_enemies`/`nearby_remote_players` in the enemy/player modules ([[06 Enemy AI & Bullet Patterns|06]], [[04 Player System|04]]): look up the caller's own `PlayerChunk` row (set once the player is in-world, kept current as they move — [[04 Player System|04]]'s concern), then hand its `(chunk_q, chunk_r)` to `surrounding_chunk_indices`. [[world/views.rs##fn nearby_terrain_tiles|nearby_terrain_tiles]] · [[aoi.rs##pub fn surrounding_chunk_indices|surrounding_chunk_indices]] ^move-1
2. `surrounding_chunk_indices` walks a hex ring of the requested radius around that chunk coordinate using the `hexx` crate's `Hex::range`, wraps every ring member back onto the finite chunk grid with `wrap_chunk_coords` (`cq.rem_euclid(chunk_cols)`, so a ring that overshoots the grid edge reappears on the opposite side instead of returning an out-of-bounds coordinate), converts each wrapped coordinate to its bijective `spiral_chunk_index`, and dedupes indices two ring members can land on the same chunk when the radius is large relative to the grid. The radius itself is a per-view tunable, not one shared constant: terrain views pass `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS` through `nearby_indices_from_chunk`, general-purpose views (player/enemy/loot) go through the `nearby_indices` wrapper's `DEFAULT_AOI_CHUNK_RADIUS` — both equal 2 today, but they're free to diverge (render distance vs. simulation range) since nothing ties them together. [[player/views.rs##pub(crate) fn nearby_indices_from_chunk|nearby_indices_from_chunk]] · [[global.rs##pub const DEFAULT_TERRAIN_AOI_CHUNK_RADIUS|global.rs]] ^move-2
3. With the index list resolved, each view builds a `WHERE` clause chaining `.eq(i).or(.eq(next))` across every index, rather than a range check on continuous coordinates — because `chunk_index` is `spiral_chunk_index`'s bijective spiral numbering, a torus-wrapped ring of chunk *coordinates* has no simple linear relationship to a contiguous range of *indices*, so membership has to be tested index-by-index. On the client, `TerrainComponent` is a plain subscriber to this pre-filtered result: `NearbyTerrainTiles`/`NearbyHexDecor` row `OnInsert`/`OnUpdate`/`OnDelete` callbacks only set a dirty flag rather than rebuild immediately, so a whole burst of chunk-crossing inserts/deletes (a player's AOI ring shifts by more than one chunk's worth of tiles at once) collapses into a single rebuild on the next `_Process` frame instead of one rebuild per row event. [[world/views.rs##fn nearby_hex_decor|nearby_hex_decor]] · [[TerrainComponent.cs##private void OnTileInsert|OnTileInsert]] ^move-3
4. `LocalPlayer._PhysicsProcess` moves the character locally every physics frame via Godot's own `MoveAndSlide` (camera-relative input, detailed in [[08 Client Rendering & Camera|08]]) and, independently, throttles a call to the `ReportMovement` reducer to once every `ReportInterval` (0.1s, 10Hz) — the reducer's name says *report*, not *set*, because the client is already the source of truth for its own position by the time this fires; the server never computes where the local player is, only records where the client says it ended up. `report_movement` passes the reported `(x, y)` through `wrap_world_pos` ([[03 World & Hex Grid|03]]'s torus-wrap math) before storing it on `PlayerPosition`, so a player who has walked past the world seam gets folded back onto the finite grid in the very next report — the server's copy of a position is always wrapped, even though the client's own `GlobalPosition` (Godot's local physics state) stays an unbounded continuous value forever (`move-6` covers how the two stay reconciled). Nothing in the reducer validates the reported distance or speed against the previous position — there's no server-side movement anti-cheat today. [[player/reducers.rs##pub fn report_movement|report_movement]] ^move-4
5. The same call recomputes `chunk_index` (`spiral_chunk_index` of `world_to_chunk` on the now-wrapped position) and writes it onto `PlayerPosition` on every single report, but only writes the separate `PlayerChunk` row — `chunk_q`/`chunk_r` — when they've actually changed from the stored value. This is the write side of the asymmetry `move-2`'s `nearby_indices_from_chunk` ([[03 World & Hex Grid|03]]) reads from: every AOI-scoped view keys off `PlayerChunk` specifically so a player's ring of nearby chunks is only recomputed on a real chunk crossing, not on every 10Hz movement tick, while `PlayerPosition.chunk_index` exists purely so `nearby_remote_players` (`move-8`) can filter that table's own rows directly by btree index without a second join through `PlayerChunk`. [[player/reducers.rs##pub fn report_movement|report_movement]] · [[player/tables.rs##pub struct PlayerChunk|PlayerChunk]] ^move-5
6. `LocalPlayer.OnPositionUpdate`, wired to the subscribed `LocalPlayerPosition` row's `OnUpdate`, is a desync check, not a movement input — it never assigns the server's reported position onto `GlobalPosition` directly. Instead it finds the nearest wrapped copy of the server's position relative to where the client already is (`TorusMath.NearestCandidate`, [[03 World & Hex Grid|03]]) and hard-snaps only if even that nearest copy is farther than `WrapSnapThreshold` (50 units) away — a real desync (packet loss, lag spikes, a future server correction), not the routine re-wrap every seam crossing produces, which this check silently absorbs by finding the equivalent copy instead of the raw one. [[LocalPlayer.cs##private void OnPositionUpdate|OnPositionUpdate]] ^move-6
7. Remote players and enemies have no local simulation of their own to trust, so both route entirely through the shared `InterpolationComponent` ([[02 Entity & Component Framework|02]]'s composition map lists it on both `non_local_player.tscn` and `default_enemy.tscn`): its `_Process` lerps the entity's `GlobalPosition`/`Rotation` toward a stored target by `LerpSpeed * delta` every frame, re-resolving the nearest wrapped copy of that target against the entity's *current* position on every single frame (not only when a new row arrives) — which is what makes a routine torus-seam crossing read as continuous motion instead of a visible jump, the same wrap-then-cull ordering [[03 World & Hex Grid|03]] describes for terrain culling. [[InterpolationComponent.cs##public override void _Process|_Process]] ^move-7
8. `RemotePlayer.OnPositionUpdate` (hooked to `nearby_remote_players`, the AOI-filtered view `move-1`-`move-3` share the resolution mechanism for) filters the view's rows down to this puppet's own `PlayerId`, then hands `InterpolationComponent.SetTarget` both the new position *and* a velocity vector — direction from the row's `rotation`, magnitude from that profile's own `PlayerStats.Speed` — so the puppet keeps advancing in the reported heading during the ~100ms gaps between 10Hz `report_movement` ticks instead of visibly pausing between snapshots. `Enemy.OnEnemyUpdate` calls the same `SetTarget` with a bare position and no velocity — enemy movement is slower and telegraphed by design ([[06 Enemy AI & Bullet Patterns|06]]), so the gap between its own behavior-tick updates is less visually obvious without extrapolation, and nothing needed it. [[RemotePlayer.cs##private void OnPositionUpdate|OnPositionUpdate]] · [[Enemy.cs##private void OnEnemyUpdate|OnEnemyUpdate]] ^move-8

### Equip and inventory

The starter loadout itself — six catalog items, the 24-slot layout, which index ranges hold what — is [[04 Player System|04]]'s `join-2`; this subsection picks up with how a player rearranges, uses, and enchants those slots once in-world. Full mechanism: [[05 Item, Equipment & Enchantment System|05]].

1. Dragging an inventory icon calls no reducer until the drop lands: `SlotComponent._GetDragData` hands the source slot's index across as the drag payload, `_CanDropData` only checks the payload is an int, and `_DropData` on the target slot fires `SwapSlots(fromIndex, toIndex)` — nothing client-side pre-validates whether the item is actually allowed in the destination, so an illegal drag round-trips to the server and back as a no-op rather than being blocked at the cursor. [[SlotComponent.cs##public override void _DropData|_DropData]] ^equip-1
2. `swap_slots` checks both directions before moving anything: the item currently in `from` must be allowed in `to`'s `allowed_slots`, and the item in `to` must be allowed in `from`'s, so a drag that would strand either item in a slot it can't legally occupy is rejected whole. The swap itself only reassigns each slot's `item_id`, though — `enchantment_ids` stays pinned to the slot index it was already on, not the item moving through it (see Known gaps in 05). Either way, this reducer round-trips before the UI ever moves an icon: unlike `04`'s optimistic profile-panel removal, `InventoryComponent` only redraws once `LocalPlayerInventory`'s row event actually arrives. [[player/reducers.rs##pub fn swap_slots|swap_slots]] ^equip-2
3. `recompute_stats` — named but not detailed in [[04 Player System|04]] — treats a slot as "equipped" whenever `allowed_slots.len() == 1`: every single-type slot (weapon, the four accessory/armor slots, both artifact slots, the bag slot, *and* the four hotbar/consumable slots) qualifies, while the eight general/backpack slots (multi-type) never do. That's a broader test than the client's `LocalPlayer.IsEquipmentSlot` (slot 0 or 5-14 only), which gates the enchant-socketing UI, not stat folding — see Known gaps in 05 for where the two diverge. For every qualifying slot holding an item, the item's own `stat_modifiers` fold in, then every enchantment named in that slot's `enchantment_ids` contributes its own `stat_modifiers` on top — plus, independent of any slot, every one of the profile's `ActiveConsumableEffect` rows folds in too. [[player/methods.rs##pub fn recompute_stats|recompute_stats]] ^equip-3
4. All of that folding lands in one pair of seven-element accumulators (six `StatKind`s plus `Hp`), flat and mult kept separate per stat; the final value is `(base + flat) * (1 + mult)` — additive percentage stacking, so two `+10%` mult sources give `+20%`, not a compounding `+21%`. Six of the seven results overwrite `PlayerStats` directly; `Hp` is the exception `04` flagged as deferred — it has no `PlayerStats` column, so its resolved value becomes the new `PlayerData.max_hp` (against `compute_base_max_hp(level)` as the baseline), and current `hp` is clamped down if it now exceeds that cap, so unequipping a `+Hp` item can't leave a player overhealed. [[player/methods.rs##pub fn recompute_stats|recompute_stats]] ^equip-4
5. `pickup_drop` resolves the dropped item's `equip_slot`, then searches for a slot to receive it: first any non-general slot whose `allowed_slots` matches and is currently empty, falling back to the general range (`GENERAL_SLOT_START`..`+GENERAL_SLOT_COUNT`, `15..23`) only if no type-specific slot is free. It copies both `item_id` *and* `enchantment_ids` from the `LootDrop` row into that slot — enchantments correctly follow the item here, unlike the `swap_slots` gap in `equip-2` — then deletes the drop row and calls `recompute_stats`. [[player/reducers.rs##pub fn pickup_drop|pickup_drop]] ^equip-5
6. `drop_item` is the inverse: it clears the source slot's `item_id` and `enchantment_ids` together (so an enchanted item's sockets travel out with it, symmetric with `equip-5`) and inserts a new `LootDrop` row at the player's current `PlayerPosition`/`chunk_index`, timestamped `expires_at: now + LOOT_DROP_EXPIRY` (300s, `main/global.rs`). No reducer anywhere reads `expires_at` back out, though — nothing sweeps expired drops, so the column and the constant exist but nothing currently acts on them (Known gaps in 05). [[player/reducers.rs##pub fn drop_item|drop_item]] · [[global.rs##pub const LOOT_DROP_EXPIRY|global.rs]] ^equip-6
7. `nearby_loot_drops` filters `LootDrop` by `chunk_index` against the same `nearby_indices` AOI helper `move-1`-`move-3` ([[03 World & Hex Grid|03]]) established for terrain and remote players — the general-purpose `DEFAULT_AOI_CHUNK_RADIUS`, not the terrain-specific radius. Client-side, `EntitySpawnerComponent.OnDropInsert`/`OnDropDelete` instance and free `drop.tscn` per row — no interpolation, a drop is static once it lands. `Drop._Ready` is glue only: `DropVisualComponent.SetItem` resolves the item's texture through the same catalog cache `01`'s `conn-7` warmed, and `PickupComponent.SetFromServer` starts a lock `Timer` only when `GameManager.IsLocal(droppedBy)` is true — so the player who just dropped an item can't immediately re-trigger its own pickup by standing on it, while any other nearby player can pick it up right away. `PickupComponent.OnBodyEntered` fires `PickupDrop(dropId)` once the body is a `LocalPlayer` and the lock (if any) has expired. [[player/views.rs##fn nearby_loot_drops|nearby_loot_drops]] · [[PickupComponent.cs##private void OnBodyEntered|OnBodyEntered]] ^equip-7
8. `InventoryComponent._Process` maps `Hotbar1`-`Hotbar4` key presses to slots 1-4 and calls `UseItem(slotIndex)` when that slot isn't empty. `use_item` gates on the slot's item having a `Consumable` behavior via `consumable_behavior` — a behavior test, not a slot-type test, matching the item schema's own design intent (an item could carry a `Consumable` behavior regardless of its `equip_slot`, though nothing in the current catalog does that). `apply_consumable_effect` then branches: `Heal` delegates straight to `combat::heal_player` ([[07 Combat & Damage Math|07]]'s territory), while `Buff` inserts a new `ActiveConsumableEffect` row (the effect's stat/amount carried over as a `StatModifier`, always `Flat` mode) and calls `recompute_stats` immediately so the buff applies without waiting for the next tick. Either branch, the item is consumed — `use_item` clears the slot's `item_id` unconditionally. [[player/reducers.rs##pub fn use_item|use_item]] · [[player/methods.rs##pub fn apply_consumable_effect|apply_consumable_effect]] ^equip-8
9. `tick_active_consumable_effects` is the third scheduled reducer `boot-1` named (`ConsumableEffectSchedule`, `CONSUMABLE_EFFECT_TICK_SECONDS` — 1s by default): every tick it decrements every active effect's `remaining`, deletes any that reach zero, and calls `recompute_stats` only for the profiles that actually lost an effect that tick — a profile with no expiring buffs costs nothing extra. The scheduling infrastructure is generic enough for a damage-over-time or regen effect (the tick-interval constant's own comment says so), but `ConsumableEffect` today only has `Heal` and `Buff` variants — no DoT exists in code (Known gaps in 05). [[player/reducers.rs##pub fn tick_active_consumable_effects|tick_active_consumable_effects]] ^equip-9
10. `apply_enchantment` gates on two independent checks: the enchantment's own `allowed_slots` must contain the *item's* `equip_slot` (not the physical inventory slot index), and the slot's current `enchantment_ids` count must be under the item's `max_enchantments` cap (seeded per item — Helmet 2, Hat 1, Skull 3, Bow 2, Bag/Bread 0). `remove_enchantment` is the plain inverse, a retain-filter over the same list. Both call `recompute_stats`. Full mechanism: [[06 Enemy AI & Bullet Patterns|06]]. `EnemyBehaviorSchedule`/`EnemySpawnSchedule` were both inserted once at `^boot-1` — nothing below waits for a player to trigger it.

1. ### Combat, both directions

Both directions funnel through one shared pipeline, `server/spacetimedb/src/combat/mod.rs` — every damage number in the game is computed there and nowhere else. Full formulas and death handling: [[07 Combat & Damage Math]].

1. **Outgoing, player→enemy:** `CombatComponent.Fire` (`Components/Weapon/CombatComponent.cs`, firing gated on `_fireTimer`/`_firePeriod` derived from the equipped weapon's `WeaponBehavior.fire_rate`, [[05 Item, Equipment & Enchantment System|05]]'s `CombatComponent` intro) does two independent things per shot: it spawns a purely cosmetic bullet through `BulletManager.Instance.SpawnPlayerBullet(s)` (same BlastBullets2D bridge [[06 Enemy AI & Bullet Patterns|06]] describes for enemy bullets, but this bullet carries no hit detection of its own), and separately calls `SpawnZonesAlong`, which instances one `HitZone` (`Scenes/Components/hit_zone.tscn`, a `DamageComponent` subclass) every `_zoneStep` world units along the same path, each one timed via `Launch(radius, delay)` so its lifetime fuse expires exactly when the cosmetic bullet would have reached that point. The visible bullet and the actual hit detection are two unrelated objects moving along the same math. 2. When a `HitZone`'s fuse (`LifetimeTimer`) expires, `OnLifetimeTimeout` calls the inherited `DamageComponent.ReportHits()`, which scans every `Area2D` currently overlapping the zone (`collision_mask: 4`, the Enemies physics layer), keeps only faction-opposed `DamageReceivingComponent`s (`FactionComponent.CheckOpposition` — the player is `Factions.Players`, `default_enemy.tscn`'s hurtbox is `Factions.Enemies`, `collision_layer: 4`), and for each hit calls `GameManager.Conn?.Reducers.ReportEnemyHit(enemy.EnemyId)` directly — no `SequenceStepRef` is involved on this side, because outgoing player damage is resolved entirely from whatever's presently equipped in inventory slot 0, not from anything the zone itself carries. [[enemy/reducers.rs##pub fn report_enemy_hit|report_enemy_hit]] ^combat-3
4. `compute_player_damage` resolves the attacker's own `PlayerStats`/`PlayerInventory` rows (defaulting to `1` damage if either is missing — a player mid-teardown, e.g.), reads slot 0's item, and looks up its `WeaponBehavior` via `weapon_behavior` (the same lookup [[05 Item, Equipment & Enchantment System|05]]'s `CombatComponent` intro names client-side); with no weapon equipped it's a deliberate `0`, not a fallback minimum. ### Camera and rendering, spectating all of it

Full mechanism: [[08 Client Rendering & Camera|08]]. Unlike the other four subsections, camera presentation isn't gated on being in-world at all — the rig and its two presenters tick every frame from the moment `main.tscn` loads, and the very first thing a player ever sees, the lobby view ([[03 Lobby and profile creation|03]]'s `lobby-1`), is driven through the exact same priority-arbitration mechanism the steps below describe for the in-world camera.

1. `CameraRigComponent` is the single source of camera state — yaw, pitch, zoom distance — for both the 2D and 3D presenters below; nothing else in the codebase owns camera input. It's a direct child of `Main`, deliberately outside the 3D `SubViewport` (`3D/SubViewportContainer/SubViewport` in `main.tscn`): a node inside a `SubViewportContainer`'s `SubViewport` only receives input the container explicitly forwards, and mouse-motion events aren't among them, so a rig placed inside the viewport would never see a drag. Every frame it folds continuous yaw-key holds, a click-drag arcball (yaw + pitch), and two cursor-relative snap gestures (snap-so-cursor-is-north / east-or-west, each captures the mouse, drags, and warps it back to a computed screen point on release) into two numbers every other camera system reads: `Yaw` (radians) and `Distance`, exposed to 2D consumers as the inverse `Zoom2D = ZoomReferenceDistance / Distance`. All of it is gated on `LocalPlayer.Local != null`, so the rig goes inert — no yaw drift, no zoom — whenever no local player exists (lobby, post-death). [[CameraRigComponent.cs##public override void _Process|_Process]] · [[CameraRigComponent.cs##public override void _Input|_Input]] ^camera-1
2. `Camera2DPresenterComponent` reads the rig every frame and writes `RotationOffset`/`Zoom` onto whichever `PhantomCamera2D` is currently registered via `RegisterCamera`/`UnregisterCamera` — it holds no camera state of its own. The actual on-screen `Camera2D` node, `MainCamera2D` (`top_level = true`, a direct child of `Main`), is never touched by this project's own code at all: a `PhantomCameraHost` node (the addon's own priority arbiter, a child of `MainCamera2D`) continuously scans every `PhantomCamera2D` sharing its `host_layers` bitmask (default layer 1, unset in `main.tscn`) and morphs `MainCamera2D`'s transform to match whichever has the highest live `Priority`. This project only ever sets `Priority` on the individual pcams — `LocalPlayerPhantomCamera2D` (registered here, `camera-4`) and `MainMenuPhantomCamera2D` (`camera-6`, also [[03 Lobby and profile creation|03]]'s `lobby-1`) — and lets the host's own arbitration decide which one is actually driving the screen at any moment. 5. This is where [[04 Player System|04]]'s `move-4` deferred "camera-relative input": `LocalPlayer._PhysicsProcess` reads raw WASD (`Input.GetVector`) and rotates it by `cameraRig.Yaw` *before* turning it into `Velocity`, so "forward" is always wherever the camera currently faces, not a fixed world axis — the same `Yaw` that `camera-2`/`camera-3` are painting onto the 2D and 3D presenters that same frame, so the player's movement and the picture on screen can never disagree about which way is forward. While any movement key is held it also sets `Rotation = yaw` (so the sprite/model visibly faces the heading being moved toward, not just moves along it) and calls `_model3D?.SyncFrom2D(GlobalPosition, Rotation)` every tick — the same clockwise/counter-clockwise sign flip as `camera-3`, converting the 2D `(x, y)` position and rotation into the 3D model's `(x, 0, y)` position and negated Y-rotation. [[LocalPlayer.cs##public override void _PhysicsProcess|_PhysicsProcess]] · [[CharacterModel3D.cs##public void SyncFrom2D|SyncFrom2D]] ^camera-5
6. On a combat death or ordinary leave, `EntitySpawnerComponent.OnLocalPlayerDelete` ([[07 Combat & Damage Math|07]]'s `combat-11` covers its `Conn.IsActive` guard) calls `localPlayer.QueueFree()` — a *deferred* free, not immediate — then, synchronously in the same call, `LobbyComponent.ShowLobby()`, which raises `MainMenuPhantomCamera2D.Priority` back to 60. For the remainder of that one frame both pcams sit at priority 60 (the local one hasn't unregistered yet), but `LocalPlayer._ExitTree` runs moments later when the queued free actually executes, disposing `_model3D`, clearing `World3DComponent`'s follow target, and calling `camera2D.UnregisterCamera()` — which drops the local pcam's `Priority` back to 0 (guarded by `IsInstanceValid`, since the pcam node can already be gone by the time this runs). By the next frame only the main-menu pcam is left at nonzero priority, so the view recenters on the lobby the instant the character disappears — the same `ShowLobby` used for the very first lobby view ([[03 Lobby and profile creation|03]]'s `lobby-1`). [[EntitySpawnerComponent.cs##private void OnLocalPlayerDelete|OnLocalPlayerDelete]] · [[LobbyComponent.cs##public void ShowLobby|ShowLobby]] · [[LocalPlayer.cs##public override void _ExitTree|_ExitTree]] ^camera-6

## 06 Session end

1. A session ends when the client disconnects — either `ConnectionComponent._ExitTree` calling `Conn.Disconnect()` as Main leaves the scene tree (the player quit the game), or an unexpected network drop reported through the same `OnDisconnect` callback wired in `conn-2`. Either way, SpacetimeDB fires the `client_disconnected` lifecycle reducer for that identity server-side. [[ConnectionComponent.cs##public override void _ExitTree|_ExitTree]] ^end-1
2. `client_disconnected` looks the identity up in `logged_in_player`; if found, it deletes that row and re-inserts the same `player_id`/`username`/`is_admin` as a `LoggedOutPlayer` row. This is a state move, not a data wipe — reconnecting later is a re-login against the preserved row, not a fresh `PlayerProfile`. If the identity was never in `logged_in_player` (disconnected from the lobby, before `join_world`), this is a no-op beyond the log line. [[lifecycle.rs##pub fn client_disconnected|client_disconnected]] ^end-2
3. Deliberately not run here: the full death-teardown path (`teardown_profile`, dropping profile/data/stats/position/inventory rows) that a *permadeath* does — that's [[07 Combat & Damage Math|07]]'s `deal_damage_to_player` on a zero-HP hit, a different trigger entirely. A disconnected `LoggedOutPlayer`'s profile, stats, and position rows are left exactly as they were, orphaned from any live connection but intact, ready to resume next login. Contrast: `client_disconnected` moves one row and stops; the death path in 07 unwinds an entire profile's worth of rows through the same archetype helper `join_world`/`leave_world` use ([[04 Player System|04]]). ^end-3
4. Client-side, Godot's normal scene-teardown does the rest: every child component under Main fires `_ExitTree` and unregisters from its entity's component registry (mechanism: [[02 Entity & Component Framework|02]]), and `GameManager._ExitTree` clears the static `instance` — after this point every static-facade call (`GameManager.Conn`, `.GetItem(...)`, ...) returns null/default rather than throwing, since `Get<T>()` guards on `IsInstanceValid(instance)`. [[GameManager.cs##public override void _ExitTree|_ExitTree]] ^end-4

## 07 Meanwhile, independently

Admin and out-of-band activity — not part of the ordinary player session above. An admin identity can claim the single global admin slot and act on world/content/enemy state at any time, concurrently with players' normal sessions. Full detail: [[09 Admin, Debug & World Lifecycle|09]].

1. There is exactly one admin slot for the whole server, not a role list: `claim_admin` scans both `LoggedInPlayer` and `LoggedOutPlayer` for any row already carrying `is_admin: true` and refuses a second claim outright ("An admin already exists. Use release_admin to remove them first.") — it doesn't matter whether the caller is currently in-world or in the lobby, since it checks whichever of the two login-state rows ([[01 Architecture & Sync Model|01]]'s `conn-3`) exists for the caller and flips that one's `is_admin` bit. `release_admin` is the plain inverse, and the only way to free the slot short of the incumbent claiming it again. No client code anywhere calls either reducer — the only way to become admin today is the SpacetimeDB CLI, `spacetime call bullethell claim_admin`, run out-of-band from any running client. [[admin.rs##pub fn claim_admin|claim_admin]] · [[admin.rs##pub fn release_admin|release_admin]] ^admin-1
2. Every reducer below gates on the same `is_admin` helper — not a separate check per reducer — which mirrors `claim_admin`'s own lookup order (`LoggedInPlayer` first, then `LoggedOutPlayer`) and defaults to `false` if neither row exists yet (e.g. a call arriving in the brief window before `client_connected`, `conn-3`, has run). A non-admin caller gets a plain `Err("Admin only.")` for every reducer this section covers. [[player/methods.rs##pub fn is_admin|is_admin]] ^admin-2
3. `change_stats` resolves its target two hops deep — `find_player_by_username` (`admin-8`) to an `Identity`, then `find_profile_by_name` to that player's specific `PlayerProfile` — and writes the six base stats onto `PlayerStats` directly. This write doesn't survive contact with the ordinary stat pipeline, though: `recompute_stats` ([[05 Item, Equipment & Enchantment System|05]]'s `equip-3`/`equip-4`) always rebuilds `PlayerStats` from `compute_base_stats(level)` plus equipped items/enchantments/active buffs, never from whatever is currently sitting in the row, so the very next equip, pickup, drop, enchant, or consumable tick after a `change_stats` call silently discards it. An admin's stat edit is a one-tick effect, not a persistent override, unless nothing ever triggers a recompute again for that profile. [[admin.rs##pub fn change_stats|change_stats]] · [[player/methods.rs##pub fn recompute_stats|recompute_stats]] ^admin-3
4. `upsert_texture_entry`, `upsert_enemy_template`, `upsert_world_def`, `upsert_biome_def`, and `upsert_biome_region_def` all share one shape — find-by-primary-key, `.update(...)` if present else `.insert(...)` — the same update-if-exists-else-insert pattern the `Seed` trait's impls (`main/seeds.rs`) use for `init`'s own one-time seeding (`boot-2`). The difference is only *when* they run: seeding fires once at first publish, these fire admin-gated at any time a server is live. Because every one of the tables they touch is `public`, an edit through one of these reducers reaches every currently-subscribed client's cache the instant it commits — no republish, no reconnect — the same push [[01 Architecture & Sync Model|01]] describes for ordinary gameplay rows applies equally to admin-edited catalog content. [[admin.rs##pub fn upsert_texture_entry|upsert_texture_entry]] · [[admin.rs##pub fn upsert_enemy_template|upsert_enemy_template]] ^admin-4
5. `spawn_enemy` and `despawn_enemy` are admin-only counterparts to the automatic biome-region spawning [[06 Enemy AI & Bullet Patterns|06]]'s `enemy-1`-`enemy-3` describes, and both carry a known bug the archetype-helper pair (`spawn_enemy_archetype`/`despawn_enemy_archetype`, `enemy-3`/`combat-5`) was written specifically to avoid. `spawn_enemy` calls `build_enemy_behavior` — which, on its own, already inserts one `EnemyBehavior` row plus that template's whole phase/attack/step tree pointed at it — and then wraps the *returned* (already-inserted) `EnemyBehavior` struct in a second `ctx.db.enemy_behavior().insert(...)` call, rather than using `spawn_enemy_archetype` the way `enemy-3` does; the `Enemy` row it inserts points at whichever `behavior_id` that second, redundant insert produces, not necessarily the one carrying the freshly-built phase tree. `despawn_enemy` is the opposite failure: it deletes only the `Enemy` row (`ctx.db.enemy().enemy_id().delete(&enemy_id)`) and never calls `despawn_enemy_archetype` or `delete_enemy_behavior` at all, so an admin-despawned enemy's whole behavior tree — `EnemyBehavior`, its `EnemyPhase`s, `EnemyAttack`s, `EnemySequenceStep`s, any `RepeatStepInstance`s — is orphaned in the database forever. Neither bug affects the automatic spawn/despawn path `06` documents, which never calls either of these reducers. [[admin.rs##pub fn spawn_enemy|spawn_enemy]] · [[admin.rs##pub fn despawn_enemy|despawn_enemy]] ^admin-5
6. `add_chunks` is a thin admin-gated wrapper around `internal_add_chunks` — the identical call `init` makes once at `boot-3` — so an admin can re-lay the chunk grid (new radius/columns/rows/hex size) against a live server. `clear_chunks` only deletes every `BuildingTile` row, though — the per-hex building-*placement* grid `place_building`/`remove_building` write into ([[03 World & Hex Grid|03]]'s territory) — and touches nothing else: not `TriangleTile`, not `HexDecor`, not `BiomeRegion`, not `MapConfig`. Clearing chunks alone doesn't blank the visible terrain a player would actually see; it only wipes where buildings could legally be placed. [[admin.rs##pub fn add_chunks|add_chunks]] · [[admin.rs##pub fn clear_chunks|clear_chunks]] ^admin-6
7. `generate_world_proc` and `generate_world_manual` are the admin-gated counterparts to the exact same `internal_generate_world_proc`/`internal_generate_world_manual` entry points `init` calls once at `boot-4` — an admin can regenerate the entire live map (a new procedural seed, or a hand-authored `Vec<ManualBiomeInput>`) at any time without republishing the module. Full generation pipeline: [[03 World & Hex Grid|03]]. [[admin.rs##pub fn generate_world_proc|generate_world_proc]] · [[admin.rs##pub fn generate_world_manual|generate_world_manual]] ^admin-7
8. `find_player_by_username`, `change_stats`'s first lookup (`admin-3`), matches loosely on purpose: it lowercases the input and checks it against every known player's `username` (case-insensitive, exact) *or* their identity's hex string (exact, or merely a prefix of it) — scanning both `LoggedInPlayer` and `LoggedOutPlayer` so a target can be found whether or not they're currently in-world. A short hex prefix is enough to identify someone from the SpacetimeDB CLI without copying a full 64-character identity. [[admin.rs##pub fn find_player_by_username|find_player_by_username]] ^admin-8
9. Separately from admin.rs, `main/debug.rs` implements one narrow diagnostic: `toggle_debug` (also `is_admin`-gated) either inserts or clears a single `PlayerPositionDebugSchedule` row — a scheduled table like the three `boot-1` describes, here running at a fixed 1s interval only while toggled on — and its paired reducer `tick_player_position_debug` mirrors every live `PlayerPosition` row into a `PlayerPositionDebug` row carrying the same x/y plus its hex-grid `(hex_q, hex_r)` equivalent, deleting any mirrored row whose player no longer has a `PlayerPosition` at all. Nothing in the client subscribes to `PlayerPositionDebug` — no C# file references it anywhere in the codebase — so as it stands this table is inspectable only by querying the database directly (`spacetime sql`), not through any in-game view. [[debug.rs##pub fn toggle_debug|toggle_debug]] · [[debug.rs##pub fn tick_player_position_debug|tick_player_position_debug]] ^admin-9
10. Entirely unrelated to the server-side reducers above beyond sharing the word "debug": `DebugOverlay` (`Scenes/UI/debug_overlay.tscn`, instanced directly under `Main` in `main.tscn` — present and ticking from scene load the same way [[08 Client Rendering & Camera|08]]'s `camera-1` describes for the camera rig, not gated on being in-world) is a local performance HUD any client can toggle with `P`, no admin check at all. Every quarter second (`UpdateInterval`) while visible, it reads Godot's own `Performance` monitors (FPS, frame time, static memory, object/node counts, draw calls) plus `GameManager.EnemyCount` ([[06 Enemy AI & Bullet Patterns|06]]'s territory) and writes them into one `Label` — nothing here is server-authoritative or tied to the admin identity, `PlayerPositionDebug`, or any other mechanism this section describes. [[DebugOverlay.cs##public override void _Process|_Process]] · [[DebugOverlay.cs##public override void _Input|_Input]] ^admin-10
