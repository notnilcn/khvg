# End-to-End Flowchart

## 01 Server bootstrap

1. `spacetime start` launches a local SpacetimeDB node; `spacetime publish <db> --module-path server/spacetimedb` compiles the Rust module to WASM and installs it. A fresh publish (or any publish with `--clear-database`) runs the module's `#[reducer(init)]` exactly once, before any client can connect. ^boot-1
2. `init` seeds every static table the game needs up front — textures, layering/adjacency/decor rules, enemy templates, world items, world defs — and schedules the three recurring reducers (enemy behavior tick, enemy spawn tick, consumable-effect tick) that drive the always-on simulation. It then lays out the starting chunk grid and procedurally generates the default world. See [[lifecycle.rs##pub fn init|init]]. ^boot-2
3. `spacetime generate --lang csharp --out-dir client/Scripts/module_bindings --module-path server/spacetimedb` reads the published module's schema and regenerates the C# table/reducer/view bindings the client compiles against. This has to be re-run any time a table, reducer, or view signature changes on the server — the client won't build against a stale schema. ^boot-3
4. Pressing F5 in the Godot editor launches `Scenes/main.tscn`. There are no autoloads — `GameManager` is the scene's own root node, so its `_Ready` runs as soon as the scene loads, with nothing else needing to bootstrap it first. See [[GameManager.cs##public override void _Ready|_Ready]]. ^boot-4

## 02 A client connects

1. `GameManager._Ready` calls `Connect(Host, DbName)`, which builds a `DbConnection` against the configured host/database name with `WithToken(null)` — there's no persisted identity yet (the `AuthToken` load/save calls in this method are present but commented out), so every launch requests a brand-new anonymous `Identity` instead of resuming a previous session's. See [[GameManager.cs##public void Connect|Connect]]. ^conn-1
2. The generated SDK opens the connection, and once the server has assigned an `Identity` and issued an auth token, invokes the client's `OnConnect` callback with both. See [[GameManager.cs##private void OnConnected|OnConnected]]. ^conn-2
3. On the server, `#[reducer(client_connected)]` fires for that identity. If it isn't already logged in or logged out under this identity, it inserts a `LoggedOutPlayer` row and a default "Knight" `PlayerProfile` — a first-time identity gets an empty lobby seat and one pre-made profile for free. See [[lifecycle.rs##pub fn client_connected|client_connected]]. ^conn-3
4. Back on the client, `OnConnected` stores the `Identity`, wires up row-insert/update/delete callbacks for the tables/views it cares about, and opens an anonymous, unfiltered subscription to the two global catalog views every client needs regardless of login state: `all_textures` and `all_items`. See [[GameManager.cs##conn.SubscriptionBuilder|initial subscription]]. ^conn-4
5. From here on, `GameManager._Process` calls `Conn.FrameTick()` every engine frame. This is what actually pumps incoming table/view updates off the connection and fires the `OnInsert`/`OnUpdate`/`OnDelete` callbacks — without it, nothing the server sends ever reaches game state, connected or not. See [[GameManager.cs##Conn?.FrameTick|FrameTick]]. ^conn-5

## 03 Lobby and profile creation

1. Immediately after the global catalog subscription in conn-4, `OnConnected` also calls `SubscribeLobby`, opening two more views scoped to just this identity: `local_lobby_player` (the caller's own `LoggedOutPlayer` row — this is what sets `GameManager.Username`) and `local_player_profiles` (every `PlayerProfile` row this identity owns, including the free "Knight" profile `client_connected` scaffolded in conn-3). See [[GameManager.cs##private void SubscribeLobby|SubscribeLobby]]. ^lobby-1
2. As `LocalPlayerProfiles` rows arrive, an `OnInsert` callback wired in `GameManager._Ready` — registered right after `Connect` is called, well before the subscription in lobby-1 has actually applied — instantiates one `PlayerProfileScene` per row into `%CharSlots/ScrollContainer/VBoxContainer` and wires that panel's Join/Delete buttons to `OnJoinPressed`/`OnDeletePressed` for that specific profile. The character-select screen a player sees is nothing but a live rendering of this table; there's no separate "profile list" state kept in sync by hand. See [[GameManager.cs##Conn.Db.LocalPlayerProfiles.OnInsert|LocalPlayerProfiles.OnInsert]]. ^lobby-2
3. Submitting the create-profile panel fires `OnCreatePressed`, which calls `create_profile(profile_name, "Knight")` — the texture is hardcoded to `"Knight"` today, there's no character customization yet. Server-side, `create_profile` caps a single identity at 3 profiles and rejects a case-insensitive duplicate name before inserting. A successful insert round-trips back through lobby-2's `OnInsert` callback, which is what actually adds the new slot to the UI — `OnCreatePressed` itself only hides the panel. See [[GameManager.cs##private void OnCreatePressed|OnCreatePressed]] and [[reducers.rs##pub fn create_profile|create_profile]]. ^lobby-3
4. Pressing a slot's Delete button fires `OnDeletePressed`, calling `delete_profile(profile_id)` — server-side this cascades across every profile-keyed table (`PlayerData`, `PlayerStats`, `PlayerInventory`, `PlayerPosition`, `ActiveConsumableEffect`, then `PlayerProfile` itself) so a deleted profile leaves no orphaned rows, even for tables `try_scaffold_profile` (join-2) never got around to populating because the profile was deleted before ever being joined. Unlike creation, the UI side doesn't react to a `LocalPlayerProfiles.OnDelete` callback: `OnDeletePressed` manually scans the slot container's children for a matching ID label and frees it directly — a stub that only works because deletion is always client-initiated. See [[GameManager.cs##private void OnDeletePressed|OnDeletePressed]] and [[reducers.rs##pub fn delete_profile|delete_profile]]. ^lobby-4

## 04 Joining the world

1. Clicking **Join** on a profile slot fires `OnJoinPressed`: the client calls the `join_world` reducer for that profile, then — without waiting for a response — immediately opens the full in-world subscription (`SubscribeGame`, covering `LocalPlayer`, `NearbyTerrainTiles`, `NearbyHexDecor`, `MapConfig`, and the rest) and unsubscribes the lobby subscription. See [[GameManager.cs##private void OnJoinPressed|OnJoinPressed]]. ^join-1
2. On the server, `join_world` checks the caller owns the profile and is currently in the lobby, moves the identity from `LoggedOutPlayer` to `LoggedInPlayer`, and calls `try_scaffold_profile` — which, only the first time this profile ever joins, inserts starting `PlayerData`/`PlayerInventory`/`PlayerPosition` rows anchored at world origin (0, 0) and a `PlayerChunk` row for whichever chunk contains that origin. World gen back in boot-2 already populated that chunk's terrain, so there's real ground under a fresh spawn. See [[player/reducers.rs##pub fn join_world|join_world]] and [[player/methods.rs##pub fn try_scaffold_profile|try_scaffold_profile]]. ^join-2
3. Those inserts flow back over the subscription opened in join-1. The player's own `LoggedInPlayer` row (surfaced via the `local_player` view) fires `OnLocalPlayerInsert`, which instantiates the `LocalPlayer` node, `BulletManager`, and `TerrainManager`; `TerrainManager`'s own subscription then walks whatever `NearbyTerrainTiles`/`NearbyHexDecor` rows have already arrived and performs its first batch build, while the `MapConfig` row primes `LapQ`/`LapR` (the torus lap vectors) used to resolve wrapped positions near a seam. See [[GameManager.cs##private void OnLocalPlayerInsert|OnLocalPlayerInsert]]. ^join-3

## 05 The parallel in-world loop

Everything from here to "Session end" is five independent systems running at once, not a sequence — each one is covered start-to-finish by its own doc, and each one below is a fork off join-3, reconverging only when the session actually ends.

### Movement and AOI

1. Between `LocalPlayer` spawning (join-3) and its first movement report, `_PhysicsProcess` turns raw WASD input into a camera-relative direction — rotated by `CameraRig`'s current yaw, since movement is relative to where the camera is looking, not a fixed world axis — drives `Velocity`/`MoveAndSlide` and idle/walk sprite state from it, and accumulates a `reportTimer` that fires `ReportMovement` once it crosses `ReportInterval` (0.1s), the ~10Hz cadence move-2 assumes. This is the client-side loop move-2's "input/movement-feel side... is the player-system doc's concern" refers to. See [[LocalPlayer.cs##public override void _PhysicsProcess|_PhysicsProcess]]. ^move-1
2. `LocalPlayer` reports its position to the server at ~10Hz via `report_movement(x, y, rotation)` — the input/movement-feel side of this is the player-system doc's concern; what matters here is that the server immediately re-wraps the reported `(x, y)` through `wrap_world_pos`, folding it back into the canonical chunk range whenever it's crossed a torus seam, and recomputes `chunk_index` via `world_to_chunk`/`spiral_chunk_index` before writing the new `PlayerPosition` row. See [[player/reducers.rs##pub fn report_movement|report_movement]]. ^move-2
3. Only if the resolved `(chunk_q, chunk_r)` actually differs from the profile's existing `PlayerChunk` row does `report_movement` update it — `PlayerChunk`, unlike `PlayerPosition`, is deliberately left untouched on every tick. ^move-3
4. Every AOI-scoped view that resolves through `nearby_indices_from_chunk` — `nearby_terrain_tiles` and `nearby_hex_decor` here, plus the sibling `nearby_enemies`/`nearby_remote_players`/`nearby_loot_drops` views documented in their own systems — keys off that `PlayerChunk` row rather than `PlayerPosition`, so the surrounding-chunk-ring recompute (`surrounding_chunk_indices`) only fires on a real chunk crossing, not on every movement report. See [[player/views.rs##pub(crate) fn nearby_indices_from_chunk|nearby_indices_from_chunk]] and [[world/views.rs##fn nearby_terrain_tiles|nearby_terrain_tiles]]. ^move-4
5. On the client, `TerrainManager`'s insert/update/delete handlers for `NearbyTerrainTiles`/`NearbyHexDecor` just flip a `_dirty` flag; the actual rebuild — regrouping tiles into `MultiMeshInstance2D` batches and culling against the camera's view rect — runs at most once per frame regardless of how many rows one chunk crossing changed at once, and only after picking whichever wrapped copy of each hex (`TorusMath.NearestCandidate`, using `MapConfig`'s `LapQ`/`LapR`) is actually nearest the camera. See [[TerrainManager.cs##private void RebuildVisibleInstances|RebuildVisibleInstances]]. ^move-5
6. `NearbyRemotePlayers` — the AOI view move-4 groups with `nearby_terrain_tiles`/`nearby_hex_decor` but defers to this doc for the details — drives `GameManager.OnNearbyRemotePlayerInsert`/`OnNearbyRemotePlayerDelete`, spawning or freeing one `RemotePlayer` node per other player's `PlayerPosition` row currently in AOI. A `RemotePlayer` doesn't snap to every position update: `OnPositionUpdate` records the new canonical position and a `snapVelocity` derived from that player's own `PlayerStats.Speed`, and `_Process` extrapolates from there every frame (`canonicalPosition + snapVelocity * timeSinceSnap`) so motion stays smooth between server updates arriving slower than the display's frame rate — the same wrap-aware `TorusMath.NearestCandidate` move-5's terrain draw uses, applied to a player instead of a hex, with a hard snap only if even the nearest wrapped copy is still far away (a real desync, not a routine wrap). See [[GameManager.cs##private void OnNearbyRemotePlayerInsert|OnNearbyRemotePlayerInsert]] and [[RemotePlayer.cs##private void OnPositionUpdate|OnPositionUpdate]]. ^move-6

### Equip and inventory

1. `PlayerInventory` arrives over the `LocalPlayerInventory` view opened in join-3's subscription, carrying the fixed 24-slot layout `try_scaffold_profile` built (weapon/hotbar/accessory/armor/artifact/general/bag, each an `InventorySlot { allowed_slots: Vec<EquipSlot>, item_id }`). `LocalPlayer.ApplyInventory` just replaces its local `List<InventorySlot>` wholesale and emits `InventoryChanged` — there's no per-slot diffing on the client, every consumer (inventory UI, combat) re-reads the whole list off this one signal instead of tracking which slot actually moved. See [[LocalPlayer.cs##private void ApplyInventory|ApplyInventory]]. ^equip-1
2. Dragging an `InventorySlotUI` onto another calls `swap_slots(from_index, to_index)`. The server looks up whichever slot(s) actually hold an item and checks the *other* slot's `allowed_slots` against that item's `equip_slot` — both directions, since a swap can move an item either way — before mutating `PlayerInventory.slots` and calling `recompute_stats`. Right-clicking a slot instead calls `drop_item(slot_index)`, which clears the slot server-side and inserts a `LootDrop` row at the player's current `PlayerPosition` (`x`/`y`/`chunk_index`) stamped with an `expires_at` `LOOT_DROP_EXPIRY` seconds out — nothing currently reads that timestamp to delete the row, so a dropped item sits on the ground forever in practice; the expiry is a stub, not enforced. See [[reducers.rs##pub fn swap_slots|swap_slots]] and [[reducers.rs##pub fn drop_item|drop_item]]. ^equip-2
3. A `LootDrop` only reaches a client through `nearby_loot_drops`, the same chunk-ring AOI view [[02 World & Hex Grid]] documents for terrain — `GameManager.OnDropInsert`/`OnDropDelete` spawn or free one `Drop` node per row, texturing itself from `GameManager.GetItem(ItemId)`/`GetResPath`. A drop dropped by the local player is untouchable by anyone (including that player) for a few seconds (`PickupLockDuration`, client-side only) purely so it doesn't get instantly re-picked-up by the same body still standing on it. See [[Drop.cs##public override void _Ready|_Ready]]. ^equip-3
4. Walking a `LocalPlayer` body into a `Drop`'s `Area2D` fires `pickup_drop(drop_id)`. The server prefers an empty *typed* slot matching the item's `equip_slot` (weapon/hotbar/accessory/armor/artifact) over the 8 general-purpose slots (`GENERAL_SLOT_START`/`GENERAL_SLOT_COUNT`), falling back to the first empty general slot only if no typed slot fits — so a picked-up sword lands in the weapon-shaped slot rather than a junk slot even though both would technically accept it. Either way the `LootDrop` row is deleted and `recompute_stats` runs. See [[reducers.rs##pub fn pickup_drop|pickup_drop]]. ^equip-4
5. Pressing a hotbar key (`Hotbar1`–`Hotbar4`, checked in `LocalPlayerInventory._Process` against `LocalPlayer.GetSlotItemId`) calls `use_item(slot_index)`. The server's only gate is "does this item carry a `Consumable` behavior" — not "is this a Consumable-typed slot" — so an item with `equip_slot: Accessory` but a `Consumable` behavior would still be usable from any slot holding it; today only `Bread` (a true `Consumable`-slot item) exercises this path. A `Heal` effect patches `PlayerData.hp` directly and never creates a row; a `Buff` effect instead inserts an `ActiveConsumableEffect` (a `StatModifier` + a countdown) and calls `recompute_stats`. Either way the consumed item's slot is cleared. See [[reducers.rs##pub fn use_item|use_item]] and [[methods.rs##pub fn apply_consumable_effect|apply_consumable_effect]]. ^equip-5
6. `recompute_stats` — called by every reducer in equip-2, equip-4, and equip-5 above, plus scheduled ticks in equip-8 below — is the one place equipped items and active buffs actually turn into numbers. It walks every slot whose `allowed_slots` names exactly one `EquipSlot` (i.e. every equipped slot — general slots and the multi-type weapon/artifact/etc. category itself don't count, only a slot instance actually pinned to one type), resolves each held item, and folds every `StatModifier` — flat amounts summed, `Mult` amounts summed separately — then folds every one of the profile's `ActiveConsumableEffect.modifier`s the same way. Each of the six `PlayerStats` fields resolves as `(base + flat) * (1 + mult)`; the seventh accumulator, `StatKind::Hp`, resolves the same way against `compute_base_max_hp` and writes straight to `PlayerData.max_hp`, clamping `hp` down if the cap just shrank (e.g. unequipping a +HP item mid-session). See [[methods.rs##pub fn recompute_stats|recompute_stats]]. ^equip-6
7. The updated `PlayerStats`/`PlayerData` rows flow back over the same `LocalPlayerStats`/`LocalPlayerData` subscriptions [[03 Player System]] covers for leveling, and the updated `PlayerInventory` row re-fires `InventoryChanged` (equip-1). Two independent client listeners react to that one signal: `LocalPlayerInventory.OnInventoryChanged` re-textures every `InventorySlotUI` icon by re-resolving `GetSlotItemId` → `GameManager.GetItem` → `GetResPath`, and `LocalPlayerCombat.OnInventoryChanged` re-reads slot 0 specifically, pulling a `WeaponBehavior` out of the equipped `Item.Behaviors` (or clearing it if slot 0 is empty or non-weapon) — comparing `ItemId` first so an unrelated inventory change (a potion used, an accessory swapped) doesn't reset the weapon's fire-rate timer. See [[LocalPlayerInventory.cs##private void OnInventoryChanged|OnInventoryChanged]] and [[LocalPlayerCombat.cs##private void OnInventoryChanged|OnInventoryChanged]]. ^equip-7
8. Independently of any player action, the scheduled `tick_active_consumable_effects` reducer (driven by `ConsumableEffectSchedule`, fired every `CONSUMABLE_EFFECT_TICK_SECONDS`) walks every `ActiveConsumableEffect` row in the whole world, counts its `remaining` down, deletes it once it hits zero, and calls `recompute_stats` for every profile that had a buff actually expire this tick — this is the only path that removes a `Buff`-sourced `StatModifier`; a one-shot `Heal` never has one to remove. See [[reducers.rs##pub fn tick_active_consumable_effects|tick_active_consumable_effects]]. ^equip-8

### Enemy spawning and behavior

1. `EnemySpawnSchedule` fires `tick_enemy_spawn` on a recurring timer (scheduled back in boot-2), which just calls `spawn_from_biome_regions` — the reducer itself is a one-line dispatch, all the logic lives in the method. For every `BiomeRegion` row (world gen's geography hook, [[02 World & Hex Grid]]'s concern for how a region's center/radius/`enemy_template_ids` got there), it first checks `has_player_near_spawn_point`, a chunk-ring search (`SPAWN_LOOKAHEAD_CHUNK_RINGS`) for any logged-in player's `PlayerPosition` near that region's center — a region with nobody nearby to ever see it skips spawning entirely, so the server isn't quietly filling empty map corners with enemies no one will meet. See [[reducers.rs##pub fn tick_enemy_spawn|tick_enemy_spawn]] and [[methods.rs##pub fn spawn_from_biome_regions|spawn_from_biome_regions]]. ^enemy-1
2. If a region does have a nearby player, it counts its own already-live enemies — matching `enemy_template_ids` and within `spawn_radius` via `wrapped_distance_sq` rather than a plain distance check, since a spawn point near a torus seam can wrap to the far side of the map while the region's own center doesn't — and skips spawning if that count already meets `max_enemies`. Otherwise it picks one template from the region's list (keyed off `region_id` XORed with the current time, not a stored per-region cursor), rolls a spawn point uniformly over the region's disc (`next_unit(seed, draw).sqrt()` on the radius draw specifically, so points don't bunch toward the center the way a raw linear radius draw would), and re-wraps that point through `wrap_world_pos` in case the roll itself landed past a seam. ^enemy-2
3. `build_enemy_behavior` is what turns a template's *static* `phases: Vec<PhaseDef>` into a *live* per-enemy state tree: one `EnemyBehavior` row (aggro/velocity state), and for every phase a `EnemyPhase` row plus one `EnemyAttack` row per `AttackSequence` plus one `EnemySequenceStep` row per step — a `RepeatStepDef` additionally gets its own fresh `RepeatStepInstance` row per enemy (rather than sharing the template's), since its `repeat_count` has to advance independently for every enemy running that template. The freshly built behavior and a new `Enemy` row (hp from `template.max_hp`, `phase: 0`) are inserted together, and that insert is the only thing that actually makes an enemy exist. See [[methods.rs##pub fn build_enemy_behavior|build_enemy_behavior]]. ^enemy-3
4. `EnemyBehaviorSchedule` drives `tick_enemy_behavior` on its own recurring timer (`BEHAVIOR_TICK_DT` = 0.1s), which loops every `Enemy` row in the world every tick — but does real work on it only if `has_player_in_simulation_range` says a player is within `template.move_sim_factor * CAMERA_VIEW_RADIUS` of it, so an enemy far from every player just sits idle rather than burning CPU simulating something invisible. `was_simulating` on `EnemyBehavior` gates aggro *retargeting* specifically: it's only recomputed (`recompute_aggro` → nearest logged-in player, locked for `aggro_lock_seconds`) on the tick an enemy first enters range, not every 100ms it stays there — a mid-fight enemy doesn't flip targets just because another player wandered slightly closer. See [[reducers.rs##pub fn tick_enemy_behavior|tick_enemy_behavior]] and [[methods.rs##pub fn recompute_aggro|recompute_aggro]]. ^enemy-4
5. `enemy.phase` (a plain `u8` on the `Enemy` row) is the thing `report_enemy_hit` (enemy-8 below) advances the instant HP crosses a `PhaseDef.hp_threshold` — `tick_enemy_behavior` doesn't decide phase transitions, it only *notices* one already happened by comparing `enemy.phase` against `behavior.active_phase_index`, and when they differ calls `begin_phase_cycle` to reset that phase's attack sequences to their starting step and, if `phase_loop_delay` is set, wait that long before firing anything — this is what makes a boss's phase 2 open with a clean beat instead of resuming mid-sequence from wherever phase 1 left its counters. See [[methods.rs##pub fn begin_phase_cycle|begin_phase_cycle]]. ^enemy-5
6. Movement and attacking are gated by two different ranges from the same `move_sim_factor`/`attack_sim_factor` pair — deliberately: an enemy starts approaching (`apply_movement`, enemy-7) as soon as it's in the wider move range, but only opens fire once a player is within the tighter attack range, so it's never shooting from off-screen before it's actually visible. Inside attack range, `tick_phase` advances every `AttackSequence` in the active phase by at most one step each tick — `tick_sequence` underneath handles `Single`/`Multi` (fire once, optionally wait `next_step_delay`) and `Repeat` (re-fire on `repeat_interval` until `repeat_count` hits `repeat_target`) — and any step that actually fires this tick becomes one `BulletPatternEvent` row, stamped with the enemy's own `chunk_index` for AOI and a `target` resolved from the step's `EnemyTarget` (`Idle` → `None`, `AggroTarget` → the behavior's locked identity) via `resolve_step_target`. See [[methods.rs##pub fn tick_phase|tick_phase]] and [[methods.rs##pub fn tick_sequence|tick_sequence]]. ^enemy-6
7. `apply_movement` resolves whichever `MovementBehavior` the active phase's `MovementDef` points to (`Stationary`/`Wander`/`Chase`/`Flee`) into a new `(x, y)` and facing direction for this tick — `Wander` derives a deterministic-but-reproducible direction from `enemy_id` plus a cycle index rather than storing one, `Chase`/`Flee` both look up the aggro target's live `PlayerPosition` and move toward or away from it, gated by the behavior's own active/pause duty cycle (`cycle_phase`) so a "wander" enemy doesn't drift continuously. The result is re-wrapped through the same `wrap_world_pos`/`world_to_chunk`/`spiral_chunk_index` helpers [[02 World & Hex Grid]] documents for players, and the tick ends by writing the new `Enemy`/`EnemyBehavior`/`EnemyPhase` rows back — this is the position `nearby_enemies` (enemy-9) streams to clients. See [[methods.rs##pub fn apply_movement|apply_movement]]. ^enemy-7
8. `report_enemy_hit(enemy_id)` is this system's entry point for a player's attack landing — `compute_player_damage`'s formula and the client-side hit-detection path that calls this reducer are [[06 Combat & Damage Math|06's]] concern; what belongs here is what happens once a damage number exists. An immortal enemy (test/debug tooling) no-ops. Otherwise HP drops by `compute_player_damage`'s result; if that reaches 0, `delete_enemy_behavior` cascades the delete across every `EnemyPhase`/`EnemyAttack`/`EnemySequenceStep`/`RepeatStepInstance` row enemy-3 built, the `Enemy` row itself is deleted, and `internal_gain_xp` awards `template.max_hp / 10` XP to the killer's profile ([[03 Player System]]'s leveling math from there). No `LootDrop` row is inserted anywhere in this path — [[04 Item & Equipment System]] already flagged "enemies don't drop loot" from the item side; this confirms it from here too, `enemy/reducers.rs` has no `LootDrop` insert at all. If the hit doesn't kill, `compute_phase` re-checks the new HP against the template's thresholds (advancing `enemy.phase` for enemy-5 to notice) and, independently, re-locks aggro onto the attacker if the current lock has expired. See [[reducers.rs##pub fn report_enemy_hit|report_enemy_hit]]. ^enemy-8
9. On the client, `nearby_enemies` — the same chunk-ring AOI view pattern [[02 World & Hex Grid]] documents for terrain — drives `GameManager.OnEnemyInsert`/`OnEnemyDelete`, spawning or freeing one `Enemy` node per row exactly like `RemotePlayer` does for other players. `Enemy` itself doesn't re-simulate anything server-owned: `_Ready` reads its own starting row straight out of `NearbyEnemies.Iter()` for position/hp/phase/texture, `OnEnemyUpdate` just records whatever the server's latest `(x, y, hp, phase)` is, and `_Process` lerps `GlobalPosition` toward `TorusMath.NearestCandidate(canonicalPosition, ...)` every frame — the same wrap-aware nearest-copy trick `RemotePlayer` and `TerrainManager` use, so an enemy near a seam doesn't jump or render on the wrong side of it. See [[GameManager.cs##private void OnEnemyInsert|OnEnemyInsert]] and [[Enemy.cs##public override void _Process|_Process]]. ^enemy-9
10. Each `BulletPatternEvent` row (enemy-6) also reaches every client in that enemy's AOI; `Enemy.cs` listens for `BulletPatternEvent.OnInsert` and forwards only the rows matching its own `EnemyId` to `BulletManager.SpawnEnemyBullet`. `BulletManager` resolves the event's `target` identity to a live position (the local player's own `LocalPlayerPosition`, or a `NearbyRemotePlayers` row) to get a firing angle, then dispatches on `PatternType` — `Ring`/`Volley`/`Curtain`/`Shotgun`/`Explosion` each build their own spread of `Transform2D`s and hand them to the BlastBullets2D plugin's `DirectionalBulletsData2D` — using a `SplitMix64` PRNG keyed by `event_id` (mirroring the server's own hash technique) for any pattern with per-pellet jitter, so every client watching the same event rolls identical-looking pellet spread without the server needing to ship one row per pellet. The bullets themselves are client-side visuals/collision only — a bullet actually connecting with a player is detected locally and reported back via `report_hit`, the reverse-direction hit path [[06 Combat & Damage Math|06]] covers. See [[BulletManager.cs##public void SpawnEnemyBullet|SpawnEnemyBullet]]. ^enemy-10

### Combat, both directions

1. On the player-attacks-enemy side, `LocalPlayerCombat._Process` gates firing on the equipped weapon's `WeaponBehavior.FireRate` (`_fireTimer`/`_firePeriod`, populated in `OnInventoryChanged` — [[04 Item & Equipment System|04's]] weapon-lookup mechanics) and left-mouse input; `Fire` dispatches on `WeaponBehavior.Pattern` (`Single`/`Triple`/`Cluster`) to one of three methods that hand angled shots to `BulletManager.SpawnPlayerBullet(s)` for the visual/collision bullet and, independently, call `SpawnZonesAlong` to lay a chain of `Area2D` "damage zones" spaced `_zoneStep` apart along the same path — hit detection is keyed off these zones, not the bullet sprite itself. See [[LocalPlayerCombat.cs##private void Fire|Fire]] and [[LocalPlayerCombat.cs##private void SpawnZonesAlong|SpawnZonesAlong]]. ^combat-1
2. Each zone is a one-shot `Area2D` `SpawnZone` creates with `Monitoring: true`/`Monitorable: false` (it detects overlaps, nothing detects it) at the exact position/time the bullet's arc would reach that point (`delay` derived from distance-along-path ÷ projectile speed); a `SceneTreeTimer` fires `ScanZone` once at that delay, then frees the zone regardless of whether it found anything — a zone is a single point-in-time overlap check, not a persistent hitbox tracked frame to frame. `ScanZone` calls `ReportEnemyHit(enemy.EnemyId)` for every `Enemy` node it finds overlapping, once per zone per enemy. See [[LocalPlayerCombat.cs##private void SpawnZone|SpawnZone]] and [[LocalPlayerCombat.cs##private static void ScanZone|ScanZone]]. ^combat-2
3. `report_enemy_hit(enemy_id)` — [[05 Enemy AI & Bullet Patterns|05's]] entry point for this side, revisited here for the damage number it deferred: an `immortal` enemy no-ops, otherwise `compute_player_damage(ctx, profile_id)` reads whatever `Item` sits in inventory slot 0, pulls its `WeaponBehavior` via the `weapon_behavior` helper ([[04 Item & Equipment System|04's]] lookup pattern), and scales `weapon.damage` by the caller's own `PlayerStats.strength` — `(damage as f32 * (1.0 + strength as f32 * 0.002)).max(1.0)`, i.e. +0.2% damage per strength point, floored at 1 — or returns 0 if slot 0 holds no weapon at all. Nothing here validates that the caller is actually in range of `enemy_id`, or throttles how often the same enemy can be hit; the only real gate is the client's own fire-rate timer and zone geometry, not anything the server checks. See [[methods.rs##pub fn compute_player_damage|compute_player_damage]] and [[reducers.rs##pub fn report_enemy_hit|report_enemy_hit]]. ^combat-3
4. HP loss, death (`delete_enemy_behavior`'s cascade, XP award), and the phase/aggro bookkeeping on a non-lethal hit are all [[05 Enemy AI & Bullet Patterns|05's]] "Taking damage" section's concern, not repeated here — this fork only adds the damage formula combat-3 covers and the client-side hit-detection combat-1–combat-2 that feed it. ^combat-4
5. On the enemy-attacks-player side, this fork picks up right where the `BulletPatternEvent` row ([[05 Enemy AI & Bullet Patterns|05's]] step 10) reaches `Enemy.cs` and gets forwarded to `BulletManager.SpawnEnemyBullet`: that method stamps every bullet it spawns with `bullets_custom_data = new BulletData { SourceStep = bulletPattern.SourceStep }` — the same `SequenceStepRef` (a `Single`/`Repeat`/`Multi` def id) the server attached to the event — before dispatching on `PatternType` to build the actual spread. This is what lets a bullet "remember" which def row it came from all the way through flight, independent of which specific pellet it is. See [[BulletManager.cs##public void SpawnEnemyBullet|SpawnEnemyBullet]]. ^combat-5
6. The BlastBullets2D plugin fires its own `area_entered` signal whenever any spawned bullet's collision shape overlaps a target `Area2D`; `BulletManager._Ready` wires this once to `OnEnemyBulletAreaEntered`, which reads the `bullets_custom_data` back off the colliding bullet as a `BulletData` and calls `ReportHit(data.SourceStep)` — the bullet's own remembered def reference, not anything recomputed at hit time. See [[BulletManager.cs##private void OnEnemyBulletAreaEntered|OnEnemyBulletAreaEntered]]. ^combat-6
7. `report_hit(attack: SequenceStepRef)` resolves `attack` against whichever table it names — `SingleStepDef`/`RepeatStepInstance`/`MultiStepDef` (indexed by `shot_index` for the `Multi` case) — to get a `base_damage`, straight off the `damage: u32` field every one of those three def/instance shapes carries. `compute_incoming_damage` then scales it down by the caller's own `PlayerStats.defense` — `(base_damage as f32 * (1.0 - defense as f32 * 0.002)).max(1.0)` — before subtracting from `PlayerData.hp`. Like `report_enemy_hit`, nothing here checks that the caller was ever actually near the bullet, or that this `SequenceStepRef` was ever sent to them in a `BulletPatternEvent` at all — the reducer trusts whatever step reference the client passes, the same way it trusts `ctx.sender()` for whose HP to touch. See [[reducers.rs##pub fn report_hit|report_hit]]. ^combat-7
8. If that subtraction reaches 0, `report_hit` deletes `PlayerData`/`PlayerInventory`/`PlayerStats`/`PlayerPosition`, clears every `ActiveConsumableEffect` row for the profile, then moves the identity from `LoggedInPlayer` to `LoggedOutPlayer` — the reverse of `join_world`'s login-state move ([[03 Player System]]'s "Login state" section) triggered by an enemy's own attack landing rather than `leave_world`. `PlayerProfile` and `PlayerChunk` both survive this cascade untouched — a dead profile can rejoin later exactly as `try_scaffold_profile`'s idempotent per-table checks expect, though the surviving `PlayerChunk` row means a respawned player's AOI still centers on wherever they died until their first post-respawn `report_movement` corrects it. Otherwise, HP is simply written down and nothing else changes. See [[reducers.rs##pub fn report_hit|report_hit]]. ^combat-8
9. Whichever way `LoggedInPlayer` disappears — this death path or a manual `leave_world` — the client reacts identically: `GameManager.OnLocalPlayerDelete` frees the `LocalPlayer`/`BulletManager`/`TerrainManager` nodes, calls `ShowLobby()`, reopens the lobby subscription, and unsubscribes the in-world one — the exact reverse of `OnJoinPressed` ("Joining the world", join-1), since from the client's perspective a death and a deliberate logout are the same event: the row it was watching just isn't there anymore. See [[GameManager.cs##private void OnLocalPlayerDelete|OnLocalPlayerDelete]]. ^combat-9

### Camera and rendering, spectating all of it

1. `CameraRig` is a plain `Node` (not a 2D or 3D node) added directly to `main.tscn`'s own scene tree, deliberately outside the 3D `SubViewportContainer/SubViewport` that hosts `world_3d.tscn` — a node inside that `SubViewport` never receives forwarded mouse-motion input, so the single source of truth for camera yaw/pitch/zoom has to live outside it rather than inside the 3D scene it partly drives. Its `_Process`/`_Input` gate every read behind `LocalPlayer.Local != null`, so none of its keyboard/mouse camera controls (yaw keys, arcball drag, cursor-relative snapping, scroll-zoom) do anything while the identity is still in the lobby. See [[CameraRig.cs##public override void _Input|_Input]]. ^camera-1
2. Clicking Join fires `HideLobby` inside `OnJoinPressed` ("Joining the world", join-1), which drops the lobby's own `MainMenuPhantomCamera2D`'s `Priority` to 0 — a `PhantomCamera2D`'s `Priority` is just "which phantom camera currently wins the shared viewport `Camera2D`," so this doesn't move anything, it just stops the lobby camera from being the winner. The player's own `%LocalPlayerPhantomCamera2D` doesn't exist yet at this point — it's a child of the `LocalPlayer` node, not instantiated until the `LoggedInPlayer` row insert reaches `OnLocalPlayerInsert` (join-3) — so there's a brief window with no in-world camera bid active at all. See [[GameManager.cs##private void OnJoinPressed|OnJoinPressed]]. ^camera-2
3. Once `LocalPlayer._Ready` actually runs, it fetches its own `%LocalPlayerPhantomCamera2D` node and hands it to `CameraController2D.RegisterCamera`, which sets that camera's `Priority` to 60 — comfortably above the lobby camera's 0, so it wins as soon as it exists. Dying or leaving reverses this asymmetrically rather than symmetrically: `OnLocalPlayerDelete` (combat-9) frees the whole `LocalPlayer` node — taking its registered `PhantomCamera2D` down with it — and calls `ShowLobby`, which puts the lobby camera's `Priority` back to 60; `CameraController2D.UnregisterCamera` exists but nothing ever calls it, a loose end `client/Scripts/World/CLAUDE.md` already flags as not currently load-bearing (the registered camera node is freed along with `LocalPlayer` regardless). See [[LocalPlayer.cs##public override void _Ready|_Ready]] and [[CameraController2D.cs##public void RegisterCamera|RegisterCamera]]. ^camera-3
4. From here on, every frame, two independent presenters read `CameraRig.Instance`'s `Yaw`/`PitchDegrees`/`Distance` and each drive their own camera — neither presenter owns any state, and neither reads from the other. `CameraController2D._Process` writes the registered `PhantomCamera2D`'s `RotationOffset` straight to `Yaw` and its `Zoom` to `Zoom2D` (`ZoomReferenceDistance / Distance` — Godot 2D zoom is inverse to camera distance, so zooming "in" is a smaller `Distance`); `WorldRenderer3D._Process` writes the 3D scene's `PhantomCamera3D` spring-arm rotation to `(PitchDegrees, -Mathf.RadToDeg(Yaw), 0)` — negated, since a clockwise rotation in Godot's y-down 2D space is a counter-clockwise rotation about 3D's +Y axis — and its `SpringLength` to `Distance`. See [[CameraController2D.cs##public override void _Process|_Process]] and [[WorldRenderer3D.cs##public override void _Process|_Process]]. ^camera-4
5. `LocalPlayer._PhysicsProcess` is the other consumer of that same `Yaw` value — [[03 Player System]] already covers this in full as the input/movement-feel side (rotating raw WASD input by `CameraRig.Instance?.Yaw` before it becomes `Velocity`, move-1); it's named here only to place it alongside the two camera presenters above as the third and last thing one shared yaw drives every frame. ^camera-5
6. Also in `LocalPlayer._Ready`, if a `KnightScene` (`Knight.fbx`) is assigned and `WorldRenderer3D.Instance` already exists, `LocalPlayer` constructs a `CharacterModel3D` — a plain `IDisposable` wrapper, not a node subclass of its own — parenting the instantiated model directly under `WorldRenderer3D` and calling `SetCameraFollowTarget` so the 3D scene's `PhantomCamera3D` (configured for third-person `follow_mode` in `world_3d.tscn`; that property is get-only from C#, so only the `.tscn` can change it) tracks the new model. No `RemotePlayer` and no `Enemy` ever does anything like this — this is the only place in the whole client that a 3D model is ever instantiated; every other player-shaped or enemy-shaped thing in the game stays 2D-only. See [[LocalPlayer.cs##public override void _Ready|_Ready]] and [[CharacterModel3D.cs##public CharacterModel3D|CharacterModel3D]]. ^camera-6
7. Every physics frame, right after `MoveAndSlide()`, `LocalPlayer._PhysicsProcess` calls `_model3D?.SyncFrom2D(GlobalPosition, Rotation)` — the only place the 3D model's transform is ever touched. `SyncFrom2D` rebuilds a `Transform3D` from scratch out of the 2D `Vector2 pos`/`float yaw2D` it's handed (`new Vector3(pos.X, 0f, pos.Y)` for position, `new Vector3(0, -yaw2D, 0)` for rotation, the same clockwise-to-counter-clockwise negation `WorldRenderer3D` uses for the camera) — there's no blending, no animation-state machine, no independent 3D physics of any kind; the 3D body is a direct, one-way mirror of whatever the 2D `CharacterBody2D` already decided, one frame behind nothing. See [[LocalPlayer.cs##public override void _PhysicsProcess|_PhysicsProcess]] and [[CharacterModel3D.cs##public void SyncFrom2D|SyncFrom2D]]. ^camera-7
8. On leaving the world — death or `leave_world`, the same `OnLocalPlayerDelete` handler camera-3 above already covers ([[06 Combat & Damage Math|06's]] "Death and the `LoggedOutPlayer` transition" section for what triggers it) — `LocalPlayer._ExitTree` disposes `_model3D` (freeing its node) and calls `WorldRenderer3D.Instance?.ClearCameraFollowTarget()`, the mirror image of camera-6's setup. See [[LocalPlayer.cs##public override void _ExitTree|_ExitTree]]. ^camera-8

## 07 Meanwhile, independently

Everything below happens on its own schedule, triggered from outside the ordinary connect → lobby → in-world flow above — an admin identity acting through the SpacetimeDB CLI/dashboard (there's no in-client UI for any of it, see [[08 Admin, Debug & World Lifecycle]]'s "Known gaps"), not a player doing something in a running session.

1. An admin identity isn't a separate login flow — it's one bit, `is_admin`, living on whichever row (`LoggedInPlayer` or `LoggedOutPlayer`) an already-connected identity currently owns. `claim_admin` sets it to `true` for the caller only if no `LoggedInPlayer`/`LoggedOutPlayer` row anywhere already has it set — there's exactly one admin slot for the whole server at a time, not a per-identity permission level. See [[admin.rs##pub fn claim_admin|claim_admin]]. ^admin-1
2. `release_admin` is the only reducer that ever clears `is_admin`, and only for the caller's own row. Neither `client_connected` nor `client_disconnected` (conn-3, end-2) ever touches it — an admin who disconnects keeps `is_admin: true` on whatever `LoggedOutPlayer` row `client_disconnected` leaves them on, so `claim_admin`'s "is anyone already admin" check still finds them and refuses every other identity until that same identity reconnects and calls `release_admin` itself. The slot doesn't free up on disconnect; it locks. See [[admin.rs##pub fn release_admin|release_admin]]. ^admin-2
3. Every other reducer in `main/admin.rs` gates on `is_admin(ctx)` — a plain read of whichever login-state row the caller currently owns — rather than a separate roles/permissions table; there's no hierarchy above or below "admin," just this one flag. ^admin-3
4. Content/catalog edits: `change_stats` (resolves a target player by username via `find_player_by_username`, then a profile on that player by name, then overwrites its `PlayerStats` wholesale) and `upsert_texture_entry`/`upsert_enemy_template` (insert-or-update a whole row into `TextureEntry`/`EnemyTemplate` by primary key) are one-off, ad-hoc table edits — none of them run on a schedule or belong to any recurring cycle. See [[admin.rs##pub fn change_stats|change_stats]]. ^admin-4
5. World-gen re-triggers: `generate_world_proc`/`generate_world_manual` and `upsert_world_def`/`upsert_biome_def`/`upsert_biome_region_def` are thin admin-gated wrappers — `generate_world_proc` calls the exact same `internal_generate_world_proc` that `init` calls at boot (boot-2), so an admin can repaint the whole live map the same way boot first painted it, without a restart. `add_chunks`/`clear_chunks` do the same for the chunk grid, wrapping the same `internal_add_chunks` `init` also calls. See [[admin.rs##pub fn generate_world_proc|generate_world_proc]] and [[admin.rs##pub fn add_chunks|add_chunks]]. ^admin-5
6. Enemy spawn/despawn: `spawn_enemy(template_id, x, y, is_elite, immortal)` is the only path anywhere that can set `is_elite`/`immortal` to anything but `false`, but it double-inserts the `EnemyBehavior` row `build_enemy_behavior` already inserted internally — a concrete bug, detailed in [[08 Admin, Debug & World Lifecycle]]'s "Known gaps". `despawn_enemy` is a plain delete-by-id. See [[admin.rs##pub fn spawn_enemy|spawn_enemy]]. ^admin-6
7. `find_player_by_username` (used by `change_stats` above, and by `item/reducers.rs`'s `give_item`/`remove_item`) matches one lookup string against three different things, tried in order: a case-insensitive `username`, a full identity hex string, or a prefix of that hex string. ^admin-7
8. Debug tooling is two unrelated things that happen to share the word "debug": `toggle_debug` (admin-gated) starts or stops a recurring `tick_player_position_debug` reducer that mirrors every `PlayerPosition` row into a parallel `PlayerPositionDebug` table (adding each position's hex coordinates) for external inspection via the SpacetimeDB CLI/dashboard — no client ever subscribes to it. The client's own `DebugOverlay` HUD (FPS, memory, node/object counts, enemy count) is entirely separate: a local perf overlay toggled by pressing P, with no server backing and no admin gate at all. See [[admin.rs##pub fn toggle_debug|toggle_debug]] and [[DebugOverlay.cs##public override void _Input|_Input]]. ^admin-8
