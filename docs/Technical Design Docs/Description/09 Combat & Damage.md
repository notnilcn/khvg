## The 30-second version

The server is the only place damage exists. When you fire, the client plays the bullet visuals and lays a fuse of invisible `HitZone` areas along each bullet's path; when a zone's timer pops inside an enemy hurtbox, the client calls `ReportEnemyHit(enemy_id)` — just the id, never a number. When an enemy bullet overlaps your hurtbox, the client calls `ReportHit(source_step)` — a reference to the attack step that fired the bullet, again never a number. The server recomputes everything: your effective weapon from your inventory rows, per-bullet damage with flat defense and a minimum of 1, XP and level-ups on kills, and — at zero hp — the full death teardown that drops you back to the lobby. Health reaches every screen as ordinary row updates into a read-only `HealthComponent` mirror. Two adjuncts round the system out: other clients corroborate your hits through a witness hurtbox + the server-only `PlayerHitFlag` table, and bullet-control abilities (delete/split/attract/slash) are relayed as `BulletControlEvent` rows that every client resolves against its own live bullets.

## The report-and-mirror rule

Every combat mechanism below is an instance of one rule, stated in `client/AGENTS.md` and enforced by the shape of the reducers: **components never mutate health or stats locally.** A client can only *report* ("this enemy id overlapped my hit zone", "this attack step's bullet overlapped me"), and it *mirrors* the result when the updated row flows back through the subscription. The reducers deliberately take ids and step references rather than amounts, so there is no client-supplied number for the server to trust in the first place. This is why there is no `Damage()` or `Heal()` method anywhere on the client — [[client/Scripts/Components/Combat/HealthComponent.cs#SetFromServer#1|HealthComponent]] exposes only `SetFromServer`.

## Outgoing damage: your weapon against enemies

### The effective weapon and the firing loop

```sync
![[00 End-to-End Timeline Flowchart#^combat-1{seamless:true,title:false,marker:01.}]]
```

Why "resolved, not read": a weapon's behavior is a composition — the weapon slot's item, the slot's `active_toggle` index into the item's pattern list (its own `Weapon` behaviors plus `WeaponToggle` grants from equipped enchantments), and the shot-count/damage enchantment behaviors folded on top. The server's [[server/spacetimedb/src/player/methods.rs#resolve_effective_weapon#1|resolve_effective_weapon]] computes that composition from table rows; the client's [[client/Scripts/Components/Weapon/EffectiveWeaponResolver.cs#Resolve#1|EffectiveWeaponResolver.Resolve]] computes the same composition from the mirrored rows. The two must agree exactly, because both index the same toggle-option list and both divide damage by the same effective shot count — so the fold order is pinned on both sides (slot index ascending: weapon 0, accessory 5, armor 6, ability slots 32–37; innate enchantments before socketed ones per slot, see [[server/spacetimedb/src/player/methods.rs#equipped_enchantment_behaviors#1|equipped_enchantment_behaviors]] and its client twin `EquippedEnchantmentBehaviors`). `Resolve` also copies the catalog's shared `WeaponBehavior` instead of mutating it, because the folded shot count is per-player while the catalog row is shared.

`CombatComponent` doesn't re-resolve every frame — that would re-walk nine inventory slots 60 times a second. It re-resolves only when [[client/Scripts/Components/Weapon/EffectiveWeaponResolver.cs#Fingerprint#1|EffectiveWeaponResolver.Fingerprint]] (a string of item ids, the weapon's `ActiveToggle`, and every equipped slot's enchantment ids) changes between `InventoryChanged` signals ([[client/Scripts/Components/Weapon/CombatComponent.cs#OnInventoryChanged#1|CombatComponent.OnInventoryChanged]]). The same change debounces the fire timer and derives `_firePeriod = 1 / fire_rate` and `_zoneStep = range / zone_count`. Pressing T (`weapon_toggle`, declared in `project.godot`) cycles the pattern server-side through `SetSlotToggle` in [[client/Scripts/Components/Weapon/CombatComponent.cs#CycleWeaponToggle#1|CycleWeaponToggle]] — the toggle is validated server-side and comes back as an inventory row update, which changes the fingerprint and re-resolves the weapon. Aim assist and lock-on come from the `LocalPlayerActiveProfile` row; `ScanNearestEnemy` re-scans the `NearbyEnemies` mirror every 0.5 s within the weapon's `range`, restricted to a ±0.52 rad cone unless lock-on is on, and a child `NearbyEnemiesBinder`'s `RowDeleted` (wired in [[client/Scenes/local_player.tscn|local_player.tscn]]) drops the lock target when the enemy despawns.

Holding `fire` dispatches on the pattern: `Single` fires one bullet, `Triple` fires `shot_count` bullets evenly across `spread_angle`, `Cluster` fires `shot_count` pellets with randomized angle, range, and speed (`FireSingle`/`FireTriple`/`FireCluster` in `CombatComponent.cs`). Each bullet is two things at once: a purely visual BlastBullets2D bullet spawned through [[client/Scripts/Game/BulletManager.cs|BulletManager]], and a fuse of `HitZone`s laid along the same path by [[client/Scripts/Components/Weapon/CombatComponent.cs#SpawnZonesAlong#1|SpawnZonesAlong]] — zone *i* sits at distance `(i + 0.5) × zoneStep` with radius `zoneStep / 2` and a timer delay of `(i + 0.5) × zoneStep / speed`, so the zone wakes exactly when the visual bullet passes through it. The hit detection is scheduled area checks, not physics-following projectiles — a deliberate decoupling: the visual bullet can jitter (Cluster pellets randomize speed) while the server only ever hears "some enemy stood in a zone", and per-pellet identity is unnecessary because per-bullet damage is uniform across a trigger pull.

### Hit zones, factions, and the report

```sync
![[00 End-to-End Timeline Flowchart#^combat-2{seamless:true,title:false,marker:02.}]]
```

A `HitZone` ([[client/Scripts/Components/Combat/HitZone.cs#OnLifetimeTimeout#1|HitZone.OnLifetimeTimeout]]) is a [[client/Scripts/Components/Combat/DamageComponent.cs#ReportHits#1|DamageComponent]] with a fuse, instanced from [[client/Scenes/Components/hit_zone.tscn|hit_zone.tscn]]. That scene's properties do real work: `collision_mask = 4` so it detects only the enemy hurtbox layer, `monitorable = false` so nothing detects *it* back, and `top_level = true` so its `GlobalPosition` isn't dragged by the moving player's transform after spawn. Its in-scene `LifetimeTimer` is `one_shot`; on timeout the zone calls `ReportHits()` and frees itself.

`ReportHits` asks the physics engine for overlapping areas, keeps only `DamageReceivingComponent`s, applies the faction filter, emits `DidHitReceiver` for local observers — and if the victim's entity is an `Enemy`, calls `ReportEnemyHit(enemy.EnemyId)`. Note what is *not* sent: no damage number, no weapon id, no zone position. The faction filter ([[client/Scripts/Components/Combat/FactionComponent.cs#CheckOpposition#1|FactionComponent.CheckOpposition]]) is `opposed = (a & b) == 0` — opposition means sharing no flag, and a missing `FactionComponent` falls back to `Neutral`, which is opposed to everything. Factions are set statically per scene (`Players = 2` in `local_player.tscn`, `Enemies = 4` in `default_enemy.tscn`) because faction is implicit in entity kind; there is nothing to sync. In practice the filter means players-vs-enemies only: `ReportHits` only ever reports `Enemy` victims, so player-vs-player damage is **not implemented** even though the flag math would permit it — PvP of any kind (including the aspirational guild-territory PvP from the design notes) stays out of scope.

### Server-side outgoing damage

```sync
![[00 End-to-End Timeline Flowchart#^combat-3{seamless:true,title:false,marker:03.}]]
```

The exact formula in [[server/spacetimedb/src/combat/mod.rs#compute_player_damage#1|compute_player_damage]], per reported bullet hit:

```
raw       = weapon.damage × (1 + strength × 0.002) / max(effective_shot_count, 1)
mitigated = max(raw + weapon.flat_bullet_mod − enemy_defense, 1)
total     = mitigated + weapon.true_flat + raw × weapon.true_pct
```

Three design decisions are encoded here. First, `weapon.damage` is per *trigger pull*, divided among the pattern's bullets (`WeaponBehavior`'s comment in `item/tables.rs` says so), which is what makes the divide-and-conquer trade real: a 12-pellet Cluster and a Single shot deal the same total before defense. Second, defense is a **flat** subtraction clamped to a minimum of 1 (`EnemyTemplate.defense` for enemies) — so against high-defense enemies each pellet of a multi-shot pattern loses the same flat amount, and few-strong-bullets patterns win; against low-defense swarms the multi-shot's coverage wins. Third, true-damage enchantment bonuses (`TrueDamageFlat`, `TrueDamagePercent`) apply *after* defense, so they always land — the counter-build against armor-stacking. `FlatBulletDamageMod` joins `raw` *before* the defense clamp, so it can be eaten by defense. Edge cases are defensive: a missing `PlayerStats` row deals 1, a missing weapon deals 0 (so an unarmed player can report hits forever and do nothing).

[[server/spacetimedb/src/enemy/reducers.rs#report_enemy_hit#1|report_enemy_hit]] guards first: the caller must be in-world (`require_in_world`), a missing enemy id is silently ignored (the enemy may have died to someone else between the client's overlap and the server's processing), and `immortal` enemies shrug the hit off. Then [[server/spacetimedb/src/combat/mod.rs#deal_damage_to_enemy#1|deal_damage_to_enemy]] runs — one of only two damage entry points in the whole module, both in `combat/mod.rs` so the player and enemy paths share one implementation.

### Kills, XP, and phase transitions

```sync
![[00 End-to-End Timeline Flowchart#^combat-4{seamless:true,title:false,marker:04.}]]
```

The XP reward is the template's `max_hp / 10` (fallback 10 if the template row is gone), awarded through [[server/spacetimedb/src/player/methods.rs#internal_gain_xp#1|internal_gain_xp]]. Level thresholds are triangular: [[server/spacetimedb/src/player/methods.rs#xp_for_level#1|xp_for_level]] is `100 × (L−1) × L / 2`, so each level costs 100 more than the last increment. Leveling heals `HP_PER_LEVEL` (5, in `main/global.rs`) *per level gained* on top of current hp — deliberately a partial heal, so leveling mid-fight doesn't fully restore you — and grants `SKILL_POINTS_PER_LEVEL` (2) unspent points into the allocation row; `recompute_stats` then folds the new base max hp (`BASE_MAX_HP` 100 + 5 per level above 1) and clamps hp to it. Death cleanup goes through the shared archetype helper: `despawn_enemy_archetype` deletes the enemy row plus its entire behavior tree, so no orphan rows outlive the kill.

A surviving enemy gets two updates in one transaction. Its new phase is recomputed from the template's descending `hp_threshold`s by [[server/spacetimedb/src/enemy/methods.rs#compute_phase#1|compute_phase]] (highest `phase_index` whose threshold the new hp% has crossed). And its aggro is re-evaluated, with a subtlety worth knowing: on a **phase change** the enemy re-picks the *nearest* player via `recompute_aggro` — not necessarily the attacker — while without a phase change it locks onto the attacker (`ctx.sender()`) provided the previous aggro lock has expired; `EnemyTemplate.aggro_lock_seconds` keeps a freshly-aggroed enemy from ping-ponging. The next 100 ms behavior tick picks the phase change up and restarts the new phase's attack cycle (`begin_phase_cycle`), which is why bosses visibly switch patterns the moment their hp bar crosses a threshold. One deliberate absence: **kills drop no loot** — `LootDrop` rows are created only by `drop_item` (see [[10 Inventory, Items & Enchantments]]).

## Incoming damage: enemy bullets against you

### Hit identity travels with the event

```sync
![[00 End-to-End Timeline Flowchart#^combat-5{seamless:true,title:false,marker:05.}]]
```

The enemy side of combat never trusts a client to say *which bullet* hit — bullets are client-side visual/simulation objects the server doesn't track. Instead it trusts the *attack step*: when the server fires a pattern it appends a `BulletPatternEvent` carrying a `SequenceStepRef` (see [[08 Enemies & AI]]), and [[client/Scripts/Components/Bullets/BulletSpawnerComponent.cs#SpawnEnemyBullet#1|BulletSpawnerComponent.SpawnEnemyBullet]] copies that reference into the spawner's `bullets_custom_data` as a [[client/Scripts/Game/BulletData.cs|BulletData]] resource, which the BlastBullets2D plugin hands back on every overlap. `SequenceStepRef` is an enum — `Single(def_id)`, `Repeat(repeat_id)`, `Multi(MultiStepRef { def_id, shot_index })` (`enemy/instance_tables.rs`) — i.e. a pointer into the server's own definition tables.

When the plugin reports an overlap, [[client/Scripts/Components/Bullets/BulletHitRouterComponent.cs#OnEnemyBulletAreaEntered#1|BulletHitRouterComponent.OnEnemyBulletAreaEntered]] (connected to the factory's `area_entered` signal in `OnRegistered`) routes by *what was hit*: the local player's `DamageReceivingComponent` gets [[client/Scripts/Components/Combat/DamageReceivingComponent.cs#ProcessBulletHit#1|ProcessBulletHit]], which calls `ReportHit(data.SourceStep)`; a remote puppet's `RemoteHitWitnessComponent` takes the witness path below; anything else on the player collision layer falls through to `ReportHit` directly. The layers make this work: enemy bullets live on layer/mask 2 (`SetupEnemyBullets`), the local player's hurtbox is layer 2 / mask 2 ([[client/Scenes/local_player.tscn|local_player.tscn]]), and enemy hurtboxes are layer 4 — so enemy bullets physically cannot touch other enemies, and player `HitZone`s (mask 4) cannot touch players. Friendly fire is excluded by the physics setup, not by a code check.

### Server resolution, mitigation, and death

```sync
![[00 End-to-End Timeline Flowchart#^combat-6{seamless:true,title:false,marker:06.}]]
```

[[server/spacetimedb/src/player/reducers.rs#report_hit#1|report_hit]] is the inverse of `report_enemy_hit`: the client names the *attack step*, the server names the *number*. It looks the `SequenceStepRef` back up — `SingleStepDef.damage` for `Single`, the per-enemy `RepeatStepInstance.damage` for `Repeat` (repeat steps are instanced per enemy, so two enemies running the same def can carry different damage), or the indexed shot's damage inside a `MultiStepDef.shots` vector for `Multi` — and errors with "Attack step not found." if the reference dangles. What the client demonstrably *cannot* do is name 99999 damage: there is no damage parameter. It could, however, report a step whose bullet never touched it — the report itself is trusted; corroborating reports is what the witness system below is for.

[[server/spacetimedb/src/combat/mod.rs#deal_damage_to_player#1|deal_damage_to_player]] then applies [[server/spacetimedb/src/combat/mod.rs#compute_incoming_damage#1|compute_incoming_damage]] — the player's resolved flat `PlayerData.defense` (gear/buff-derived, modifier-only, not one of the six allocatable stats), minimum 1 — and subtracts with `saturating_sub`. At zero hp the reducer runs the full death cleanup inside the same transaction: [[server/spacetimedb/src/player/methods.rs#teardown_profile#1|teardown_profile]] deletes the profile's `PlayerData`, `PlayerStats`, `PlayerStatAllocation`, every `PlayerInventorySlot`, the position and chunk rows, and any active consumable effects; then the `LoggedInPlayer` row is deleted and a `LoggedOutPlayer` row inserted. **Death *is* the lobby round-trip** — the client doesn't get a "you died" message, it watches its own rows disappear and the lobby profile views reappear (the teardown mechanics are [[13 Disconnect & Teardown]]'s; note that dying costs the profile its inventory — the slots are deleted, not dropped). Healing is the same file's [[server/spacetimedb/src/combat/mod.rs#heal_player#1|heal_player]], clamped to `max_hp`, reached from consumables and Heal abilities via `apply_consumable_effect`.

## Health mirroring

```sync
![[00 End-to-End Timeline Flowchart#^combat-7{seamless:true,title:false,marker:07.}]]
```

The mirror is deliberately dumb, and that is the design. [[client/Scripts/Components/Combat/HealthComponent.cs#SetFromServer#1|HealthComponent.SetFromServer]] sets `MaxValue` then `Value` on the shared `Stat` resource and diffs old vs new to emit `HealthDidDecrease`/`HealthDidIncrease`/`HealthDidZero` — pure observer signals for UI and effects, never a write path back. Because the `Stat` clamps (`MinValue = 0`), out-of-order or duplicate row updates can't push hp negative, and re-applying the same value is a no-op with no signals. Your own hp arrives on the `LocalPlayerData` view into [[client/Scripts/Components/Data/LocalPlayerDataComponent.cs#OnDataRow#1|LocalPlayerDataComponent.OnDataRow]] (which also lifts `Level`, `Defense`, and `BaseSpeed` off the same row); enemy hp rides `NearbyEnemies` row updates into [[client/Scripts/Players/Enemies/Enemy.cs#OnEnemyRowUpdated#1|Enemy.OnEnemyRowUpdated]], with `max_hp` taken from the `EnemyTemplate` catalog on insert. Both entity kinds then register that same `Health` instance under `StatKind.Hp` in their `StatsComponent` (comedot's shared-Stat pattern), so a HUD reading "the Hp stat" and a damage flash listening to `HealthComponent` signals are observing literally one object.

The consequence for the feel of combat: there is no client-side prediction of damage. You see your hp drop when the server round-trip completes — the price of the never-trust-the-client rule, accepted because bullet-hell dodging is about *not* getting hit rather than frame-perfect hit feedback.

## Anti-cheat: corroborating witnesses

```sync
![[00 End-to-End Timeline Flowchart#^combat-8{seamless:true,title:false,marker:08.}]]
```

The witness system exists because `report_hit` trusts the reporter. Every remote puppet carries a [[client/Scripts/Components/Combat/RemoteHitWitnessComponent.cs|RemoteHitWitnessComponent]] hurtbox — declared inline in [[client/Scenes/non_local_player.tscn|non_local_player.tscn]] on layer 2 with mask 0 (it is detected by bullets but detects nothing itself) plus a capsule shape child. Because enemy bullets sit on layer/mask 2, they physically collide with other players' puppets on *every* client, and the plugin's own per-bullet collision counting disables the bullet at `bullet_max_collision_count` (0 = piercing) — so a bullet seen hitting your teammate disappears on your screen too, keeping everyone's bullet field consistent without the server tracking bullets at all. The router forwards those overlaps to `ProcessBulletHit()`, which calls `FlagPlayerHit(player.PlayerId)` — the witness reports *who was seen hit*, never damage. Server-side, [[server/spacetimedb/src/anticheat/reducers.rs#flag_player_hit#1|flag_player_hit]] requires the caller to be in-world, silently drops self-reports (the victim's own report path is `report_hit`), and appends a [[server/spacetimedb/src/anticheat/tables.rs#PlayerHitFlag#1|PlayerHitFlag]] row — who was hit, who witnessed it, when, and deliberately no bullet identity. The table is not `public`, so clients can't read (or farm) the flags; the idea is the server can later cross-check a victim's self-reports against independent witnesses.

## Bullet-control abilities

```sync
![[00 End-to-End Timeline Flowchart#^combat-9{seamless:true,title:false,marker:09.}]]
```

The four bullet-control effects (`DeleteBullets`/`SplitBullets`/`AttractBullets`/`SlashBullets`, an `AbilityEffect` in `item/tables.rs`) are networked as *casts*, not as bullet state — because the server tracks no live bullets, it cannot delete "bullet #417". The caster's [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#TryActivateAbility#1|LocalPlayerInventoryComponent.TryActivateAbility]] does a cooldown/charge pre-check against the mirrored slot row, calls `ActivateAbility(head_slot, cursor_x, cursor_y)`, and applies the effect **optimistically** on its own `BulletControllerComponent` so the caster sees zero-latency feedback. Server-side, [[server/spacetimedb/src/player/reducers.rs#activate_ability#1|activate_ability]] re-validates everything (ability-role head slot, item has an `Ability` behavior, cooldown not started, charges remain), scales the effect by the head's position multiplier (`scale_ability_effect` over `ABILITY_POSITION_MULTIPLIERS` — first ability slot stronger), clamps the cursor target into `MAX_ABILITY_TARGET_RANGE` (600) of the *server's own position row* so a lagging or lying client can't slash across the map, appends the [[server/spacetimedb/src/enemy/instance_tables.rs#BulletControlEvent#1|BulletControlEvent]] row, fires any `OnAbilityUseBuff` enchantment triggers, and writes the new `cooldown_until`/`charges` — note the item is *not* consumed, unlike `use_item`.

Every *other* client receives the cast as a row insert on the child `BulletControlEventBinder` (wired to `OnBulletControlEventRow` in [[client/Scenes/game.tscn|game.tscn]]) and [[client/Scripts/Components/Bullets/BulletControllerComponent.cs#OnBulletControlEventRow#1|BulletControllerComponent]] replays it — own echoes skipped via `GameManager.IsLocal(row.CastBy)`, because the caster already applied it. All four effects share proximity queries over `BulletSpawnerComponent.LiveEnemyBullets` (the tracked `DirectionalBullets2D` instances — the factory can't enumerate its own spawns): `FindBulletsNear` for the radial Delete/Split/Attract, `FindBulletsInRect` for Slash. `DeleteNear` disables bullets in place; `SplitNear` disables each and respawns it as a fan via `SpawnEnemyBulletFan`, *keeping the source bullet's `BulletData`* so split pellets still report the original `SourceStep` on hit (damage identity survives the split); `AttractNear` pushes homing targets for a blackhole pull. Slash encodes its rectangle as origin (the server position row) + far end (origin + direction × `length`) + width in the `radius` field, with a fixed +X fallback direction when the cursor sits exactly on the player — mirrored in `TryActivateAbility` so the optimistic rect matches the echo — and every client draws the same brief black `Polygon2D` flash (`SpawnSlashVisual`), so the visual replicates with the cast. There is also a direct [[server/spacetimedb/src/enemy/reducers.rs#control_bullets#1|control_bullets]] reducer (validate in-world, append the event, no clamp/cooldown) — the thin admin/debug-grade sibling of the `activate_ability` relay.

Two honest caveats, both by design. First, because each client resolves the proximity query against its *own* simulated bullets, a bullet exactly at the radius edge may be deleted on one screen and survive on another; the next hits are still server-resolved, so the divergence is cosmetic. Second, the queries are torus-naive (plain `DistanceSquaredTo`/dot products) — a slash across the wrap seam misses bullets just over the border. (The 3D backdrop gets its own read-only mirror of the same `LiveEnemyBullets` set each frame via [[client/Scripts/Components/Bullets/EnemyBullets3DComponent.cs#SyncInstance#1|EnemyBullets3DComponent]] — presentation only, covered in [[11 Camera & Presentation]].)

## Scene wiring reference

- [[client/Scenes/non_local_player.tscn|non_local_player.tscn]] — the inline `RemoteHitWitnessComponent` (layer 2, mask 0, capsule child).
- [[client/Scenes/Components/hit_zone.tscn|hit_zone.tscn]] — the `HitZone` root (`Area2D`, `top_level`, mask 4, `monitorable = false`), its `CircleShape2D` (`resource_local_to_scene`, so each zone resizes independently), and the one-shot `LifetimeTimer`.
- [[client/Scenes/game.tscn|game.tscn]] — the `BulletManager` subtree declared **inline** (`z_index = 1` so bullets draw above spawned entities): the `BulletFactory2D` node, `BulletSpawnerComponent`, `BulletHitRouterComponent`, and `BulletControllerComponent` with its `BulletControlEventBinder` child (`RowInserted` → `OnBulletControlEventRow`).

## Known gaps / stubs

- **The deleted bullet-despawn protocol.** `combat/mod.rs`'s comment above `PlayerDamageOutcome` still cites "the slash/bullet-despawn reducers in src/plan.md" as upcoming — but `server/spacetimedb/src/plan.md` has been **deleted** and that design (a `BulletDespawnEvent` table, a `slash_bullet` reducer, an extended `report_hit(attack, pattern_event_id, bullet_index, chunk_index)`) was never built. The implemented protocol is the simpler `BulletControlEvent` + `control_bullets` (+ the `activate_ability` relay) documented above, and `report_hit` still takes the single `SequenceStepRef` argument. Treat the comment as archaeological.
- **Discarded outcome payloads.** `PlayerDamageOutcome`/`EnemyDamageOutcome` in `combat/mod.rs` are `#[allow(dead_code)]`: both callers (`report_hit`, `report_enemy_hit`) ignore the returned variant — they were earmarked for the unbuilt protocol above. No behavior depends on them.
- **Witness flags are write-only.** Nothing in the module ever reads `player_hit_flag` — flags accumulate for a cross-check that isn't implemented. The corroboration half of the anti-cheat loop exists; the enforcement half doesn't.
- **No loot on kill.** Kills award XP only; `LootDrop` rows come exclusively from `drop_item`. If kill-drop loot is a design goal, it has no code today.
- **Drift hazards (unreferenced scenes).** `Scenes/Components/Combat/damage_component.tscn` is one of the seven unreferenced duplicate component scenes — `DamageComponent`'s only live use is as `HitZone`'s base class; never wire from it. Similarly `Scenes/bullet_manager.tscn` exists on disk (instancing the `bullet_*_component.tscn` scenes) but is **not instanced by any live scene** — `game.tscn` declares the same subtree inline with a different composition (inline `BulletControllerComponent` + its binder). Edit the inline tree in `game.tscn`, not the stray scene.
- **Torus-naive bullet control.** The proximity queries ignore world wrap; effects cast near the wrap seam can miss bullets across the border (see the caveat above).
