# 03 Connection, Subscriptions & Views

The read path every table shares: how the client connects, which rows cross the wire, and how a row becomes a signal a component can handle. Later docs say things like "read via the `nearby_enemies` view in the game wave" — this doc is what makes those sentences intelligible.

Code is the only source of truth; the maintainer refs are jump-off points: [[AGENTS.md|root AGENTS.md]], [[server/AGENTS.md|server AGENTS.md]], [[client/AGENTS.md|client AGENTS.md]].

## 2 The 30-second version

The [[client/sstdbsdk/DatabaseConnector.cs#DatabaseConnector|DatabaseConnector]] autoload owns the single `DbConnection` and pumps it every frame; the [[client/sstdbsdk/TableSubscriber.cs#TableSubscriber|TableSubscriber]] node (declared inline in `game.tscn`) subscribes in three waves — catalog, lobby, game — whose contents are static name lists; one [[client/sstdbsdk/TableBinderComponent.cs#TableBinderComponent|TableBinderComponent]] child per consumed table turns row callbacks into editor-wireable signals; and on the server, parameterized views (`ViewContext` per-caller, `AnonymousViewContext` global, AOI-filtered over `PlayerChunk`) decide which rows each caller receives, with append-only event tables subscribed raw and replayed never.

## 5 The connector

One connection exists per client, and it is owned by the [[client/sstdbsdk/DatabaseConnector.cs#DatabaseConnector|DatabaseConnector]] autoload — a `Node` script attached via the one-node [[client/sstdbsdk/DatabaseConnector.tscn#DatabaseConnector|DatabaseConnector.tscn]] scene, registered in `project.godot`, *not* a child of any game scene — so every node in every scene reaches it through [[client/sstdbsdk/DatabaseConnector.cs#Instance|Instance]] with no entity-registry lookup. It owns [[client/sstdbsdk/DatabaseConnector.cs#Conn|Conn]] (the `DbConnection`), the [[client/sstdbsdk/DatabaseConnector.cs#LocalIdentity|LocalIdentity]] stamped at connect time, and the mirrored [[client/sstdbsdk/DatabaseConnector.cs#Username|Username]]; it exports [[client/sstdbsdk/DatabaseConnector.cs#Host|Host]] (default `https://khvgames.com/server`) and [[client/sstdbsdk/DatabaseConnector.cs#DbName|DbName]] (`bullethell`).

Connecting happens in [[client/sstdbsdk/DatabaseConnector.cs#_Ready|_Ready]] → [[client/sstdbsdk/DatabaseConnector.cs#Connect|Connect]], because the autoload loads before any scene and must be usable by whoever arrives first. Before building the connection it scans launch args for a `--pN` token suffix: [[client/sstdbsdk/DatabaseConnector.cs#IsPlayerArg|IsPlayerArg]] requires the exact whole-arg shape `^--p\d+$` (a plain `StartsWith("--p")` also matched Godot's own `--path`, which once made every editor-run instance share one identity), checking `OS.GetCmdlineArgs` then `OS.GetCmdlineUserArgs`, and stores the suffix in [[client/sstdbsdk/DatabaseConnector.cs#TokenAppend|TokenAppend]]. `Connect` then derives the token key from the host plus that suffix and loads the saved token through the SDK's own `AuthToken` helper — so two parallel run instances (`--p1`, `--p2`) hold distinct tokens and therefore distinct server identities, which is also what makes the editor's two auto-joining instances (see §6) coexist.

The `DbConnection.Builder` pins [[client/sstdbsdk/DatabaseConnector.cs#OnConnected|OnConnected]], [[client/sstdbsdk/DatabaseConnector.cs#OnConnectError|OnConnectError]], and [[client/sstdbsdk/DatabaseConnector.cs#OnDisconnected|OnDisconnected]]. `OnConnected` stamps `LocalIdentity`, persists the fresh token under the suffixed key, hooks `LocalLobbyPlayer` `OnInsert`/`OnUpdate` to mirror `Username` — the one sanctioned direct table hook outside a binder, kept here because the connector owns identity — and emits [[client/sstdbsdk/DatabaseConnector.cs#Connected|Connected]]. Every consumer wires its callbacks off that signal, but must first guard with `Conn?.IsActive`, because the autoload can finish connecting before Main loads and the signal will already have fired (both [[client/sstdbsdk/TableSubscriber.cs#OnRegistered|TableSubscriber.OnRegistered]] and [[client/sstdbsdk/TableBinderComponent.cs#OnEntityReady|TableBinderComponent.OnEntityReady]] implement the check-then-hook shape for exactly this reason).

Two runtime behaviors complete the picture. First, [[client/sstdbsdk/DatabaseConnector.cs#_Process|_Process]] pumps `Conn?.FrameTick()` every frame inside try/catch: `FrameTick` dispatches every queued table/reducer callback, so one throwing handler must be logged (`PrintErr`, pump kept going) rather than killing network processing for the session. Second, identity comparison goes through [[client/sstdbsdk/DatabaseConnector.cs#IsLocal|IsLocal]] (`LocalIdentity` equality, reached by components via the `GameManager.IsLocal` facade in [[client/Scripts/Game/GameManager.cs#IsLocal|GameManager]]), which is what echo-skip checks (§8) call. On a dropped connection `OnDisconnected` emits [[client/sstdbsdk/DatabaseConnector.cs#Disconnected|Disconnected]] — deliberately *not* on shutdown, guarded by the `_shuttingDown` flag set in [[client/sstdbsdk/DatabaseConnector.cs#_ExitTree|_ExitTree]], which disconnects quietly and clears `Instance`. Off `Disconnected`, `ConnectionLostComponent` shows its reconnect panel; reconnect is `Connect()` again (rebuilding `Conn` with the saved token) plus a return through `main_menu.tscn`, with no auto-rejoin of the world.

Scene-wise the connector's footprint is minimal but load-bearing: [[client/Scenes/main_menu.tscn#TwoD|main_menu.tscn]] carries no subscriber and no binders — its `TwoD`/`ThreeD` buttons (via [[client/Scripts/Game/LobbyGui.cs#TwoDPressed|LobbyGui.TwoDPressed]] / `ThreeDPressed`) only set `GameVisuals.Mode` (see [[client/Scripts/Game/VisualMode.cs#Mode|VisualMode]]) and change scene to `game.tscn`, with `--2D`/`--3D` launch args (parsed once in [[client/Scripts/Game/LaunchArgs.cs#ForcedMode|LaunchArgs]]) pressing the matching button in `_Ready`. All subscription machinery lives in [[client/Scenes/game.tscn#TableSubscriber|game.tscn]], which declares the subscriber node inline.

## 6 Subscriber waves

Subscriptions are grouped into waves, and the wave contents are three static string arrays on [[client/sstdbsdk/TableSubscriber.cs#TableSubscriber|TableSubscriber]] — the single source of truth for "what is subscribed": [[client/sstdbsdk/TableSubscriber.cs#BaseTables|BaseTables]] (`AllTextures`, `AllItems`, `AllEnchantments`, `AllAnimations` — static catalog every screen needs), [[client/sstdbsdk/TableSubscriber.cs#LobbyTables|LobbyTables]] (`LocalLobbyPlayer`, `LocalPlayerProfiles` — profile selection before joining), and [[client/sstdbsdk/TableSubscriber.cs#GameTables|GameTables]] (everything the live world needs: local-player views, nearby/AOI views, the three raw event tables, and the raw persistent tables like `GroundZone` and `ActiveStatusEffect`). The same lists feed [[client/sstdbsdk/TableBinderComponent.cs#TableName|TableBinderComponent]]'s inspector dropdown via [[client/sstdbsdk/TableSubscriber.cs#AllSubscribedTables|AllSubscribedTables]], so a binder can only pick a table some wave actually carries. The wire format is built by [[client/sstdbsdk/TableSubscriber.cs#TableSql|TableSql]]/`TablesSql` as `SELECT * FROM …` through the generated `From` API rather than hand-written SQL, so a server-side rename stays correct when bindings regenerate — at the cost that an unknown name throws `InvalidOperationException` instead of failing silently.

`TableSubscriber` itself is a `Component` node declared inline in [[client/Scenes/game.tscn#TableSubscriber|game.tscn]] (reached by siblings via `GetSibling<TableSubscriber>()`, not via any autoload). Its [[client/sstdbsdk/TableSubscriber.cs#OnRegistered|OnRegistered]] handles both connection orderings — connected already, call [[client/sstdbsdk/TableSubscriber.cs#OnConnected|OnConnected]] directly; otherwise hook `DatabaseConnector.Connected`. `OnConnected` hooks `MapConfig` insert/update to [[client/sstdbsdk/TableSubscriber.cs#OnMapConfigInsert|OnMapConfigInsert]]/`OnMapConfigUpdate` → [[client/sstdbsdk/TableSubscriber.cs#SetLap|SetLap]], which mirrors the world's torus lap vectors into the statics [[client/sstdbsdk/TableSubscriber.cs#LapQ|LapQ]]/[[client/sstdbsdk/TableSubscriber.cs#LapR|LapR]]; those are static (not a `GameManager` facade lookup) because [[client/Scripts/Components/Movement/InterpolationComponent.cs#LapQ|InterpolationComponent]] reads them per entity per frame for torus-aware dead reckoning, and they reset to zero in [[client/sstdbsdk/TableSubscriber.cs#_ExitTree|_ExitTree]] so a fresh subscriber never inherits stale vectors. `OnConnected` then subscribes the base wave (fire-and-forget — no handle is kept, the catalog stays for the session) and calls [[client/sstdbsdk/TableSubscriber.cs#SubscribeLobby|SubscribeLobby]].

The lobby and game waves are handles with applied/error callbacks, and switching between them is the join/leave lifecycle. [[client/sstdbsdk/TableSubscriber.cs#SubscribeLobby|SubscribeLobby]] registers [[client/sstdbsdk/TableSubscriber.cs#OnLobbySubApplied|OnLobbySubApplied]], which raises the [[client/sstdbsdk/TableSubscriber.cs#LobbyApplied|LobbyApplied]] event; the [[client/sstdbsdk/TableSubscriber.cs#LobbySubActive|LobbySubActive]] property reports whether the lobby handle is active. `LobbyComponent`'s `--charN` auto-join (from [[client/Scripts/Game/LaunchArgs.cs#CharIndex|LaunchArgs.CharIndex]]) consumes both in [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnRegistered|LobbyComponent.OnRegistered]]: if `LobbySubActive`, [[client/Scripts/Components/Lobby/LobbyComponent.cs#AutoJoin|AutoJoin]] immediately (the Nth panel by ProfileId, else the last profile); otherwise it waits for `LobbyApplied` first, because counting profiles before the wave applies would join with a partial list. On join success `LobbyComponent` calls [[client/sstdbsdk/TableSubscriber.cs#SubscribeGame|SubscribeGame]] then [[client/sstdbsdk/TableSubscriber.cs#UnsubscribeLobby|UnsubscribeLobby]] (the lobby stays visible until the `JoinWorld` reducer callback succeeds, with a `JoinTimeoutSeconds` 5 s abort); the leave/death path reverses it via [[client/sstdbsdk/TableSubscriber.cs#UnsubscribeGame|UnsubscribeGame]] + `SubscribeLobby`. `EntitySpawnerComponent` mirrors the teardown side in its [[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#_ExitTree|_ExitTree]] — `DespawnAll` (frees tracked puppets, cancels deferred adds) plus back to the lobby wave — so stale entity ids can never wedge a later respawn. `SubscribeGame` additionally registers [[client/sstdbsdk/TableSubscriber.cs#OnGameSubError|OnGameSubError]], which logs subscription failures that would otherwise surface as mysteriously absent rows.

`_ExitTree` unhooks `Connected` and the `MapConfig` row handlers and unsubscribes both wave handles — but only when the connection is still active; on the disconnect path the old hooks die with the old `DbConnection`, so the handles are just dropped (and `LapQ`/`LapR` still reset, since static state must not outlive the scene).

## 7 The binder

The binder is the standard — and nearly only — way components consume rows: one [[client/sstdbsdk/TableBinderComponent.cs#TableBinderComponent|TableBinderComponent]] child per consumed table, placed on the consuming component and wired in the `.tscn`. The node name is `<Table>Binder` (e.g. `NearbyEnemiesBinder`), not the class name; the table it binds is the [[client/sstdbsdk/TableBinderComponent.cs#TableName|TableName]] export, offered as an inspector dropdown sourced from `AllSubscribedTables` via [[client/sstdbsdk/TableBinderComponent.cs#_GetPropertyList|_GetPropertyList]], with [[client/sstdbsdk/TableBinderComponent.cs#_GetConfigurationWarnings|_GetConfigurationWarnings]] warning when it is unset or names a table no wave subscribes (binding still proceeds, with a `PushWarning` in [[client/sstdbsdk/TableBinderComponent.cs#Bind|Bind]] — a misconfigured binder fails as "no rows ever arrive", which is why the warning exists).

Binding happens in `OnEntityReady` (runtime only — the `[Tool]` script skips registration in the editor, where no `IEntity` ancestor exists): bind immediately if the connector is active, else wait for `Connected`, with [[client/sstdbsdk/TableBinderComponent.cs#OnConnected|OnConnected]] guarding via `IsInstanceValid` because the signal can fire after the binder was freed. `Bind` resolves `TableName` against the generated `RemoteTables` fields (a missing field is a hard `PrintErr` — the bindings are stale or the name is wrong) and attaches handlers through [[client/sstdbsdk/TableBinderComponent.cs#Hook|Hook]], which recovers each row type from the event delegate's own signature via reflection. That genericity is also what tolerates event tables: they expose no `OnUpdate`/`OnDelete`, and `Hook` simply skips events that do not exist.

Row events are re-exposed as the editor-wireable signals [[client/sstdbsdk/TableBinderComponent.cs#RowInserted|RowInserted]] / [[client/sstdbsdk/TableBinderComponent.cs#RowUpdated|RowUpdated]] / [[client/sstdbsdk/TableBinderComponent.cs#RowDeleted|RowDeleted]], connected to parent handlers in the scene file (e.g. the `BulletControlEventBinder → OnBulletControlEventRow` connection in `game.tscn`). The signals carry no arguments — rows are plain C# classes and cannot cross the signal boundary — so handlers read [[client/sstdbsdk/TableBinderComponent.cs#LastRow|LastRow]] (inserted row, or the new row on update), [[client/sstdbsdk/TableBinderComponent.cs#LastOldRow|LastOldRow]] (update only), or [[client/sstdbsdk/TableBinderComponent.cs#LastDeletedRow|LastDeletedRow]] and cast to the row type. [[client/sstdbsdk/TableBinderComponent.cs#ReplayExistingRows|ReplayExistingRows]] replays already-cached rows through `RowInserted` at bind time, covering late binds and rows delivered before the parent's signals were wired — and it **must stay off for event tables** (`BulletPatternEvent`, `BulletControlEvent`, `AbilityVisualEvent`): with no last-seen-id tracking, replay would re-fire the table's whole history on every scene entry. Persistent tables (`GroundZone`, catalog, `NearbyEnemies`, …) replay on; event binders omit the flag, which defaults to off — verify by the absence of any `ReplayExistingRows` line on those three binder nodes. Diagnostics are opt-in: the `[Export]` [[client/sstdbsdk/TableBinderComponent.cs#Verbose|Verbose]] flag (off by default) gates the bind confirmation and first-insert prints in `Bind`/`HandleInsert` — enable it on one binder when a table is not delivering. [[client/sstdbsdk/TableBinderComponent.cs#_ExitTree|_ExitTree]] detaches `Connected` and removes every hooked table handler, so freed binders stop receiving rows.

Only infrastructure keeps direct table hooks instead of binders: `TableSubscriber`'s `MapConfig` lap vectors (§6) and the connector's `LocalLobbyPlayer` username mirror (§5).

## 8 View flavors and the event-table pattern

Reducers are transactional and return no data, so subscriptions are the client's only read path — and the client never writes SQL. It subscribes to view accessors by name (the §6 wave lists), and each `views.rs` on the server decides what rows that name yields *for that caller*. There are three view flavors plus the raw-table case, all following the canonical shapes documented in [[server/AGENTS.md|server AGENTS.md]] (Views section).

**Per-caller views** (`ViewContext`) answer "my rows". The shape, e.g. [[server/spacetimedb/src/player/views.rs#local_player_data|local_player_data]]: resolve the caller's `profile_id` imperatively via `ctx.db.logged_in_player().player_id().find(ctx.sender())` — `ctx.sender()` is the authenticated principal, a method call, never a passed-in argument — fall back to the `u64::MAX` sentinel when logged out (which matches nothing, so logged-out callers get an empty view rather than an error), then filter declaratively with `ctx.from.player_data().r#where(move |d| d.profile_id.eq(profile_id)).build()`. Three things to notice, because every per-caller view repeats them: `r#where` (raw identifier — `where` is a Rust keyword), predicates as closures over column accessors (`.eq`, `.ne`, `.or`, `.and` — not plain comparisons), and `move` capture of everything the closure borrows. The family is large: [[server/spacetimedb/src/player/views.rs#local_player|local_player]], [[server/spacetimedb/src/player/views.rs#local_lobby_player|local_lobby_player]], `local_player_profiles`, `local_player_active_profile`, `local_player_stats`, `local_player_stat_allocation`, `local_player_inventory`, [[server/spacetimedb/src/player/views.rs#local_player_position|local_player_position]], and `local_player_knowledge` all share this exact skeleton, differing only in which table they filter and which id they filter by.

**Global views** (`AnonymousViewContext`) answer "everything, for everyone": no `ctx.sender`, no filter. [[server/spacetimedb/src/enemy/views.rs#enemy_templates|enemy_templates]] and [[server/spacetimedb/src/item/views.rs#all_items|all_items]] (plus `all_enchantments`, `all_textures`, `all_animations`) are one-line `ctx.from.<table>().build()` bodies. They are cheap to reason about and expensive to abuse — they belong only to small static datasets (catalogs, templates), which is why they ride the base wave (§6) that every screen holds.

**AOI views** (`ViewContext` + chunk filter) answer "what's near me", and they are where the two load-bearing idioms live. Every AOI view starts from [[server/spacetimedb/src/player/views.rs#nearby_indices|nearby_indices]] (or [[server/spacetimedb/src/player/views.rs#nearby_indices_from_chunk|nearby_indices_from_chunk]] with an explicit radius, e.g. [[server/spacetimedb/src/world/views.rs#nearby_terrain_tiles|nearby_terrain_tiles]] passing [[server/spacetimedb/src/main/global.rs#DEFAULT_TERRAIN_AOI_CHUNK_RADIUS|DEFAULT_TERRAIN_AOI_CHUNK_RADIUS]]), which resolves the caller's profile through `LoggedInPlayer`, reads their `PlayerChunk`, and returns the surrounding chunk-index set. Keying off `PlayerChunk` instead of `PlayerPosition` is deliberate: the chunk row is written only on real chunk crossings, so these views recompute on crossings rather than on every 10 Hz movement report. From there, e.g. [[server/spacetimedb/src/enemy/views.rs#nearby_enemies|nearby_enemies]]: first, the query builder has no `IN`, so the chunk set becomes an **OR-chain** — seed the condition with `indices[0]`, then fold `.or(e.chunk_index.eq(i))` over the rest. Second, a view must always return a query, so the no-chunk case returns a **sentinel query** built up front (`enemy_id.eq(u64::MAX)`, matching nothing) instead of an early empty return. Two refinements appear across the family: [[server/spacetimedb/src/player/views.rs#nearby_remote_players|nearby_remote_players]] excludes the caller's own row (own position streams via `local_player_position`) and left-semijoins `LoggedInPlayer` so logged-out "ghost" position rows never leak to clients; [[server/spacetimedb/src/player/views.rs#nearby_remote_players_profiles|nearby_remote_players_profiles]] needs profiles for exactly that filtered set, but the builder cannot filter the right side of a `left_semijoin` — so it drives from the filtered `player_position` scan and `right_semijoin`s `player_profile` out of it. Rotation rides the same filter over its own table ([[server/spacetimedb/src/player/views.rs#nearby_remote_player_rotations|nearby_remote_player_rotations]]) because facing streams on a faster cadence than movement; loot ([[server/spacetimedb/src/player/views.rs#nearby_loot_drops|nearby_loot_drops]]), chests ([[server/spacetimedb/src/chest/mod.rs#nearby_chests|nearby_chests]] / [[server/spacetimedb/src/chest/mod.rs#nearby_chest_items|nearby_chest_items]] — note `ChestItem` mirrors the parent's `chunk_index` at insert precisely so the view can filter directly, with no two-query fan-out), terrain, decor, and building tiles all repeat the OR-chain + sentinel skeleton.

**The event-table pattern** is the fourth case: no view at all. `BulletPatternEvent`, `BulletControlEvent`, and `AbilityVisualEvent` are `#[table(..., public, event)]` append-only tables (see the `event` flag on e.g. [[server/spacetimedb/src/enemy/instance_tables.rs#bullet_pattern_event|bullet_pattern_event]]), subscribed **raw by table name** in the game wave because every client needs every event — bullets fly across the whole world, and each client resolves proximity locally, so per-caller or AOI filtering would be wrong. The three binders all run with replay off (no `ReplayExistingRows` line on any of them): the single shared `BulletPatternEventBinder` in [[client/Scenes/Components/Bullets/bullet_spawner_component.tscn#BulletPatternEventBinder|bullet_spawner_component.tscn]] feeding [[client/Scripts/Components/Bullets/BulletSpawnerComponent.cs#OnBulletPatternRowInserted|OnBulletPatternRowInserted]] (one binder total, not one per enemy, because event rows carry absolute origins baked server-side — no per-enemy fan-out, no volley lost while a puppet is still in its deferred-spawn window), plus `BulletControlEventBinder` → [[client/Scripts/Components/Bullets/BulletControllerComponent.cs#OnBulletControlEventRow|OnBulletControlEventRow]] and `AbilityVisualEventBinder` → [[client/Scripts/Components/Visual/SpellVisualComponent.cs#OnAbilityVisualEventRow|OnAbilityVisualEventRow]], both wired under `BulletManager`/`SpellVisualComponent` in [[client/Scenes/game.tscn#BulletControlEventBinder|game.tscn]] with `RowInserted` only (event tables have no updates or deletes, which §7's `Hook` already tolerates). Two halves complete the protocol: each handler skips its own echo via `cast_by` + `IsLocal` (the connector's identity check, §5), and the caster applies the same cast optimistically without waiting for the round trip — bullet-control casts through [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#TryActivateAbility|TryActivateAbility]], spell flashes through the shared optimistic render path — so the local player never perceives subscription latency on their own actions.

## 9 Known gaps

- **Unconditional subscription-ready prints.** The opt-in side is done — the binder's bind/first-insert diagnostics are gated behind its `[Export]` `Verbose` flag (off by default; see §7). But [[client/sstdbsdk/TableSubscriber.cs#OnLobbySubApplied|OnLobbySubApplied]] and [[client/sstdbsdk/TableSubscriber.cs#OnGameSubApplied|OnGameSubApplied]] still `GD.Print` unconditionally on every wave application (verified by grep: the only two bare `GD.Print` calls in `client/sstdbsdk/` outside the `Verbose` gates). They should either be removed or folded behind the same kind of opt-in flag; only the error path (`OnGameSubError` → `PrintErr`) earns an unconditional print today.
