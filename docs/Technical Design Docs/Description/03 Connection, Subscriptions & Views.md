# 03 Connection, Subscriptions & Views

## Assumed knowledge

[[01 Roadmap]] (conventions and audience) and [[02 The Component Framework]] (what a component is and how `TableBinderComponent` fits the entity/component model). This doc owns no tables of its own — it explains the machinery every table doc from 04 onward assumes: how the client connects, how rows get from the server to a component, and what a server-side *view* is. [[00 Table Map]] references this doc for the mechanism and references the per-table anchors below.

## The 30-second version

The client is a Godot game; the server is a SpacetimeDB module. The server never pushes data at a specific client — the client **subscribes** to tables and **views**, and SpacetimeDB streams matching rows (plus insert/update/delete events on them) into a client-side cache. Connection is owned by the `DatabaseConnector` autoload ([[client/sstdbsdk/DatabaseConnector.cs]]), subscriptions by the `TableSubscriber` node in `game.tscn` ([[client/sstdbsdk/TableSubscriber.cs]]) as three static wave lists — `BaseTables` (catalog), `LobbyTables` (profile selection), `GameTables` (the live world) — and row delivery to components by `TableBinderComponent` ([[client/sstdbsdk/TableBinderComponent.cs]]), one child node per consumed table with its signals wired in the `.tscn`. On the server, most client-visible data is exposed through **views** (`*/views.rs`) in three flavors: anonymous global, per-caller local, and AOI-filtered — plus a few raw `public` tables and the three append-only `event` tables.

## Main body

### The SpacetimeDB vocabulary (60 seconds)

A **table** is a persisted row set inside the server module; `public` tables are subscribable by clients. A **reducer** is a transactional server function the client calls by name — it mutates tables and returns nothing (clients learn results through the rows). A **view** is a named, server-defined query the client subscribes to *instead of* a raw table: the server evaluates it per caller and streams only matching rows. A **subscription** is the client's standing request "keep these tables/views in my local cache"; the SDK then fires insert/update/delete callbacks as rows change. An **`event` table** is a table flagged append-only-ephemeral — rows broadcast to subscribers but aren't retained state. All the server-side shapes are codified in [[server/AGENTS.md]]; this doc explains how the client side hangs off them.

On the Godot side: a **scene** (`.tscn` file) is a saved node tree — nodes declared in the file rather than built in code. An **autoload** is a scene the engine instantiates once at startup, before the main scene, reachable from anywhere — this project's connection singleton is one.

### Connecting: `DatabaseConnector`

`DatabaseConnector` is declared as an autoload in [[client/project.godot|project.godot]], pointing at [[client/sstdbsdk/DatabaseConnector.tscn|DatabaseConnector.tscn]] — a one-node scene whose only job is attaching [[client/sstdbsdk/DatabaseConnector.cs#_Ready|DatabaseConnector.cs]] to a plain `Node`. Because autoloads outlive every scene, any code in any scene reaches the connection through the static `DatabaseConnector.Instance` — no node-path walks.

Startup is a chain of cause and effect:

1. The engine loads the autoload before the main scene ([[client/Scenes/main_menu.tscn|main_menu.tscn]], per `run/main_scene` in `project.godot`), so `_Ready` runs first thing. It scans the command line for a `--pN` arg via [[client/sstdbsdk/DatabaseConnector.cs#IsPlayerArg|IsPlayerArg]] — the editor runs two game instances (`--p1`/`--p2`) and each needs a distinct saved token or both would share one identity. The match must be exact: a prefix match also caught Godot's own `--path`, which once made every editor instance share the token key `"_path"` (the regression guard comment in `IsPlayerArg`).
2. `_Ready` calls [[client/sstdbsdk/DatabaseConnector.cs#Connect|Connect]], which builds the token storage key from the `Host` export (each host signs its own tokens, so the key embeds the host) plus the `--pN` suffix, loads any saved token through the SpacetimeDB SDK's own `AuthToken` helper (there is no first-party `AuthToken.cs`), and builds the `DbConnection` with `DbConnection.Builder()` — `WithUri(Host)`, `WithDatabaseName(DbName)` (default `"bullethell"`, host default `https://khvgames.com/server`), and the three lifecycle callbacks.
3. On success, [[client/sstdbsdk/DatabaseConnector.cs#OnConnected|OnConnected]] stores the assigned `Identity`, saves the token for next launch, hooks `LocalLobbyPlayer` row events internally (just to mirror `Username` — one of only two internal hook sites outside the binder pattern; see below), and emits the `Connected` signal. Consumers wire their table callbacks off `Connected`, but must first guard with `Conn?.IsActive` *because* the autoload can finish connecting before the scene that consumes it has loaded — [[client/sstdbsdk/TableSubscriber.cs#OnRegistered|TableSubscriber.OnRegistered]] and [[client/sstdbsdk/TableBinderComponent.cs#OnEntityReady|TableBinderComponent.OnEntityReady]] both handle both orders.
4. Every frame, `_Process` pumps [[client/sstdbsdk/DatabaseConnector.cs#_Process|Conn.FrameTick()]] inside a try/catch. `FrameTick` is what dispatches queued row/reducer callbacks onto the main thread, and the catch exists *because* one throwing table handler must not kill the pump — that would silently stop all network processing for the session.

Two identity/disconnect details matter downstream:

- `IsLocal(Identity)` compares against the stored local identity; it's how `EntitySpawnerComponent` skips spawning a remote puppet for yourself and how event-table consumers skip their own echo.
- A dropped connection (anything but deliberate shutdown) emits `Disconnected`. The consumer is `ConnectionLostComponent`, declared inline under the `UI` layer of [[client/Scenes/game.tscn|game.tscn]] (hidden by default): [[client/Scripts/Game/ConnectionLostComponent.cs#OnDisconnected|OnDisconnected]] calls `EntitySpawnerComponent.DespawnAll()` *because* nothing spawned from a dead subscription is trustworthy, then shows the panel. Its Reconnect button ([[client/Scripts/Game/ConnectionLostComponent.cs#OnReconnectPressed|OnReconnectPressed]], wired in `game.tscn`) calls `Connect()` again — the saved token rebuilds the same identity — and returns through `main_menu.tscn`. There is deliberately no auto-rejoin; the fresh `game.tscn` re-runs the whole subscription path off `Connected`.

The server's end of the connection lives in [[server/spacetimedb/src/main/lifecycle.rs|main/lifecycle.rs]]: `client_connected` inserts a `LoggedOutPlayer` row (plus a default "Knight" `PlayerProfile`) for a first-time identity, and `client_disconnected` moves an in-world player back to `LoggedOutPlayer` after purging their statuses/zones. `init` seeds the catalog/world and arms the two always-on schedules. The row-level details belong to [[04 Lobby & Identity Tables]] and [[13 Admin & Debug Tables]]; what matters here is that a *connect* is just a reducer-like hook firing on the server — everything the client then sees arrives through subscriptions.

### Subscribing: `TableSubscriber` and the three waves

The client never writes SQL by hand. `TableSubscriber` — a plain `Node` declared inline in [[client/Scenes/game.tscn|game.tscn]] (its only declaration site; the main menu has none, so nothing streams until you enter the game scene) — owns three static string arrays that are the single source of truth for "what is subscribed":

- `BaseTables` — `AllTextures`, `AllItems`, `AllEnchantments`: the static catalog every screen needs.
- `LobbyTables` — `LocalLobbyPlayer`, `LocalPlayerProfiles`: profile selection.
- `GameTables` — the live world: the `LocalPlayer*` per-caller views, the `Nearby*` AOI views, `EnemyTemplates`, `MapConfig`, the three `event` tables (`BulletPatternEvent`, `BulletControlEvent`, `AbilityVisualEvent`), and four raw `public` tables subscribed without a view (`ActiveStatusEffect`, `ActiveEnemyStatusEffect`, `GroundZone`, `AbilityCharge` — accepted co-op-scale debt, filtered in the consuming component).

Names are the PascalCase `RemoteTables` field names from the generated bindings; [[client/sstdbsdk/TableSubscriber.cs#TableSql|TableSql]] turns each into `SELECT * FROM …` through the generated `From` API *because* the SQL then stays correct across a server-side rename + binding regeneration instead of breaking on a stale string.

The wave lifecycle is driven by scene/gameplay events, not by the connection alone:

1. [[client/sstdbsdk/TableSubscriber.cs#OnConnected|OnConnected]] subscribes `BaseTables` unconditionally and then `LobbyTables` via `SubscribeLobby()` — you always start in the lobby.
2. Joining the world swaps waves: [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnJoinPressed|LobbyComponent.OnJoinPressed]] calls `SubscribeGame()` + `UnsubscribeLobby()` right after firing the `JoinWorld` reducer, *because* the game wave must already be live when the server inserts the `LoggedInPlayer` row — that row's arrival is the join's success signal ([[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerInsert|EntitySpawnerComponent.OnLocalPlayerInsert]] hides the lobby). If the reducer fails or times out, [[client/Scripts/Components/Lobby/LobbyComponent.cs#FailJoin|FailJoin]] rolls the waves back.
3. Leaving the world (death, `leave_world`) deletes the `LocalPlayer` row, and [[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerDelete|EntitySpawnerComponent.OnLocalPlayerDelete]] swaps back: `DespawnAll()`, re-show lobby, `SubscribeLobby()` + `UnsubscribeGame()`.

`TableSubscriber` also keeps the second of the two internal-hook exceptions: it hooks `MapConfig` row events directly ([[client/sstdbsdk/TableSubscriber.cs#OnMapConfigInsert|OnMapConfigInsert]]/[[client/sstdbsdk/TableSubscriber.cs#SetLap|SetLap]]) to maintain the static `LapQ`/`LapR` torus lap vectors, because every `InterpolationComponent` reads them per entity per frame and a static saves a facade lookup per read. Its [[client/sstdbsdk/TableSubscriber.cs#_ExitTree|_ExitTree]] zeroes those statics (a fresh scene must not inherit stale vectors), unhooks `Connected`, and unsubscribes both wave handles — skipping the unhook when the connection is already dead, since those callbacks die with the old `DbConnection` anyway.

### The view layer (server side)

Views are how this module exposes data: the client subscribes to a view *accessor by name* (the PascalCase names in the wave lists are the generated bindings' fields for those accessors), so adding a view — not granting table access — is the exposure mechanism. Every view file follows the 2.x parameterized-view API shown in [[server/AGENTS.md]]; there are three flavors in use.

**Anonymous global views** take an `AnonymousViewContext` and return an unfiltered query — every subscriber gets every row. Used for catalog data identical for all players: `all_textures` ([[server/spacetimedb/src/world/views.rs#all_textures|world/views.rs]]), `all_items` / `all_enchantments` ([[server/spacetimedb/src/item/views.rs#all_items|item/views.rs]]), `enemy_templates` ([[server/spacetimedb/src/enemy/views.rs#enemy_templates|enemy/views.rs]]). All four ride the `BaseTables`/`GameTables` waves into `CatalogComponent`'s caches or direct `Iter()` reads.

**Per-caller local views** take a `ViewContext` (which exposes `ctx.sender()` — the calling identity) and filter to the caller's own rows: `local_player`, `local_lobby_player`, `local_player_profiles`, `local_player_active_profile`, `local_player_data`, `local_player_stats`, `local_player_stat_allocation`, `local_player_inventory`, `local_player_position` — all in [[server/spacetimedb/src/player/views.rs|player/views.rs]]. Most resolve the caller's `profile_id` through their `LoggedInPlayer` row and fall back to `u64::MAX` when there isn't one; that's a sentinel, not an error — a view must always return a query, and `u64::MAX` simply matches nothing. This is how a private table like `LoggedOutPlayer` (not `public`) still reaches its owner: through `local_lobby_player` and nothing else.

**AOI-filtered views** stream only what is near the caller. The shared helper is [[server/spacetimedb/src/player/views.rs#nearby_indices_from_chunk|nearby_indices_from_chunk]]: it reads the caller's chunk from `PlayerChunk` — deliberately not `PlayerPosition`, because `PlayerChunk` is written only on real chunk crossings, so these views recompute on crossings rather than on every 10 Hz movement report (the rationale on ^table-player-chunk in [[00 Table Map]]) — wraps the chunk coords through `MapConfig` (read directly here because a `ViewContext` can't call the `MapConfig::load` helper), and expands them to a ring of chunk indices via [[server/spacetimedb/src/world/aoi.rs#surrounding_chunk_indices|surrounding_chunk_indices]] (`DEFAULT_AOI_CHUNK_RADIUS` = 2 rings; terrain uses `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS`, also 2). Every AOI view then builds the same two idioms, because the query builder has no `IN` and views can't early-return nothing:

- **`IN` is an OR-chain** over `chunk_index` — seed with the first index, fold the rest with `.or(...)`.
- **Empty needs a sentinel query** — a pre-built deliberately-unmatchable query (`profile_id.eq(u64::MAX)` and friends), returned when the caller has no chunk row yet.

The AOI views: `nearby_remote_players` (excludes the caller's own row and left-semijoins `LoggedInPlayer` so logged-out ghost position rows never stream), `nearby_remote_player_rotations` (same filter over the faster-cadence rotation table), `nearby_remote_players_profiles` (a right semijoin — the builder can't filter the right side of a left semijoin, so the chunk-filtered position scan drives and `PlayerProfile` rows come out), `nearby_loot_drops` (all in [[server/spacetimedb/src/player/views.rs|player/views.rs]]), `nearby_enemies` ([[server/spacetimedb/src/enemy/views.rs#nearby_enemies|enemy/views.rs]]), `nearby_terrain_tiles` / `nearby_hex_decor` ([[server/spacetimedb/src/world/views.rs#nearby_terrain_tiles|world/views.rs]]), and `nearby_chests` / `nearby_chest_items` in [[server/spacetimedb/src/chest/mod.rs#nearby_chests|chest/mod.rs]] — the latter an OR-chain over nearby chest ids computed imperatively, because `ChestItem` has no `chunk_index` of its own.

Two exposure paths bypass views entirely:

- **Raw `public` tables**: `MapConfig` (the world singleton — every consumer wants the one row) and the four status/zone/charge tables listed in `GameTables`, whose consumers filter in code.
- **`event` tables**: `BulletPatternEvent`, `BulletControlEvent`, `AbilityVisualEvent` ([[server/spacetimedb/src/enemy/instance_tables.rs#BulletPatternEvent|enemy/instance_tables.rs]]) carry the `event` flag, making them append-only ephemeral broadcasts — inserts stream to subscribers; rows are never updated, and there is no explicit delete site. This is a protocol, not state: the server stamps everything the client needs onto the row at insert time (absolute origin, resolved damage) precisely *because* clients can't join an event row back to anything. `BulletControlEvent` and `AbilityVisualEvent` add `cast_by` so the casting client — which already applied the effect optimistically — can skip its own echo. The full field encodings are documented in [[server/spacetimedb/src/enemy/AGENTS.md|enemy/AGENTS.md]] and on the tables themselves.

### Consuming rows: `TableBinderComponent`

The rule (from [[client/AGENTS.md]]): **no direct `conn.Db.*.OnInsert/OnUpdate/OnDelete` hooks outside `sstdbsdk/`** — the only two exceptions are the `TableSubscriber`/`DatabaseConnector` internal hooks above. Everything else consumes rows through a `TableBinderComponent` child node, one per table, named `<Table>Binder`, with its signals wired in the `.tscn`. The binder exists *because* Godot signals are the editor's wiring mechanism but row types aren't Variant-compatible — the binder bridges the SDK's typed C# events to editor-wireable, argument-free Godot signals.

The mechanics, in [[client/sstdbsdk/TableBinderComponent.cs|TableBinderComponent.cs]]:

1. `TableName` is a dropdown populated from `TableSubscriber.AllSubscribedTables` (via `_GetPropertyList`), and `_GetConfigurationWarnings` flags a name that isn't in any wave — a binder bound to an unsubscribed table compiles fine but never fires, so the warning is the only feedback.
2. [[client/sstdbsdk/TableBinderComponent.cs#OnEntityReady|OnEntityReady]] binds immediately if the connection is already active, else waits for `Connected` (the `OnConnected` handler guards `IsInstanceValid` *because* the signal can still fire after a deferred free). [[client/sstdbsdk/TableBinderComponent.cs#Bind|Bind]] reflects the named field out of the generated `RemoteTables` and hooks its events.
3. [[client/sstdbsdk/TableBinderComponent.cs#Hook|Hook]] closes the generic `HandleInsert`/`HandleUpdate`/`HandleDelete` over the row type recovered from each event's own delegate signature — so one binder class serves every table without codegen. Event tables expose no `OnUpdate`/`OnDelete`, and `Hook` silently skips missing events, which is exactly right for them.
4. Handlers stash the row on `LastRow` / `LastOldRow` / `LastDeletedRow` and emit `RowInserted` / `RowUpdated` / `RowDeleted` with no arguments — handlers read and cast `LastRow` (rows can't cross the signal boundary as arguments).
5. `ReplayExistingRows` re-fires `RowInserted` once per already-cached row (via `Iter()`) right after binding. It stays **on** for persistent tables so late joiners and late-spawned puppets see existing rows, and **off** on the `event` tables — there is no last-seen-id tracking, so replay would re-fire the table's entire history (every bullet pattern and cast ever appended) each time the scene is entered.

Live wiring (cite these scenes, not the standalone component scenes — seven of those are unreferenced duplicates; see [[02 The Component Framework]]'s Known gaps): [[client/Scenes/game.tscn|game.tscn]] declares the `TableSubscriber` node and the scene-level binders — CatalogComponent's `AllTextures`/`AllItems`/`AllEnchantments` binders, EntitySpawnerComponent's five spawn binders (`LocalPlayer`, `NearbyRemotePlayers`, `NearbyEnemies`, `NearbyLootDrops`, `NearbyChests` — all replay on), TerrainComponent's three, HexGridOverlayComponent's `MapConfigBinder`, ZoneRendererComponent's `GroundZoneBinder` (replay **on** — persistent table, so late joiners see live zones; the opposite of the event-table rule), SpellVisualComponent's `AbilityVisualEventBinder` and BulletControllerComponent's `BulletControlEventBinder` (both replay **off** — event tables) — each with its `[connection]` lines at the bottom of the file. The one shared `BulletPatternEventBinder` lives in [[client/Scenes/Components/Bullets/bullet_spawner_component.tscn|bullet_spawner_component.tscn]] — one binder suffices because event rows are self-contained, so there is no per-enemy binder fan-out and no volley is lost during a puppet's deferred-spawn window. [[client/Scenes/local_player.tscn|local_player.tscn]] wires the local player's per-caller binders (`LocalPlayerPosition`, `LocalPlayerData`, `LocalPlayerStats`, `LocalPlayerStatAllocation`, `LocalPlayerInventory`, `LocalPlayerActiveProfile`, `AbilityCharge`, `ActiveStatusEffect` — replay on) plus CombatComponent's `NearbyEnemiesBinder` with only `RowDeleted` wired and replay off (aim-lock invalidation only). [[client/Scenes/default_enemy.tscn|default_enemy.tscn]] wires each enemy puppet's own `NearbyEnemiesBinder` (replay on, so late-spawned puppets still initialize) and `ActiveEnemyStatusEffectBinder`; [[client/Scenes/non_local_player.tscn|non_local_player.tscn]] wires two `RowUpdated`-only binders (replay off) feeding `InterpolationComponent`.

Callers that can't reach these components through their own entity registry (spawned entities, UI) go through the static facade on [[client/Scripts/Game/GameManager.cs|GameManager]] — `Conn`, `IsLocal`, `LapQ`/`LapR`, catalog and spawner lookups — which delegates to the autoload and the registered scene-level components.

### One end-to-end read path, assembled

An enemy shot ties every piece together: [[server/spacetimedb/src/enemy/reducers.rs#tick_enemy_behavior|tick_enemy_behavior]] appends a `BulletPatternEvent` row with the origin and damage baked in; the row matches the `GameTables` subscription every client holds; `FrameTick` dispatches the insert; the shared `BulletPatternEventBinder` in `bullet_spawner_component.tscn` (replay off, because it's an event table) stashes it on `LastRow` and emits `RowInserted`; and the handler wired in that `.tscn` renders the pattern verbatim. The same shape — *table or view row → subscription wave → binder → `.tscn`-wired handler* — is the read path every table doc from here on references as, e.g., "read via the `nearby_enemies` view in the game wave".
