# 02 The Component Framework

How client entities are built (the `IComponent`/`Component` bases and the `IEntity`/`EntityRegistry` side, plus their `_Ready` ordering contract) and how the server mirrors that shape (one table per concern, scaffolded and torn down as a unit by the profile/enemy archetype helpers).

## 1 Assumed knowledge

- [[docs/Technical Design Docs/Description/00 Table Map.md|00 Table Map]] — the per-table spine; this doc links into its `^table-*` anchors wherever a row is named.
- [[docs/Technical Design Docs/Description/01 Roadmap.md|01 Roadmap]] — reading order, link conventions, what stays out.
- Maintainer refs (jump-off points, not authority): [[AGENTS.md|root AGENTS.md]], [[client/AGENTS.md|client AGENTS.md]], [[server/AGENTS.md|server AGENTS.md]]. Naming convention (node name = class name = file name, `<Table>Binder` child names) lives in [[client/AGENTS.md|client AGENTS.md]] and is not restated here.

A few stack terms, used everywhere below. In Godot the game is a tree of *nodes*; a *scene* (`.tscn` file) is a saved subtree you instance into the running tree. In C# every script derives from one native node type (`Node`, `Node2D`, `Area2D`, …) and single inheritance means a script gets exactly one native base. In SpacetimeDB the server holds *tables* (rows) and *reducers* (the only writers — transactional functions that return no data, so clients learn everything through table subscriptions, never from call results).

## 2 The 30-second version

The client has no plain data objects for gameplay state: every gameplay entity is a scene root implementing `IEntity`, and every behavior on it is a child component deriving from one of six `*Component` bases — one base per native root type, because C# single inheritance forbids a single shared base. Components register with their entity on `_Ready`, talk to siblings only after a deferred ready pass, and mirror server rows through `SetFromServer(...)` while reporting intent back through reducers; the server alone computes damage and stats. The server mirrors this shape as one table per concern (`PlayerData`, `PlayerPosition`, `PlayerInventorySlot`, `Enemy`, …) joined by `profile_id`/`enemy_id` as the entity id, and whole entities are scaffolded and destroyed as a unit: `try_scaffold_profile`/`teardown_profile` for players, `spawn_enemy_archetype`/`despawn_enemy_archetype` for enemies. How rows travel over the wire (connector, subscription waves, binders, views) is [[docs/Technical Design Docs/Description/03 Connection, Subscriptions & Views.md|03]]'s story; this doc is the shape on each end.

## 5 Component base classes — one per native root type

The whole component contract in [[client/Scripts/Components/IComponent.cs|IComponent.cs]] is a single member: an `Entity` back-reference to the owning [[client/Scripts/Entities/IEntity.cs|IEntity]], null before `_Ready` registration and null again after `_ExitTree`. Everything else lives in the six bases, and there are six of them for exactly one reason: C# has single inheritance, so a component whose scene root is an `Area2D` cannot also derive from a `Node`-based `Component`. The codebase follows the comedot rule that a component's root is the closest matching builtin type, hence one base per root: [[client/Scripts/Components/Component.cs|Component]] (`Node`), [[client/Scripts/Components/AreaComponent.cs|AreaComponent]] (`Area2D` — hitboxes/hurtboxes such as [[client/Scripts/Components/Combat/HitZone.cs|HitZone]] and the victim hurtbox), [[client/Scripts/Components/Node2DComponent.cs|Node2DComponent]] (`Node2D`), [[client/Scripts/Components/Node3DComponent.cs|Node3DComponent]] (`Node3D` — used by the components inside `world_3d.tscn`, which register with the `GameManager` entity through the SubViewport ancestor walk), [[client/Scripts/Components/ControlComponent.cs|ControlComponent]] (`Control` UI), and [[client/Scripts/Components/VisualComponent.cs|VisualComponent]] (`AnimatedSprite2D` entity sprites). All six run identical registration logic; because they cannot share a base class, that logic lives in the static [[client/Scripts/Components/ComponentRegistration.cs|ComponentRegistration]] helper they all call: [[client/Scripts/Components/ComponentRegistration.cs#Register|Register]] walks ancestors for the nearest `IEntity` and registers there — logging a `PushError` and returning null (leaving the component inert) when there is no entity ancestor — while [[client/Scripts/Components/ComponentRegistration.cs#ValidateRequired|ValidateRequired]] logs one `PushWarning` per missing required sibling.

Two small pieces complete the client contract. [[client/Scripts/Components/NodeExtensions.cs#GetAncestor|GetAncestor]] walks `GetParent()` for the first ancestor of type `T`, which works across instanced sub-scene boundaries where `Node.Owner` does not — so a node inside an instanced child scene can still find a node from the parent scene. And each base exposes the same three override points plus sibling access: [[client/Scripts/Components/Component.cs#OnRegistered|OnRegistered]] (grab child nodes, wire local state — runs immediately after registration), [[client/Scripts/Components/Component.cs#OnEntityReady|OnEntityReady]] (talk to siblings — runs deferred, see [§7](#7-lifecycle-and-registration-ordering)), `GetRequiredComponents()` (declare sibling dependencies for the warning check), and `GetSibling<T>()` (entity-registry lookup shorthand). Real overrides show the intended split: [[client/Scripts/Components/Data/LocalPlayerDataComponent.cs#GetRequiredComponents|LocalPlayerDataComponent]] declares `HealthComponent` + `StatsComponent` as required and only touches them in `OnEntityReady` (shared-Stat wiring), while the bullet controller declares its spawner dependency and resolves it in [[client/Scripts/Components/Bullets/BulletControllerComponent.cs#OnEntityReady|OnEntityReady]] — never in `OnRegistered`, when the sibling may not exist yet.

The subscription layer's binder is itself a component, which is why it composes with this lifecycle instead of fighting it: `TableBinderComponent` derives from `Component`, binds its table in `OnEntityReady` (so the parent's signal connections, authored in the `.tscn`, already exist), skips registration under the editor hint (its `[Tool]` attribute runs `_Ready` in the editor, where no entity ancestor exists), and unhooks its table events plus the connector signal in `_ExitTree`. Its [[client/sstdbsdk/TableBinderComponent.cs#Verbose|Verbose]] export is opt-in diagnostics only — bind confirmation and first-insert prints, off by default, for debugging why a table is not delivering rows — and its [[client/sstdbsdk/TableBinderComponent.cs#ReplayExistingRows|ReplayExistingRows]] replay rule (on for persistent tables, off for append-only event tables) is [[docs/Technical Design Docs/Description/03 Connection, Subscriptions & Views.md|03]]'s story.

## 6 The entity side — `IEntity` and `EntityRegistry`

[[client/Scripts/Entities/IEntity.cs|IEntity]] declares `RegisterComponent` / `UnregisterComponent` / `GetComponent(Type)`, plus a default-implemented generic `GetComponent<T>()` that filters the untyped lookup. Roots come in two kinds because of the same single-inheritance constraint: roots needing a native base (`LocalPlayer`/`Enemy` are `CharacterBody2D`, `GameManager` is `Node2D` — see [[client/Scripts/Game/GameManager.cs#GetComponent|GameManager]] keeping its own `EntityRegistry` field) implement `IEntity` directly, while roots that can live on a plain `Node` derive from the [[client/Scripts/Entities/Entity.cs|Entity]] convenience class, which just forwards to its private registry. The storage behind both is [[client/Scripts/Entities/EntityRegistry.cs|EntityRegistry]]: a flat list whose [[client/Scripts/Entities/EntityRegistry.cs#Get|Get]] returns the *first* component the requested type `IsInstanceOfType` — so subclass queries work, but lookups are order-dependent when two components share a base — memoized per query type in a cache cleared on every register/unregister, keeping repeated lookups (e.g. the `GameManager` facade's `Get<T>()`) cheap with identical semantics.

## 7 Lifecycle and registration ordering

Registration order is the load-bearing contract of the whole framework, because Godot fires `_Ready` per node as it enters the tree and sibling order is not something a component may assume. Each base therefore splits startup in two. In `_Ready` the component registers with its entity, runs `OnRegistered()` for self-only setup (a concrete case: `LocalPlayerDataComponent._Ready` calls `base._Ready()` then resolves its three child binder nodes with `GetNode`), and — only if registration found an entity — defers the second pass with `CallDeferred`. That deferred `AfterSiblingsReady` pass runs on idle time after every sibling has finished its own `_Ready`, and it does two things in order: validate `GetRequiredComponents()` (warnings, e.g. `DamageReceivingComponent` requiring its `FactionComponent`), then run `OnEntityReady()` where sibling access via `GetSibling<T>()` is finally safe. Teardown mirrors it: `_ExitTree` unregisters the component and nulls `Entity`, so dynamically spawned components such as `HitZone`s never leak stale entries in the registry. Enforcement is deliberately soft — a missing sibling is a warning and a missing entity ancestor is an error with an inert component, never a crash — because scenes are authored in the editor and miswiring should surface in the console, not take down the run.

The live wiring sites are inline in the composition-root scenes (never standalone component scenes): `game.tscn` holds the `GameManager` entity with its scene-level components (`EntitySpawnerComponent` with its `LocalPlayer`/`NearbyRemotePlayers`/`NearbyEnemies`/`NearbyLootDrops`/`NearbyChests` binders, the catalog binders, the terrain and zone components, and the `BulletControlEventBinder`/`AbilityVisualEventBinder` under `BulletManager`/`SpellVisualComponent`); `local_player.tscn` holds the `LocalPlayer` entity with its `PositionSyncComponent`/`LocalPlayerDataComponent`/`LocalPlayerInventoryComponent`/`LocalPlayerProfileComponent` components and their `LocalPlayerPositionBinder`-style children (row signals wired to `OnPositionRowInserted`-style handlers); `default_enemy.tscn` holds the `Enemy` entity whose `NearbyEnemiesBinder` feeds [[client/Scripts/Players/Enemies/Enemy.cs#OnEnemyRowInserted|OnEnemyRowInserted]] / `OnEnemyRowUpdated`; `non_local_player.tscn` holds the remote-player puppet with its position + rotation binders; and `world_3d.tscn` holds the 3D components registering up through the viewport to the same `GameManager` entity.

## 8 The server-side mirror — one table per concern plus archetype helpers

SpacetimeDB-side, a reducer is the only thing that may write rows, and reducers return no data — so the client never asks "what changed", it subscribes to tables and mirrors whatever arrives. The module therefore shapes each logical entity as one table per concern, with `profile_id` (players) or `enemy_id`/`behavior_id` (enemies) acting as the entity id joining the rows — the server half of the component split. A player is `PlayerData` (level/xp/hp plus resolved `defense`/`base_speed`) + `PlayerStats` (the six resolved allocatable stats) + `PlayerStatAllocation` (the allocation input) + `PlayerPosition` + `PlayerRotation` + `PlayerChunk` + one `PlayerInventorySlot` row per slot + knowledge/survival/validation rows (full per-table detail in ^table-player-data and its neighbors in [[docs/Technical Design Docs/Description/00 Table Map.md|00 Table Map]]). Each maps onto one client concern: `LocalPlayerDataComponent` feeds data/stat/allocation rows into the sibling `HealthComponent`/`StatsComponent` mirrors through [[client/Scripts/Components/Combat/HealthComponent.cs#SetFromServer|SetFromServer]]-style setters, and `PositionSyncComponent` owns the position/rotation rows. Components are mirrors only — `HealthComponent` documents that it has no damage/heal methods because damage is computed by the server and new values arrive via `SetFromServer`; the client reports intent (hit claims, movement reports) through reducers and reads back the authoritative result.

Whole player entities are built and destroyed by the archetype helpers in `player/methods.rs`, so no reducer hand-assembles the row set. [[server/spacetimedb/src/player/methods.rs#try_scaffold_profile|try_scaffold_profile]] idempotently scaffolds every per-profile row — data, the full 0–37 slot set (starter `Bow`/`Hat`/`Helmet`/`Bread`/`Bag` plus the `Skull`/`Tome of Mending` ability spans), allocation (maxed for the auto-created `Knight`, zero otherwise), stats via `recompute_stats`, survival, knowledge, and a spawn reset to the world origin with its chunk recomputed — and its call site is [[server/spacetimedb/src/player/reducers.rs#join_world|join_world]], which first moves the identity row from `LoggedOutPlayer` to `LoggedInPlayer` and then scaffolds. [[server/spacetimedb/src/player/methods.rs#teardown_profile|teardown_profile]] is the single shared cleanup list (data, stats, allocation, all slots, position, rotation, chunk, movement state, displacement allowance, hit rate, move strikes, knowledge, survival, channeled actions, consumable effects, plus the status/zone purges); it deliberately leaves identity rows to its callers — [[server/spacetimedb/src/player/methods.rs#kill_player|kill_player]] (the combat death path) tears down and moves the player back to `LoggedOutPlayer`, while [[server/spacetimedb/src/player/reducers.rs#delete_profile|delete_profile]] tears down and deletes the `PlayerProfile` itself. (`leave_world`/disconnect purge only statuses/zones and keep position rows — the "ghosts" the AOI views semijoin out — which belongs to the player module doc, not this one.)

Enemies follow the same archetype shape with one structural difference: the `Enemy` row stays flat (template link, behavior link, x/y, angle+scalar movement, hp/phase/stagger/chunk) while the behavior tree fans out into `EnemyBehavior` → `EnemyPhase` → `EnemyAttack` → `EnemySequenceStep` → `RepeatStepInstance` rows, with per-enemy `RepeatStepInstance` copies of the shared `RepeatStepDef` so each enemy's `repeat_count` advances independently. [[server/spacetimedb/src/enemy/methods.rs#spawn_enemy_archetype|spawn_enemy_archetype]] builds the tree via [[server/spacetimedb/src/enemy/methods.rs#build_enemy_behavior|build_enemy_behavior]] and inserts the flat row; [[server/spacetimedb/src/enemy/methods.rs#despawn_enemy_archetype|despawn_enemy_archetype]] deletes the row together with its whole tree via [[server/spacetimedb/src/enemy/methods.rs#delete_enemy_behavior|delete_enemy_behavior]], so no orphan component rows outlive the entity. The three call directions are admin authoring (`spawn_enemy`/`despawn_enemy`), the biome spawner tick, and combat kills with XP credit — see ^table-enemy. The client puppet mirrors the flat row through its `default_enemy.tscn` binder (`OnEnemyRowInserted`/`OnEnemyRowUpdated` into `HealthComponent`, the stagger bar, and interpolation targets) while bullet patterns bypass the puppet entirely through the single shared event-table binder — the full read paths live in [[docs/Technical Design Docs/Description/00 Table Map.md|00 Table Map]] and the wire in [[docs/Technical Design Docs/Description/03 Connection, Subscriptions & Views.md|03]].
