# 02 The Component Framework

## Assumed knowledge

## The 30-second version

This system owns **no tables** — it is the machinery every other doc assumes. The client is built as **entities** (scene roots implementing `IEntity`) whose children are **components** (one behavior each, deriving from a `*Component` base); on `_Ready` each component registers itself with the nearest entity ancestor, so any component can reach its siblings through the entity's registry instead of node paths. Components consume server state through `TableBinderComponent` children — one per table — that re-expose SpacetimeDB row events as editor-wireable Godot signals. The server mirrors the same model relationally: **one table per concern** is a component, and ids like `profile_id`/`enemy_id` are the entity id joining one logical entity's rows across tables; the archetype helpers (`try_scaffold_profile`/`teardown_profile`, `spawn_enemy_archetype`/`despawn_enemy_archetype`) insert and delete those row bundles atomically, the way instancing or freeing a scene creates and destroys its component children together.

## Main body

### Godot in five sentences

A Godot game is a tree of **nodes**; a **scene** is a saved subtree, stored in a text **`.tscn` file** (node declarations, exported property values, and signal **connections**), that can be instanced inside other scenes. When a node enters the tree the engine calls its `_Ready()` (children before parents, siblings in tree order), and when it leaves, `_ExitTree()`. An **autoload** is a scene the engine keeps loaded above every scene change — here, the `DatabaseConnector` connection singleton. **Signals** are Godot's typed events, wired either in code or as `[connection]` lines in the `.tscn`. This project declares nodes in `.tscn` files rather than building them in code wherever feasible, so the scene files are the authoritative wiring diagram.

### Entities and components

The client is fully compositional, modeled on the **Comedot** component framework (see [[client/AGENTS.md]]). An **entity** is a scene root — `LocalPlayer`, `Enemy`, `RemotePlayer`, `Drop`, `Chest`, `TileComponent`, `BulletManager`, `GameManager` — and a **component** is a child node that provides exactly one piece of behavior for it: `HealthComponent` mirrors hp, `InterpolationComponent` lerps toward server positions, and so on. The naming convention makes the tree self-describing: a component's **node name = class name = file name** (the `HealthComponent` node in a `.tscn` is an instance of `HealthComponent.cs`), with three deliberate exceptions — pure data nodes with zero behavior (a `CollisionShape2D` inside an Area component), `TableBinderComponent` children (named `<Table>Binder`, e.g. `NearbyEnemiesBinder`), and code-instantiated scenes whose count is data-driven (`HitZone`s, server-row entities, terrain pool leaves).

The contract between the two sides is deliberately tiny. [[client/Scripts/Components/IComponent.cs|IComponent]] has one member — an `Entity` back-reference to the owning `IEntity`, null before `_Ready` and null again after `_ExitTree` — and [[client/Scripts/Entities/IEntity.cs|IEntity]] has three: `RegisterComponent`/`UnregisterComponent`/`GetComponent(Type)`, plus a default-implemented generic [[client/Scripts/Entities/IEntity.cs#GetComponent#2|GetComponent&lt;T&gt;()]]. Everything else is convention and shared base-class behavior.

### Why six component base classes

C# has single inheritance, and a component's scene root must be the closest matching Godot builtin — a hurtbox *is* an `Area2D`, a UI piece *is* a `Control` — so the shared lifecycle can't live on one common node base. Instead there is one abstract base per native root type, each duplicating the same dozen lines: [[client/Scripts/Components/Component.cs|Component]] (`Node`), [[client/Scripts/Components/AreaComponent.cs|AreaComponent]] (`Area2D` — hitboxes/hurtboxes like `DamageReceivingComponent` and `HitZone`), [[client/Scripts/Components/Node2DComponent.cs|Node2DComponent]], [[client/Scripts/Components/Node3DComponent.cs|Node3DComponent]] (the `world_3d.tscn` components, which register with the `GameManager` entity through the SubViewport ancestor walk), [[client/Scripts/Components/ControlComponent.cs|ControlComponent]] (UI), and [[client/Scripts/Components/VisualComponent.cs|VisualComponent]] (`AnimatedSprite2D` — `RemoteVisualComponent`). The behavior the six share lives in two static helpers on [[client/Scripts/Components/ComponentRegistration.cs|ComponentRegistration]].

The lifecycle, beat by beat, using [[client/Scripts/Components/Component.cs#_Ready|Component._Ready]]:

1. `ComponentRegistration.Register(this, this)` walks the `GetParent()` chain and registers the component with the **nearest `IEntity` ancestor** — this is why components can sit at any depth under their entity root. No entity ancestor means a `PushError` and an inert component (its `Entity` stays null and every later step bails).
2. `OnRegistered()` runs immediately — the override point for setup that only needs the entity reference, like `SlotComponent` neutering its icon's `mouse_filter`.
3. `CallDeferred(nameof(AfterSiblingsReady))` postpones the rest by one frame, *because* Godot readies siblings in tree order: at a component's own `_Ready`, the siblings below it haven't registered yet, so any cross-sibling lookup now could miss. The deferred `AfterSiblingsReady` first runs `ComponentRegistration.ValidateRequired` — a `PushWarning` per type returned by the component's `GetRequiredComponents()` that the registry lacks (`LocalPlayerDataComponent` requires `HealthComponent` + `StatsComponent`; `BulletControllerComponent` requires `BulletSpawnerComponent`) — then runs `OnEntityReady()`, the override point for setup that touches siblings, like `BulletControllerComponent` caching its spawner via `GetSibling<BulletSpawnerComponent>()`.

[[client/Scripts/Components/Component.cs#_ExitTree|Component._ExitTree]] unregisters the component and nulls the back-reference, *because* components are also spawned dynamically at runtime — `CombatComponent` instantiates a fresh `HitZone` per attack ([[client/Scripts/Components/Weapon/CombatComponent.cs#HitZoneScene|HitZoneScene]]) — and a freed node left in the registry would be a dangling reference handed out by every later `GetComponent` call. Sibling access inside a component is always `GetSibling<T>()` (defined on each base), which forwards to `Entity.GetComponent<T>()` — never `GetNode` paths, which would hardcode tree layout.

### The entity side: IEntity, EntityRegistry, Entity

Entity roots need native base classes of their own — `LocalPlayer` and `Enemy` are `CharacterBody2D`, most others are `Node2D` — so they **implement `IEntity` directly** and forward the three methods to a private [[client/Scripts/Entities/EntityRegistry.cs|EntityRegistry]] field (the same single-inheritance workaround as the component bases, one level up). `EntityRegistry` itself is a flat `List<IComponent>` whose `Get(Type)` returns the first component the requested type `IsInstanceOfType` — subclass-friendly *because* a query for a base type matches its derivatives, and order-dependent when two components share a base. Results are memoized per query type in a cache cleared on every Register/Unregister, so repeated lookups (the `GameManager` facade makes several per call) stay O(1) with identical semantics. [[client/Scripts/Entities/Entity.cs|Entity]] is a convenience base for roots that could derive from plain `Node`; today no root does — every entity needs a native base, so `Entity` exists for future plain-`Node` roots only.

Two ancestor walks coexist and shouldn't be confused: `ComponentRegistration.Register` walks for the nearest `IEntity` (interface — any node type), while [[client/Scripts/Components/NodeExtensions.cs#GetAncestor|NodeExtensions.GetAncestor&lt;T&gt;()]] walks for a concrete node type and is what **plain scripts** (not components — `InventoryPanel`, `StatsSidebar`, `ItemSidebar`) use to reach their `LocalPlayer`, and what entity roots use to reach the `GameManager` above them ([[client/Scripts/Players/Enemies/Enemy.cs|Enemy.cs]] grabs `GetAncestor<GameManager>()?.GetComponent<World3DComponent>()`). Unlike `Node.Owner`, it works across instanced sub-scene boundaries — inside `local_player.tscn` as instanced by `game.tscn`.

### GameManager: the scene-level entity and its static facade

[[client/Scripts/Game/GameManager.cs|GameManager]] (`Node2D, IEntity`) is the root of [[client/Scenes/game.tscn|game.tscn]] (node named `game`) and the entity the **scene-level** components register with: `TableSubscriber`, `CatalogComponent`, `EntitySpawnerComponent`, `LobbyComponent`, and the camera/overlay/zone/spell components. (`BulletManager` is its own `IEntity` — its `BulletSpawnerComponent`/`BulletControllerComponent` children register with it, not with `GameManager`.) It holds no game logic; it exists *because* a spawned entity's components can only see their own entity's registry — an `Enemy` puppet's components cannot `GetSibling` their way to the item catalog, and a node-path walk from a spawned scene into `game.tscn` would be brittle. So `GameManager` exposes a **static facade** (`instance` captured in `_Ready`, guarded by `IsInstanceValid`) that delegates to its registered components and to the autoload: `Conn`/`Username`/`IsLocal` → `DatabaseConnector`, `LapQ`/`LapR` → the `TableSubscriber` statics, `GetItem`/`GetEnchantment(s)`/`GetResPath`/`CatalogVersion`/`CatalogChanged` → `CatalogComponent`, `GetEnemy`/`EnemyCount` → `EntitySpawnerComponent`, `SpellVisuals` → `SpellVisualComponent`. Anything without a facade property is reached through `GameManager`'s instance `GetComponent<T>()`.

### TableBinderComponent: how components eat table rows

One rule covers the whole client: **components never hook `conn.Db.*.OnInsert` directly**; they place a [[client/sstdbsdk/TableBinderComponent.cs|TableBinderComponent]] child per consumed table and wire its signals in the `.tscn`. (SpacetimeDB primer: the server module exposes **tables** whose rows replicate to subscribed clients; the C# SDK mirrors them into a local cache and fires per-table insert/update/delete callbacks. The full connection/subscription story is [[03 Connection, Subscriptions & Views]].) The binder is itself a `Component`, so it registers with the same entity as its parent and starts work in `OnEntityReady` — deferred, *because* binding before siblings are ready would fire replay rows at half-initialized handlers.

The mechanics, all in `TableBinderComponent.cs`:

- `TableName` is picked from an inspector dropdown built in [[client/sstdbsdk/TableBinderComponent.cs#_GetPropertyList|_GetPropertyList]] from `TableSubscriber.AllSubscribedTables`; the class is `[Tool]` solely so that dropdown works in the editor, and [[client/sstdbsdk/TableBinderComponent.cs#_Ready|its _Ready]] skips entity registration under `Engine.IsEditorHint()` *because* the entity scripts aren't tool-enabled, so no `IEntity` ancestor exists at edit time. A binder whose table isn't in any subscription wave gets an editor configuration warning and a runtime `PushWarning` — it will never receive rows.
- [[client/sstdbsdk/TableBinderComponent.cs#Bind|Bind]] resolves the table **by reflection** — `typeof(RemoteTables).GetField(TableName)` against the generated bindings — then `Hook`s `OnInsert`/`OnUpdate`/`OnDelete`, closing the generic `HandleInsert/Update/Delete<TRow>` over the row type recovered from each event's own delegate signature. `Hook` silently skips events that don't exist, *because* append-only **event tables** (`BulletPatternEvent` and friends) have no `OnUpdate`/`OnDelete` to hook.
- The re-exposed Godot signals `RowInserted`/`RowUpdated`/`RowDeleted` **carry no arguments** — row objects are plain C# classes and can't cross the Variant signal boundary — so handlers read `LastRow` (inserted/new), `LastOldRow` (update only), or `LastDeletedRow` and cast.
- `ReplayExistingRows` re-fires every already-cached row through `RowInserted` at bind time, replacing manual `Iter()` replay loops. It stays **on** for persistent tables (a late-joining or late-spawned consumer still sees existing rows — e.g. each `Enemy` puppet's own binder) and **off** for event tables, *because* there is no last-seen-id tracking: replaying an event table would re-fire its entire history — every bullet pattern ever appended — on every scene entry.
- If the connection isn't up yet at `OnEntityReady`, the binder waits for `DatabaseConnector.Connected` ([[client/sstdbsdk/TableBinderComponent.cs#OnConnected|OnConnected]] guards `IsInstanceValid(this)` first — a deferred free can race the connection pump's dispatch). `_ExitTree` removes every hooked handler, so a freed binder never gets called from a connection that outlives it.

Live wiring example, from [[client/Scenes/game.tscn|game.tscn]]: `CatalogComponent` declares three inline binder children (`AllTexturesBinder`, `AllItemsBinder`, `AllEnchantmentsBinder`, each `TableName = "…"`), and the scene's `[connection]` lines wire their signals back to `CatalogComponent.OnTextureRow`/`OnItemRow`/`OnEnchantmentRow`. Same pattern per entity: [[client/Scenes/default_enemy.tscn|default_enemy.tscn]] declares a `NearbyEnemiesBinder` with `ReplayExistingRows = true` (replay on *because* a puppet instanced after its row already streamed must still initialize) wired to `Enemy.OnEnemyRowInserted`/`OnEnemyRowUpdated`.

### The server-side mirror: tables as components, ids as entity ids

The same compositional model appears in the Rust module, relationally: **one table per concern is a component**, and an id column — `profile_id`, `enemy_id` — is the **entity id** joining one logical entity's rows across tables (see the composition mapping in [[server/AGENTS.md]]). A "player" is not a row; it is the bundle of `PlayerData` + `PlayerStats` + `PlayerStatAllocation` + 38 `PlayerInventorySlot` rows + `PlayerPosition`/`PlayerRotation`/`PlayerChunk` + … that share a `profile_id`. Where the client creates an entity by instancing a scene (the root and its component children appear together), the server creates one through an **archetype helper** that inserts the whole bundle in one reducer call. (Reducer primer: a **reducer** is a server function clients invoke by name — transactional, returning no data; callers learn the result through the subscribed rows that change.)

[[server/spacetimedb/src/player/methods.rs#try_scaffold_profile|try_scaffold_profile]] is the player archetype build, called by [[server/spacetimedb/src/player/reducers.rs#join_world|join_world]] after the lobby→world row swap. Every insert is guarded by an `is_none()` check *because* `leave_world` deliberately keeps most rows — a rejoin scaffolds only what's missing and keeps the character's progress. It inserts `PlayerData` (level 1, base hp/speed) if absent; the full fixed slot scaffold at load-bearing indices (weapon 0 pre-equipped with a `Bow`, hotbar 1–4 with `Bread` at 1, accessory 5 `Hat`, armor 6 `Helmet`, general 7–30, bag 31 `Bag`, ability 32–37) plus two pre-placed ability spans (`Skull` at 32, `Tome of Mending` spanning 33–35) so activation is testable immediately; `PlayerStatAllocation` (the auto-created "Knight" profile starts with 999 points everywhere for testing, manual profiles at zero); `PlayerStats` via [[server/spacetimedb/src/player/methods.rs#recompute_stats|recompute_stats]]; and the position/rotation/chunk trio — **reset to the world origin** even when a row exists, *because* `leave_world` keeps the position/chunk rows and a rejoin would otherwise resume wherever the player logged out (the ghost-row consequence of that retention is a known gap tracked in [[06 Movement & AOI Tables]]). [[server/spacetimedb/src/player/methods.rs#teardown_profile|teardown_profile]] is the exact inverse — the **one shared cleanup list** deleting every per-profile row (data, stats, allocation, slots, position/rotation/chunk, movement state, displacement allowance, hit rate, consumable effects) plus `purge_profile_statuses`/`purge_profile_zones`. It is called by both profile-death paths: the combat death cleanup in [[server/spacetimedb/src/combat/mod.rs#deal_damage_to_player_opts|deal_damage_to_player_opts]] (which keeps `PlayerProfile` and moves the identity to `LoggedOutPlayer`) and [[server/spacetimedb/src/player/reducers.rs#delete_profile|delete_profile]] (which deletes `PlayerProfile` too). Centralizing the list is the same discipline as the entity registry: there is exactly one place that knows what rows make up a player, so a new table added to the archetype can't be forgotten at cleanup.

[[server/spacetimedb/src/enemy/methods.rs#spawn_enemy_archetype|spawn_enemy_archetype]] / [[server/spacetimedb/src/enemy/methods.rs#despawn_enemy_archetype|despawn_enemy_archetype]] are the enemy pair — the only sanctioned spawn/despawn paths, called by the 2 s biome tick ([[server/spacetimedb/src/enemy/methods.rs#spawn_from_biome_regions|spawn_from_biome_regions]]), the combat kill path, and the admin reducers. Spawn runs [[server/spacetimedb/src/enemy/methods.rs#build_enemy_behavior|build_enemy_behavior]] — one `EnemyBehavior` root row, one `EnemyPhase` per template phase, one `EnemyAttack` per attack sequence, one `EnemySequenceStep` per step, and a per-enemy `RepeatStepInstance` **copy** of each shared `RepeatStepDef` *because* `repeat_count` (the spin accumulator) must advance independently per enemy — then inserts the flat `Enemy` row (hp = template max, phase 0, position, `chunk_index`) pointing at the tree via `behavior_id`. The flat row staying flat is deliberate: it carries the hot fields the client actually subscribes to, so puppets mirror one table instead of joining the tree. Despawn runs [[server/spacetimedb/src/enemy/methods.rs#delete_enemy_behavior|delete_enemy_behavior]], which cascades behavior → phases → attacks → steps → repeat instances, **collecting each btree-filter result into a Vec before deleting** — removing rows while iterating an index filter skips entries, the exact bug the matching collect-first loop in `teardown_profile` avoids — then deletes the `Enemy` row, so no orphan component rows outlive the entity.

The symmetry to hold onto: **client entity = scene root + registered component children; server entity = an id + the row bundle the archetype helper maintains.** Client-side mirroring discipline follows from it — components never mutate health/stats locally; they mirror server rows (`SetFromServer(...)`) and report intent through reducers, and the updated row flows back through a binder into the mirror.
