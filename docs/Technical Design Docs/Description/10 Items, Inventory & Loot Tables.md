## The 30-second version

Six tables: `Item` and `Enchantment` are the shared static catalog (seeded at publish, upserted by admins, streamed to every client through the `all_items`/`all_enchantments` global views into `CatalogComponent`'s caches). `PlayerInventorySlot` is one row per inventory slot per profile — 38 fixed slots scaffolded at join — carrying the item id, socketed enchantments, and per-slot runtime state (cooldown, charges, toggle index, span occupancy); every mutation goes through `update_slot`, and the client mirrors the rows through the per-caller `local_player_inventory` view. `ActiveConsumableEffect` holds ticking buff rows the client never sees (they reach it only as recomputed stats), driven by the single 1 Hz `ConsumableEffectSchedule` job behind `tick_status_effects`. `LootDrop` is an item on the ground with a 10-second expiry, AOI-streamed through `nearby_loot_drops` and spawned client-side as `Drop` puppets whose `PickupComponent` calls `pickup_drop` on touch.

## Main body

### The catalog: one table per concept, slot and behavior as independent axes

`Item` ([[server/spacetimedb/src/item/tables.rs#Item|definition]]) is deliberately flat: there are no per-type side tables (no `Weapon`/`Armor`/`Consumable` rows to join) because an item's *equip slot* and its *behavior* are independent axes. `equip_slot` (`EquipSlot` — Weapon/Armor/Accessory/Bag/Consumable/Ability; "artifacts" are 1-cost abilities, there is no Artifact variant) says only *where* the item goes; `stat_modifiers` (`Vec<StatModifier>` — a `StatKind`, an amount, and `Flat`/`Mult` mode) plus `behaviors` (`Vec<ItemBehavior>` — `Weapon(WeaponBehavior)` / `Consumable(ConsumableBehavior)` / `Ability(AbilityBehavior)`) say *what it does*. That split is what makes "an accessory that fires projectiles" expressible, and it dictates every lookup: capability checks go through the behavior lookups [[server/spacetimedb/src/player/methods.rs#consumable_behavior|consumable_behavior]] / [[server/spacetimedb/src/player/methods.rs#ability_behavior|ability_behavior]] in `player/methods.rs`, never through `equip_slot`.

`WeaponBehavior.damage` is **per trigger pull, divided among the bullets fired** — per-bullet damage is `damage / effective_shot_count` (the comment on the struct; the division happens in [[server/spacetimedb/src/combat/mod.rs#compute_player_damage|compute_player_damage]], doc 09) — so multi-shot and single-shot patterns trade off against flat enemy defence. `AbilityBehavior` carries `cooldown_seconds` and `max_charges` (0 = unlimited) on top of its `AbilityEffect`; abilities are never consumed on use — they go on cooldown and optionally spend a charge. `Item.slot_cost` is 1 for everything except multi-slot ability items (tome 3, spell 2, shield 6) and only has meaning inside the ability region (see spans below). `innate_enchantment_ids` are enchantments born on the item: always applied while equipped, free of socket cost, unremovable — they live on the `Item` row, not the slot row. `stat_requirements` are flat per-stat minimums checked when an item *enters an equipped role*, which is how classes emerge from gear (the seeded class gates are the `REQ_*` consts at the top of [[server/spacetimedb/src/item/seeds.rs#seed_world_items|item/seeds.rs]] — primary stat ≥ 15, secondary ≥ 12; `NO_REQUIREMENTS` for generic gear).

`Enchantment` ([[server/spacetimedb/src/item/tables.rs#Enchantment|definition]]) is the same shape minus an equip slot: `stat_modifiers`, `behaviors` (`EnchantmentBehavior` — shot-count/damage weapon modifiers, `OnAbilityUseBuff`, and `WeaponToggle`, which grants the equipped weapon an extra toggle pattern), and `allowed_slots` restricting which `EquipSlot`s it may be socketed into (empty = nowhere socketable, which is how the innate-only toggle enchantments `point_blank`/`scatter_fan` stay un-socketable).

Content is seeds. [[server/spacetimedb/src/main/lifecycle.rs#init|init]] calls [[server/spacetimedb/src/item/seeds.rs#seed_world_items|seed_world_items]] and [[server/spacetimedb/src/item/seeds.rs#seed_world_enchantments|seed_world_enchantments]] on every publish (the DB is wiped each time, so anything not seeded does not exist); `Item::seed` ([[server/spacetimedb/src/item/seeds.rs#seed|item/seeds.rs]]) and `Enchantment::seed` ([[server/spacetimedb/src/main/seeds.rs#seed#7|main/seeds.rs]]) upsert by primary key, so reseeding is idempotent. Single-effect ability seeds go through the `ability_item` helper ([[server/spacetimedb/src/item/seeds.rs#ability_item|item/seeds.rs]]), which stamps the class gate as its last parameter. The admin reducers [[server/spacetimedb/src/item/reducers.rs#upsert_item|upsert_item]] / [[server/spacetimedb/src/item/reducers.rs#upsert_enchantment|upsert_enchantment]] are the runtime escape hatch; the catalog tables are never deleted from.

Both tables reach the client as **anonymous global views** — [[server/spacetimedb/src/item/views.rs#all_items|all_items]] and [[server/spacetimedb/src/item/views.rs#all_enchantments|all_enchantments]] return the full table to every subscriber with no per-caller filtering, because the catalog is shared and tiny. They ride the `BaseTables` wave (subscribed on connect, before any lobby/game state) and land in [[client/Scripts/Components/Catalog/CatalogComponent.cs|CatalogComponent]], declared inline in `game.tscn` with three child binders (`AllTexturesBinder`, `AllItemsBinder`, `AllEnchantmentsBinder`, all replaying; `RowInserted`/`RowUpdated`/`RowDeleted` wired in the scene to `OnItemRow`/`OnEnchantmentRow`/etc.). `CatalogComponent` keeps three dictionaries (`GetItem`, `GetEnchantment(s)`, `GetResPath`) behind the `GameManager` facade — every item display name, icon, and behavior lookup client-side resolves through this cache. It also bumps `CatalogVersion` and fires `CatalogChanged` on any item/enchantment row change so catalog-derived caches (the effective weapon, below) re-resolve even when the inventory is untouched, and `EnchantmentsChanged` so the sidebar's socket list refreshes.

### PlayerInventorySlot: 38 rows per profile, load-bearing indices

[[server/spacetimedb/src/player/tables.rs#PlayerInventorySlot|PlayerInventorySlot]] is **one row per slot** (auto-inc `slot_id` PK, a `profile_id` btree, and a composite `(profile_id, slot_index)` index that makes [[server/spacetimedb/src/player/methods.rs#get_slot|get_slot]] a point read). One row per slot — rather than one `Vec` on a profile row — because ability slots need a home for per-slot runtime state (`cooldown_until`, `charges`, `active_toggle`, span occupancy) that has no business being replicated as part of a value type on every swap.

The slot layout is fixed and load-bearing on both sides: **0** weapon, **1–4** hotbar consumables, **5** accessory, **6** armor, **7–30** general (backpack), **31** bag, **32–37** ability ([[server/spacetimedb/src/main/global.rs#ABILITY_SLOT_START|ABILITY_SLOT_START]]/`ABILITY_SLOT_COUNT`). [[server/spacetimedb/src/player/methods.rs#try_scaffold_profile|try_scaffold_profile]] inserts the full 38-row scaffold at join (with starter gear — Bow, Hat, Helmet, Bag, Bread, and the pre-equipped Skull at 32 plus Tome of Mending spanning 33–35 via `place_span`), and [[server/spacetimedb/src/player/methods.rs#teardown_profile|teardown_profile]] deletes the rows; mid-game, slots are only ever *updated* (cleared by writing `item_id: None`), never deleted.

What a slot accepts is derived from its `SlotRole` by [[server/spacetimedb/src/player/methods.rs#slot_allowed|slot_allowed]]: every role accepts exactly its matching `EquipSlot`, except **General, which accepts everything** — the backpack stores ability items loose in one cell, because `slot_cost` only applies inside the ability region.

**Spans.** An ability item with `slot_cost > 1` occupies contiguous ability cells: the head row holds the item and its runtime state; follower rows hold nothing and are marked `occupied_by = Some(head_index)`. [[server/spacetimedb/src/player/methods.rs#place_span|place_span]] writes a span (initializing the head's charges from the item's `AbilityBehavior` — `max_charges` 0 becomes `u32::MAX`, the unlimited sentinel), [[server/spacetimedb/src/player/methods.rs#clear_span|clear_span]] resets it, and [[server/spacetimedb/src/player/methods.rs#find_free_span|find_free_span]] finds the first free run. Followers never hold an item, so stat/behavior folds skip them by checking `occupied_by.is_some()`.

**Runtime state travels with the item, not the slot.** `cooldown_until`/`charges`/`active_toggle` move with the item in both directions of every move path — [[server/spacetimedb/src/player/reducers.rs#swap_slots|swap_slots]] carries them through plain swaps *because* leaving a cooldown on the slot would let a backpack shuffle launder it before re-entering the ability region; [[server/spacetimedb/src/player/reducers.rs#drop_item|drop_item]] stamps them onto the `LootDrop` row and [[server/spacetimedb/src/player/reducers.rs#pickup_drop|pickup_drop]] restores them, so a picker-upper inherits residual cooldowns. The one exception: entering the ability region from a *fresh* backpack cell (no cooldown, unlimited charges) initializes charges from the item — a cell with residual state keeps it.

**swap_slots** ([[server/spacetimedb/src/player/reducers.rs#swap_slots|player/reducers.rs]]) is the drag-and-drop reducer. Its rules, in order: follower indices resolve to their span head (a drop onto your *own* span's follower is treated as a nudge to move the head there); `slot_allowed` acceptance is checked both directions; [[server/spacetimedb/src/player/methods.rs#check_stat_requirements|check_stat_requirements]] gates any item entering an equipped role (Weapon/Accessory/Armor/Ability) from loose storage — this is the equip-time class-gate enforcement. Span handling is **region-based, not item-based**: it triggers only when source or target is an Ability-role slot. A span move needs `slot_cost` contiguous free cells at the target (the source's own cells count as freed), can't 1:1 swap onto an occupied slot, and re-marks followers at the destination. Ability items swapped between non-ability slots are plain single-cell swaps. Every successful swap ends in `recompute_stats`, because equipped items feed stats.

**use_item** ([[server/spacetimedb/src/player/reducers.rs#use_item|player/reducers.rs]]) is the hotbar-consumable reducer: it requires the `Hotbar` role (matching the client UI, which only exposes use on hotbar keys), rejects any item carrying an `Ability` behavior as defense in depth (consuming a span head would orphan its followers), then delegates to [[server/spacetimedb/src/player/methods.rs#apply_consumable_effect|apply_consumable_effect]] and **clears the slot** — consumables are the one item kind consumed on use. The guard is behavior-based, not slot-based: a hypothetical accessory-with-a-Consumable-behavior still can't be used from the hotbar, because the role check fires first.

**Enchanting.** [[server/spacetimedb/src/player/reducers.rs#apply_enchantment|apply_enchantment]] validates the enchantment exists, its `allowed_slots` contains the item's `equip_slot`, the slot isn't already holding it, and `slot.enchantment_ids.len() < item.max_enchantments`, then pushes onto the slot row's `enchantment_ids`; [[server/spacetimedb/src/player/reducers.rs#remove_enchantment|remove_enchantment]] retains everything but it. Both recompute stats. Innate enchantments bypass all of this — they live on the catalog row and are folded identically but can't be removed and don't count against `max_enchantments`.

**Admin item editing** ([[server/spacetimedb/src/item/reducers.rs#give_item|give_item]] / [[server/spacetimedb/src/item/reducers.rs#remove_item|remove_item]]) writes into the first free General slot / clears every slot holding the item (spans via `clear_span`) — the CLI-only path playtesting uses to hand items out.

### Stat resolution and the effective weapon

**[[server/spacetimedb/src/player/methods.rs#recompute_stats|recompute_stats]] is the one place stats resolve.** It accumulates per-`StatKind` `(flat, mult)` pairs — mults additive, never compounding — from four sources, in order: allocated skill points from `PlayerStatAllocation` (folded as flat, so gear mults scale them); `stat_modifiers` of equipped items; `stat_modifiers` of those items' innate *and* socketed enchantments; and active consumable buff rows. "Equipped" is an explicit `SlotRole` check: Weapon/Accessory/Armor heads contribute at scale 1.0, **Ability heads contribute scaled by their position multiplier** ([[server/spacetimedb/src/main/global.rs#ABILITY_POSITION_MULTIPLIERS|ABILITY_POSITION_MULTIPLIERS]] = `[1.5, 1.25, 1.1, 1.0, 0.9, 0.8]` — "order matters, first ability stronger"), backpack/hotbar/bag contribute nothing, and span followers never contribute. The resolve is `(base + flat) * (1 + mult)`, rounded — the six allocatable stats land on `PlayerStats` over `BASE_STAT` = 10, while the modifier-only kinds land on `PlayerData`: `Hp` into `max_hp` (with current hp clamped down), `Defense` into `defense`, `BaseSpeed` into `base_speed` (unrounded, over `BASE_SPEED` = 100). Callers decide when it runs — every slot mutation above calls it, and so do the consumable tick's expiries.

Enchantment *behaviors* (as opposed to stat modifiers) are folded separately by [[server/spacetimedb/src/player/methods.rs#equipped_enchantment_behaviors|equipped_enchantment_behaviors]]: equipped heads only, sorted by slot index, innate before socketed per slot, and **never position-scaled**. The order is deterministic and load-bearing, because toggle indexing and the client's mirror both depend on it.

**The effective weapon** is what the player actually fires: [[server/spacetimedb/src/player/methods.rs#resolve_effective_weapon|resolve_effective_weapon]] takes the weapon head slot's item, builds the **toggle options** — the item's own `Weapon` behaviors plus `WeaponToggle` grants from all equipped enchantments ([[server/spacetimedb/src/player/methods.rs#weapon_toggle_options|weapon_toggle_options]]) — picks `options[active_toggle]` (clamped, because removing a toggle-granting enchantment can leave the index pointing past the end), then folds the shot/damage behaviors: `AddShots` sums, `ShotCountMult`s sum *additively* before applying (`(count + add) * (1 + mult)`, rounded, min 1), and `FlatBulletDamageMod`/`TrueDamageFlat`/`TrueDamagePercent` accumulate for the combat pipeline (doc 09). [[server/spacetimedb/src/player/reducers.rs#set_slot_toggle|set_slot_toggle]] is the only writer of `active_toggle`: weapon slot only, no followers, index bounds-checked against the same options list.

The client mirrors this exactly in [[client/Scripts/Components/Weapon/EffectiveWeaponResolver.cs#Resolve|EffectiveWeaponResolver]] — same equipped-index order (0, 5, 6, 32–37), same innate-before-socketed fold, same toggle list, same shot-count formula — because the client fires bullets at the resolved rate/pattern/count and the server validates against its own resolution; any drift double-counts or rejects legitimate fire. The resolver never mutates the catalog's shared `WeaponBehavior` — it copies with the folded count. `CombatComponent` caches the result and re-resolves only when the `Fingerprint` (item ids, toggle index, socketed + innate enchantment ids per equipped slot, plus `CatalogVersion`) changes on `InventoryChanged`/`CatalogChanged`; the `weapon_toggle` input (T) cycles the weapon slot's toggle client-side by calling `SetSlotToggle(0, (current + 1) % count)`.

### Ability activation: one shared pipeline, optimistic client

The instant-cast path is [[server/spacetimedb/src/player/reducers.rs#activate_ability|activate_ability]] → `resolve_ability_slot` (ability head slot, item has an `Ability` behavior, not on cooldown, charges > 0 — charge-capable abilities are rejected here so they can't bypass the hold-to-charge path) → `apply_ability_effect` (the shared dispatch: scales the effect by the span head's position multiplier via [[server/spacetimedb/src/player/reducers.rs#scale_ability_effect|scale_ability_effect]], clamps the client-supplied cursor to [[server/spacetimedb/src/main/global.rs#MAX_ABILITY_TARGET_RANGE|MAX_ABILITY_TARGET_RANGE]] = 600 around the server's own position row, then executes — self effects delegate to `apply_consumable_effect`, bullet-control effects append a `BulletControlEvent`, status effects go through the status module, spell damage goes through the combat pipeline; the effect arms themselves are docs 09 and 11) → `spend_ability` (fires `OnAbilityUseBuff` enchantment triggers, stamps `cooldown_until`, decrements charges unless unlimited).

The client drives this from [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#TryActivateAbility|TryActivateAbility]] (shared by the Ability1–6 hotkeys in `InventoryPanel` and the slot path): it pre-checks cooldown/charges locally, calls the `ActivateAbility` reducer with the cursor's world position, and applies bullet-control and spell effects **optimistically** — the caster deletes its own bullets / draws its own flash immediately, while remote clients apply the same cast from the server-echoed event row (skipping the caster's own echo via `cast_by`). Because firing is fast, a per-head-slot optimistic-cast guard (`castPendingUntilMs`, ~500 ms — about one round-trip) rejects double-click recasts until the echoed slot row lands; the echo clears the guard early in `OnInventoryRow`, so legitimate recasts are gated on the echo, not the window. The optimistic geometry (zero-length-direction fallback, position scaling, range clamp) mirrors the server arms exactly — both sides must change together, which is why the mirrored constants live in `client/Scripts/World/ServerConstants.cs`, each naming its `main/global.rs` counterpart.

Charge-capable abilities (`Teleport`/`Spell` with `charge_scaled`, decided by [[server/spacetimedb/src/player/methods.rs#ability_is_charge_capable|ability_is_charge_capable]] and mirrored by [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#IsChargeCapable|IsChargeCapable]]) route key-down/key-up through `TryBeginCharge`/`TryReleaseCharge` → the `BeginAbilityCharge`/`ReleaseAbilityCharge` reducers, which share `resolve_ability_slot`/`apply_ability_effect`/`spend_ability` with the instant path. The charge state itself is the `AbilityCharge` table — doc 11 owns it.

### Consumables and the single 1 Hz tick

`apply_consumable_effect` splits the two `ConsumableEffect` kinds: **Heal bypasses the table entirely** — it calls [[server/spacetimedb/src/combat/mod.rs#heal_player|heal_player]] and is done. **Buff** inserts an [[server/spacetimedb/src/player/tables.rs#ActiveConsumableEffect|ActiveConsumableEffect]] row (`StatModifier` + `remaining` seconds) and recomputes stats immediately. The same helper serves ability Heal/Buff effects and `OnAbilityUseBuff` enchantment triggers, so all three share one code path.

[[server/spacetimedb/src/player/tables.rs#ConsumableEffectSchedule|ConsumableEffectSchedule]] is a scheduled table armed once by `init` at a 1-second interval — **the only 1 Hz schedule in the module**. Each run of [[server/spacetimedb/src/player/reducers.rs#tick_status_effects|tick_status_effects]] decrements every buff row's `remaining`, deletes expired rows and recomputes stats per affected profile (this is the only path that *removes* a buff mid-game), then sweeps stale anti-cheat flags (doc 09), sweeps expired loot drops, and calls `status::methods::tick` for everything the status module does per second (doc 11). The table is `public` but in no subscription wave — clients never see buff rows; a buff's only client-visible effect is the recomputed `PlayerStats`/`PlayerData` rows it feeds (doc 05).

### Loot drops: runtime state on the ground

[[server/spacetimedb/src/player/reducers.rs#drop_item|drop_item]] (the client reports it from a right-click in the backpack) resolves a follower index to its span head (dropping a follower drops the whole span), clears the span or slot, and inserts a [[server/spacetimedb/src/player/tables.rs#LootDrop|LootDrop]] at the caller's position/chunk with `expires_at` = now + [[server/spacetimedb/src/main/global.rs#LOOT_DROP_EXPIRY|LOOT_DROP_EXPIRY]] (10 s), `dropped_by` = the caller, and the slot's enchantments/cooldown/charges stamped onto the row — the runtime state travels with the item even while it lies on the ground. Rows are never updated.

Drops stream to clients through the AOI view [[server/spacetimedb/src/player/views.rs#nearby_loot_drops|nearby_loot_drops]] (the standard `nearby_indices` chunk filter over the `chunk_index` btree — doc 03 explains the idiom) in the `GameTables` wave. `EntitySpawnerComponent`'s `NearbyLootDropsBinder` (declared inline in `game.tscn`, replay on, `RowInserted`/`RowDeleted` wired to `OnDropInsert`/`OnDropDelete`) spawns/despawns a `Drop` puppet per row through the same deferred-add machinery as every server-row entity. The puppet is `client/Scenes/drop.tscn`: a plain `Sprite2D` plus an instanced `pickup_component.tscn`. [[client/Scripts/Items/Drop.cs#_Ready|Drop._Ready]] resolves the item's texture through the catalog cache itself, and [[client/Scripts/Components/Interaction/PickupComponent.cs|PickupComponent]] owns detection: `SetFromServer` starts the declared `PickupLockTimer` when the local player is the one who dropped it (so you can't instantly re-grab your own drop), and `OnBodyEntered` — a `LocalPlayer` entering the area, lock expired — calls the `PickupDrop` reducer with the row id.

[[server/spacetimedb/src/player/reducers.rs#pickup_drop|pickup_drop]] re-validates everything server-side because the client's touch is self-reported: the drop must be unexpired (an expired drop touched is deleted on the spot), and the caller's position row must be within wrap-aware [[server/spacetimedb/src/main/global.rs#INTERACT_RADIUS|INTERACT_RADIUS]] = 128 of the drop — no cross-map grabs. Placement goes through the shared [[server/spacetimedb/src/player/methods.rs#store_item_in_inventory|store_item_in_inventory]] helper (also used by chest takes, doc 12): ability items auto-equip into the first free span **if their stat requirements pass**, else fall back to loose backpack storage; other items prefer a free matching typed slot (requirements gate equipped roles) and fall back to General; carried cooldown/charges restore onto the destination when present. The row is deleted and stats recomputed. Independently of pickups, the 1 Hz `tick_status_effects` sweep deletes every row whose `expires_at` has passed — the 10-second lifetime is enforced both eagerly (at touch) and lazily (by the tick).

### The inventory UI: 39 SlotComponents over one mirrored dictionary

The whole inventory UI is **declared inline in `local_player.tscn`** under `InventoryCanvas` — that inline copy is the only copy the game runs. Its data source is [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs|LocalPlayerInventoryComponent]], whose child `LocalPlayerInventoryBinder` (declared in `local_player.tscn`, `TableName = "LocalPlayerInventory"`, `ReplayExistingRows = true`, insert/update/delete wired to `OnInventoryRow`/`OnInventoryRowDeleted`) feeds the per-caller `local_player_inventory` view ([[server/spacetimedb/src/player/views.rs#local_player_inventory|player/views.rs]]) into a `Dictionary<int, PlayerInventorySlot>` keyed by slot index. Because the server stores one row per slot, each row event touches exactly one entry — no whole-list replacement. Every event also raises `InventoryChanged` on the owning `LocalPlayer`, the one signal all UI observers subscribe to, and clears the optimistic-cast guard for that slot (above). `ResolveSlotAt(index)` is the single read API: slot row plus the catalog-resolved `Item` (or empty), with followers still pointing at their own row — callers chase `OccupiedBy` when they need the head.

Four UI scripts render that state, all reaching the player via `GetAncestor<LocalPlayer>()` (never `LocalPlayer.Local`, which is still null during `_Ready`):

- [[client/Scripts/Components/Inventory/InventoryPanel.cs#_Input|InventoryPanel]] (plain `Control` on the `InventoryPanel` node) toggles the Tab menu (`open_inventory` flips `Menu` and `Hotbar` visibility), routes hotbar keys 1–4 to `UseItem` (only while the hotbar is visible), and routes ability keys 1–6 to the instant or charge path per `IsChargeCapableAt`. On `InventoryChanged` it refreshes every slot icon, dimming followers and on-cooldown heads to 40 % alpha.
- [[client/Scripts/Components/Inventory/SlotComponent.cs#_DropData|SlotComponent]] — the 39 authored slot nodes (5-slot `Hotbar` at indices 0–4, 9-slot always-visible `Equipment` panel at 0/5/6/32–37, 25-slot `Backpack` grid at 7–30 plus Bag 31; several indices appear in two visible slots, so the exported `SlotIndex` is authoritative). Drag/drop reports `SwapSlots` — or `TakeFromChest` when the drag data is a chest dictionary (doc 12) — right-click in the backpack reports `DropItem`, and hover shows the scene-unique `ItemSidebar`. The icon's `mouse_filter` is forced to Ignore in `OnRegistered` *because* Godot asks the hovered control for drag data — a hit-testable icon on top of the slot would silently kill drag start.
- [[client/Scripts/Components/Inventory/ItemSidebar.cs#RenderDetails|ItemSidebar]] renders the hovered slot's full composition: stat modifiers, requirements (red while unmet, compared against the player's resolved stats), the equipped weapon's toggle-option list with the active one marked (from `EffectiveWeaponResolver.ToggleOptions`), ability effect/cooldown/charge lines, innate enchantments (no buttons), socketed enchantments (`N / MaxEnchantments`), and — for enchantable items in equipment slots — the applicable-enchantment list with Socket/Remove buttons calling `ApplyEnchantment`/`RemoveEnchantment`. Each enchantment entry is an instance of `client/Scenes/UI/enchantment_row.tscn` (icon + name + stats + one action button, count data-driven). It refreshes on `InventoryChanged` and `EnchantmentsChanged`, and clears only once the mouse has left both the slots and the sidebar itself, so the buttons stay clickable.
- [[client/Scripts/Components/Inventory/StatsSidebar.cs|StatsSidebar]] shows the resolved stats and owns the per-stat `+` buttons calling `AllocateStat` (visible only with unspent points) — the tables behind it are doc 05's.

## Known gaps / stubs

- **Left-click ability activation is disabled.** `SlotComponent._GuiInput` contains the left-click-on-ability-slot → `TryActivateAbility` path fully commented out ("Disabled for now"); ability activation currently works only through the Ability1–6 hotkeys in `InventoryPanel._Input`.
- **The `Bag` item does nothing.** The seeded Bag (`item/seeds.rs`) has no stat modifiers and no behaviors — bag capacity as a behavior is not built — so slot 31 holds a cosmetic item. (The other not-built item-system feature, the procedural item generator, has no code at all and stays out of these docs per the plan.)
- **The Bag slot's icon never refreshes.** The `Bag - 31` SlotComponent (Backpack `Row - 7` in `local_player.tscn`) is not referenced by any of `InventoryPanel`'s exported slot arrays, so `OnInventoryChanged` never updates its icon — the starter Bag the scaffold places in slot 31 renders as an empty slot (drag/drop and the hover sidebar still work, since those live on `SlotComponent` itself).
