# 03 World & Hex Grid

## Assumed knowledge

[[01 Architecture & Sync Model]] — tables, reducers, subscriptions, and *views* (subscriptions whose result differs per connection) are used throughout this doc without re-explaining them. [[02 Entity & Component Framework]] — the client-side component pattern (`TerrainComponent` and its children are ordinary components on `Main`'s composition).

## The 30-second version

The map is a fixed grid of hex-shaped **chunks**, each chunk itself a cluster of individual hexes (a "hex of hexes," courtesy of the `hexx` crate) — and the whole grid wraps around on itself into a **torus**, so walking off the east edge puts you back on the west edge with no seam a player can see. At boot, the server lays out that grid once (`main/admin.rs`'s `internal_add_chunks`) and then procedurally paints it once (`world/terrain/`'s generation pipeline): a weighted Voronoi split into biomes and biome-regions, then a per-hex pass that picks a ground texture, an optional overlay, and an optional decor prop, all checked against content-driven adjacency rules so textures don't clash with their neighbors. Every hex's six triangular "wedges" and any decor become rows (`TriangleTile`, `HexDecor`) the client renders through a pooled `TerrainComponent`. Players never subscribe to the whole map — chunk-radius **Area of Interest (AOI)** views narrow both terrain and gameplay tables down to a ring of chunks around each player individually. A separate, much smaller table (`BuildingTile`) tags every hex as ownable/placeable, with `place_building`/`remove_building` reducers already implemented server-side, though nothing in the client calls them yet.

## Main body

### Hex and chunk coordinates

Every position in the world resolves to a **fine hex** `(hex_q, hex_r)` — axial coordinates on a pointy-top hex grid, using the `hexx` crate's `HexLayout` for the geometry (`world_to_hex`/`hex_to_world` just wrap `layout.world_pos_to_hex`/`hex_to_world_pos`, scaled by `DEFAULT_HEX_OUTER_RADIUS`). [[hex.rs##pub fn world_to_hex|world_to_hex]] · [[hex.rs##pub fn hex_to_world|hex_to_world]]

A **chunk** is not a rectangle of hexes — it's a hex-shaped cluster of fine hexes, "a hex made of hexes." `hexx` calls the fine-hex-to-chunk relationship *resolution*: `chunk_center_hex` uses `Hex::to_higher_res` to find a chunk coordinate's fine-hex center, and the reverse direction (`world_to_chunk`) uses `Hex::to_lower_res`. `hex_area(chunk_hex_radius)` (`Hex::range_count`) is how many fine hexes make up one chunk — at the shipped `DEFAULT_CHUNK_HEX_RADIUS = 2` that's 19. `inv_hexmod` turns a chunk-local index `m` (`0..area`) into that hex's `(q, r)` offset from the chunk center, using `hexx`'s `hexmod` coordinate system — the bijection that makes "hex #7 of this chunk" well-defined. [[hex.rs##pub fn chunk_center_hex|chunk_center_hex]] · [[hex.rs##pub fn inv_hexmod|inv_hexmod]] · [[hex.rs##pub fn hex_area|hex_area]]

Every chunk also gets a single `i64` **chunk index** via `spiral_chunk_index` — a closed-form bijection from `(cq, cr)` to a spiral numbering (ring 0 is index 0, ring 1 is indices 1-6, ring 2 is 7-18, …) ported by hand into the client's `HexGridOverlayComponent`/`HexGridOverlay3DComponent` (`HexSpiralIndex`) purely for debug-label parity — there's no shared code between the Rust and C# copies, so a change to one without the other is a silent desync risk for the debug overlays specifically (nothing gameplay-facing depends on the client's copy). This index, not the `(cq, cr)` pair, is what every AOI-filtered table keys its rows on (`chunk_index` columns on `TriangleTile`, `HexDecor`, `BuildingTile`, and the player/enemy/loot tables covered in [[04 Player System|04]]/[[06 Enemy AI & Bullet Patterns|06]]) — a single indexed integer is a simpler join key than a coordinate pair, and it's stable garbage-in-garbage-out under torus wrap once `wrap_chunk_coords` (below) has already folded the coordinate back onto the finite grid. [[hex.rs##pub fn spiral_chunk_index|spiral_chunk_index]]

`enumerate_world_hexes(chunk_hex_radius, chunk_cols, chunk_rows, hex_outer_radius)` walks every chunk row/column and every hex within each chunk, producing one `HexCell` (fine hex coords, chunk index, world position) per hex in the whole grid — this is the single enumeration both `internal_add_chunks` (building tiles) and the terrain generation pipeline (below) iterate over, so "how many hexes are in the world" and "what order do they generate in" are defined in exactly one place. [[hex.rs##pub fn enumerate_world_hexes|enumerate_world_hexes]] · [[hex.rs##pub struct HexCell|HexCell]]

Each hex is rendered as six triangular **wedges** (`tri_index` 0-5), not one flat tile — this is what lets ground and overlay textures vary within a single hex. `same_hex_neighbor_indices` gives a wedge's two neighbors inside the same hex (wedge N borders N-1 and N+1, since wedges tile the hex edge-to-edge); `cross_hex_neighbor` gives the one neighbor wedge across the hex boundary, computed from the wedge's outer-edge direction. Both exist purely to support the adjacency-rule checks the generation pipeline runs (see below) — they're not used for gameplay collision or movement. [[hex.rs##pub fn same_hex_neighbor_indices|same_hex_neighbor_indices]] · [[hex.rs##pub fn cross_hex_neighbor|cross_hex_neighbor]]

### The chunk grid and buildable tiles

`internal_add_chunks` (`^boot-3` above) is the one function that actually lays the grid out: for every `(cq, cr)` in `chunk_cols × chunk_rows`, it inserts one `BuildingTile` row per hex in that chunk (`building_type` empty, `owner_id` `None`) via the same `enumerate`-style loop as `enumerate_world_hexes`, then computes and stores the torus **lap vectors** (next section) into the singleton `MapConfig` row. At the shipped defaults (`DEFAULT_CHUNK_COLS = DEFAULT_CHUNK_ROWS = 6`, `DEFAULT_CHUNK_HEX_RADIUS = 2`) that's `6 × 6 × 19 = 684` `BuildingTile` rows, one per hex in the whole map — every hex is a potential build site by default, not an opt-in subset. `add_chunks`/`clear_chunks` are the admin-gated reducer wrappers (see [[09 Admin, Debug & World Lifecycle|09]]); `init` calls the `internal_` version directly at boot. [[admin.rs##pub fn internal_add_chunks|internal_add_chunks]] · [[world/tables.rs##pub struct BuildingTile|BuildingTile]]

`place_building`/`remove_building` (`world/reducers.rs`) are the only reducers that touch `BuildingTile` after that: `place_building` looks a tile up by `(hex_q, hex_r)` (not chunk-scoped — a flat scan filtered by `hex_q` then matched on `hex_r`), rejects if already occupied, and stamps `building_type` + `owner_id: Some(ctx.sender())`; `remove_building` clears both fields, refusing unless the caller is the owner or an admin. Both reducers are fully implemented and require nothing more than "the tile exists" — but a repo-wide search finds **no client code calling either one**: there is no build-mode UI, no placement cursor, nothing wiring a keypress to `PlaceBuilding`/`RemoveBuilding`. This matches the [[00 Roadmap|roadmap]]'s note that base-building beyond this reducer pair is aspirational — the pair itself is real, tested-by-nothing server plumbing waiting for a client feature that doesn't exist yet. [[world/reducers.rs##pub fn place_building|place_building]] · [[world/reducers.rs##pub fn remove_building|remove_building]]

### Torus wrap

The grid is finite (`chunk_cols × chunk_rows` chunks) but the *world* it represents has no edge: `wrap_chunk_coords` folds any chunk coordinate back into range with `rem_euclid` — a coordinate one chunk past the east edge becomes column 0, exactly like modular arithmetic on a clock face. [[wrap.rs##pub fn wrap_chunk_coords|wrap_chunk_coords]]

Wrapping a *continuous* world position is more work than wrapping a chunk coordinate, because crossing the seam has to shift `x`/`y` by exactly one grid-traversal's worth of world space, not just relabel the chunk. `wrap_world_pos` converts the position to a chunk coordinate, wraps that coordinate, and — only if it actually changed — shifts `x`/`y` by `laps_q`/`laps_r` multiples of two **lap vectors**: the world-space position of the fine hex at chunk `(chunk_cols, 0)` and at chunk `(0, chunk_rows)` respectively, i.e. "how far walking one full lap around the grid in each axis moves you in continuous coordinates." `internal_add_chunks` computes these two vectors once and stores them on `MapConfig` (`lap_q_x/y`, `lap_r_x/y`) specifically so nothing downstream has to re-derive the hex-of-hexes math to answer "how far is one lap" — `report_movement` ([[04 Player System|04]]) calls `wrap_world_pos` on every move, and the client mirrors the same two vectors into `SubscriptionComponent.LapQ`/`LapR` off the subscribed `MapConfig` row. [[wrap.rs##pub fn wrap_world_pos|wrap_world_pos]] · [[world/tables.rs##pub struct MapConfig|MapConfig]]

A second, distinct problem: comparing two *already-wrapped* positions (e.g. "is this hex near the camera") can't use plain Euclidean distance, because either point might be the "wrong" copy relative to the other — one could be sitting just past a seam from the other's canonical position. `wrapped_distance_sq` checks all 9 combinations of `{-1,0,1}` lap shifts on both axes and returns the smallest, guaranteeing the true nearest copy is found regardless of which side of a seam either point landed on; it's what the Voronoi seed-distance check (below) uses to pick a wrap-aware nearest biome/region seed. The client's `TorusMath.NearestCandidate` is the same idea from the opposite direction — given one canonical position and a reference point (the camera), it tries the 8 single/combined lap-vector shifts and returns whichever copy is actually closest to the reference, which is what `TerrainComponent.RebuildVisibleInstances` calls before every cull check (stored hex centers are canonical, and near a seam that canonical position can be far from the camera even though a wrapped copy is right in view). [[wrap.rs##pub fn wrapped_distance_sq|wrapped_distance_sq]] · [[TorusMath.cs##public static Vector2 NearestCandidate|NearestCandidate]]

### Area of Interest (AOI)

No client subscribes to the whole map — everything spatial is filtered down to a ring of chunks around that connection's own player, and `^move-1`-`^move-3` above cover the shared mechanism: `surrounding_chunk_indices` resolves a wrap-aware ring of chunk indices around a `(chunk_q, chunk_r)`, and the AOI-scoped views (`nearby_terrain_tiles`/`nearby_hex_decor` here; `nearby_enemies`/`nearby_remote_players`/`nearby_loot_drops` in [[04 Player System|04]]/[[06 Enemy AI & Bullet Patterns|06]]) all resolve their caller's own chunk through the same `player/views.rs` helpers before filtering. [[aoi.rs##pub fn surrounding_chunk_indices|surrounding_chunk_indices]]

Two views live in `world/views.rs`: `all_textures` is a plain unfiltered view over `TextureEntry` (part of the base wave — [[01 Architecture & Sync Model|01]]'s `conn-5`), while `nearby_terrain_tiles`/`nearby_hex_decor` are AOI-filtered at `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS` (2 chunk-rings today). Both AOI views share one defensive pattern worth naming: if the caller has no resolvable chunk yet (not in-world, or their `PlayerChunk` row hasn't landed), the view returns a query pre-filtered to an impossible id (`t.tile_id.eq(u64::MAX)`) rather than an unfiltered scan — a subtle but important default, since an unfiltered fallback here would mean "no known position" silently subscribes to the entire map instead of nothing. [[world/views.rs##fn all_textures|all_textures]] · [[world/views.rs##fn nearby_terrain_tiles|nearby_terrain_tiles]]

### Terrain generation: two front-ends, one pipeline

`world/terrain/mod.rs` is the orchestrator. `internal_generate_world_proc` (the one `init` calls — `^boot-4` above) and `internal_generate_world_manual` (used by admin-authored one-off worlds, [[09 Admin, Debug & World Lifecycle|09]]) are two different ways of *resolving generation input* — a `WorldDef`'s weighted biome list versus an explicit list of biome/region placements — that both funnel into the same `run_generation`, so every world, however it was specified, runs through identical passes in identical order. [[world/terrain/mod.rs##pub fn internal_generate_world_proc|internal_generate_world_proc]] · [[world/terrain/mod.rs##pub fn internal_generate_world_manual|internal_generate_world_manual]]

Generation is **deterministic**: every random-ish decision draws from `world/prng.rs`'s `splitmix64`-based PRNG, seeded by `(seed, draw)` where `draw` is a counter threaded through the whole pipeline and incremented on every draw — the same `(world_id, seed)` always reproduces the same map, because nothing about the pipeline reads real randomness or wall-clock time (`internal_generate_world_manual`'s only source of "freshness" is deriving its seed from `ctx.timestamp`, still fully deterministic *given* that timestamp). This PRNG is the same family `BulletManager` mirrors client-side for bullet jitter, noted in [[01 Architecture & Sync Model|01]]. [[prng.rs##pub fn splitmix64|splitmix64]]

`run_generation`'s four passes, in order:

1. **Clear** any previously-generated `BiomeRegion`/`TriangleTile`/`HexDecor` rows — regeneration is a full replace, not an incremental patch.
2. **Bucket every world hex under its nearest biome seed.** `distribute_biome_seeds` gives each biome a share of `BIOME_VORONOI_SEED_BUDGET` (16 total) seed points proportional to its combined weight — every weight `> 0` gets at least one seed so a small biome can't round down to zero — then `group_cells_by_seeds` assigns every `HexCell` to whichever seed (from *any* biome's pool, all competing in one space) is nearest, using the wrap-aware `nearest_seed_index`/`wrapped_distance_sq` from the torus-wrap section above. This is why biome borders look organic rather than following the chunk grid: they're Voronoi cells around scattered points, not tile-aligned regions. [[voronoi.rs##pub fn distribute_biome_seeds|distribute_biome_seeds]] · [[voronoi.rs##pub fn nearest_seed_index|nearest_seed_index]]
3. **Per biome, resolve its regions the same way** — one Voronoi seed per `RegionWeight` entry (picked uniformly among that biome's own cells, not proportional to weight the way biome seeds are; `global.rs`'s comment on `BIOME_VORONOI_SEED_BUDGET` calls this out explicitly as not-yet-wired-up) — insert the resulting `BiomeRegion` rows, then re-bucket the biome's cells under whichever region seed is nearest. A `BiomeRegion` carries `enemy_template_ids`/`max_enemies`/`spawn_radius` straight from its `BiomeRegionDef` — this is the table [[06 Enemy AI & Bullet Patterns|06]]'s spawn-region logic reads. [[world/instance_tables.rs##pub struct BiomeRegion|BiomeRegion]]
4. **Per hex, ground → overlay → decor.** `write_triangle_tiles` runs the ground pass then the overlay pass for each of the hex's 6 wedges, recording each wedge's decided tags into an in-memory `NeighborTagMap` (not persisted — it only needs to outlive this one generation run) so not-yet-visited neighbor wedges can check compatibility against it; `place_decor` then runs once per hex, after all 6 wedges are decided. [[world/terrain/mod.rs##fn write_triangle_tiles|write_triangle_tiles]] · [[rules.rs##pub type NeighborTagMap|NeighborTagMap]]

**Ground** (`choose_ground`) picks one `GroundTextureConfig` per wedge, first following the biome's noise field ([[noise.rs##pub fn value_noise2d|value_noise2d]]) when `ground_noise_scale > 0` so texture choices cluster into patches instead of scattering independently per wedge — nearby world positions land in the same noise band, and different biomes/passes use decorrelated seed offsets (`OVERLAY_NOISE_SEED_OFFSET`/`DECOR_NOISE_SEED_OFFSET`) so, e.g., debris clustering doesn't just trace the ground-texture boundary. If the noise-driven (or plain-random, when clustering is disabled) first pick conflicts with an already-decided neighbor via `base_tags_conflict` (`BaseAdjacencyRule`, a deny-list — e.g. swamp never lands next to sand), the pass retries plain-random among the remaining candidates until one clears every neighbor or the wedge is left blank. **Overlay** (`choose_overlay`) is the same shape one layer up — eligible overlays are first filtered to those tag-compatible with the ground texture *actually chosen* (`overlay_compatible_with_base`, `LayeringRule`, an allow-list), then picked/retried the same noise-then-conflict-retry way, with "no overlay" as a real, always-available outcome via [[prng.rs##pub fn weighted_pick_with_remainder(chances|weighted_pick_with_remainder]] (chances don't have to sum to 100 — whatever's left over is "nothing"). **Decor** (`place_decor`) rolls at most one prop per hex: eligible decor is filtered by `decor_ground_conflict` against the union of that hex's own 6 wedges' tags (both ground and overlay), then a type-agnostic minimum-separation check (`decor_min_separation`, a straight radius scan against a `decided_decor` set — if anything nearby was already decided this generation pass, no decor at all goes here, no retry) gates the roll before the same noise-then-weighted-pick as the other two passes. [[ground.rs##pub(super) fn choose_ground|choose_ground]] · [[overlay.rs##pub(super) fn choose_overlay|choose_overlay]] · [[decor.rs##pub(super) fn place_decor|place_decor]] · [[rules.rs##pub fn base_tags_conflict|base_tags_conflict]] · [[rules.rs##pub fn overlay_compatible_with_base|overlay_compatible_with_base]]

Every wedge becomes a `TriangleTile` row (`hex_q`/`hex_r`/`tri_index`/`chunk_index`, chosen `texture_id`/`rotation`, optional `overlay_texture_id`/`overlay_rotation`/`overlay_scale`); every hex gets at most one `HexDecor` row (texture + paired shadow texture, since decor art bakes its shadow in as a separate sprite rotating with the prop — decor is deliberately never rotated on placement, since a baked shadow relationship would break under rotation). [[world/instance_tables.rs##pub struct TriangleTile|TriangleTile]] · [[world/instance_tables.rs##pub struct HexDecor|HexDecor]]

### What's actually seeded at boot

`main/seeds.rs`'s `seed_world_defs` (called from `init`, `^boot-2`) defines the one `WorldDef` `init` generates (`"Earth"`, 40% Grassland / 30% Meadow / 30% Highlands) and its `BiomeDef`s — today, ground textures only (`Grass`/`Flowers`/`HalfStones` at biome-specific weighted chances), no overlays and, despite the mechanism above being fully built and working (`DecorConfig`/`HexDecor`/`DecorGroundRule`, the client's decor rendering), **no seeded biome currently has a non-empty `decor_configs`** — a comment in `seeds.rs` explains why: 2D top-down decor collision/walkability isn't decided yet, and the current decor art doesn't read well enough to be worth turning on. All 9 seeded regions across the 3 biomes (3 Grassland + 2 Meadow + 4 Highlands) share the same `enemy_template_ids: ["Enemy", "Archer"]`, `max_enemies: 5`, `spawn_radius: 300.0` via `seed_region_def` — today's content varies ground textures per biome, not region composition. `seed_adjacency_rules` inserts *zero* rows today (it only clears any prior rows) — the demo's texture set has no clashing pairs yet, so `BaseAdjacencyRule`/`OverlayAdjacencyRule` exist and run every generation but currently reject nothing. [[main/seeds.rs##pub fn seed_world_defs|seed_world_defs]]

### Client terrain rendering

`TerrainComponent` (child of `Main`, [[02 Entity & Component Framework|02]]'s composition map) is the terrain system: it subscribes to `NearbyTerrainTiles`/`NearbyHexDecor`/`MapConfig` (`^move-3` above covers the dirty-flag row-callback pattern) and owns two kinds of shared state — mesh/texture caches, because a wedge's mesh only depends on `(TriIndex, Rotation, TextureId)` and never on which chunk or layer draws it, so one cache serves every chunk; and a pool of `TileComponent` instances, pre-warmed to the AOI ring count (`1 + 3R(R+1)` for radius `R`, matching `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS`) so the first subscription burst doesn't hitch on instantiation, growing on demand if more chunks are ever visible at once. [[TerrainComponent.cs##public partial class TerrainComponent|TerrainComponent]]

Each visible frame (camera moved, or the dirty flag is set), `RebuildVisibleInstances` re-groups every cached tile/decor row by chunk into ground/overlay/decor-shadow/decor batches, wrap-correcting each hex's canonical center against the camera via `TorusMath.NearestCandidate` before culling against the viewport rectangle (plus a margin) — this wrap step has to happen before culling, not after, because a hex's stored position can be canonically far from the camera while a wrapped copy of it is on-screen. Each chunk still present after culling is handed to one pooled `TileComponent` via `Populate`; chunks that dropped out of view get `Clear()`'d (zeroed, not freed) and their `TileComponent` returned to the pool. [[TerrainComponent.cs##private void RebuildVisibleInstances|RebuildVisibleInstances]] · [[TileComponent.cs##public void Populate(|Populate]]

A `TileComponent` is per-chunk scaffolding, not a single mesh — it holds four declared layer children (`GroundComponent` z=0, `OverlayComponent` z=1, `DecorShadowComponent` z=2, `DecorComponent` z=3), each a `TerrainLayerComponent` owning pooled `MultiMeshInstance2D` **batch leaves**, one leaf per `(TriIndex, Rotation, TextureId)` key (ground/overlay) or per texture (the two decor layers, sorted by hex row so nearer rows draw over farther ones of the same texture). A leaf that goes inactive between passes is zeroed (`InstanceCount = 0`), not freed, so a chunk crossing back and forth reuses its batches instead of reallocating every pass — `ClearLeaves`/`ClearMeshes` (a full free) only run when `hex_outer_radius` itself changes, which invalidates every cached mesh at once. [[TerrainLayerComponent.cs##public abstract partial class TerrainLayerComponent|TerrainLayerComponent]] · [[DecorLayerComponent.cs##public abstract partial class DecorLayerComponent|DecorLayerComponent]]

### Debug hex-grid overlays

`HexGridOverlayComponent` (2D, child of `Main`) and `HexGridOverlay3DComponent` (3D, declared in `world_3d.tscn`, [[08 Client Rendering & Camera|08]]'s viewport) are standalone debug visualizations, not terrain renderers — they draw a colored, labeled hex/chunk grid around the camera for verifying the server's layout math against what the client thinks it is. Both independently re-implement `hex.rs`'s coordinate math in C# (`WorldToHex`/`HexToWorld`/`ToLowerRes`/`HexSpiralIndex`) purely for this purpose — there's no shared code between the Rust source of truth and these two ports, the same hand-mirrored-math situation as the chunk-index mirroring noted above. Both read `MapConfig` off `GameManager.Conn`, but not through [[01 Architecture & Sync Model|01]]'s usual `ConnectionComponent.Connected`-signal pattern — each polls `GameManager.Conn` for non-null every `_Process` frame until it succeeds (`TrySubscribe`), per their own comment: "conn may not exist yet when `_Ready` fires (lobby is shown first)." Functionally equivalent to the signal-hook pattern once it lands, just a poll instead of a callback — worth knowing as a second, coexisting way components in this codebase reach the connection. [[HexGridOverlayComponent.cs##public partial class HexGridOverlayComponent|HexGridOverlayComponent]] · [[HexGridOverlay3DComponent.cs##public partial class HexGridOverlay3DComponent|HexGridOverlay3DComponent]]

## Known gaps / stubs

- **`place_building`/`remove_building` have no client caller.** Both reducers are complete and correct against the `BuildingTile` grid `internal_add_chunks` lays down, but nothing in `client/Scripts` calls either one — no build-mode UI, no placement input. Matches the roadmap's line on base-building being out of scope beyond this reducer pair; the pair itself simply predates any UI for it.
- **No biome currently seeds decor**, despite the full pipeline (`DecorConfig`/`place_decor`/`HexDecor`/`DecorGroundRule`) and full client rendering path (`DecorComponent`/`DecorShadowComponent`) working end to end — `main/seeds.rs` leaves every `BiomeDef.decor_configs` empty, by design for now (collision/walkability and art quality aren't ready).
- **`BaseAdjacencyRule`/`OverlayAdjacencyRule` are seeded empty.** The conflict-check machinery (`base_tags_conflict`/`overlay_tags_conflict`) runs on every generation pass but has zero rows to match against with the current texture set, so it currently rejects nothing.
- **Region seed placement isn't weight-proportional** the way biome seed placement is — `run_generation` draws exactly one Voronoi seed per `RegionWeight` entry, uniformly among the biome's own cells, regardless of that entry's `weight` value. `global.rs`'s comment on `BIOME_VORONOI_SEED_BUDGET` flags this explicitly: region weights currently only gate the "must sum to 100" validation, not actual area share.
- **`HexGridOverlayComponent`'s `DrawHudText` is dead code** — fully implemented (player position/hex/chunk HUD text) but its only call site is commented out (`// DrawHudText(cam);`), and nothing else invokes it.
- **Neither debug hex-grid overlay has an in-game toggle.** `HexGridOverlayComponent` starts `visible = false` in its `.tscn` with nothing in the codebase ever setting it back to `true` (unlike `DebugOverlay`'s P-key toggle); `HexGridOverlay3DComponent` has no such default at all, so it renders from the moment `world_3d.tscn` loads. Toggling either today means editing the scene file or setting `Visible` from the debugger, not a documented player-facing bind.
