# 00 End-to-End Timeline Flowchart

The whole game as one causal timeline, from server boot to disconnect. Each numbered step is one cause-and-effect beat ("X does Y because Z"), names the file/function that implements it, and ends in a `^prefix-N` block anchor so the system docs (02–13) can transclude steps instead of re-typing them. Steps cross-refer to each other by anchor name ("the subscription opened in join-1"). Where a step only sketches a mechanism, it links the system doc that owns the details.

Primer for the terminology used below: the **server** is a SpacetimeDB module — tables hold all state, **reducers** are the only way to mutate them (transactional remote calls that return nothing), **views** are per-client filtered queries the client **subscribes** to, and **scheduled tables** re-fire a reducer on a timer. The **client** is a Godot scene tree: `.tscn` files declare trees of nodes, scripts attach behavior, and every server-row consumer is a `*Component` child node fed by a `TableBinderComponent` that re-exposes table row events as Godot signals. The server is authoritative: the client mirrors rows and reports intent through reducers; it never computes damage or stats locally.

# Boot & Connection

1. Publishing the module runs the `init` reducer once, which inserts the three scheduled job rows that drive all server-side time: `EnemyBehaviorSchedule` (100 ms interval, fires `tick_enemy_behavior`), `EnemySpawnSchedule` (2 s, fires `tick_enemy_spawn`), and `ConsumableEffectSchedule` (1 s, fires `tick_active_consumable_effects`) — see [[server/spacetimedb/src/main/lifecycle.rs#init#1|init]]. Because every publish wipes the database (`build.sh` passes `--delete-data`), these schedules and everything seeded below are rebuilt from scratch each publish. ^boot-1

2. `init` then seeds the static content tables in a fixed order: texture catalog and terrain rule sets from [[server/spacetimedb/src/main/seeds.rs#seed_default_textures#1|seed_default_textures]] / [[server/spacetimedb/src/main/seeds.rs#seed_layering_rules#1|seed_layering_rules]] / [[server/spacetimedb/src/main/seeds.rs#seed_adjacency_rules#1|seed_adjacency_rules]] / [[server/spacetimedb/src/main/seeds.rs#seed_decor_ground_rules#1|seed_decor_ground_rules]], enemy templates (including the test bosses) from [[server/spacetimedb/src/main/seeds.rs#seed_default_enemies#1|seed_default_enemies]], the item and enchantment catalogs from [[server/spacetimedb/src/item/seeds.rs#seed_world_items#1|seed_world_items]] / [[server/spacetimedb/src/item/seeds.rs#seed_world_enchantments#1|seed_world_enchantments]], and the world-generation definitions (`WorldDef` "Earth" + three `BiomeDef`s + nine `BiomeRegionDef`s) from [[server/spacetimedb/src/main/seeds.rs#seed_world_defs#1|seed_world_defs]]. Most seeds go through the `Seed` trait's upsert so a republish overwrites rather than duplicates ([[server/spacetimedb/src/main/seeds.rs#seed#4|Seed::seed]]); the rule tables (`LayeringRule`, the base/overlay adjacency rules, `DecorGroundRule`) have no natural key to upsert against, so `seed_layering_rules`/`seed_adjacency_rules`/`seed_decor_ground_rules` clear-and-reinsert instead. Details: [[08 Enemies & AI]], [[10 Inventory, Items & Enchantments]], [[07 Terrain & World Streaming]]. ^boot-2

3. `init` calls [[server/spacetimedb/src/main/admin.rs#internal_add_chunks#1|internal_add_chunks]] (the non-gated helper behind the admin `add_chunks` reducer), which enumerates the chunk grid and inserts one `BuildingTile` row per hex plus the singleton `MapConfig` row — the row that carries the grid dimensions and the two torus **lap vectors** (`lap_q`/`lap_r`, the world-space displacement of one full grid traversal) every wrap-aware computation on both sides depends on. ^boot-3

4. Finally `init` calls [[server/spacetimedb/src/world/terrain/mod.rs#internal_generate_world_proc#1|internal_generate_world_proc]] for "Earth", which runs the shared generation pipeline (`run_generation`): distribute weighted Voronoi biome seeds, bucket every world hex under its nearest seed, insert `BiomeRegion` rows (the enemy spawn regions), then per hex run the ground → overlay → decor passes and emit the `TriangleTile` (six wedges per hex) and `HexDecor` rows the client later renders (with the current seeds every `BiomeDef.decor_configs` is empty, so this run emits zero `HexDecor` rows — the decor pipeline runs; the content is parked). The pass order and PRNG draw counter are deterministic, so the same seed reproduces the same map. Details: [[07 Terrain & World Streaming]]. ^boot-4

1. On the client, Godot reads [[client/project.godot|project.godot]]: it registers three autoloads — `PhantomCameraManager` (the phantom-camera plugin's singleton; the camera priority handoff of camera-2 runs through it), `McpRuntimeAutoload` (the open_godot_mcp plugin's runtime bridge), and `DatabaseConnector` (a singleton scene wrapping [[client/sstdbsdk/DatabaseConnector.cs#_Ready#1|DatabaseConnector]] — one instance reachable from any scene as `DatabaseConnector.Instance`) — and sets the main scene to `Scenes/main_menu.tscn`. Note the file names read swapped: `main_menu.tscn` is the *menu* scene (root script [[client/Scripts/Game/LobbyGui.cs|LobbyGui]]), while `game.tscn` is the actual gameplay scene. ^conn-1

2. The autoload's `_Ready` builds the `DbConnection` to the exported `Host`/`DbName`, reusing the auth token the SpacetimeDB SDK persists per host (a `--pN` command-line argument suffixes the token key so parallel debug instances get distinct identities), and pumps `FrameTick()` every frame so network callbacks dispatch on the main thread — see [[client/sstdbsdk/DatabaseConnector.cs#Connect#1|Connect]]. (Token persistence is the SDK's own `AuthToken` helper; there is no first-party `AuthToken.cs` despite what older notes say.) ^conn-2

3. When the connection opens, [[client/sstdbsdk/DatabaseConnector.cs#OnConnected#1|OnConnected]] stores the identity/token, wires the client's own `LocalLobbyPlayer` row into its `Username` property, and fires the `Connected` signal that every consumer waits on before touching tables. On the server, the same connect fires the `client_connected` lifecycle reducer: a brand-new identity gets a `LoggedOutPlayer` row (the lobby seat) plus a default "Knight" `PlayerProfile`, so every player always has at least one character to join with — see [[server/spacetimedb/src/main/lifecycle.rs#client_connected#1|client_connected]]. ^conn-3

4. Nothing subscribes while the menu scene is up; subscriptions start when `game.tscn` loads (lobby-1) and its inline [[client/sstdbsdk/TableSubscriber.cs#OnConnected#1|TableSubscriber]] component runs. Because the autoload usually finishes connecting *before* the scene loads, `OnRegistered` handles both orders: subscribe immediately if `Conn.IsActive`, else wait for `Connected`. ^conn-4

5. `TableSubscriber` opens two subscription waves: the **base wave** (`AllTextures`, `AllItems`, `AllEnchantments` — static catalogs every screen needs) and the **lobby wave** (`LocalLobbyPlayer`, `LocalPlayerProfiles`), built from the static name lists that are the single source of truth for "what is subscribed" and turned into `SELECT *` SQL through the generated bindings' `From` API so renames can't silently break the SQL — see [[client/sstdbsdk/TableSubscriber.cs#TablesSql#1|TablesSql]]. A third wave (game) opens later at join-1. Details: [[03 Boot & Connection]]. ^conn-5

6. Row events reach game logic through one mechanism everywhere: a [[client/sstdbsdk/TableBinderComponent.cs#Bind#1|TableBinderComponent]] child per consumed table, which hooks the table's `OnInsert`/`OnUpdate`/`OnDelete` and re-fires them as the editor-wireable Godot signals `RowInserted`/`RowUpdated`/`RowDeleted` (signals carry no row argument — handlers read `LastRow`/`LastOldRow`/`LastDeletedRow`), with `ReplayExistingRows` replaying already-cached rows through the insert path so late-binding components still initialize. Every binder/signal pair cited below is declared inline in one of the live scenes (`game.tscn`, `local_player.tscn`, `default_enemy.tscn`, `non_local_player.tscn`, `world_3d.tscn`). Details: [[02 The Component Framework]]. ^conn-6

# Lobby & Profiles

1. The game opens on the menu: `main_menu.tscn` (root `MainMenu`, a `Control` running [[client/Scripts/Game/LobbyGui.cs|LobbyGui]]) shows three buttons, and **Character Slots** calls [[client/Scripts/Game/LobbyGui.cs#CharSlotsPressed#1|CharSlotsPressed]] → `ChangeSceneToFile("res://Scenes/game.tscn")`. *Known gap:* `LobbyGui` is scene navigation only — its Server List and Settings panels are show/hide stubs, and no reducer call (not even `set_username`, which exists server-side in [[server/spacetimedb/src/player/reducers.rs#set_username#1|set_username]]) has a client caller today. ^lobby-1

2. `game.tscn` loads with root node `game` running [[client/Scripts/Game/GameManager.cs|GameManager]] — an `IEntity` whose registered child components (TableSubscriber, CatalogComponent, EntitySpawnerComponent, the camera/terrain/overlay components) it exposes through a static facade, so spawned entities and UI can reach the connection and catalogs without node-path walks. Its `UI` CanvasLayer holds the instanced `LobbyComponent`, which immediately shows the character-select and raises the menu `MainMenuPhantomCamera2D`'s priority to 60 so the menu camera owns the viewport while no player exists — see [[client/Scripts/Components/Lobby/LobbyComponent.cs#ShowLobby#1|ShowLobby]] (the camera handoff itself is camera-2). ^lobby-2

3. The lobby's idea of "you" is the `LocalLobbyPlayer` view — your `LoggedOutPlayer` row filtered to your identity ([[server/spacetimedb/src/player/views.rs#local_lobby_player#1|local_lobby_player]]) — which the `DatabaseConnector` already wired into `Username` at conn-3, while [[client/Scripts/Components/Catalog/CatalogComponent.cs|CatalogComponent]] caches the base-wave catalog rows from conn-5 behind `GetItem`/`GetEnchantment`/`GetResPath` so every later texture or item lookup is a dictionary read. ^lobby-3

4. The profile list is data-driven: `LobbyComponent`'s child `LocalPlayerProfiles` binder (insert-only, replaying) instantiates one `Scenes/profile_panel.tscn` per `PlayerProfile` row delivered by the [[server/spacetimedb/src/player/views.rs#local_player_profiles#1|local_player_profiles]] view, wiring each panel's Join/Delete buttons to that row — see [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnProfileRowInserted#1|OnProfileRowInserted]]. ^lobby-4

5. CREATE → [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnCreatePressed#1|OnCreatePressed]] calls the `CreateProfile` reducer, which [[server/spacetimedb/src/player/reducers.rs#create_profile#1|server-side]] guards on being in the lobby, caps profiles at three per identity, rejects duplicate names case-insensitively, and inserts a bare `PlayerProfile` row (no stats yet — those are scaffolded at join, join-2). The new row flows back through the binder from lobby-4 as another panel. ^lobby-5

6. A panel's DELETE calls the `DeleteProfile` reducer, which verifies ownership and then runs [[server/spacetimedb/src/player/methods.rs#teardown_profile#1|teardown_profile]] — the shared archetype cleanup that deletes the per-profile rows (data, stats, allocation, all inventory slots, position, chunk, active consumable effects — but not the `PlayerRotation` row, which dangles; see [[04 Lobby & Profiles#Known gaps / stubs]]) — before deleting the `PlayerProfile` row itself. The panel removal stays purely local (the binder ignores deletes), which is why the button also frees the panel node. ^lobby-6

7. XP and leveling have no lobby UI, but the math lives here conceptually: [[server/spacetimedb/src/player/methods.rs#xp_for_level#1|xp_for_level]] / [[server/spacetimedb/src/player/methods.rs#compute_level#1|compute_level]] (triangular 100·(n−1)·n/2 thresholds) and [[server/spacetimedb/src/player/methods.rs#compute_base_max_hp#1|compute_base_max_hp]] define what the profile's `PlayerData` row will mean once scaffolded. Details: [[04 Lobby & Profiles]]. ^lobby-7

# Joining the World

1. Pressing a profile panel's **Join** runs [[client/Scripts/Components/Lobby/LobbyComponent.cs#OnJoinPressed#1|OnJoinPressed]], which hides the lobby, calls the `JoinWorld` reducer with the profile id, and immediately flips subscription waves — `SubscribeGame()` plus `UnsubscribeLobby()` on the TableSubscriber — so the client starts receiving world rows in parallel with the server processing the join. This is the step the whole "server is authoritative" pattern hinges on: the client *calls the reducer* and then only mirrors what comes back. ^join-1

2. Server-side, [[server/spacetimedb/src/player/reducers.rs#join_world#1|join_world]] guards `require_in_lobby` + profile ownership, moves the identity row from `LoggedOutPlayer` to `LoggedInPlayer` (now carrying the chosen `profile_id`), then runs the archetype helper [[server/spacetimedb/src/player/methods.rs#try_scaffold_profile#1|try_scaffold_profile]]: first join only, it inserts the `PlayerData` row (level 1, full hp), the 38 `PlayerInventorySlot` rows (weapon 0 = Bow, hotbar 1–4 with Bread at 1, accessory 5 = Hat, armor 6 = Helmet, general 7–30, bag 31 = Bag, ability 32–37 with the Skull and 3-slot Tome of Mending pre-placed as spans), the zeroed `PlayerStatAllocation`, resolved `PlayerStats` via `recompute_stats`, and the position/rotation/chunk rows at world origin. One helper per entity = the server-side mirror of the client's component tree. ^join-2

3. The game wave from join-1 subscribes the 19 game tables ([[client/sstdbsdk/TableSubscriber.cs#GameTables#1|GameTables]]): per-caller views (`LocalPlayer*`) plus the AOI views (`NearbyRemotePlayers`, `NearbyEnemies`, `NearbyLootDrops`, `NearbyTerrainTiles`, `NearbyHexDecor`, …). Every AOI view keys off `PlayerChunk` through [[server/spacetimedb/src/player/views.rs#nearby_indices_from_chunk#1|nearby_indices_from_chunk]] — a row written only on real chunk crossings, so the views recompute per crossing instead of per movement report. ^join-3

4. The `LocalPlayer` view row (your `LoggedInPlayer` row, [[server/spacetimedb/src/player/views.rs#local_player#1|local_player]]) hits `EntitySpawnerComponent`'s replaying `LocalPlayerBinder`, and [[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerInsert#1|OnLocalPlayerInsert]] instantiates `Scenes/local_player.tscn` under the scene root — the only client-side "you exist in the world" signal, and the reason death/leaving (which deletes that row) is what returns you to the lobby (end-3). ^join-4

5. The new `LocalPlayer` entity's `_Ready` does three presentation registrations: it hands its child `LocalPlayerPhantomCamera2D` to [[client/Scripts/Components/Camera/Camera2DPresenterComponent.cs#RegisterCamera#1|RegisterCamera]] (priority 60 — the gameplay camera takes over from the menu pcam of lobby-2), creates a [[client/Scripts/Players/CharacterModel3D.cs#CharacterModel3D#1|CharacterModel3D]] mirror of itself inside the 3D backdrop viewport and makes it the 3D camera's follow target, and caches the scene-level camera components for per-frame reads — see [[client/Scripts/Players/Local/LocalPlayer.cs#_Ready#1|LocalPlayer._Ready]]. ^join-5

6. Its server-state components initialize from replayed rows through their binders (wired in `local_player.tscn`): the first `LocalPlayerPosition` row snaps the spawn position in [[client/Scripts/Components/Movement/PositionSyncComponent.cs#OnPositionRowInserted#1|OnPositionRowInserted]]; `LocalPlayerData`/`LocalPlayerStats`/`LocalPlayerStatAllocation` rows flow through [[client/Scripts/Components/Data/LocalPlayerDataComponent.cs#OnDataRow#1|LocalPlayerDataComponent]] into the `HealthComponent`/`StatsComponent` mirrors; `LocalPlayerInventory` rows build the slot dictionary in [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#OnInventoryRow#1|LocalPlayerInventoryComponent]]; and the active profile row sets name/sprite via [[client/Scripts/Components/Visual/LocalPlayerProfileComponent.cs#OnProfileRowInserted#1|LocalPlayerProfileComponent]]. Mirroring only — none of these components ever write the values back locally. ^join-6

7. The same spawner turns AOI inserts into the rest of the cast: `NearbyRemotePlayers` → `RemotePlayer` puppets, `NearbyEnemies` → `Enemy` puppets, `NearbyLootDrops` → `Drop` nodes, each tracked in an id-keyed dictionary with a matching delete path — see [[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnEnemyInsert#1|OnEnemyInsert]] and siblings. Deletes arrive when rows leave your AOI or the entity dies, so the visible world always equals the subscribed row set. ^join-7

8. Profile *visuals* for remote players come from the `NearbyRemotePlayersProfiles` view, read once per puppet in [[client/Scripts/Players/Remote/RemotePlayer.cs#_Ready#1|RemotePlayer._Ready]] to pick the sprite. *Known gap:* despite the name, [[server/spacetimedb/src/player/views.rs#nearby_remote_players_profiles#1|nearby_remote_players_profiles]] is **not** AOI-filtered — it semijoins the profiles of *all* logged-in players (contrast `nearby_remote_players`, which OR-chains the AOI chunk indices first), so every client caches every online player's profile row. Details: [[05 Joining the World]], [[06 Movement & Position Sync]]. ^join-8

# Movement & Position Sync

1. Locally, movement is plain client-side physics: [[client/Scripts/Players/Local/LocalPlayer.cs#_PhysicsProcess#1|LocalPlayer._PhysicsProcess]] reads the WASD input vector, rotates it by the camera rig's yaw (so "up" is screen-up even when the camera is turned), scales it by `PositionSyncComponent.CurrentSpeed` (the server-resolved `BaseSpeed` × the player's persistent Ctrl+scroll speed scale × the 0.4 hold-R self-slow), and integrates with `MoveAndSlide`. The server is not in the input loop — it only receives reports. ^move-1

2. [[client/Scripts/Components/Movement/PositionSyncComponent.cs#ReportNow#1|PositionSyncComponent]] reports that actual movement as an **angle + scalar speed** (zero when idle, last direction retained) — never an invented velocity, which caused the old constant-drift bug on puppets. Reports fire on a timer (`ReportInterval`, 0.1 s default but overridden to 1.0 s in `local_player.tscn`, so timed reports are 1 Hz) *plus* immediately on movement-key press/release edges and speed-setting changes, so starts/stops reach remotes without waiting for the tick. ^move-2

3. The server [[server/spacetimedb/src/player/reducers.rs#report_movement#1|report_movement]] reducer canonicalizes the position through [[server/spacetimedb/src/world/wrap.rs#wrap_world_pos#1|wrap_world_pos]] (the continuous world is a torus), recomputes the chunk via [[server/spacetimedb/src/world/hex.rs#world_to_chunk#1|world_to_chunk]] + [[server/spacetimedb/src/world/hex.rs#spiral_chunk_index#1|spiral_chunk_index]] (a bijective hex-spiral chunk id), clamps the reported speed to the resolved `PlayerData.base_speed` (gear can raise it; anything above is a cheat or bug), and updates `PlayerPosition`. The `PlayerChunk` row is rewritten **only when the chunk actually changed** — that row exists precisely so the AOI views of join-3 recompute on crossings rather than on every report. ^move-3

4. Facing streams on its own faster cadence because camera rotation needs it: a ~30 Hz timer (`RotationReportInterval` 0.033 s) fires `ReportScreenRotation` only when the facing changed beyond an epsilon, updating the separate `PlayerRotation` table — split out of `PlayerPosition` so rotation doesn't ride the slower movement cadence — with `chunk_index` mirrored from the position row so the AOI view filters identically. See [[client/Scripts/Components/Movement/PositionSyncComponent.cs#_PhysicsProcess#1|_PhysicsProcess]] and [[server/spacetimedb/src/player/reducers.rs#report_screen_rotation#1|report_screen_rotation]]. ^move-4

5. Remote puppets consume those rows through binders wired in `non_local_player.tscn`: [[client/Scripts/Players/Remote/RemotePlayer.cs#OnPositionRowUpdated#1|OnPositionRowUpdated]] reconstructs velocity = direction × speed and hands position+velocity to [[client/Scripts/Components/Movement/InterpolationComponent.cs#SetTarget#1|InterpolationComponent.SetTarget]], which each frame extrapolates the target by velocity × time-since-update (**dead reckoning**) and lerps toward it; rotation rows go to [[client/Scripts/Components/Movement/InterpolationComponent.cs#SetScreenRotationTarget#1|SetScreenRotationTarget]] and lerp separately. ^move-5

6. Your own position row echo is *not* authoritative for your local position: [[client/Scripts/Components/Movement/PositionSyncComponent.cs#OnPositionRowUpdated#1|OnPositionRowUpdated]] keeps the local frame continuous and unbounded, and only hard-corrects when even the nearest wrapped copy of the server position is farther than `WrapSnapThreshold` (50 units) — i.e. a real desync, not a routine torus wrap. The same nearest-candidate trick drives `InterpolationComponent`'s smooth lerps and `RemotePlayer`'s snap-on-teleport (`WrapSnapThreshold = 50` in `non_local_player.tscn`). ^move-6

7. All wrap math on the client goes through [[client/Scripts/World/TorusMath.cs#NearestCandidate#1|TorusMath.NearestCandidate]]: a stored canonical position has infinitely many equivalent copies on the torus, and the one nearest a reference point (camera, puppet) is picked using the `LapQ`/`LapR` vectors the TableSubscriber mirrored from the `MapConfig` row of boot-3. The server mirrors the same 9-candidate check in [[server/spacetimedb/src/world/wrap.rs#wrapped_distance_sq#1|wrapped_distance_sq]] wherever it compares distances across a seam. Details: [[06 Movement & Position Sync]]. ^move-7

# Terrain & World Streaming

1. The visible world is the `TriangleTile` + `HexDecor` rows generated at boot-4: each hex is six triangular wedges (ground texture + rotation, optional overlay), and at most one decor prop per hex. Generation is a deterministic pipeline in [[server/spacetimedb/src/world/terrain/mod.rs#run_generation#1|run_generation]] — Voronoi biome/region bucketing ([[server/spacetimedb/src/world/terrain/voronoi.rs#group_cells_by_seeds#1|group_cells_by_seeds]]), then per wedge a noise-clustered ground pick with adjacency-conflict retry ([[server/spacetimedb/src/world/terrain/ground.rs#choose_ground#1|choose_ground]]), an overlay pick gated by the `LayeringRule` allow-list ([[server/spacetimedb/src/world/terrain/overlay.rs#choose_overlay#1|choose_overlay]]), and a decor roll gated by separation + `DecorGroundRule` deny-lists ([[server/spacetimedb/src/world/terrain/decor.rs#place_decor#1|place_decor]]). ^terrain-1

2. The client learns the grid from the `MapConfig` row (boot-3): `TableSubscriber` lifts its lap vectors for the wrap math of move-7, and `TerrainComponent`'s own `MapConfigBinder` updates the hex outer radius and invalidates every cached mesh via [[client/Scripts/Components/Terrain/TerrainComponent.cs#OnMapConfigRow#1|OnMapConfigRow]] → `InvalidateMeshes` — a dev-time path, since the radius only changes when chunks are re-added. ^terrain-2

3. Terrain streams by AOI like everything else: the [[server/spacetimedb/src/world/views.rs#nearby_terrain_tiles#1|nearby_terrain_tiles]] and [[server/spacetimedb/src/world/views.rs#nearby_hex_decor#1|nearby_hex_decor]] views filter rows to the chunk ring around the caller's `PlayerChunk` (`DEFAULT_TERRAIN_AOI_CHUNK_RADIUS` = 2), so crossing a chunk boundary (move-3) silently inserts the new ring's rows and deletes the old on every client. ^terrain-3

4. Client-side, [[client/Scripts/Components/Terrain/TerrainComponent.cs|TerrainComponent]] (declared inline in `game.tscn` with three child binders) stores every row by id and by hex, and its callbacks only set a dirty flag — the actual rebuild happens once per frame in `_Process`, so a whole chunk-crossing burst of inserts/deletes collapses into a single [[client/Scripts/Components/Terrain/TerrainComponent.cs#RebuildVisibleInstances#1|RebuildVisibleInstances]] pass. ^terrain-4

5. That pass wraps every cached hex center to its camera-nearest copy (`TorusMath.NearestCandidate`, because chunks near a seam are stored at far-away canonical positions), culls to the camera window, and groups surviving instances per chunk per batch key — wedges by `(TriIndex, Rotation, TextureId)`, decor by texture — then hands each present chunk's batches to a pooled `TileComponent`, pre-warmed to the AOI ring count (`1+3R(R+1)` = 19 at radius 2) so the first subscription burst doesn't hitch. ^terrain-5

6. Each [[client/Scripts/Components/Terrain/TileComponent.cs#Populate#1|TileComponent]] (one per visible chunk, from `tile_component.tscn`) distributes its chunk's batches into four declared layers — `GroundComponent` (z=0), `OverlayComponent` (z=1, instances centroid-scaled so a small overlay stays centered in its wedge), `DecorShadowComponent` (z=2), `DecorComponent` (z=3) — each layer pooling `MultiMeshInstance2D` leaves per batch key, with meshes and textures shared across chunks from `TerrainComponent`'s caches because wedge geometry depends only on the batch key. Inactive leaves are zeroed, not freed; a chunk leaving the AOI parks its tile via `Clear()`. ^terrain-6

7. The hex/chunk math exists in three places that must stay in lockstep: the server's [[server/spacetimedb/src/world/hex.rs#spiral_chunk_index#1|spiral_chunk_index]] (built on the `hexx` crate's hex-of-hexes resolution change) and the `HexSpiralIndex` duplicated inside both [[client/Scripts/Components/Camera/HexGridOverlayComponent.cs#HexSpiralIndex#1|HexGridOverlayComponent]] and its 3D sibling. *Stale comments:* `hex.rs` still points at a `hex_grid_overlay.gd` and a `TerrainManager.cs` that no longer exist — the client is C#-only and the old `TerrainManager` class was replaced by `TerrainComponent`. ^terrain-7

8. The only player-facing world mutation is building placement: [[server/spacetimedb/src/world/reducers.rs#place_building#1|place_building]] / [[server/spacetimedb/src/world/reducers.rs#remove_building#1|remove_building]] write `building_type`/`owner_id` onto the `BuildingTile` rows created in boot-3 (removal requires ownership or admin). *Known gap:* no client UI calls these reducers today, and nothing renders `BuildingTile` rows — base-building beyond this pair is an aspirational system. Details: [[07 Terrain & World Streaming]]. ^terrain-8

# Enemies & AI

1. Enemies are content, not code: each `EnemyTemplate` row (seeded at boot-2 by [[server/spacetimedb/src/main/seeds.rs#seed_default_enemies#1|seed_default_enemies]] via the [[server/spacetimedb/src/main/seeds.rs#make_phase#1|make_phase]]/`seq_single`/`seq_repeat`/`seq_multi` helpers, which insert the shared `MovementDef`/`SingleStepDef`/`RepeatStepDef`/`MultiStepDef` definition rows) declares max hp, flat defense, sim-range factors, and a `phases` list — each phase an hp threshold, a movement behavior, and attack sequences of bullet-pattern steps (`Ring`/`Volley`/`Curtain`/`Shotgun`/`Explosion` with parameter structs). Details: [[08 Enemies & AI]]. ^enemy-1

2. The 2-second spawn tick ([[server/spacetimedb/src/enemy/reducers.rs#tick_enemy_spawn#1|tick_enemy_spawn]] → [[server/spacetimedb/src/enemy/methods.rs#spawn_from_biome_regions#1|spawn_from_biome_regions]]) walks every `BiomeRegion` (boot-4), skips regions with no player near their center (lookahead rings, with a `logged_in_player` check so ghosts don't hold a region open — end-4), counts live region enemies with wrap-aware distance against `max_enemies`, then picks a template by a time-rotating index (`(region_id ^ (micros / 1_000_000)) % template_count`, not a PRNG draw) and a uniform-disc spawn point from a deterministic SplitMix64 draw and calls [[server/spacetimedb/src/enemy/methods.rs#spawn_enemy_archetype#1|spawn_enemy_archetype]]. ^enemy-2

3. `spawn_enemy_archetype` builds the enemy's server-side component tree: [[server/spacetimedb/src/enemy/methods.rs#build_enemy_behavior#1|build_enemy_behavior]] inserts the `EnemyBehavior` root row plus per-phase `EnemyPhase` → `EnemyAttack` → `EnemySequenceStep` rows (each `Repeat` step getting its own `RepeatStepInstance` copy of the shared def so repeat counts advance per enemy), and the flat `Enemy` row (position/hp/phase) points at it by `behavior_id`. [[server/spacetimedb/src/enemy/methods.rs#despawn_enemy_archetype#1|despawn_enemy_archetype]] deletes the whole tree, so no orphan rows outlive the entity. ^enemy-3

4. The 100 ms behavior tick ([[server/spacetimedb/src/enemy/reducers.rs#tick_enemy_behavior#1|tick_enemy_behavior]]) simulates each enemy only while a player is within `move_sim_factor × CAMERA_VIEW_RADIUS` ([[server/spacetimedb/src/enemy/methods.rs#has_player_in_simulation_range#1|has_player_in_simulation_range]] — again ghost-guarded), retargeting aggro onto the nearest player only on the tick an enemy *enters* range ([[server/spacetimedb/src/enemy/methods.rs#recompute_aggro#1|recompute_aggro]], locked for `aggro_lock_seconds`) so mid-fight enemies aren't re-aggroed every 100 ms. ^enemy-4

5. While a player is inside the tighter `attack_sim_factor` range, the tick advances the phase's attack sequences — [[server/spacetimedb/src/enemy/methods.rs#tick_phase#1|tick_phase]] → [[server/spacetimedb/src/enemy/methods.rs#tick_sequence#1|tick_sequence]] persists step progress on the `EnemyAttack` rows between ticks, firing Single/Multi steps once (Multi = all shots at once, tagged by shot index) and Repeat steps on their interval until their target count — and each fired step inserts a `BulletPatternEvent` row (an append-only event table) carrying the pattern, origin, target, texture, lifetime, and the `SequenceStepRef` that later identifies its damage on hit (combat-5). The two-tier range means enemies approach from off-screen but never shoot from off-screen. ^enemy-5

6. Movement runs every simulating tick through [[server/spacetimedb/src/enemy/methods.rs#apply_movement#1|apply_movement]] (Stationary/Wander/Chase/Flee with deterministic Wander directions from `hash_to_unit(splitmix64(enemy_id + cycle))`, so paths are reproducible without stored state), wraps the new position onto the torus, recomputes its chunk, and updates the `Enemy` row — which is the whole "network protocol": the `NearbyEnemies` view ([[server/spacetimedb/src/enemy/views.rs#nearby_enemies#1|nearby_enemies]], AOI-filtered like join-3) pushes that row to clients ~10×/s. ^enemy-6

7. Each `NearbyEnemies` insert spawns a `default_enemy.tscn` puppet (join-7) whose [[client/Scripts/Players/Enemies/Enemy.cs#OnEnemyRowInserted#1|OnEnemyRowInserted]] snaps position, loads the template's SpriteFrames, and seeds the `HealthComponent`/`StatsComponent` mirrors (max hp from the cached `EnemyTemplate`, hp from the row); updates just retarget the [[client/Scripts/Components/Movement/InterpolationComponent.cs|InterpolationComponent]] lerp and refresh hp/phase. Its second binder filters `BulletPatternEvent` rows to its own `enemy_id` and forwards them to [[client/Scripts/Game/BulletManager.cs#SpawnEnemyBullet#1|BulletManager.SpawnEnemyBullet]]. ^enemy-7

8. [[client/Scripts/Components/Bullets/BulletSpawnerComponent.cs#SpawnEnemyBullet#1|BulletSpawnerComponent]] dispatches on `PatternType` and spawns through the BlastBullets2D factory node via **untyped `Call(…)`** (a GDExtension — no compile-time checking, so typos surface only at runtime): Ring/Curtain as one multi-bullet `DirectionalBullets2D` instance, Volley/Shotgun/Explosion as per-pellet instances whose speed/angle/lifetime jitter comes from a SplitMix64 hash seeded by `event_id` ([[client/Scripts/Components/Bullets/BulletSpawnerComponent.cs#Jitter#1|Jitter]]) so every client derives identical trajectories. Each `spawn_controllable_directional_bullets` instance is tracked in `LiveEnemyBullets` (the factory can't enumerate actives) with defensive pruning, because the bullet-control abilities of combat-9 need to find live bullets later. ^enemy-8

# Combat & Damage

1. The local player's weapon is resolved, not read: [[client/Scripts/Components/Weapon/CombatComponent.cs#OnInventoryChanged#1|CombatComponent]] re-resolves its `EffectiveWeapon` via [[client/Scripts/Components/Weapon/EffectiveWeaponResolver.cs#Resolve#1|EffectiveWeaponResolver]] whenever the resolver's fingerprint (weapon item, active toggle, every equipped slot's enchantments) changes — the exact client mirror of the server's [[server/spacetimedb/src/player/methods.rs#resolve_effective_weapon#1|resolve_effective_weapon]], including fold order (slot index ascending, innate before socketed), because both sides index the same toggle-option list. Holding `fire` then runs the pattern (Single/Triple/Cluster) at the weapon's fire rate, spawning player bullets through `BulletManager` and a fuse of `HitZone`s along each bullet's path via [[client/Scripts/Components/Weapon/CombatComponent.cs#SpawnZonesAlong#1|SpawnZonesAlong]]. ^combat-1

2. Each [[client/Scripts/Components/Combat/HitZone.cs#OnLifetimeTimeout#1|HitZone]] (a `DamageComponent` with a lifetime fuse) wakes at its scheduled delay and calls [[client/Scripts/Components/Combat/DamageComponent.cs#ReportHits#1|ReportHits]], which finds overlapping `DamageReceivingComponent` hurtboxes, filters them by faction opposition ([[client/Scripts/Components/Combat/FactionComponent.cs#CheckOpposition#1|CheckOpposition]] — no shared flag, so Players vs Enemies), and for each enemy victim calls the `ReportEnemyHit` reducer with just the enemy id. The client never computes or applies damage — it reports, and the mirror updates later (combat-7). ^combat-2

3. [[server/spacetimedb/src/enemy/reducers.rs#report_enemy_hit#1|report_enemy_hit]] (immortal/missing enemies silently ignored) delegates to [[server/spacetimedb/src/combat/mod.rs#deal_damage_to_enemy#1|deal_damage_to_enemy]] — one of only two damage entry points, both in `combat/mod.rs`. [[server/spacetimedb/src/combat/mod.rs#compute_player_damage#1|compute_player_damage]] re-derives the attacker's effective weapon server-side and computes per-bullet damage: `raw = damage × (1 + strength×0.002) / shot_count`, then `max(raw + flat_bullet_mod − defense, 1)` — the `FlatBulletDamageMod` enchantment's flat mod and the template's **flat** defense both land before the minimum-1 clamp (what makes many-weak-bullets trade against few-strong-bullets) — and finally the true-damage bonuses (`+ true_flat + raw × true_pct`) applied after defense. ^combat-3

4. A kill runs `despawn_enemy_archetype` (enemy-3) and awards `max_hp/10` XP through [[server/spacetimedb/src/player/methods.rs#internal_gain_xp#1|internal_gain_xp]], which recomputes level from the triangular thresholds, heals `HP_PER_LEVEL` per level gained (partial heal, not full), grants `SKILL_POINTS_PER_LEVEL` unspent points per level into the allocation row, and re-resolves stats. A survival recomputes the phase from hp thresholds ([[server/spacetimedb/src/enemy/methods.rs#compute_phase#1|compute_phase]]): on a phase change `deal_damage_to_enemy` re-runs `recompute_aggro`, which targets the *nearest* player (not necessarily the attacker); with no phase change the enemy re-aggros onto the attacker only once `aggro_locked_until` has expired. The phase change is picked up by the next behavior tick, which resets the new phase's attack cycle (`begin_phase_cycle`). *Note:* no loot drops from kills today — `LootDrop` rows come only from `drop_item` (loot-1). ^combat-4

5. Incoming fire works by event identity: every enemy bullet carries its spawner event's `SequenceStepRef` in its custom data ([[client/Scripts/Game/BulletData.cs|BulletData]]), and when the BlastBullets plugin reports an overlap, [[client/Scripts/Components/Bullets/BulletHitRouterComponent.cs#OnEnemyBulletAreaEntered#1|BulletHitRouterComponent]] routes it by what was hit — the local player's `DamageReceivingComponent` → [[client/Scripts/Components/Combat/DamageReceivingComponent.cs#ProcessBulletHit#1|ProcessBulletHit]] → `ReportHit(sourceStep)`, a remote puppet's `RemoteHitWitnessComponent` → the witness path (combat-8), or anything else on the player layer → `ReportHit` directly. ^combat-5

6. The server [[server/spacetimedb/src/player/reducers.rs#report_hit#1|report_hit]] resolves base damage by looking the `SequenceStepRef` back up in the step tables (`SingleStepDef.damage`, the per-enemy `RepeatStepInstance.damage`, or the indexed shot of a `MultiStepDef`) — damage identity travels with the event, so clients can't name a number — then [[server/spacetimedb/src/combat/mod.rs#deal_damage_to_player#1|deal_damage_to_player]] applies [[server/spacetimedb/src/combat/mod.rs#compute_incoming_damage#1|compute_incoming_damage]] (flat `PlayerData.defense`, minimum 1) and subtracts. At zero hp it runs the full death cleanup: `teardown_profile` drops the profile's rows and the player is moved back to `LoggedOutPlayer` — death *is* the lobby round-trip (end-2). Healing is the same file's [[server/spacetimedb/src/combat/mod.rs#heal_player#1|heal_player]], clamped to max hp. ^combat-6

7. Health changes reach every screen as row updates, never as local mutation: your `LocalPlayerData` row flows through `LocalPlayerDataComponent` into [[client/Scripts/Components/Combat/HealthComponent.cs#SetFromServer#1|HealthComponent.SetFromServer]] (emitting decrease/increase/zero signals for observers), enemy hp rides `NearbyEnemies` updates into `Enemy.OnEnemyRowUpdated`, and `StatsComponent` exposes both through comedot's shared-Stat pattern (the same `Stat` instance listed under `StatKind.Hp`). ^combat-7

8. Other players' hits are corroborated, not trusted: every remote puppet carries a [[client/Scripts/Components/Combat/RemoteHitWitnessComponent.cs|RemoteHitWitnessComponent]] hurtbox on the bullet collision layer, so enemy bullets physically collide with other players on *every* client — the plugin's own collision counting despawns the bullet consistently — and the witness forwards the overlap to the `FlagPlayerHit` reducer, which records a server-only `PlayerHitFlag` row ([[server/spacetimedb/src/anticheat/reducers.rs#flag_player_hit#1|flag_player_hit]], self-reports silently dropped) the server can check against the victim's own `report_hit`. ^combat-8

9. Bullet-control abilities are casts relayed as data: [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#TryActivateAbility#1|TryActivateAbility]] applies the effect optimistically on the caster and calls `activate_ability`, which server-side clamps the cursor target to `MAX_ABILITY_TARGET_RANGE` around the authoritative position row and appends a `BulletControlEvent` ([[server/spacetimedb/src/player/reducers.rs#activate_ability#1|activate_ability]] — the server tracks no live bullets). Every *other* client's [[client/Scripts/Components/Bullets/BulletControllerComponent.cs#OnBulletControlEventRow#1|BulletControllerComponent]] applies the same Delete/Split/Attract/Slash proximity query over its own `LiveEnemyBullets` on row insert (own echoes skipped via `cast_by`), so edge-of-radius results can legitimately differ per client; Slash encodes its rectangle as origin + far end + width and every client draws the same black slash flash, so the visual replicates with the cast. *Known gap:* `combat/mod.rs`'s comment still cites a deleted `src/plan.md` design (a `BulletDespawnEvent`/`slash_bullet` protocol) that was never built — the implemented protocol is this event table + `control_bullets`, and `report_hit` still takes the single `SequenceStepRef` arg; the `PlayerDamageOutcome`/`EnemyDamageOutcome` enums are `#[allow(dead_code)]` because both callers discard them. Details: [[09 Combat & Damage]]. ^combat-9

# Inventory, Items & Enchantments

1. Everything wearable is a row in the unified `Item` catalog table — no per-type side tables: `equip_slot` says only *where* an item goes while `stat_modifiers` + `behaviors` say *what it does* (that's what makes "an accessory that fires projectiles" expressible), and `Enchantment` rows add socketable or innate (`innate_enchantment_ids` — always on, unremovable, socket-free) modifiers/behaviors. The client caches both catalogs plus textures from the base wave (conn-5) in [[client/Scripts/Components/Catalog/CatalogComponent.cs|CatalogComponent]]; the server seeds them from [[server/spacetimedb/src/item/seeds.rs#seed_world_items#1|seed_world_items]] / [[server/spacetimedb/src/item/seeds.rs#seed_world_enchantments#1|seed_world_enchantments]] at boot-2. Details: [[10 Inventory, Items & Enchantments]]. ^equip-1

2. Inventory state is one `PlayerInventorySlot` row per slot (not a list on one row), delivered by the `LocalPlayerInventory` view into [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs|LocalPlayerInventoryComponent]]'s per-slot dictionary, with the slot indices load-bearing on both sides: 0 weapon, 1–4 hotbar consumables, 5 accessory, 6 armor, 7–30 general backpack, 31 bag, 32–37 ability. Multi-slot ability items occupy a contiguous **span**: the head row holds the item, followers are marked `occupied_by`, and `slot_cost` only applies inside the ability region (loose backpack ability items sit in one cell). ^equip-2

3. Stats resolve in exactly one place, server-side: [[server/spacetimedb/src/player/methods.rs#recompute_stats#1|recompute_stats]] folds allocated points, every stat modifier from equipped heads (Weapon/Accessory/Armor at scale 1.0, ability heads scaled by `ABILITY_POSITION_MULTIPLIERS` — first ability stronger), innate *and* socketed enchantments, and active consumable buffs into per-`StatKind` flat/mult accumulators (mults additive, not compounding) and resolves `(base + flat) × (1 + mult)` into `PlayerStats` plus the modifier-only kinds onto `PlayerData` (Hp→max_hp, Defense→defense, BaseSpeed→base_speed). Every mutation below ends by calling it. The mirrors land in the components of join-6 and surface in [[client/Scripts/Components/Inventory/StatsSidebarComponent.cs|StatsSidebarComponent]], whose `+` buttons (visible only with unspent points) call `AllocateStat` — which rejects the modifier-only kinds. ^equip-3

4. Drag/drop between slots calls the `SwapSlots` reducer from [[client/Scripts/Components/Inventory/SlotComponent.cs#_DropData#1|SlotComponent._DropData]]; [[server/spacetimedb/src/player/reducers.rs#swap_slots#1|server-side]] it enforces `slot_allowed` role acceptance (General accepts everything), gates any item entering an equipped role from loose storage on `check_stat_requirements`, and handles spans region-based: entering/leaving the ability region re-places or clears the whole span (contiguous free cells required, source cells count as freed, runtime state travels, backpack→ability re-initializes charges), while swaps outside the region are plain single-cell swaps even for ability items. The updated rows raise `InventoryChanged` on the `LocalPlayer` entity, and [[client/Scripts/Components/Inventory/InventoryComponent.cs#OnInventoryChanged#1|InventoryComponent]] refreshes every slot icon (followers dimmed, on-cooldown dimmed). ^equip-4

5. The weapon's shot-pattern toggle (T) cycles through [[client/Scripts/Components/Weapon/CombatComponent.cs#CycleWeaponToggle#1|CycleWeaponToggle]] → `SetSlotToggle`, validated server-side by the `set_slot_toggle` reducer against the same toggle-option list (`weapon_toggle_options` — the item's own Weapon behaviors plus `WeaponToggle` enchantment grants) that both resolvers index — and the reducer *rejects* an out-of-range index (`value >= count` errors). The lenient half lives in the resolvers instead: `resolve_effective_weapon` server-side and `EffectiveWeaponResolver.Resolve` client-side both clamp the stored index (`min(active_toggle, len − 1)`) rather than erroring, because removing a toggle-granting enchantment can leave the stored index dangling. The updated slot row changes the resolver fingerprint, which re-resolves the firing weapon from combat-1. ^equip-5

6. Hovering a slot opens [[client/Scripts/Components/Inventory/ItemSidebarComponent.cs#ShowSlot#1|ItemSidebarComponent]], which renders the item's full composition — stat modifiers, requirements (red when unmet), behavior summary (the equipped weapon lists its toggle patterns with the active marked), innate enchantments, and socketed `N / MaxEnchantments` — and, for enchantable items in equipment slots, lists applicable enchantments with Socket/Remove buttons calling `ApplyEnchantment`/`RemoveEnchantment`; server-side those check `allowed_slots`, capacity, and duplicates before rewriting the slot row's `enchantment_ids` and recomputing stats. ^equip-6

7. Hotbar keys 1–4 call `UseItem` ([[client/Scripts/Components/Inventory/InventoryComponent.cs#_Process#1|InventoryComponent._Process]]), which guards on the item *having a Consumable behavior* (not on its equip slot), applies it through [[server/spacetimedb/src/player/methods.rs#apply_consumable_effect#1|apply_consumable_effect]] — heals delegate to `combat::heal_player`, buffs insert an `ActiveConsumableEffect` row — consumes the item, and recomputes; the 1-second scheduled [[server/spacetimedb/src/player/reducers.rs#tick_active_consumable_effects#1|tick_active_consumable_effects]] decrements `remaining` and deletes expired rows, triggering a final recompute so buffs wear off on their own. ^equip-7

8. Ability keys (or left-clicking an ability slot) go through [[client/Scripts/Components/Inventory/LocalPlayerInventoryComponent.cs#TryActivateAbility#1|TryActivateAbility]] (follow span followers to the head, pre-check cooldown/charges, passive items no-op) → `activate_ability`, which scales potency by the span head's position multiplier, routes Heal/Buff through the same consumable path as equip-7, relays bullet-control effects as the `BulletControlEvent` of combat-9, fires any equipped `OnAbilityUseBuff` enchantment triggers, and writes cooldown + decremented charges onto the slot row **without consuming the item**. Its mirrored `AbilityPositionMultipliers` constant must change in lockstep with the server's `ABILITY_POSITION_MULTIPLIERS`. ^equip-8

1. Drops enter the world through [[server/spacetimedb/src/player/reducers.rs#drop_item#1|drop_item]] (right-click in the backpack, from [[client/Scripts/Components/Inventory/SlotComponent.cs#_GuiInput#1|SlotComponent._GuiInput]]): the slot (or whole span, if a follower was dropped) is cleared and a `LootDrop` row is inserted at the player's server-side position with `dropped_by` set. *Known gap:* `expires_at` is written (`LOOT_DROP_EXPIRY` = 300 s) but never enforced — no expiry sweeper exists and the constant is referenced nowhere else. ^loot-1

2. The AOI-filtered `NearbyLootDrops` view inserts spawn `drop.tscn` nodes (join-7): [[client/Scripts/Items/Drop.cs|Drop]] glue mirrors the row into [[client/Scripts/Components/Visual/DropVisualComponent.cs#SetItem#1|DropVisualComponent]] (item texture via the catalog) and [[client/Scripts/Components/Interaction/PickupComponent.cs#SetFromServer#1|PickupComponent]], which starts its pickup-lock timer when the local player was the dropper — so you can't instantly re-grab your own toss. ^loot-2

3. When the local player walks into an unlocked drop, [[client/Scripts/Components/Interaction/PickupComponent.cs#OnBodyEntered#1|OnBodyEntered]] calls `PickupDrop`; server-side, multi-slot ability items auto-equip into the first free span *if stat requirements pass* (else they fall back to loose backpack storage), everything else prefers a matching typed slot (requirements-checked) then any general cell, and the `LootDrop` row is deleted — which propagates as a delete that despawns the node on every client (loot-2's path in reverse). ^loot-3

# Camera & Presentation

1. One rig, two presenters: [[client/Scripts/Components/Camera/CameraRigComponent.cs|CameraRigComponent]] (a child of the `game.tscn` root, deliberately *not* inside the 3D SubViewport, because mouse-motion input never reaches nodes in there) owns the canonical yaw/pitch/distance and handles every camera input — Q/E yaw, scroll zoom, arcball drag, cursor-relative snap rotates, resets. It writes nothing else; both presenters read it each frame, so 2D and 3D can never disagree. ^camera-1

2. The 2D presenter, [[client/Scripts/Components/Camera/Camera2DPresenterComponent.cs#_Process#1|Camera2DPresenterComponent]], writes the rig's yaw/derived zoom into the local player's PhantomCamera2D every frame; camera *authority* is a priority handoff — the menu pcam sits at 60 while the lobby is up (lobby-2), the player's pcam takes 60 at join-5 and drops back via `UnregisterCamera` when the player entity dies. The actual `MainCamera2D` + `PhantomCameraHost` live in `game.tscn`; `local_player.tscn` additionally carries a **disabled legacy `Camera2D`** child superseded by this setup (kept, not deleted). ^camera-2

3. The 3D backdrop is `world_3d.tscn` inside a `SubViewport` under `game.tscn`'s `3D` CanvasLayer: [[client/Scripts/Components/Camera/World3DComponent.cs#_Process#1|World3DComponent]] (the 3D presenter) drives its PhantomCamera3D spring arm from the same rig (negating yaw, because 2D rotation is clockwise in y-down space and 3D yaw about +Y is counter-clockwise), and each entity that opts in mirrors its 2D position/rotation into the viewport through a [[client/Scripts/Players/CharacterModel3D.cs#SyncFrom2D#1|CharacterModel3D]] (LocalPlayer's Knight, Enemy's skeleton). *Verified against the scene:* the `3D` CanvasLayer is currently `visible = false` in `game.tscn` (line ~105), so the backdrop is off in the shipped scene even though all its machinery runs. ^camera-3

4. Enemy bullets exist only in 2D (the BlastBullets factory renders into the 2D world), so [[client/Scripts/Components/Bullets/EnemyBullets3DComponent.cs#_Process#1|EnemyBullets3DComponent]] mirrors them into the 3D viewport each frame: it enumerates enabled bullets of every tracked `LiveEnemyBullets` instance (per-index `is_bullet_status_enabled`, because the bulk status array only ever reports index 0) and lays a pooled set of hex-bullet nodes over their transforms. ^camera-4

5. Debug rendering rides the same component model: [[client/Scripts/Components/Camera/HexGridOverlayComponent.cs#_Draw#1|HexGridOverlayComponent]] (2D chunk/hex grid with spiral indices, **declared `visible = false` in `game.tscn` but still subscribed** through its MapConfig binder — known waste) and [[client/Scripts/Components/Camera/HexGridOverlay3DComponent.cs|HexGridOverlay3DComponent]] (3D tiles + per-hex labels around the player) both re-derive the server's hex math client-side, which is why `HexSpiralIndex` exists three times (terrain-7). ^camera-5

6. The camera reaches *into the simulation* through shared constants: `CLIENT_VIEWPORT_HEIGHT_PX` / `CLIENT_CAMERA_ZOOM` in [[server/spacetimedb/src/main/global.rs#CAMERA_VIEW_RADIUS#1|main/global.rs]] derive `CAMERA_VIEW_RADIUS`, and every enemy template's `move_sim_factor`/`attack_sim_factor` are multiples of it (enemy-4/enemy-5) — so changing the client camera zoom changes how far away enemies wake up and open fire, by design. ^camera-6

7. Character presentation is row-driven throughout: the local sprite comes from the active profile's `texture_id` (join-6), remote sprites from the profile view (join-8) with Walk/Idle driven by `InterpolationComponent.Moving` in [[client/Scripts/Components/Visual/RemoteVisualComponent.cs#_Process#1|RemoteVisualComponent]], enemies from their template (enemy-7), and drops from the item catalog (loot-2) — every one a `res://` path resolved through `CatalogComponent.GetResPath` from the seeded `TextureEntry` table. Details: [[11 Camera & Presentation]]. ^camera-7

4. The client debug HUD is [[client/Scripts/Game/DebugOverlay.cs|DebugOverlay]], declared inline in `game.tscn` (layer 100, hidden until the `toggle_debug_overlay` action flips it): every 0.25 s it redraws FPS/frame time/memory/node and draw-call counts from Godot's `Performance` monitors plus the live enemy count from the `GameManager` facade. The standalone `Scenes/UI/debug_overlay.tscn` is an unreferenced duplicate — one of seven stale component scenes that mirror wiring now declared inline in the live scenes (the full list lives in [[02 The Component Framework]]). ^admin-4

The server-side debug feed is opt-in: the admin-only [[server/spacetimedb/src/main/debug.rs#toggle_debug#1|toggle_debug]] inserts or deletes a `PlayerPositionDebugSchedule` row, and while scheduled, [[server/spacetimedb/src/main/debug.rs#tick_player_position_debug#1|tick_player_position_debug]] mirrors every `PlayerPosition` (+ rotation, chunk, hex coords) into the server-only `PlayerPositionDebug` table once a second, pruning rows for positions that no longer exist. *Known gap:* nothing in the client calls `toggle_debug` or reads the table — it's a CLI/`spacetime sql` tool. ^admin-5

6. Leftover debug prints are scattered through the client and documented per-doc as gaps: `GD.Print` DEBUG lines in `TableBinderComponent.Bind/HandleInsert` (→ [[03 Boot & Connection]]), `TerrainComponent._Ready/OnTileRowInserted` (→ [[07 Terrain & World Streaming]]), `EntitySpawnerComponent.OnDropInsert` (→ [[05 Joining the World]]), `LobbyComponent.OnProfileRowInserted` (→ [[04 Lobby & Profiles]]), the `[Desync]` print in `PositionSyncComponent` (→ [[06 Movement & Position Sync]]), and `Camera2DPresenterComponent.RegisterCamera` (→ [[11 Camera & Presentation]]). ^admin-6

7. Operationally, admin work is publish-driven: `server/build.sh` regenerates the C# bindings into `client/Scripts/module_bindings/` and publishes with `--delete-data` (hard cut, no migrations — boot-1..boot-4 re-run), and `spacetime logs bullethell` is the first place to look when a reducer misbehaves. Details: [[12 Admin & Debug]]. ^admin-7

# Disconnect & Teardown

1. Leaving the world voluntarily is the [[server/spacetimedb/src/player/reducers.rs#leave_world#1|leave_world]] reducer: delete the `LoggedInPlayer` row, insert a `LoggedOutPlayer` row, done — profile rows deliberately survive (you keep your character and its scaffolded inventory). *Known gap:* no client UI calls it today; the only in-game paths back to the lobby are death (combat-6) and disconnect. ^end-1

2. Death is the thorough teardown: `deal_damage_to_player` at zero hp runs [[server/spacetimedb/src/player/methods.rs#teardown_profile#1|teardown_profile]], the one shared table list that deletes the profile's data/stats/allocation/inventory-slot/position/chunk/consumable-effect rows (used by both combat death and `delete_profile` at lobby-6), then moves the identity to `LoggedOutPlayer` — the `PlayerProfile` row itself survives death so you can re-join and re-scaffold. *Known gap found while writing this:* `teardown_profile` does **not** delete the `PlayerRotation` row, so a rotation ghost outlives even full teardown. ^end-2

3. The client notices *any* of these exits the same way: the `LocalPlayer` view row disappears, and [[client/Scripts/Components/Spawning/EntitySpawnerComponent.cs#OnLocalPlayerDelete#1|EntitySpawnerComponent.OnLocalPlayerDelete]] frees the player entity, re-shows the lobby (restoring the menu camera of lobby-2), and flips subscriptions back — `SubscribeLobby()` + `UnsubscribeGame()` — returning the client to the exact state of lobby-2. ^end-3

4. Disconnecting (or dying while offline matters here too) is gentler: [[server/spacetimedb/src/main/lifecycle.rs#client_disconnected#1|client_disconnected]] only moves the identity row to `LoggedOutPlayer`, leaving `PlayerPosition`/`PlayerChunk` rows behind as **ghosts** — and the enemy sim explicitly guards against simulating or spawning near them via `logged_in_player` checks in [[server/spacetimedb/src/enemy/methods.rs#has_player_in_simulation_range#1|has_player_in_simulation_range]] rather than cleaning the rows up. Cleanup happens only in `teardown_profile` (death or `delete_profile`). On every other client, the departed player's puppet despawns because `nearby_remote_players` semijoins `logged_in_player` — the identity-row delete arrives as a position-row delete — while enemies and drops near the departed player simply stay, owned by the world rather than the player. ^end-4

5. Reconnecting has a known sharp edge: if the server still has you as `LoggedInPlayer` (e.g. a stale row), [[server/spacetimedb/src/main/lifecycle.rs#client_connected#1|client_connected]] mishandles it — it *deletes* the `LoggedInPlayer` row and drops you into the lobby instead of rejecting or resuming, flagged as a bug only inside a `log::error!` message, not a comment. ^end-5

6. Shutdown on the client is symmetric with startup: [[client/sstdbsdk/DatabaseConnector.cs#_ExitTree#1|DatabaseConnector._ExitTree]] disconnects an active connection and clears the singleton, and every [[client/sstdbsdk/TableBinderComponent.cs#_ExitTree#1|TableBinderComponent._ExitTree]] removes its table event handlers, so freed scenes (despawned puppets, the whole `game.tscn` on scene change) never leave dangling callbacks into freed nodes. ^end-6

7. And the loop closes: back in the lobby the player can join again (join-1) — `try_scaffold_profile` will find surviving rows and skip re-scaffolding, unless death or deletion tore them down (end-2), in which case the next join rebuilds the archetype from scratch. Details: [[13 Disconnect & Teardown]]. ^end-7
