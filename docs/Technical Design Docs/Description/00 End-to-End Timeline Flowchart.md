# Boot & Connection

1. When the Godot app launches, the `[autoload]` section of [[project.godot##[autoload]|project.godot]] loads three autoloads before any scene exists — `PhantomCameraManager` (the phantom-camera plugin), `McpRuntimeAutoload` (dev tooling), and [[DatabaseConnector.cs##public partial class DatabaseConnector : Node|DatabaseConnector]], the game's SpacetimeDB connection owner. An autoload is a node Godot keeps alive for the whole run, reachable from any scene. [[DatabaseConnector.cs##public override void _Ready()|DatabaseConnector._Ready]] stashes the singleton in `Instance` and immediately calls [[DatabaseConnector.cs##public void Connect(string host, string dbName)|Connect]] — so the connection attempt starts before any scene loads. ^boot-1
2. `Connect` first loads the saved auth token through [[AuthToken.cs##public static void Init(string filePath)|AuthToken.Init]] from a per-host file in the user-data dir — scoped per host because a token minted by one SpacetimeDB instance is signed with that instance's key and gets rejected (401) by another, so local and maincloud tokens can't share one file. It then builds the `DbConnection` with `DbConnection.Builder()` (uri, database name, token, and the connect/error/disconnect callbacks). ^boot-2
3. The first scene loaded is [[project.godot##run/main_scene|run/main_scene]] = `lobby_gui.tscn` — a main-menu-only scene whose root [[LobbyGui.cs##public partial class LobbyGui : Control|LobbyGui]] shows Character Slots / Server List / Settings buttons ([[lobby_gui.tscn##[node name="LobbyGui" type="Control"|lobby_gui.tscn]]). The world scene `main.tscn` is *not* the boot scene; it loads later (see conn-3). Meanwhile [[DatabaseConnector.cs##public override void _Process(double delta)|_Process]] pumps `Conn.FrameTick()` every frame, because SpacetimeDB callbacks only dispatch when the client pumps them — this keeps them on the Godot main thread. ^boot-3
4. Server side, publishing the module runs the [[server/spacetimedb/src/main/lifecycle.rs##pub fn init|init]] reducer once: it inserts the three scheduled-reducer rows that drive the game's timers (`EnemyBehaviorSchedule` at 100 ms, `EnemySpawnSchedule` at 2 s, `ConsumableEffectSchedule` at `CONSUMABLE_EFFECT_TICK_SECONDS`), then calls the seed functions in `main/seeds.rs` ([[server/spacetimedb/src/main/seeds.rs##pub fn seed_default_textures|seed_default_textures]] and siblings: texture catalog, layering/adjacency/decor rules, enemy templates and test bosses, world items/enchantments, biome and world defs). Seeds either upsert by natural key (the `Seed` trait) or clear-and-reinsert, so a republish refreshes the defs instead of duplicating them. ^boot-4
5. `init` then calls [[server/spacetimedb/src/main/admin.rs##pub fn internal_add_chunks|internal_add_chunks]] with the `DEFAULT_*` constants from [[server/spacetimedb/src/main/global.rs##pub const DEFAULT_CHUNK_HEX_RADIUS|global.rs]] (6×6 chunks of hex-radius 2, 48-unit hexes): it inserts one `BuildingTile` row per world hex and upserts the single `MapConfig` row, including the torus lap vectors the client later mirrors into `TableSubscriber.LapQ`/`LapR` (see conn-4). ^boot-5
6. Finally `init` calls [[server/spacetimedb/src/world/terrain/mod.rs##pub fn internal_generate_world_proc|internal_generate_world_proc]]("Earth", 0), which reads the seeded `WorldDef`/`BiomeDef` rows, lays biomes out by weighted Voronoi, and rewrites the world's `BiomeRegion`/`TriangleTile`/`HexDecor` rows — the terrain the client streams once it's in the world. The generation pipeline itself is documented in [[07 Terrain & World Streaming]]. ^boot-6

1. When the handshake from boot-2 succeeds, [[DatabaseConnector.cs##private void OnConnected(DbConnection conn, Identity identity, string token)|OnConnected]] stores the `Identity`, persists the server-issued token through [[AuthToken.cs##public static void SaveToken(string token)|AuthToken.SaveToken]] (so the next launch reuses the same identity instead of minting a new anonymous one), hooks the `LocalLobbyPlayer` view's insert/update events to keep `Username` current, and emits the `Connected` signal that everything downstream waits on. ^conn-1
2. The same connect fires the server's [[server/spacetimedb/src/main/lifecycle.rs##pub fn client_connected|client_connected]] reducer: a brand-new identity gets a [[server/spacetimedb/src/player/tables.rs##pub struct LoggedOutPlayer|LoggedOutPlayer]] row (lobby state, empty username, not admin) plus a default "Knight" [[server/spacetimedb/src/player/tables.rs##pub struct PlayerProfile|PlayerProfile]]; an identity already sitting in the lobby is left alone; an identity still marked `LoggedInPlayer` hits a bug path that drops it back to the lobby (see [[03 Boot & Connection]] → Known gaps). ^conn-2
3. In the main menu, the Character Slots button runs [[LobbyGui.cs##public void CharSlotsPressed|CharSlotsPressed]] → `ChangeSceneToFile("res://Scenes/main.tscn")`: the world scene loads, its root [[GameManager.cs##public partial class GameManager : Node2D, IEntity|GameManager]] becomes the scene-level entity, and every component declared inline in the scene — including the [[main.tscn##[node name="TableSubscriber" type="Node" parent="."|TableSubscriber]] node — registers with it (the registration lifecycle is [[02 The Component Framework]]). ^conn-3
4. [[TableSubscriber.cs##protected override void OnRegistered|TableSubscriber.OnRegistered]] must cope with both orders, because the autoload usually finishes connecting before `main.tscn` loads: if `Conn.IsActive` it proceeds immediately, otherwise it waits for the conn-1 `Connected` signal. Either way, `OnConnected` installs the `MapConfig` insert/update hooks that mirror rows into the `LapQ`/`LapR` lap vectors, subscribes the **base wave** (`BaseTables`: `AllTextures`, `AllItems`, `AllEnchantments` — static catalogs every screen needs), and calls [[TableSubscriber.cs##public void SubscribeLobby|SubscribeLobby]] for the **lobby wave** (`LocalLobbyPlayer`, `LocalPlayerProfiles`). The `MapConfig` row itself arrives with the game wave (see [[05 Joining the World]]). ^conn-4
5. With the connection live, the `TableBinderComponent`s declared inline in `main.tscn` bind their tables — each applies the same both-orders guard on `Connected` — and re-emit server rows as the Godot signals wired at the bottom of `main.tscn` (the binder mechanism is [[02 The Component Framework]]). The third, **game** wave is deliberately not subscribed at boot; it starts on `join_world` in [[05 Joining the World]]. ^conn-5

# Lobby & Profiles

1. The lobby is a *server-side state*, not a scene: after conn-2 the identity owns a [[server/spacetimedb/src/player/tables.rs##pub struct LoggedOutPlayer|LoggedOutPlayer]] row, and the lobby wave subscribed in conn-4 ([[TableSubscriber.cs##public static readonly string[] LobbyTables|LobbyTables]] = `LocalLobbyPlayer`, `LocalPlayerProfiles`) delivers two caller-scoped **views** — server-side queries filtered by `ctx.sender()`, so each client receives only its own lobby row and its own profiles. [[server/spacetimedb/src/player/views.rs##fn local_lobby_player(ctx|local_lobby_player]] keeps the conn-1 username mirror fed; [[server/spacetimedb/src/player/views.rs##fn local_player_profiles(ctx|local_player_profiles]] feeds the profile list below. ^lobby-1
2. When the conn-3 scene switch loads `main.tscn`, the [[main.tscn##[node name="LobbyComponent" parent="UI"|LobbyComponent instance]] under the `UI` CanvasLayer — instanced from `lobby_component.tscn`, which *is* a live wiring site, unlike the nine unreferenced duplicate component scenes — registers with `GameManager`, and [[LobbyComponent.cs##protected override void OnRegistered|OnRegistered]] grabs the `MainMenuPhantomCamera2D` sibling and calls [[LobbyComponent.cs##public void ShowLobby|ShowLobby]]: show the character-select UI and raise the menu camera's phantom priority to 60 so it drives the camera while the lobby is open. ^lobby-2
3. The binder child declared in [[lobby_component.tscn##[node name="LocalPlayerProfilesBinder"|lobby_component.tscn]] (`TableName = "LocalPlayerProfiles"`, `ReplayExistingRows = true`) re-emits every subscribed profile row — including the ones that arrived before the scene loaded — as a `RowInserted` signal, and [[LobbyComponent.cs##private void OnProfileRowInserted|OnProfileRowInserted]] instantiates one [[profile_panel.tscn##[node name="Profile" type="Panel"|profile_panel.tscn]] per row: it fills the `Name`/`ID` labels and hooks that panel's `Join`/`Delete` buttons to closures capturing the profile. The list is fully data-driven — one panel per `PlayerProfile` row, however many the wave delivered. ^lobby-3
4. The CREATE button toggles the hidden `CreateProfilePanel` via [[LobbyComponent.cs##private void OnCreatePanelPressed|OnCreatePanelPressed]]; confirming runs [[LobbyComponent.cs##private void OnCreatePressed|OnCreatePressed]], which calls `conn.Reducers.CreateProfile(name, "Knight")` — the texture id is hardcoded to `"Knight"`. (All profile reducer calls live here in `LobbyComponent`; the `LobbyGui` main menu is scene navigation only.) ^lobby-4
5. Server side, [[server/spacetimedb/src/player/reducers.rs##pub fn create_profile|create_profile]] first proves the caller is in the lobby via [[server/spacetimedb/src/player/methods.rs##pub fn require_in_lobby|require_in_lobby]] (a `LoggedOutPlayer` row *is* "in the lobby"), then validates: 1–20 non-whitespace characters, at most 3 profiles per player, and no case-insensitive duplicate name among that player's own profiles. Only then does it insert the [[server/spacetimedb/src/player/tables.rs##pub struct PlayerProfile|PlayerProfile]] row (auto-increment `profile_id`, `aim_assist`/`lock_on` false). The insert flows back through the lobby-1 view and the lobby-3 binder, so the new panel appears on its own. ^lobby-5
6. A panel's DELETE button runs [[LobbyComponent.cs##private void OnDeletePressed|OnDeletePressed]] → `DeleteProfile(profile_id)`. [[server/spacetimedb/src/player/reducers.rs##pub fn delete_profile|delete_profile]] re-checks lobby state and profile ownership, runs [[server/spacetimedb/src/player/methods.rs##pub fn teardown_profile|teardown_profile]] (deletes the profile's `PlayerData`/`PlayerStats`/`PlayerInventory`/`PlayerPosition`/`PlayerChunk` rows and any active consumable effects), then deletes the `PlayerProfile` row itself. The client doesn't wait for a server delete event — only `RowInserted` is wired — so it `QueueFree`s the panel whose `ID` label matches the deleted profile. ^lobby-6
7. A panel's JOIN button runs [[LobbyComponent.cs##private void OnJoinPressed|OnJoinPressed]]: it refuses while the create panel is open, hides the lobby (phantom priority back to 0), calls `JoinWorld(profile_id)`, and swaps subscription waves — [[TableSubscriber.cs##public void SubscribeGame|SubscribeGame]] in, [[TableSubscriber.cs##public void UnsubscribeLobby|UnsubscribeLobby]] out. The server-side [[server/spacetimedb/src/player/reducers.rs##pub fn join_world|join_world]] and everything it starts belong to [[05 Joining the World]]. ^lobby-7

# Joining the World

1. The `JoinWorld(profile_id)` call from lobby-7 lands in [[server/spacetimedb/src/player/reducers.rs##pub fn join_world|join_world]], which proves the caller is in the lobby via `require_in_lobby` (lobby-5's guard), looks up the [[server/spacetimedb/src/player/tables.rs##pub struct PlayerProfile|PlayerProfile]] and rejects `profile_id`s the caller doesn't own — then performs the state transition as a row move: delete the [[server/spacetimedb/src/player/tables.rs##pub struct LoggedOutPlayer|LoggedOutPlayer]] row, insert a [[server/spacetimedb/src/player/tables.rs##pub struct LoggedInPlayer|LoggedInPlayer]] row carrying `username`/`is_admin` over plus the chosen `profile_id`. Because lobby membership is a row (lobby-1), this one transaction is the entire "join" — no flags to desync. ^join-1
2. Still inside the join-1 reducer, [[server/spacetimedb/src/player/methods.rs##pub fn try_scaffold_profile|try_scaffold_profile]] lazily creates the profile's per-row "components" — each guarded by an `is_none()` check, so a rejoin after `leave_world` keeps accumulated progress while a first join starts fresh: [[server/spacetimedb/src/player/tables.rs##pub struct PlayerData|PlayerData]] (level 1, full `BASE_MAX_HP`), a 24-slot [[server/spacetimedb/src/player/tables.rs##pub struct PlayerInventory|PlayerInventory]] pre-filled with starter items (Bow, Bread, Hat, Helmet, Skull, Bag), `PlayerStats` computed by `recompute_stats` (its flat/mult pipeline is [[10 Inventory, Items & Enchantments]]), and [[server/spacetimedb/src/player/tables.rs##pub struct PlayerPosition|PlayerPosition]]/[[server/spacetimedb/src/player/tables.rs##pub struct PlayerChunk|PlayerChunk]] parked at world origin (0, 0) with the matching `chunk_index`. This lazy split exists *because* lobby-5's `create_profile` inserts only the `PlayerProfile` row — a profile that is created but never joined costs one row, not six. ^join-2
3. Client side, lobby-7's `OnJoinPressed` already fired [[TableSubscriber.cs##public void SubscribeGame()|SubscribeGame]] — optimistically, before the reducer's result is known — subscribing the **game wave** ([[TableSubscriber.cs##public static readonly string[] GameTables|GameTables]]: the caller-scoped `local_player*` views, the AOI-filtered `nearby_*` views, `EnemyTemplates`, `BulletPatternEvent`, and `MapConfig`) and then dropping the lobby wave via `UnsubscribeLobby`. The server evaluates the views as the join-1 row move commits, so the wave's rows stream in right behind it; `MapConfig`'s arrival finally populates the `LapQ`/`LapR` torus lap vectors whose hooks conn-4 installed. The `local_player*` views fall back to the impossible id `u64::MAX` when the caller has no `LoggedInPlayer` row (lobby-1's pattern), so if `join_world` *rejected* the call the wave simply delivers nothing — the client has no error callback to notice (see [[05 Joining the World]] → Known gaps). ^join-3
4. The moment the caller's `LoggedInPlayer` row reaches the client, the `LocalPlayerBinder` declared inline in [[main.tscn##[node name="LocalPlayerBinder" type="Node" parent="EntitySpawnerComponent"|main.tscn]] (`TableName = "LocalPlayer"` — the [[server/spacetimedb/src/player/views.rs##fn local_player(ctx|local_player]] view over `LoggedInPlayer`) fires `RowInserted`, and [[EntitySpawnerComponent.cs##private void OnLocalPlayerInsert|OnLocalPlayerInsert]] instantiates `local_player.tscn` plus `bullet_manager.tscn` and adds both to the current scene with `CallDeferred` (deferring because you can't mutate the scene tree mid-signal). [[LocalPlayer.cs##public override void _Ready()|LocalPlayer._Ready]] then publishes the `LocalPlayer.Local` static, registers its phantom camera with `Camera2DPresenterComponent`, and spawns its 3D backdrop model — the camera/presentation half of that is [[11 Camera & Presentation]], the movement half is [[06 Movement & Position Sync]]. ^join-4
5. The AOI views deliver everyone *else*: [[EntitySpawnerComponent.cs##private void OnNearbyRemotePlayerInsert|OnNearbyRemotePlayerInsert]] spawns one `RemotePlayer` per [[server/spacetimedb/src/player/views.rs##fn nearby_remote_players(ctx|nearby_remote_players]] row (a `PlayerPosition` filtered to chunks near the caller's), explicitly skipping the caller's own row via [[DatabaseConnector.cs##public bool IsLocal(Identity id)|DatabaseConnector.IsLocal]] — the view's semijoin over `logged_in_player` does not exclude self, so the client must. The same binder pattern spawns `Enemy` nodes from `NearbyEnemies` rows and `Drop` nodes from `NearbyLootDrops` rows, all wired by `[connection]` entries at the bottom of [[main.tscn##[node name="EntitySpawnerComponent" type="Node" parent="."|main.tscn]]. "Nearby" is chunk-based: views key off [[server/spacetimedb/src/player/tables.rs##pub struct PlayerChunk|PlayerChunk]], which `report_movement` rewrites only on chunk crossings, so these views recompute per crossing rather than per 10 Hz movement tick (the AOI machinery itself is [[06 Movement & Position Sync]]). ^join-5
6. The way back out is symmetric: [[server/spacetimedb/src/player/reducers.rs##pub fn leave_world|leave_world]] deletes the `LoggedInPlayer` row and reinserts `LoggedOutPlayer` (no client UI calls it today — see [[05 Joining the World]] → Known gaps), and combat death does the same move inside [[server/spacetimedb/src/combat/mod.rs##pub fn deal_damage_to_player|deal_damage_to_player]] after a full `teardown_profile`. Either way the `local_player` view's row vanishes, the binder fires `RowDeleted`, and [[EntitySpawnerComponent.cs##private void OnLocalPlayerDelete|OnLocalPlayerDelete]] despawns the player and bullet manager, re-shows the lobby, and swaps the waves back (`SubscribeLobby` in, `UnsubscribeGame` out) — returning the client to exactly the lobby-1 state. The full teardown story is [[13 Disconnect & Teardown]]. ^join-6

# Movement & Position Sync

1. Every physics tick, [[LocalPlayer.cs##public override void _PhysicsProcess(double delta)|LocalPlayer._PhysicsProcess]] turns WASD into motion: `Input.GetVector("Left", "Right", "Up", "Down")` reads the four input actions as one 2D vector, the vector is rotated by the camera rig's yaw (so "Up" means away-from-camera, not world-north), and `Velocity = input * Speed * SpeedPerStat` converts the server's Speed stat into engine velocity at [[LocalPlayer.cs##private const float SpeedPerStat = 10f|10 units per stat point]] before `MoveAndSlide()` integrates it with collision. Movement is fully client-authoritative — the server never simulates the player, it only stores and relays the positions it is told (move-3). ^move-1
2. The outbound half lives on the [[local_player.tscn##[node name="PositionSyncComponent" type="Node" parent="."|PositionSyncComponent]] child declared in `local_player.tscn`: [[PositionSyncComponent.cs##public override void _PhysicsProcess(double delta)|its _PhysicsProcess]] accumulates frame `delta` and calls [[PositionSyncComponent.cs##GameManager.Conn?.Reducers.ReportMovement|Reducers.ReportMovement]](x, y, rotation) every `ReportInterval` (0.1 s). It's a fixed 10 Hz heartbeat — there is no "only when moved" check, so the reducer below runs ten times a second whether or not anything changed. ^move-2
3. Server side, [[server/spacetimedb/src/player/reducers.rs##pub fn report_movement|report_movement]] guards the caller with [[server/spacetimedb/src/player/methods.rs##pub fn require_in_world|require_in_world]], then canonicalizes the report onto the torus: [[server/spacetimedb/src/world/wrap.rs##pub fn wrap_world_pos|wrap_world_pos]] shifts x/y by whole lap vectors until its chunk coords fall inside the 6×6 chunk grid, and [[server/spacetimedb/src/world/hex.rs##pub fn world_to_chunk|world_to_chunk]] + [[server/spacetimedb/src/world/hex.rs##pub fn spiral_chunk_index|spiral_chunk_index]] recompute the spiral `chunk_index`. The [[server/spacetimedb/src/player/tables.rs##pub struct PlayerPosition|PlayerPosition]] row is rewritten on *every* call; the [[server/spacetimedb/src/player/tables.rs##pub struct PlayerChunk|PlayerChunk]] row is rewritten only when (chunk_q, chunk_r) actually changed — the join-5 trade that lets AOI views recompute per chunk crossing instead of per 10 Hz tick. ^move-3
4. The report echoes home through the caller-scoped [[server/spacetimedb/src/player/views.rs##fn local_player_position|local_player_position]] view to the [[local_player.tscn##[node name="LocalPlayerPositionBinder" type="Node" parent="PositionSyncComponent"|LocalPlayerPositionBinder]] (`ReplayExistingRows = true`): the first, replayed row is the initial placement via [[PositionSyncComponent.cs##private void OnPositionRowInserted|OnPositionRowInserted]], and every later update runs [[PositionSyncComponent.cs##private void OnPositionRowUpdated|OnPositionRowUpdated]] — which deliberately does *not* force the server's position onto the player. The local copy lives in an unbounded continuous frame, so the handler asks [[TorusMath.cs##public static Vector2 NearestCandidate|TorusMath.NearestCandidate]] for the closest wrapped copy of the server position and snaps only when even that copy is more than `WrapSnapThreshold` (50 units) away: a real desync (lag, rubber-band, correction), never a routine lap wrap. ^move-4
5. Everyone else receives the position through the AOI view [[server/spacetimedb/src/player/views.rs##fn nearby_remote_players(ctx|nearby_remote_players]]: [[server/spacetimedb/src/player/views.rs##pub(crate) fn nearby_indices_from_chunk|nearby_indices_from_chunk]] reads the *calling* client's `PlayerChunk`, [[server/spacetimedb/src/world/aoi.rs##pub fn surrounding_chunk_indices|surrounding_chunk_indices]] expands it into [[server/spacetimedb/src/main/global.rs##pub const DEFAULT_AOI_CHUNK_RADIUS|DEFAULT_AOI_CHUNK_RADIUS]] (2) rings of chunks wrapped around the torus, and the view OR-chains `chunk_index` equality over those indices before semijoining `logged_in_player` (join-5 covers why the caller's own row survives this and the client must skip it). Each spawned `RemotePlayer` carries its own binder in [[non_local_player.tscn##[node name="NearbyRemotePlayersBinder" type="Node" parent="."|non_local_player.tscn]] whose `RowUpdated` runs [[RemotePlayer.cs##private void OnPositionRowUpdated|RemotePlayer.OnPositionRowUpdated]], which discards rows belonging to other players (`PlayerId` mismatch — every RemotePlayer sees the whole nearby set) and forwards position, rotation, and a derived velocity to its interpolation component. ^move-5
6. [[InterpolationComponent.cs##public override void _Process(double delta)|InterpolationComponent._Process]] runs every rendered frame: it extrapolates the last server target by `snapVelocity * timeSinceSnap`, picks the [[TorusMath.cs##public static Vector2 NearestCandidate|NearestCandidate]] copy of that extrapolated target so lap crossings lerp smoothly instead of snapping across the map, then eases `GlobalPosition`/`Rotation` toward it at `LerpSpeed` (10 per second) — leaving the puppet a fraction of a second behind the server by design. The `WrapSnapThreshold = 50.0` override in [[non_local_player.tscn##WrapSnapThreshold = 50.0|non_local_player.tscn]] hard-snaps on real desyncs, and [[RemoteVisualComponent.cs##public override void _Process(double delta)|RemoteVisualComponent]] plays Walk/Idle from the component's `Moving` flag (more than 1 unit from target). ^move-6

# Terrain & World Streaming

1. World generation runs at publish time (boot-6), not at join: [[server/spacetimedb/src/world/terrain/mod.rs##pub fn internal_generate_world_proc|internal_generate_world_proc]]("Earth", 0) is the **procedural front-end** — it loads the seeded [[server/spacetimedb/src/world/def_tables.rs##pub struct WorldDef|WorldDef]]/[[server/spacetimedb/src/world/def_tables.rs##pub struct BiomeDef|BiomeDef]] rows, rejects biome weights that don't sum to 100 (±0.5, [[server/spacetimedb/src/world/terrain/voronoi.rs##pub fn validate_weights_sum_100|validate_weights_sum_100]]), and expands the `MapConfig` grid from boot-5 into a flat cell list via [[server/spacetimedb/src/world/hex.rs##pub fn enumerate_world_hexes|enumerate_world_hexes]] — 6×6 chunks × 19 hexes per chunk (hex-radius 2) = 684 hexes. A second front-end, [[server/spacetimedb/src/world/terrain/mod.rs##pub fn internal_generate_world_manual|internal_generate_world_manual]], takes fully explicit biome/region inputs from the admin reducer `generate_world_manual` and seeds its randomness from the wall clock instead of a fixed seed. Both funnel into one shared pipeline, [[server/spacetimedb/src/world/terrain/mod.rs##fn run_generation|run_generation]], whose first act is [[server/spacetimedb/src/world/terrain/mod.rs##fn clear_world_geometry|clear_world_geometry]] — deleting every `BiomeRegion`/`TriangleTile`/`HexDecor` row so a regen replaces the world instead of appending to it. ^terrain-1
2. The biome layout is a **weighted Voronoi diagram**: [[server/spacetimedb/src/world/terrain/voronoi.rs##pub fn combine_biome_weights|combine_biome_weights]] sums duplicate `BiomeWeight` entries per biome (preserving first-seen order — a HashMap's unstable iteration would silently change the layout for the same seed), [[server/spacetimedb/src/world/terrain/voronoi.rs##pub fn distribute_biome_seeds|distribute_biome_seeds]] then scatters [[server/spacetimedb/src/main/global.rs##pub const BIOME_VORONOI_SEED_BUDGET|BIOME_VORONOI_SEED_BUDGET]] (16) seed points across random world hexes, split proportionally to each biome's weight share with a one-seed minimum, and [[server/spacetimedb/src/world/terrain/voronoi.rs##pub fn group_cells_by_seeds|group_cells_by_seeds]] buckets every hex under its *nearest* seed — where "nearest" is wrap-aware, measured with [[server/spacetimedb/src/world/wrap.rs##pub fn wrapped_distance_sq|wrapped_distance_sq]] against the torus lap vectors, so a seed hugging a wrap seam isn't cheated out of the cells across the seam. ^terrain-2
3. Each biome then grows **regions** — the enemy-spawn districts: one seed is drawn per `RegionWeight` entry whose [[server/spacetimedb/src/world/def_tables.rs##pub struct BiomeRegionDef|BiomeRegionDef]] resolves (missing defs are skipped without consuming a PRNG draw, keeping the stream deterministic), each seed becomes an inserted [[server/spacetimedb/src/world/instance_tables.rs##pub struct BiomeRegion|BiomeRegion]] row carrying the def's enemy template ids / `max_enemies` / `spawn_radius`, and every hex in the biome is assigned to its nearest region seed. Note the asymmetry the [[server/spacetimedb/src/main/global.rs##pub const BIOME_VORONOI_SEED_BUDGET|BIOME_VORONOI_SEED_BUDGET]] comment calls out: region weights only gate validation (they must sum to 100 per biome) — unlike biome weights they don't buy area share, so every region in a biome gets exactly one seed regardless of weight. The seeded "Earth" world ([[server/spacetimedb/src/main/seeds.rs##pub fn seed_world_defs|seed_world_defs]]) is Grassland 40 / Meadow 30 / Highlands 30 with nine regions total; what regions *do* with their enemy templates is [[08 Enemies & AI]]. ^terrain-3
4. Content is written hex by hex, wedge by wedge — a hex is 6 triangles (`tri_index` 0–5) and each becomes one [[server/spacetimedb/src/world/instance_tables.rs##pub struct TriangleTile|TriangleTile]] row from [[server/spacetimedb/src/world/terrain/mod.rs##fn write_triangle_tiles|write_triangle_tiles]]. The **ground pass** ([[server/spacetimedb/src/world/terrain/ground.rs##pub(super) fn choose_ground|choose_ground]]) makes its first pick from a spatially-coherent noise field — [[server/spacetimedb/src/world/noise.rs##pub fn value_noise2d|value_noise2d]] at the hex's world position drives [[server/spacetimedb/src/world/prng.rs##pub fn weighted_pick_index_from_unit|weighted_pick_index_from_unit]] over the biome's weighted `GroundTextureConfig`s, so neighboring hexes land in the same noise band and textures cluster into patches instead of per-wedge confetti. If the pick clashes with an already-written neighbor under the deny-list [[server/spacetimedb/src/world/tables.rs##pub struct BaseAdjacencyRule|BaseAdjacencyRule]] (neighbor lookup: [[server/spacetimedb/src/world/terrain/rules.rs##pub fn decided_neighbor_tags|decided_neighbor_tags]] via [[server/spacetimedb/src/world/hex.rs##pub fn same_hex_neighbor_indices|same_hex_neighbor_indices]]/[[server/spacetimedb/src/world/hex.rs##pub fn cross_hex_neighbor|cross_hex_neighbor]]), it re-rolls plain-random among the remaining candidates; if every candidate conflicts, the wedge is left blank (empty `texture_id`). ^terrain-4
5. The **overlay pass** ([[server/spacetimedb/src/world/terrain/overlay.rs##pub(super) fn choose_overlay|choose_overlay]]) runs on top of the ground pick in the same wedge loop: candidates are filtered to overlays tag-compatible with the chosen ground via the allow-list [[server/spacetimedb/src/world/tables.rs##pub struct LayeringRule|LayeringRule]], then rolled by [[server/spacetimedb/src/world/prng.rs##pub fn weighted_pick_with_remainder_from_unit|weighted_pick_with_remainder_from_unit]] — chances are percentages that needn't sum to 100, and whatever is left under 100 is a real "no overlay" outcome (over 100 gets scaled down). It samples its own decorrelated noise field (`seed ^ OVERLAY_NOISE_SEED_OFFSET`) so debris patches don't trace the ground boundaries, retries against the [[server/spacetimedb/src/world/tables.rs##pub struct OverlayAdjacencyRule|OverlayAdjacencyRule]] deny-list like the ground pass, and stores `overlay_scale` on the `TriangleTile` row so the client never has to join back through `BiomeDef`. The **decor pass** ([[server/spacetimedb/src/world/terrain/decor.rs##pub(super) fn place_decor|place_decor]]) rolls once per *hex* after that hex's wedges are decided: decor whose tags hit the deny-list [[server/spacetimedb/src/world/tables.rs##pub struct DecorGroundRule|DecorGroundRule]] against the hex's own 6 wedges are filtered out, `decor_min_separation` vetoes the hex entirely if any decor already sits within that hex distance (tracked in a `decided_decor` set — type-agnostic, so no two props of any kind can crowd together), and a surviving roll inserts one [[server/spacetimedb/src/world/instance_tables.rs##pub struct HexDecor|HexDecor]] row with `rotation_degrees = 0` — prop shadows are baked into the art, so rotating would detach shadow from prop. (Today's seeded biomes ship empty overlay/decor configs, so both passes are live machinery generating nothing — see [[07 Terrain & World Streaming]] → Known gaps.) ^terrain-5
6. Terrain reaches the client through the join-3 game wave: [[TableSubscriber.cs##public static readonly string[] GameTables|GameTables]] subscribes `NearbyTerrainTiles`, `NearbyHexDecor`, and `MapConfig`. The first two are AOI views ([[server/spacetimedb/src/world/views.rs##fn nearby_terrain_tiles|nearby_terrain_tiles]], [[server/spacetimedb/src/world/views.rs##fn nearby_hex_decor|nearby_hex_decor]]) built on the move-5 pattern: [[server/spacetimedb/src/player/views.rs##pub(crate) fn nearby_indices_from_chunk|nearby_indices_from_chunk]] resolves the caller's `PlayerChunk` into [[server/spacetimedb/src/main/global.rs##pub const DEFAULT_TERRAIN_AOI_CHUNK_RADIUS|DEFAULT_TERRAIN_AOI_CHUNK_RADIUS]] (2) rings of spiral chunk indices, and the view OR-chains `chunk_index` equality over them — recomputing only when `report_movement` rewrites `PlayerChunk` on a chunk crossing (move-3), never per 10 Hz move tick. A caller with no in-world row gets the impossible-id empty query (`tile_id == u64::MAX`), so the wave is harmless before `join_world` commits. ^terrain-6
7. On the client, the inline [[main.tscn##[node name="TerrainComponent" type="Node2D" parent="."|TerrainComponent]] in `main.tscn` owns the whole render side, fed by its three child binders ([[main.tscn##[node name="TerrainTilesBinder" type="Node" parent="TerrainComponent"|TerrainTilesBinder]], `HexDecorBinder`, `MapConfigBinder` — all `ReplayExistingRows = true`, so cached rows replay through the same insert path). Every row callback ([[TerrainComponent.cs##private void OnTileRowInserted|OnTileRowInserted]] and siblings) just updates the `_tilesById`/`_tilesByHex`/`_decorById` caches and sets a dirty flag; [[TerrainComponent.cs##public override void _Process(double delta)|_Process]] performs at most one rebuild per frame, so a chunk crossing's burst of hundreds of row events collapses into a single rebuild. `OnEntityReady` pre-warms a pool of `RingChunkCount(AoiChunkRadius)` = 19 TileComponent instances from [[tile_component.tscn##[node name="TileComponent" type="Node2D"]|tile_component.tscn]] (1 + 3r(r+1) hexes in 2 rings), so the first subscription burst doesn't hitch on instantiation. ^terrain-7
8. The rebuild itself, [[TerrainComponent.cs##private void RebuildVisibleInstances|RebuildVisibleInstances]], is wrap-aware culling plus batching: for every cached hex it picks the wrapped copy nearest the camera with [[TorusMath.cs##public static Vector2 NearestCandidate|TorusMath.NearestCandidate]] (canonical positions near a seam are stored far away — the move-6 lap-vector problem), discards hexes outside the camera window plus a 2×hex-radius margin, and groups the survivors per chunk into batch keys — `(TriIndex, Rotation, TextureId)` for ground and overlay wedges, texture id for decor. Each present chunk's batches go to one pooled [[TileComponent.cs##public void Populate(|TileComponent.Populate]], which distributes them across the four layer components declared in `tile_component.tscn` — [[GroundComponent.cs##public partial class GroundComponent : TerrainLayerComponent|GroundComponent]] (z=0), OverlayComponent (z=1, scaled around its wedge's own centroid via [[TerrainComponent.cs##public Vector2 GetWedgeCentroid|GetWedgeCentroid]]), DecorShadowComponent (z=2), DecorComponent (z=3) — each a set of `MultiMeshInstance2D` batch leaves managed by [[TerrainLayerComponent.cs##public abstract partial class TerrainLayerComponent : Node2DComponent|TerrainLayerComponent]], drawing shared meshes from TerrainComponent's caches ([[TerrainComponent.cs##public (ArrayMesh Mesh, Texture2D? Texture) GetWedgeMeshAndTexture|GetWedgeMeshAndTexture]] builds one UV-cropped wedge `ArrayMesh` per batch key). Chunks that left the AOI have their tile zeroed and parked back in the pool — no allocations in steady state. ^terrain-8
9. Separate from generated terrain, every world hex also got a [[server/spacetimedb/src/world/tables.rs##pub struct BuildingTile|BuildingTile]] row from boot-5's `internal_add_chunks` — the buildable-plot layer. [[server/spacetimedb/src/world/reducers.rs##pub fn place_building|place_building]] lets any logged-in player claim an empty hex (non-empty `building_type`, tile must exist and be unoccupied; the row records `owner_id = ctx.sender()`), and [[server/spacetimedb/src/world/reducers.rs##pub fn remove_building|remove_building]] clears it for the owner or an admin. This is a reducer-only stub today: no client code calls either reducer and no subscription wave carries `BuildingTile`, so placed buildings are invisible in-game — details in [[07 Terrain & World Streaming]] → Known gaps. ^terrain-9

# Enemies & AI

1. Enemy *content* is seeded at publish time with boot-4's other seeds: [[server/spacetimedb/src/main/seeds.rs##pub fn seed_default_enemies|seed_default_enemies]] upserts three [[server/spacetimedb/src/enemy/def_tables.rs##pub struct EnemyTemplate|EnemyTemplate]] rows ("Enemy", "Archer", "TestBoss") and [[server/spacetimedb/src/main/seeds.rs##pub fn seed_test_boss_p2|seed_test_boss_p2]] through `seed_test_boss_p6` add five more single-phase bosses — all `Seed`-trait upserts by `template_id`, so a republish refreshes them. A template is a bullet-hell script in data: `max_hp`, `texture_id`, two range factors (`move_sim_factor`/`attack_sim_factor`, multiples of [[server/spacetimedb/src/main/global.rs##pub const CAMERA_VIEW_RADIUS|CAMERA_VIEW_RADIUS]] rather than absolute units, so templates stay correctly scaled if the camera changes), `aggro_lock_seconds`, and a `Vec<`[[server/spacetimedb/src/enemy/def_tables.rs##pub struct PhaseDef|PhaseDef]]`>` — each phase an HP threshold, a movement behavior, and attack sequences. The helpers [[server/spacetimedb/src/main/seeds.rs##pub fn make_phase|make_phase]]/[[server/spacetimedb/src/main/seeds.rs##pub fn seq_single|seq_single]]/[[server/spacetimedb/src/main/seeds.rs##pub fn seq_repeat|seq_repeat]]/[[server/spacetimedb/src/main/seeds.rs##pub fn seq_multi|seq_multi]] insert the shared def rows (`MovementDef`/`SingleStepDef`/`RepeatStepDef`/`MultiStepDef`) and hand back ids, so step definitions are template data shared by every enemy of that type, never duplicated per spawn. ^enemy-1
2. Spawning is one of the two scheduled reducers boot-4 planted: every 2 s the `EnemySpawnSchedule` row re-fires [[server/spacetimedb/src/enemy/reducers.rs##pub fn tick_enemy_spawn|tick_enemy_spawn]] → [[server/spacetimedb/src/enemy/methods.rs##pub fn spawn_from_biome_regions|spawn_from_biome_regions]], which walks every [[server/spacetimedb/src/world/instance_tables.rs##pub struct BiomeRegion|BiomeRegion]] (terrain-3's spawn districts) and per region: skips it unless [[server/spacetimedb/src/enemy/methods.rs##pub fn has_player_near_spawn_point|has_player_near_spawn_point]] finds a logged-in player's `PlayerPosition` within [[server/spacetimedb/src/main/global.rs##pub const SPAWN_LOOKAHEAD_CHUNK_RINGS|SPAWN_LOOKAHEAD_CHUNK_RINGS]] (2) chunks of the region center — no audience, no spawns; counts live enemies of the region's templates within `spawn_radius` using [[server/spacetimedb/src/world/wrap.rs##pub fn wrapped_distance_sq|wrapped_distance_sq]] (a spawn offset can wrap across a lap seam to the far side of the map, and a plain distance check would then never count its own children, defeating the cap) and stops at `max_enemies`; then picks a template by `region_id ^` current-second (varies tick to tick), draws a uniform-disc offset with two [[server/spacetimedb/src/world/prng.rs##pub fn next_unit|next_unit]] draws (the `sqrt` on the radius draw spreads points evenly over the disc's area instead of bunching at the center), wraps the position onto the torus, and calls `spawn_enemy_archetype`. At most one enemy per region per 2 s tick. ^enemy-2
3. [[server/spacetimedb/src/enemy/methods.rs##pub fn spawn_enemy_archetype|spawn_enemy_archetype]] is the server-side mirror of the client's component model ([[02 The Component Framework]]): [[server/spacetimedb/src/enemy/methods.rs##pub fn build_enemy_behavior|build_enemy_behavior]] instantiates the template into per-enemy rows — one [[server/spacetimedb/src/enemy/instance_tables.rs##pub struct EnemyBehavior {|EnemyBehavior]], one `EnemyPhase` per phase, one `EnemyAttack` per attack sequence, one `EnemySequenceStep` per step — and because `RepeatStepDef` is *shared* template data with a mutable counter, each enemy gets its own `RepeatStepInstance` copy so repeat counts advance independently. `behavior_id` joins the tree to the flat [[server/spacetimedb/src/enemy/instance_tables.rs##pub struct Enemy {|Enemy]] row (position, hp, phase, `chunk_index`) exactly like component rows join an entity; [[server/spacetimedb/src/enemy/methods.rs##pub fn despawn_enemy_archetype|despawn_enemy_archetype]] tears the whole tree down (collecting before deleting, because removing rows while iterating a btree index filter skips entries). ^enemy-3
4. The second schedule row re-fires [[server/spacetimedb/src/enemy/reducers.rs##pub fn tick_enemy_behavior|tick_enemy_behavior]] every 100 ms. Each enemy first passes an audience gate: [[server/spacetimedb/src/enemy/methods.rs##pub fn has_player_in_simulation_range|has_player_in_simulation_range]] looks for a logged-in player (the `logged_in_player` semijoin is the ghost-row guard — `PlayerPosition` outlives logout; see [[13 Disconnect & Teardown]]) within `move_sim_factor × CAMERA_VIEW_RADIUS`. An enemy with no audience is frozen in place (`was_simulating` false, skipped); one *entering* range retargets exactly once via [[server/spacetimedb/src/enemy/methods.rs##pub fn recompute_aggro|recompute_aggro]] (nearest logged-in player, plus an aggro lock whose expiry is consulted when hits arrive — [[09 Combat & Damage]]). Phase changes are also driven externally — `report_enemy_hit` advances `enemy.phase` when HP crosses a threshold (doc 09) — and the tick detects the transition by comparing against `behavior.active_phase_index` and runs [[server/spacetimedb/src/enemy/methods.rs##pub fn begin_phase_cycle|begin_phase_cycle]] to reset the new phase's attack sequences. ^enemy-4
5. Firing happens only inside the tighter `attack_sim_factor × CAMERA_VIEW_RADIUS` range — an enemy is already approaching by the time it's close, but it never shoots from off-screen. [[server/spacetimedb/src/enemy/methods.rs##pub fn tick_phase|tick_phase]] advances every attack sequence of the active phase, and [[server/spacetimedb/src/enemy/methods.rs##pub fn tick_sequence|tick_sequence]] fires at most one step per attack per tick by kind: **Single** fires once then waits `next_step_delay`; **Repeat** re-fires every `repeat_interval` until `repeat_target` hits; **Multi** fires all its shots in one tick. Each fired shot becomes one [[server/spacetimedb/src/enemy/instance_tables.rs##pub struct BulletPatternEvent|BulletPatternEvent]] row — an `event` table, SpacetimeDB's fire-and-forget channel: the row never persists, it just streams the shot description (pattern params, origin, target, texture, lifetime) to subscribers in that transaction. When every attack exhausts its steps, the phase loops through `begin_phase_cycle`, honoring `phase_loop_delay` as a breather. ^enemy-5
6. The same tick then moves the enemy: [[server/spacetimedb/src/enemy/methods.rs##pub fn apply_movement|apply_movement]] reads the active phase's `MovementDef` and integrates one [[server/spacetimedb/src/main/global.rs##pub const BEHAVIOR_TICK_DT|BEHAVIOR_TICK_DT]] (0.1 s) step — `Stationary` holds; `Wander` picks a deterministic direction per active cycle from `splitmix64(enemy_id + cycle_index)` (reproducible for audits without storing any extra state); `Chase` homes on the aggro target's `PlayerPosition`; `Flee` runs directly away but only while inside `min_range` — all three gated on [[server/spacetimedb/src/enemy/methods.rs##pub fn cycle_phase|cycle_phase]] active/pause windows. The result goes through [[server/spacetimedb/src/world/wrap.rs##pub fn wrap_world_pos|wrap_world_pos]] and [[server/spacetimedb/src/world/hex.rs##pub fn world_to_chunk|world_to_chunk]]/[[server/spacetimedb/src/world/hex.rs##pub fn spiral_chunk_index|spiral_chunk_index]] — move-3's canonicalization — before the `Enemy` row is rewritten, keeping `chunk_index` fresh for the AOI view in enemy-7. ^enemy-6
7. Client side, enemies arrive through join-5's spawner like any other AOI entity: the game wave (join-3) subscribes the [[server/spacetimedb/src/enemy/views.rs##fn nearby_enemies|nearby_enemies]] view (`Enemy` rows OR-chained over the caller's nearby chunk indices — move-5's pattern), the anonymous full-table [[server/spacetimedb/src/enemy/views.rs##fn enemy_templates|enemy_templates]] view, and the whole `BulletPatternEvent` event table. The `NearbyEnemiesBinder` declared inline in [[main.tscn##[node name="NearbyEnemiesBinder" type="Node" parent="EntitySpawnerComponent"|main.tscn]] fires [[EntitySpawnerComponent.cs##private void OnEnemyInsert|OnEnemyInsert]], which instantiates the scene its `EnemyScene` export points at — [[main.tscn##EnemyScene = ExtResource("8_u50mg")|default_enemy.tscn]] — one puppet per row, keyed by `EnemyId`; `OnEnemyDelete` frees it. Because `BulletPatternEvent` is subscribed as a raw event table rather than an AOI-filtered view, every in-world client receives *every* enemy's shot events; each puppet keeps only its own (enemy-9) and the rest are discarded. ^enemy-7
8. The puppet itself, [[default_enemy.tscn##[node name="DefaultEnemy" type="CharacterBody2D"|default_enemy.tscn]], is an [[Enemy.cs##public partial class Enemy : CharacterBody2D, IEntity|Enemy]] root — a `CharacterBody2D` implementing `IEntity` with its own registry, the same pattern as `LocalPlayer` — with component children (`InterpolationComponent`, `HealthComponent`, `StatsComponent`, `FactionComponent`, `DamageReceivingComponent`) and two binders wired by `[connection]` entries at the bottom of the scene. The [[default_enemy.tscn##[node name="NearbyEnemiesBinder" type="Node" parent="."|NearbyEnemiesBinder]] (`ReplayExistingRows = true`, so cached rows replay through the same path) feeds [[Enemy.cs##private void OnEnemyRowInserted|OnEnemyRowInserted]]/[[Enemy.cs##private void OnEnemyRowUpdated|OnEnemyRowUpdated]]: both filter rows to this puppet's `EnemyId` (every puppet sees the whole nearby set), snap/retarget the interpolation component (move-6's machinery), load the `AnimatedSprite2D` frames from the template's `texture_id` via [[GameManager.cs##public static string? GetResPath(string textureId)|GameManager.GetResPath]], and mirror `hp` into `HealthComponent`. The `BulletPatternEventBinder` deliberately has no replay — replaying an event table would re-fire old shots. ^enemy-8
9. A kept event runs [[Enemy.cs##private void OnBulletPatternRowInserted|OnBulletPatternRowInserted]] → [[BulletManager.cs##public void SpawnEnemyBullet(BulletPatternEvent bulletPattern)|BulletManager.SpawnEnemyBullet]] → [[BulletSpawnerComponent.cs##public void SpawnEnemyBullet(BulletPatternEvent bulletPattern)|BulletSpawnerComponent.SpawnEnemyBullet]] on the `bullet_manager.tscn` entity spawned in join-4: the origin is the enemy's position plus the step's offset, and the base angle is [[BulletSpawnerComponent.cs##private static float ResolveTargetAngle|ResolveTargetAngle]] (the target `Identity`'s position read from the local row cache; `EnemyTarget::Idle` resolves to no target and angle 0) plus `base_angle_offset`. Then a per-pattern dispatch builds the bullet transforms — [[BulletSpawnerComponent.cs##private void SpawnRing|SpawnRing]] spreads `count` bullets over 360°, [[BulletSpawnerComponent.cs##private void SpawnCurtain|SpawnCurtain]] over `angle_span` with `gap_index` skipped, and [[BulletSpawnerComponent.cs##private void SpawnVolley|SpawnVolley]]/[[BulletSpawnerComponent.cs##private void SpawnShotgun|SpawnShotgun]]/[[BulletSpawnerComponent.cs##private void SpawnExplosion|SpawnExplosion]] jitter per-pellet speed/angle/lifetime through a client-side SplitMix64 seeded by `event_id` (mirroring the server's hash technique, so every client derives identical trajectories) — and hands them to the BlastBullets2D `BulletFactory2D` child via `spawn_directional_bullets`, a GDExtension that owns the actual bullet simulation. What a bullet does when it overlaps something — hit routing, `report_enemy_hit`, damage — is [[09 Combat & Damage]]. ^enemy-9

# Combat & Damage

1. The local player's offense lives on the [[local_player.tscn##[node name="CombatComponent" type="Node" parent="."|CombatComponent]] declared inline in `local_player.tscn`, its `HitZoneScene` export pointing at `hit_zone.tscn` and its `NearbyEnemiesBinder` child wired to [[CombatComponent.cs##private void OnNearbyEnemyDeletedRow()|OnNearbyEnemyDeletedRow]] at the bottom of the scene. [[CombatComponent.cs##private void OnInventoryChanged()|OnInventoryChanged]] (re-fired by `LocalPlayer`'s `InventoryChanged` signal) reads the equipped weapon's `WeaponBehavior` out of [[LocalPlayer.cs##public Item? EquippedWeapon|EquippedWeapon]] and derives the fire period (1 / `FireRate`) and the hit-zone spacing (`Range` / `ZoneCount`) from it — how items reach the weapon slot and what those stats mean is [[10 Inventory, Items & Enchantments]]. The aim-assist/lock-on scanner ([[CombatComponent.cs##private void ScanNearestEnemy|ScanNearestEnemy]]) is fully implemented but inert: `create_profile` hardcodes `aim_assist`/`lock_on` to false (lobby-5) and nothing ever sets them, so [[CombatComponent.cs##private Vector2 GetAimDir|GetAimDir]] always falls back to the player's facing direction. ^combat-1
2. Holding the left mouse button fires once per fire period from [[CombatComponent.cs##public override void _Process(double delta)|_Process]] → [[CombatComponent.cs##private void Fire()|Fire]], dispatching on the weapon's `WeaponPattern`: Single is one shot, Triple a `ShotCount`-wide fan over `SpreadAngle`, Cluster `ShotCount` pellets jittered with `GD.RandRange` ([[CombatComponent.cs##private void FireCluster|FireCluster]] — deliberately non-deterministic, unlike enemy-9's hashed pellets, because no other client ever needs to reproduce *your* shot). Every shot then does two separate things: spawn a purely visual tracer via [[BulletManager.cs##public void SpawnPlayerBullet(Vector2 origin, float angle|BulletManager.SpawnPlayerBullet]] — [[BulletSpawnerComponent.cs##private void SetupPlayerBullets|SetupPlayerBullets]] configures no collision layer or mask, so the projectile graphic can hit nothing — and lay down the *real* hitboxes via [[CombatComponent.cs##private void SpawnZonesAlong|SpawnZonesAlong]]. ^combat-2
3. `SpawnZonesAlong` instances one [[hit_zone.tscn##[node name="HitZone" type="Area2D"|hit_zone.tscn]] per `_zoneStep` of range along the aim line. A HitZone is a hitbox — an `Area2D` that *detects* victims, as opposed to a hurtbox, which is detected — and its scene makes the direction of detection explicit: [[hit_zone.tscn##collision_mask = 4|collision_mask = 4]] sees only enemy hurtboxes (the enemy puppet's `DamageReceivingComponent` sits on layer 4, combat-4), and [[hit_zone.tscn##monitorable = false|monitorable = false]] means nothing can detect the zone back. Each zone's [[HitZone.cs##public void Launch(float radius, float delay)|Launch]] sets its radius and starts the one-shot [[hit_zone.tscn##[node name="LifetimeTimer" type="Timer"|LifetimeTimer]] with a delay of `(i + 0.5) × _zoneStep / speed`, so the zone's report lands at the exact moment the visual tracer crosses its position — the timed-fuse trick that lets an area-overlap hit report masquerade as a projectile hit without the server ever simulating a bullet. On timeout, [[HitZone.cs##private void OnLifetimeTimeout()|OnLifetimeTimeout]] reports and frees the zone. ^combat-3
4. [[DamageComponent.cs##public int ReportHits()|ReportHits]] — inherited from `DamageComponent`, `HitZone`'s base class and its only live use (`damage_component.tscn` is one of the nine unreferenced duplicate component scenes) — asks the faction question before anything else: [[DamageComponent.cs##public bool CanDamage|CanDamage]] → [[FactionComponent.cs##public static bool CheckOpposition|CheckOpposition]] treats factions as bit flags ([[FactionComponent.cs##public enum Factions|Neutral = 1, Players = 2, Enemies = 4]]) and permits damage only when the two sides share no flag, so players can't hit players, and a zone — registered to the `LocalPlayer` entity by the framework's ancestor walk ([[02 The Component Framework]]) — inherits the shooter's faction. Each surviving hurtbox gets [[DamageReceivingComponent.cs##public void ProcessHit|ProcessHit]] (which emits `DidReceiveDamage` for observer components) and, because only the server may decide damage, one `Reducers.ReportEnemyHit(enemyId)` call. Note the trust split: the client decides *that* a hit happened; the server recomputes *how much* it does — and several zones along one path can each report the same enemy, with no rate-limit anywhere. ^combat-4
5. Server side, [[server/spacetimedb/src/enemy/reducers.rs##pub fn report_enemy_hit|report_enemy_hit]] guards the caller with `require_in_world` (move-3's guard), silently succeeds if the enemy id is already gone (a report can land after someone else's kill), and skips `immortal` enemies — a flag only the admin [[server/spacetimedb/src/main/admin.rs##pub fn spawn_enemy|spawn_enemy]] reducer can set ([[12 Admin & Debug]]). [[server/spacetimedb/src/combat/mod.rs##pub fn deal_damage_to_enemy|deal_damage_to_enemy]] then computes the attacker's damage server-side via [[server/spacetimedb/src/combat/mod.rs##pub fn compute_player_damage|compute_player_damage]] — the weapon slot's item `damage` (resolved through [[server/spacetimedb/src/player/methods.rs##pub fn weapon_behavior|weapon_behavior]]) scaled by `1 + strength × 0.002`, minimum 1, and 0 if no weapon is equipped; the report carried only an enemy id, so there is no client number to trust. A kill runs enemy-3's `despawn_enemy_archetype` and awards XP through [[server/spacetimedb/src/player/methods.rs##pub fn internal_gain_xp|internal_gain_xp]] (`template.max_hp / 10`, fallback 10 — the level math is [[04 Lobby & Profiles]]'s, the stat recomputation [[10 Inventory, Items & Enchantments]]'s). A non-kill recomputes the phase from HP thresholds (enemy-4's `compute_phase`, which the behavior tick then detects) and re-aggros the enemy onto the attacker — unless a phase transition just ran `recompute_aggro` fresh, or the previous hit's `aggro_locked_until` hasn't expired. ^combat-5
6. The return direction starts from enemy-9's BlastBullets2D bullets, whose [[BulletSpawnerComponent.cs##private void SetupEnemyBullets|collision layer/mask 2]] makes them overlap exactly one thing in the game: the local player's hurtbox, the [[local_player.tscn##[node name="DamageReceivingComponent" parent="." unique_id=1719362505|DamageReceivingComponent]] on layer 2 in `local_player.tscn`. The factory node's `area_entered` reaches [[BulletHitRouterComponent.cs##private void OnEnemyBulletAreaEntered|OnEnemyBulletAreaEntered]] on the `bullet_manager.tscn` entity (connected in `OnRegistered`, because a GDExtension node can't participate in component wiring); it drops any overlap whose custom data isn't the [[BulletData.cs##public SequenceStepRef SourceStep|BulletData]] breadcrumb stashed at spawn — which also filters out combat-2's player tracers, since they carry none — then forwards to [[DamageReceivingComponent.cs##public void ProcessBulletHit|ProcessBulletHit]] → `Reducers.ReportHit(data.SourceStep)` (or calls `ReportHit` directly for anything else on layer 2, a fallback with no current occupants). The plugin auto-disables the bullet on *this* client only (the default max-collision-count of 1 is never overridden), so every other client keeps rendering the bullet that hit you — see [[09 Combat & Damage]] → Known gaps. ^combat-6
7. [[server/spacetimedb/src/player/reducers.rs##pub fn report_hit|report_hit]] resolves the base damage from the [[server/spacetimedb/src/enemy/instance_tables.rs##pub enum SequenceStepRef|SequenceStepRef]] the client echoed back — Single → that `SingleStepDef`'s `damage`, Repeat → the per-enemy `RepeatStepInstance`'s `damage`, Multi → the indexed shot's `damage` — the one place the step definitions' `damage` fields (enemy-1) are actually read. This lookup works at report time because the def tables *persist*, while the `BulletPatternEvent` that carried the shot is long gone (event tables never persist, enemy-7). [[server/spacetimedb/src/combat/mod.rs##pub fn deal_damage_to_player|deal_damage_to_player]] mitigates through [[server/spacetimedb/src/combat/mod.rs##pub fn compute_incoming_damage|compute_incoming_damage]] (`damage × (1 − defense × 0.002)`, minimum 1) and subtracts with `saturating_sub`. A survivor's new `PlayerData.hp` flows back through the game wave to the `LocalPlayerDataBinder` and mirrors into [[LocalPlayerDataComponent.cs##HealthComponent?.SetFromServer(data.Hp, data.MaxHp)|HealthComponent.SetFromServer]] — [[HealthComponent.cs##public void SetFromServer|HealthComponent]] is a read-only mirror with no `Damage()`/`Heal()` methods; it just diffs consecutive server values and emits decrease/increase/zero signals. ^combat-7
8. If the subtraction reaches zero, `deal_damage_to_player` performs the whole death in one transaction: [[server/spacetimedb/src/player/methods.rs##pub fn teardown_profile|teardown_profile]] deletes every per-profile row (the same helper lobby-6's `delete_profile` uses — one table list per entity, per [[02 The Component Framework]]'s archetype rule), then the join-1 row move runs in reverse — delete `LoggedInPlayer`, insert `LoggedOutPlayer` — parking the player back in the lobby exactly as join-6's `leave_world` does. The client's `local_player` view row vanishes, the join-6 despawn path frees the player and bullet manager and re-shows the lobby: dying and leaving the world are the same exit. (The reverse adjustment, [[server/spacetimedb/src/combat/mod.rs##pub fn heal_player|heal_player]] clamped to `max_hp`, exists only to serve consumables — [[10 Inventory, Items & Enchantments]]; the lingering-row side of teardown is [[13 Disconnect & Teardown]].) ^combat-8

# Inventory, Items & Enchantments

1. Every client's item knowledge arrives with the always-on **base wave** ([[TableSubscriber.cs##public static readonly string[] BaseTables|BaseTables]] = `AllTextures`/`AllItems`/`AllEnchantments`): three public anonymous views — [[server/spacetimedb/src/item/views.rs##fn all_items|all_items]], [[server/spacetimedb/src/item/views.rs##fn all_enchantments|all_enchantments]], and `all_textures` from the world module — whose rows were seeded at publish time by boot-4's `init` calling [[server/spacetimedb/src/item/seeds.rs##pub fn seed_world_items|seed_world_items]] / [[server/spacetimedb/src/item/seeds.rs##pub fn seed_world_enchantments|seed_world_enchantments]] (six items, five enchantments). The [[main.tscn##[node name="CatalogComponent" type="Node" parent="."|CatalogComponent]] declared inline in `main.tscn` caches each view in a dictionary via its three child binders and answers every lookup — [[CatalogComponent.cs##public Item? GetItem(string itemId)|GetItem]] / `GetEnchantment` / `GetEnchantments` / `GetResPath` — behind the [[GameManager.cs##public static Item? GetItem(string itemId)|GameManager]] facade, so no UI or gameplay code touches subscription tables directly. (The `catalog_component.tscn` its docstring mentions is one of the nine unreferenced duplicate component scenes — `main.tscn` is the live wiring.) ^equip-1
2. The server-side inventory is one row: a [[server/spacetimedb/src/player/tables.rs##pub struct PlayerInventory|PlayerInventory]] keyed by `profile_id` holding a fixed 24-slot `Vec` of [[server/spacetimedb/src/player/tables.rs##pub struct InventorySlot|InventorySlot]] — each slot declares which `EquipSlot` types it accepts (`allowed_slots`), what it holds (`item_id`), and which enchantments are socketed (`enchantment_ids`). join-2's `try_scaffold_profile` builds the layout from factory helpers ([[server/spacetimedb/src/player/methods.rs##fn weapon_slot(item_id|weapon_slot]] and friends): slot 0 weapon-only, 1–4 consumable hotbar, 5–8 accessories, 9–12 armor, 13–14 artifacts, 15–22 general mixed (bounded by [[server/spacetimedb/src/main/global.rs##pub const GENERAL_SLOT_START|GENERAL_SLOT_START]]/[[server/spacetimedb/src/main/global.rs##pub const GENERAL_SLOT_COUNT|GENERAL_SLOT_COUNT]]), 23 bag — then hardcodes the starter loadout (Bow, Bread, Hat, Helmet, Skull, Bag). Slot *type* is data, not position convention: `swap_slots` enforces `allowed_slots` server-side, so the client's section split is presentation over the same rule. ^equip-2
3. Client side, the [[local_player.tscn##[node name="LocalPlayerInventoryComponent" type="Node" parent="."|LocalPlayerInventoryComponent]] declared inline in `local_player.tscn` mirrors the row: its child binder (`TableName = "LocalPlayerInventory"`, signals wired at the bottom of the scene) fires [[LocalPlayerInventoryComponent.cs##private void OnInventoryRow()|OnInventoryRow]] on both insert and update — the whole slot list is replaced either way — then raises `InventoryChanged` on the `LocalPlayer` entity via [[LocalPlayer.cs##internal void RaiseInventoryChanged|RaiseInventoryChanged]]. `LocalPlayer` exposes pass-through accessors ([[LocalPlayer.cs##public Item? EquippedWeapon => InventoryState|EquippedWeapon]], `GetSlotItemId`, `ResolveSlotAt`, the typed slot slices) so readers stay stable: combat-1's `CombatComponent` re-derives its fire period from `EquippedWeapon`, and the UI components of equip-4 repaint their icons. ^equip-3
4. The inventory UI is `inventory_panel.tscn`, instanced as `InventoryCanvas` under the local player ([[local_player.tscn##path="res://Scenes/UI/inventory_panel.tscn" id="9_inv"|local_player.tscn]]), with [[inventory_panel.tscn##[node name="InventoryCanvas" type="CanvasLayer"|a CanvasLayer root]] so it floats over the world. Its [[InventoryComponent.cs##public partial class InventoryComponent : ControlComponent|InventoryComponent]] toggles the Menu/Backpack against the always-on Hotbar on Tab ([[InventoryComponent.cs##public override void _Input(InputEvent @event)|_Input]]) and repaints slot icons from the catalog on `InventoryChanged`. The 29 [[SlotComponent.cs##public partial class SlotComponent : ControlComponent|SlotComponent]] panels (one per server slot in the menu, plus five hotbar echoes of slots 0–4) each carry their server `SlotIndex`; hovering one opens the sibling [[ItemSidebarComponent.cs##public void ShowSlot(uint slotIndex)|ItemSidebarComponent]], dragging one onto another calls `Reducers.SwapSlots(from, to)` from [[SlotComponent.cs##public override void _DropData(Vector2 atPosition, Variant data)|_DropData]], and right-clicking one inside the Backpack container calls `Reducers.DropItem` from [[SlotComponent.cs##public override void _GuiInput(InputEvent @event)|_GuiInput]] (loot-1). Every one of these is a fire-and-forget reducer call — the UI never mutates local state, it waits for equip-3's row update to come back. ^equip-4
5. [[server/spacetimedb/src/player/reducers.rs##pub fn swap_slots|swap_slots]] is the only way items move between slots: guarded by move-3's `require_in_world`, it validates *both* directions — the dragged item's `equip_slot` must be in the target's `allowed_slots`, and the target's occupant must be legal in the source slot (so you can't stash a helmet in the weapon slot even by swapping) — then exchanges the two slots' `item_id`s and runs equip-8's `recompute_stats`, because moving armor to the backpack *is* a stat change. Note it swaps only `item_id`: `enchantment_ids` stay in the slot they were socketed into — see [[10 Inventory, Items & Enchantments]] → Known gaps. ^equip-5
6. Pressing hotbar keys 1–4 fires `Reducers.UseItem(i + 1)` from [[InventoryComponent.cs##public override void _Process(double delta)|InventoryComponent._Process]] (guarded by a non-empty slot check). [[server/spacetimedb/src/player/reducers.rs##pub fn use_item|use_item]] requires the item to expose a `Consumable` behavior via [[server/spacetimedb/src/player/methods.rs##pub fn consumable_behavior|consumable_behavior]], applies it through [[server/spacetimedb/src/player/methods.rs##pub fn apply_consumable_effect|apply_consumable_effect]] — `Heal` calls combat-8's `heal_player` (clamped to `max_hp`), `Buff` inserts an [[server/spacetimedb/src/player/tables.rs##pub struct ActiveConsumableEffect|ActiveConsumableEffect]] row (`remaining` = duration) and recomputes immediately — then deletes the item from the slot: consuming is destruction. The [[server/spacetimedb/src/player/tables.rs##pub struct ConsumableEffectSchedule|ConsumableEffectSchedule]] row inserted by boot-4's `init` re-fires [[server/spacetimedb/src/player/reducers.rs##pub fn tick_active_consumable_effects|tick_active_consumable_effects]] every [[server/spacetimedb/src/main/global.rs##pub const CONSUMABLE_EFFECT_TICK_SECONDS|CONSUMABLE_EFFECT_TICK_SECONDS]] (1s), decrementing every active buff, deleting the expired ones, and recomputing the affected profiles — buffs wear off even if the player does nothing. ^equip-6
7. Enchanting is sidebar-driven: for a hovered equipment slot, [[ItemSidebarComponent.cs##private void RenderDetails|ItemSidebarComponent.RenderDetails]] shows `Sockets filled / max_enchantments`, one [[enchantment_row.tscn##[node name="EnchantmentRow" type="HBoxContainer"|enchantment_row.tscn]] per socketed enchantment, and — only when [[LocalPlayerInventoryComponent.cs##public static bool IsEquipmentSlot|IsEquipmentSlot]] says the slot is worn equipment — every catalog enchantment whose `allowed_slots` contains the item's `equip_slot`, each row's `ActionButton` wired to `Reducers.ApplyEnchantment` / `Reducers.RemoveEnchantment`. Server side, [[server/spacetimedb/src/player/reducers.rs##pub fn apply_enchantment|apply_enchantment]] re-checks all three rules the UI implied (slot type legal, under `max_enchantments`, not already socketed) before pushing the id and recomputing; [[server/spacetimedb/src/player/reducers.rs##pub fn remove_enchantment|remove_enchantment]] just retains the others. Enchantments are free and reversible — there is no cost, cooldown, or rarity roll anywhere in the code. ^equip-7
8. Every mutation above converges on [[server/spacetimedb/src/player/methods.rs##pub fn recompute_stats|recompute_stats]]: base attributes from `compute_base_stats(level)` (10 + level−1 in each of the six stats), then fold `StatModifier`s — `Flat` amounts sum into `flat[stat]`, `Mult` amounts into `mult[stat]` — from three sources: the items and socketed enchantments of **single-purpose slots only** (`allowed_slots.len() != 1` skips the slot, which is exactly why general-slot storage grants no stats), and every active consumable buff. The resolve formula is `round((base + flat) × (1 + mult))` per stat; the same formula with `StatKind::Hp` against `compute_base_max_hp(level)` (100 + 5 per level) yields `max_hp`, with current hp clamped down if it exceeds the new cap. The resulting `PlayerStats`/`PlayerData` rows ride the game wave back to the `local_player.tscn` binders, where [[LocalPlayerDataComponent.cs##private void OnStatsRow()|OnStatsRow]] pushes them into the [[StatsComponent.cs##public void SetFromServer(StatKind kind, int value)|StatsComponent]] mirrors (and `OnDataRow` into combat-7's `HealthComponent`), raising `StatsChanged` for [[StatsSidebarComponent.cs##private void HandleStatsChanged|StatsSidebarComponent]] — the client never computes a stat; it displays the server's round-trip. What Strength and Defense then *do* with those numbers is combat-5's and combat-7's scaling formulas. ^equip-8
9. Right-clicking a backpack slot (equip-4) lands in [[server/spacetimedb/src/player/reducers.rs##pub fn drop_item|drop_item]], which clears the slot's item *and* its enchantments, and inserts a [[server/spacetimedb/src/player/tables.rs##pub struct LootDrop|LootDrop]] row at the player's current position and chunk — carrying the enchantments with it (`enchantment_ids`), stamped with `dropped_by = ctx.sender()` and `expires_at = now + [[server/spacetimedb/src/main/global.rs##pub const LOOT_DROP_EXPIRY|LOOT_DROP_EXPIRY]]` (300s — a deadline nothing ever enforces; see [[10 Inventory, Items & Enchantments]] → Known gaps) — then recomputes, since dropping worn gear is a stat change. Today this reducer is the *only* producer of `LootDrop` rows; enemy kills award XP but no loot. ^loot-1
10. The new row reaches every nearby client through the AOI-filtered [[server/spacetimedb/src/player/views.rs##fn nearby_loot_drops|nearby_loot_drops]] view (same `PlayerChunk`-keyed OR-chain as move-5's other nearby views), and join-5's binder path does the rest: [[EntitySpawnerComponent.cs##private void OnDropInsert()|OnDropInsert]] instances [[drop.tscn##[node name="Drop" type="Node2D"|drop.tscn]], stamps `DropId`/`ItemId`/`DroppedBy`/position *before* `AddChild`, so [[Drop.cs##public override void _Ready()|Drop._Ready]] can forward them into its two components — [[DropVisualComponent.cs##public void SetItem(string itemId)|DropVisualComponent.SetItem]] resolves the item's texture through equip-1's catalog, and [[PickupComponent.cs##public void SetFromServer(ulong dropId, Identity? droppedBy)|PickupComponent.SetFromServer]] starts the one-shot 5-second `PickupLockTimer` ([[pickup_component.tscn##wait_time = 5.0|pickup_component.tscn]]) when the local player is the dropper — a grace period so you don't instantly re-vacuum what you just threw away. ^loot-2
11. Pickup is physical, not menu-driven: walking the local player into the drop's `Area2D` fires [[PickupComponent.cs##private void OnBodyEntered|OnBodyEntered]] (ignored while the loot-2 lock runs or the body isn't the `LocalPlayer`), which reports `Reducers.PickupDrop(DropId)`. [[server/spacetimedb/src/player/reducers.rs##pub fn pickup_drop|pickup_drop]] finds a home for the item — first empty *typed* slot accepting its `equip_slot`, else first empty general slot (equip-2's layout constants) — copies item and enchantments in, deletes the `LootDrop` row, and recomputes; the delete propagates back through the same view and join-5's `OnDropDelete` frees the node on every client. Like combat-4's hit reports, the server takes the client's word for the overlap: `pickup_drop` checks no distance and no `dropped_by` lock — the lock exists only client-side. ^loot-3

# Camera & Presentation

1. All camera state lives in one place: the [[main.tscn##[node name="CameraRigComponent" type="Node" parent="."]|CameraRigComponent declared inline in main.tscn]], a component of the `Main`/`GameManager` entity, holds the canonical `Yaw`, `PitchDegrees`, and `Distance` ([[CameraRigComponent.cs##public partial class CameraRigComponent : Component|CameraRigComponent]]) — the 2D and 3D presenters read it every frame and write their own phantom cameras, so neither presenter owns state and the two views can never disagree. The rig sits in the main scene tree, deliberately *not* inside camera-4's 3D SubViewport, because a node inside a SubViewport only receives input the `SubViewportContainer` forwards — mouse-motion events never arrive there, which is why the old arcball wired inside `World3DComponent` silently did nothing (per the class comment). [[CameraRigComponent.cs##protected override void OnRegistered()|OnRegistered]] defaults to pitch −90° (straight-down top-down) and distance 300, and the [[CameraRigComponent.cs##public float Zoom2D =>|Zoom2D]] property maps distance to 2D zoom as `ZoomReferenceDistance / Distance` — so the defaults land exactly on zoom 1.0. (`main.tscn` overrides the exported `PitchMax` to 0.) ^camera-1
2. Every camera input goes through the rig: [[CameraRigComponent.cs##public override void _Process(double delta)|_Process]] integrates `Camera_Left`/`Camera_Right` into yaw at `YawSpeed` (90°/s), and [[CameraRigComponent.cs##public override void _Input(InputEvent e)|_Input]] handles the rest of the [[project.godot##Camera_Snap_So_That_Cursor_Is_North|input map]] — `Zoom_In`/`Zoom_Out` scale `Distance` multiplicatively by `ZoomStep` (1.1, clamped 50–1200, so 2D zoom spans 6× down to 0.25×), `Reset_Camera_Yaw`/`Reset_Camera_Pitch` restore the defaults, and holding `Arcball_Camera_Controls` captures the mouse to drag yaw and pitch, warping the cursor back to where the drag started on release. The two cursor-snap actions compute the angle from the player's on-canvas position to the cursor, add it to yaw so the cursor ends up north (or east/west) of the player, and warp the mouse to that screen edge — the camera turns *to* your cursor instead of making you drag it around. All of it is gated on `LocalPlayer.Local != null`, so camera input is inert in the lobby. The same yaw steers movement: [[LocalPlayer.cs##public override void _PhysicsProcess(double delta)|LocalPlayer._PhysicsProcess]] rotates the WASD vector by `cameraRig.Yaw` and sets the body's `Rotation = yaw` while moving, so "Up" always means screen-up however the camera is turned (the position-sync half of that method is [[06 Movement & Position Sync]]). ^camera-2
3. The 2D presenter is the [[main.tscn##[node name="Camera2DPresenterComponent" type="Node2D" parent="."]|Camera2DPresenterComponent declared inline in main.tscn]], but the camera it drives belongs to the player: join-4's `LocalPlayer._Ready` hands over its own [[local_player.tscn##[node name="LocalPlayerPhantomCamera2D" type="Node2D" parent="."|LocalPlayerPhantomCamera2D]] (follow target = the `DamageReceivingComponent` child, tween duration 0 — snap, no glide) via [[Camera2DPresenterComponent.cs##public void RegisterCamera(Node2D pcamNode)|RegisterCamera]], which raises the phantom camera's priority to 60. Priority is the phantom-camera addon's whole switching mechanism: the [[main.tscn##[node name="PhantomCameraHost" type="Node" parent="MainCamera2D"]|PhantomCameraHost]] child of the real [[main.tscn##[node name="MainCamera2D" type="Camera2D" parent="."]|MainCamera2D]] copies whichever phantom camera has the highest priority — lobby-2 holds the menu's `MainMenuPhantomCamera2D` at 60 while the lobby is open, lobby-7's `HideLobby` drops it to 0 on join, and this registration raises the player's to 60 in the same breath. Each frame [[Camera2DPresenterComponent.cs##public override void _Process(double delta)|the presenter's _Process]] then writes `RotationOffset = rig.Yaw` and `Zoom = rig.Zoom2D`; the pcam's `rotate_with_target` flag is set but its follow target never rotates locally (`LocalPlayer` rotates itself, not the child), so all camera rotation actually arrives through the offset. On leave or death, [[LocalPlayer.cs##public override void _ExitTree()|LocalPlayer._ExitTree]] calls [[Camera2DPresenterComponent.cs##public void UnregisterCamera()|UnregisterCamera]], which zeroes the priority behind an `IsInstanceValid` guard, because the pcam — a child of the dying player — may already be freed. ^camera-3
4. The 3D layer is a second world rendered into a texture: [[main.tscn##[node name="3D" type="CanvasLayer" parent="."]|main.tscn's `3D` CanvasLayer]] holds a full-rect `SubViewportContainer` whose [[main.tscn##[node name="SubViewport" type="SubViewport" parent="3D/SubViewportContainer"]|SubViewport]] (384×216, transparent background, `handle_input_locally = false`) instances [[world_3d.tscn##[node name="World3DComponent" type="Node3D" unique_id=1360330812]|world_3d.tscn]] — a `World3DComponent` root with a `DirectionalLight3D`, a procedural-sky `WorldEnvironment`, a third-person [[world_3d.tscn##[node name="PhantomCamera3D" type="Node3D" parent="."]|PhantomCamera3D]] (`follow_mode` 6 = SpringArm3D follow, on `host_layers` 2 so it never contests the 2D pcam's default layer), and the real `Camera3D` with its own `PhantomCameraHost`. A CanvasLayer renders above the world canvas, so the 3D view composits *over* the 2D world, and the transparent background lets only the rendered models show through. [[World3DComponent.cs##public partial class World3DComponent : Node3DComponent|World3DComponent]] registers with the `GameManager` entity through the SubViewport ancestor walk ([[02 The Component Framework]]), which makes the rig its sibling component, and its [[World3DComponent.cs##public override void _Process(double delta)|_Process]] pushes `rig.PitchDegrees`, *negated* `rig.Yaw`, and `rig.Distance` into the spring arm every frame — negated because 2D rotation runs clockwise in Godot's y-down space while 3D yaw about +Y runs counter-clockwise, a sign convention the code states once, here, and nowhere else. ^camera-4
5. The only 3D *content* is the local player's model: join-4's `_Ready` also builds a [[CharacterModel3D.cs##public CharacterModel3D(PackedScene scene|CharacterModel3D]] from the exported [[local_player.tscn##KnightScene = ExtResource("2_tfukw")|Knight scene]], parenting it into the 3D world at scale 50 and aiming the pcam3D at it through [[World3DComponent.cs##public void SetCameraFollowTarget(Node3D model)|SetCameraFollowTarget]]. `CharacterModel3D` is a plain C# class rather than a node — a handle owning one instantiated `Node3D` — because the model lives in a different scene tree (the SubViewport) from its 2D owner and can't be scene-wired; every physics frame [[CharacterModel3D.cs##public void SyncFrom2D(Vector2 pos, float yaw2D)|SyncFrom2D]] copies the 2D `GlobalPosition` to `(x, 0, z)` with the same negated yaw, and `_ExitTree` disposes it and clears the follow target. Remote players and enemies get no 3D model — they stay 2D sprites (move-6) — so the 3D layer is a cosmetic skin over the authoritative 2D simulation, never a second simulation. ^camera-5
6. Two debug overlays render the hex grid itself, both fed by the game wave's `MapConfig` row (join-3) through their own child binders — the second and third `MapConfigBinder`s after terrain-7's. The 2D [[main.tscn##[node name="HexGridOverlayComponent" type="Node2D" parent="."]|HexGridOverlayComponent]] in `main.tscn` queues a redraw whenever the camera moves or zooms ([[HexGridOverlayComponent.cs##public override void _Process(double delta)|_Process]]) and [[HexGridOverlayComponent.cs##public override void _Draw()|_Draw]]s every hex in view — chunks 3-colored by `(cq − cr) mod 3` so no two adjacent chunks share a color, each hex labeled with its hex coords, chunk coords, and [[HexGridOverlayComponent.cs##private static long HexSpiralIndex|HexSpiralIndex]] (a direct port of the server's `spiral_chunk_index`, [[07 Terrain & World Streaming]]) — but the node is declared `visible = false`, so it stays subscribed and keeps tracking the camera while drawing nothing (see [[11 Camera & Presentation]] → Known gaps). Its 3D sibling, the [[world_3d.tscn##[node name="HexGridOverlay3DComponent" type="Node3D" parent="."]|HexGridOverlay3DComponent]] in `world_3d.tscn`, *is* visible and doubles as the 3D ground: [[HexGridOverlay3DComponent.cs##private void RefreshTiles(Vector3 center)|RefreshTiles]] maintains a 12-hex-radius ring (`ViewRadiusHexes`) of tinted KayKit hex-grass tiles around the player — purple/pink/grey by `(2cq + cr) mod 3` — spawning and freeing tiles as the player crosses hex boundaries, with a `Label3D` of hex/chunk/spiral coords floating over each one. ^camera-6
7. The server never sees the camera, but it hard-codes what the camera can see: [[server/spacetimedb/src/main/global.rs##pub const CLIENT_VIEWPORT_HEIGHT_PX|CLIENT_VIEWPORT_HEIGHT_PX]] (360 px) divided by [[server/spacetimedb/src/main/global.rs##pub const CLIENT_CAMERA_ZOOM|CLIENT_CAMERA_ZOOM]] (0.75) and halved gives [[server/spacetimedb/src/main/global.rs##pub const CAMERA_VIEW_RADIUS|CAMERA_VIEW_RADIUS]] = 240 world units — the assumed half-height of the visible screen. Enemy simulation ranges are multiples of it (enemy-4's move range and enemy-5's attack range are each `factor × CAMERA_VIEW_RADIUS`, so templates stay correctly scaled if the camera changes), and [[server/spacetimedb/src/main/global.rs##pub const SIMULATION_CHUNK_RINGS|SIMULATION_CHUNK_RINGS]] (2) is the chunk pre-filter that must cover the largest such range or simulation silently stops. Note the 0.75 matches the zoom of the [[local_player.tscn##[node name="Camera" type="Camera2D" parent="."]|disabled legacy Camera2D]] in `local_player.tscn`, not the live rig's default zoom of 1.0 — see [[11 Camera & Presentation]] → Known gaps. ^camera-7

# Admin & Debug

1. Adminhood is a flag on the lobby/world row, claimed first-come-first-served: [[server/spacetimedb/src/main/admin.rs##pub fn claim_admin|claim_admin]] scans *both* `LoggedInPlayer` and `LoggedOutPlayer` for any existing `is_admin` and refuses if one exists — a single global admin slot — otherwise it updates whichever of the caller's two rows is present, flipping `is_admin` to true (an idempotent no-op if already set). [[server/spacetimedb/src/main/admin.rs##pub fn release_admin|release_admin]] flips it back and is the only way to free the slot. The flag survives the join-1 row move because `join_world` copies `username`/`is_admin` from the `LoggedOutPlayer` row into the `LoggedInPlayer` row, so an admin stays admin across lobby↔world transitions; the guard every other step here uses is [[server/spacetimedb/src/player/methods.rs##pub fn is_admin|is_admin]], which reads the flag off whichever row the caller currently has. ^admin-1
2. Every admin reducer is CLI-only: no client script calls any of them (they're driven with `spacetime call` against the running database), and each opens with the same `if !is_admin(ctx) { return Err("Admin only.") }` gate from admin-1. Reducers that act on a *player* resolve their target through two helpers: [[server/spacetimedb/src/main/admin.rs##pub fn find_player_by_username|find_player_by_username]] chains both player tables and matches a case-insensitive username, a full identity hex, or an identity-hex *prefix* (so a few hex characters of the identity are enough), and [[server/spacetimedb/src/player/methods.rs##pub fn find_profile_by_name|find_profile_by_name]] then picks the profile by case-insensitive name among that player's own profiles — the same targeting pair doc 10's `give_item`/`remove_item` use. ^admin-2
3. [[server/spacetimedb/src/main/admin.rs##pub fn change_stats|change_stats]] overwrites a profile's six base stats ([[server/spacetimedb/src/player/tables.rs##pub struct PlayerStats|PlayerStats]]) directly, keeping the rest of the row — but the write is *fragile by construction*: [[server/spacetimedb/src/player/methods.rs##pub fn recompute_stats|recompute_stats]] rebuilds those same six fields from `compute_base_stats(level)` plus item/enchantment/consumable modifiers every time gear or effects change, so the admin-set values silently revert on the next recompute. The item-side admin reducers ([[server/spacetimedb/src/item/reducers.rs##pub fn give_item|give_item]] into the first empty general slot, [[server/spacetimedb/src/item/reducers.rs##pub fn remove_item|remove_item]] stripping the item id from every slot that has it) have the mirror-image quirk: they edit `PlayerInventory` *without* calling `recompute_stats`, so a granted weapon's stats don't apply until something else triggers one — both halves are detailed in [[10 Inventory, Items & Enchantments]]. ^admin-3
4. Catalog content is editable live through natural-key upserts: [[server/spacetimedb/src/main/admin.rs##pub fn upsert_texture_entry|upsert_texture_entry]] (texture catalog), [[server/spacetimedb/src/item/reducers.rs##pub fn upsert_item|upsert_item]]/[[server/spacetimedb/src/item/reducers.rs##pub fn upsert_enchantment|upsert_enchantment]] (item/enchantment defs), and [[server/spacetimedb/src/main/admin.rs##pub fn upsert_enemy_template|upsert_enemy_template]] each update by primary key if the row exists and insert otherwise — the same upsert-by-natural-key pattern as boot-4's `Seed` trait, exposed as runtime reducers so content can be patched without a republish. ^admin-4
5. Enemy *behavior* authoring is live too: [[server/spacetimedb/src/main/admin.rs##pub fn upsert_movement_def|upsert_movement_def]], [[server/spacetimedb/src/main/admin.rs##pub fn upsert_single_step_def|upsert_single_step_def]], [[server/spacetimedb/src/main/admin.rs##pub fn upsert_repeat_step_def|upsert_repeat_step_def]], and [[server/spacetimedb/src/main/admin.rs##pub fn upsert_multi_step_def|upsert_multi_step_def]] edit the shared def tables enemy-1's `seq_*` helpers seed. Because their `def_id` is auto-increment, passing 0 inserts a new row (discoverable afterwards via `spacetime sql`) while a real id updates in place — a footgun, since passing 0 with the intent to update *creates* a def nothing references. Either way only *future* spawns see the change: enemy-3's `spawn_enemy_archetype` instantiates templates into per-enemy rows at spawn time, so live enemies keep the behavior they were born with. ^admin-5
6. [[server/spacetimedb/src/main/admin.rs##pub fn spawn_enemy|spawn_enemy]]/[[server/spacetimedb/src/main/admin.rs##pub fn despawn_enemy|despawn_enemy]] route through the same archetype helpers as natural spawning (enemy-3), so an admin-spawned enemy is indistinguishable from a spawned one downstream — same per-enemy behavior rows, same AOI delivery to clients. `spawn_enemy` canonicalizes the requested position first ([[server/spacetimedb/src/world/wrap.rs##pub fn wrap_world_pos|wrap_world_pos]] + `world_to_chunk` + `spiral_chunk_index`, move-3's pipeline, against the live `MapConfig`), and it is the *only* way to set the `is_elite`/`immortal` flags — natural spawns hardcode both to false in `spawn_from_biome_regions`, so the `immortal` early-return in `report_enemy_hit` ([[09 Combat & Damage]]) and the seeded "TestBossP2–P6" templates (which no `BiomeRegion` references, enemy-1/enemy-2) are reachable only through this reducer. ^admin-6
7. World-shape reducers are thin admin gates over the publish-time machinery: [[server/spacetimedb/src/main/admin.rs##pub fn add_chunks|add_chunks]]/[[server/spacetimedb/src/main/admin.rs##pub fn clear_chunks|clear_chunks]] wrap boot-5's `internal_add_chunks` (inserting `BuildingTile` rows and upserting the `MapConfig` row) and delete every `BuildingTile` respectively — `clear_chunks` leaves `MapConfig` alone, so the grid dims survive a tile wipe. [[server/spacetimedb/src/main/admin.rs##pub fn upsert_world_def|upsert_world_def]]/[[server/spacetimedb/src/main/admin.rs##pub fn upsert_biome_def|upsert_biome_def]]/[[server/spacetimedb/src/main/admin.rs##pub fn upsert_biome_region_def|upsert_biome_region_def]] edit the generation inputs, and [[server/spacetimedb/src/main/admin.rs##pub fn generate_world_proc|generate_world_proc]]/[[server/spacetimedb/src/main/admin.rs##pub fn generate_world_manual|generate_world_manual]] re-run terrain-1's two front-ends on demand — which means `clear_world_geometry` deletes and rewrites every `BiomeRegion`/`TriangleTile`/`HexDecor` row *while players are subscribed*, so a live regen streams a full terrain teardown-and-rebuild through every client's AOI views (terrain-6) with no warning. ^admin-7

The server-side debug channel is opt-in and SQL-only: the admin-gated [[server/spacetimedb/src/main/debug.rs##pub fn toggle_debug|toggle_debug]] inserts a [[server/spacetimedb/src/main/debug.rs##pub struct PlayerPositionDebugSchedule|PlayerPositionDebugSchedule]] row (a 1-second interval schedule — the same scheduled-reducer mechanism boot-4 uses for enemy ticks) or, if one exists, deletes it *and* wipes the data table. While scheduled, [[server/spacetimedb/src/main/debug.rs##pub fn tick_player_position_debug|tick_player_position_debug]] mirrors every `PlayerPosition` row into [[server/spacetimedb/src/main/debug.rs##pub struct PlayerPositionDebug {|PlayerPositionDebug]] with `world_to_hex`-derived `hex_q`/`hex_r` added (the debug value: server positions pre-decoded into the hex addressing of terrain-2), deleting rows whose player no longer has a position row. The table is not `public` and nothing client-side subscribes it — it's inspected with `spacetime sql` by the module owner. ^admin-8

The client-side half is the [[main.tscn##[node name="DebugOverlay" type="CanvasLayer" parent="."]|DebugOverlay declared inline in main.tscn]] (a `CanvasLayer` at layer 100 so it draws over every other layer, declared `visible = false`): [[DebugOverlay.cs##public override void _Input(InputEvent @event)|_Input]] toggles visibility on the P key, and while visible [[DebugOverlay.cs##public override void _Process(double delta)|_Process]] rewrites its child `Label` every 0.25 s ([[DebugOverlay.cs##private const double UpdateInterval|UpdateInterval]]) with `Performance.GetMonitor` readouts — FPS, frame time in ms, static memory, object/node/draw-call counts — plus [[GameManager.cs##public static int EnemyCount|GameManager.EnemyCount]], the facade's read of join-5's spawner dictionary. It's purely local instrumentation: it calls no reducer and subscribes no table. (`Scenes/UI/debug_overlay.tscn` is one of the nine unreferenced duplicate component scenes, [[02 The Component Framework]] → Known gaps.) ^admin-9

# Disconnect & Teardown

1. There are exactly three server-side exits from the world, and they share one shape. [[server/spacetimedb/src/player/reducers.rs##pub fn leave_world|leave_world]] — guarded by the `LoggedInPlayer` lookup itself ("Not in world.") — deletes the caller's [[server/spacetimedb/src/player/tables.rs##pub struct LoggedInPlayer|LoggedInPlayer]] row and inserts a [[server/spacetimedb/src/player/tables.rs##pub struct LoggedOutPlayer|LoggedOutPlayer]] row carrying `username`/`is_admin` over: join-1's row move in reverse, with **no** profile teardown, so level, gear, and position survive logout and join-2's lazy scaffolding makes the rejoin cheap. Combat death (combat-8) runs [[server/spacetimedb/src/player/methods.rs##pub fn teardown_profile|teardown_profile]] first — a full progress reset that keeps the `PlayerProfile` row — then performs the same row move; lobby-6's `delete_profile` runs the same teardown and deletes the profile row too. Nothing in the client calls `LeaveWorld` today ([[05 Joining the World]] → Known gaps), so in practice this reducer is CLI-only. ^end-1
2. Whichever exit fired, the client side is driven entirely by row deletes. The row move empties every game-wave view at once — the caller-scoped `local_player*` views fall back to their `u64::MAX` sentinel, and [[server/spacetimedb/src/player/views.rs##pub(crate) fn nearby_indices_from_chunk|nearby_indices_from_chunk]] returns `None` without a `LoggedInPlayer` row, collapsing the AOI views — so the `LocalPlayerBinder` declared inline in `main.tscn` (join-4) fires `RowDeleted`, and [[EntitySpawnerComponent.cs##private void OnLocalPlayerDelete()|OnLocalPlayerDelete]] `QueueFree`s the `LocalPlayer` and the `BulletManager` (join-4's pair; the phantom camera unregisters itself through camera-3's `_ExitTree` path). Then, only if the connection is still active, it reverses lobby-7's wave swap — [[LobbyComponent.cs##public void ShowLobby|ShowLobby]] (menu camera priority back to 60), [[TableSubscriber.cs##public void SubscribeLobby()|SubscribeLobby]] in, [[TableSubscriber.cs##public void UnsubscribeGame()|UnsubscribeGame]] out — while the emptied `nearby_*` views run the matching [[EntitySpawnerComponent.cs##private void OnNearbyRemotePlayerDelete()|OnNearbyRemotePlayerDelete]] / `OnEnemyDelete` / `OnDropDelete` handlers, each freeing its node out of the spawner's tracking dictionaries. Dying and leaving the world are the same exit on the client, exactly as join-6 noted. ^end-2
3. Closing the app or losing the network is the unplanned exit: SpacetimeDB runs the [[server/spacetimedb/src/main/lifecycle.rs##pub fn client_disconnected|client_disconnected]] lifecycle reducer whenever a connection ends — graceful quit or crash alike — and it performs the same row move as end-1 (delete `LoggedInPlayer`, insert `LoggedOutPlayer` with `username`/`is_admin` preserved), again with no teardown. A player who was sitting in the lobby matches no `LoggedInPlayer` row, so their `LoggedOutPlayer` row simply stays. On the client, a clean quit runs [[DatabaseConnector.cs##public override void _ExitTree()|DatabaseConnector._ExitTree]] → `Conn.Disconnect()`, but [[DatabaseConnector.cs##private void OnDisconnected(DbConnection conn, Exception? e)|OnDisconnected]] — the callback for *losing* the connection — only logs the error: no despawn, no reconnect, no return to the lobby, so a dropped client keeps rendering its last world state (see [[13 Disconnect & Teardown]] → Known gaps). ^end-3
4. Because end-1 and end-3 both skip teardown, the [[server/spacetimedb/src/player/tables.rs##pub struct PlayerPosition|PlayerPosition]]/[[server/spacetimedb/src/player/tables.rs##pub struct PlayerChunk|PlayerChunk]] rows outlive every logout and disconnect — "ghosts" deleted only by `teardown_profile` (death or `delete_profile`). Instead of cleaning them up, every consumer guards against them with a `logged_in_player` semijoin: [[server/spacetimedb/src/enemy/methods.rs##pub fn has_player_in_simulation_range|has_player_in_simulation_range]] (enemy-4's audience gate — its own comment states this exact reason), [[server/spacetimedb/src/enemy/methods.rs##pub fn has_player_near_spawn_point|has_player_near_spawn_point]] (enemy-2's spawn gate), [[server/spacetimedb/src/enemy/methods.rs##pub fn find_nearest_player_id|find_nearest_player_id]] (aggro targeting) and [[server/spacetimedb/src/enemy/methods.rs##pub fn find_player_pos_by_id|find_player_pos_by_id]] (chase/flee movement), plus the [[server/spacetimedb/src/player/views.rs##fn nearby_remote_players(ctx|nearby_remote_players]] / `nearby_remote_players_profiles` views. The net effect: a ghost is invisible to other clients and inert to the simulation, but it occupies its rows until the profile dies or is deleted. ^end-4
5. Everything else per-profile persists across logout too — [[server/spacetimedb/src/player/tables.rs##pub struct PlayerData|PlayerData]] (level/xp/hp), `PlayerInventory`, `PlayerStats`, and any active [[server/spacetimedb/src/player/tables.rs##pub struct ActiveConsumableEffect|ActiveConsumableEffect]] buffs — and the buffs are the one place the end-4 guard pattern is absent: equip-6's [[server/spacetimedb/src/player/reducers.rs##pub fn tick_active_consumable_effects|tick_active_consumable_effects]] iterates *all* active effects with no logged-in check, so a buff keeps ticking down and expires while its owner is logged out, each expiry triggering a `recompute_stats` on an offline profile (harmless — it touches only that profile's own rows — but the countdown doesn't pause). Meanwhile admin-8's `PlayerPositionDebug` mirror reflects *every* `PlayerPosition` row including ghosts, which makes the debug table double as a ghost-row detector. ^end-5
6. Reconnecting replays boot with the same identity: conn-1's saved token means `client_connected` (conn-2) finds the end-3 `LoggedOutPlayer` row already present and changes nothing, and rejoining the same profile skips all of join-2's scaffolding — progress, and even the ghost position, are picked up where they were left. The client side of "leaving" is thinner: [[LobbyGui.cs##public void CharSlotsPressed|CharSlotsPressed]]'s `ChangeSceneToFile("res://Scenes/main.tscn")` is the only scene switch in the game — there is no path back to the main-menu scene, and end-2's `ShowLobby` is an in-scene overlay, not a scene change — so "exit to main menu" doesn't exist short of restarting the app. (The pathological reconnect — the server still thinking you're in-world — is conn-2's already-in-world bug, [[03 Boot & Connection]] → Known gaps.) ^end-6
