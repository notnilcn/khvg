# client/AGENTS.md

Per-file map of the Godot client. See the root `AGENTS.md` for the project-wide domain map, folders to skip, and run/publish commands.

100% C# (Godot 4.7, .NET 8) and fully compositional, modeled on the **Comedot** component framework.

## Naming convention

Every high-level parent node's children are **components named `<Role>Component`** — node name = class name = file name (the `HealthComponent` node in a `.tscn` is an instance of `HealthComponent.cs`). Exceptions:

- Pure data nodes with zero behavior: `CollisionShape2D` inside Area components, `SpriteFrames`, the BlastBullets GDExtension node, phantom_camera addon nodes.
- `TableBinderComponent` children: node name is `<Table>Binder` (e.g. `NearbyEnemiesBinder`), not the class name — one per consumed table, signals wired in the `.tscn`.
- Code-instantiated scenes whose count is data-driven: server-row entities, `HitZone`s, enchantment rows, profile panels, terrain MultiMesh batch leaves + the chunk pool.

Nodes are declared in the `.tscn`, not built in code, wherever feasible.

## `client/sstdbsdk/` — connection + subscription layer (first-party)

Everything else here depends on these three. Not under `addons/`, despite the name.

- `DatabaseConnector.cs` — **autoload singleton** (`DatabaseConnector.Instance`, declared in `project.godot` as `res://sstdbsdk/DatabaseConnector.tscn` — a one-node scene whose only job is attaching the script to a `Node` — *not* a child of Main). Owns the `DbConnection` (`Conn`), pumps `FrameTick()` every frame (try/catch — a throwing table callback is logged and the pump keeps going), does the `IsLocal` identity check, exports `Host`/`DbName`. Consumers wire table callbacks from its `Connected` signal — guard with `Conn?.IsActive` first, since the autoload can finish connecting before Main loads. A dropped connection (not deliberate shutdown) emits `Disconnected` — `ConnectionLostComponent` (below) shows the reconnect panel off it; reconnect = `Connect()` again (rebuilds `Conn` with the saved token) + back through `main_menu.tscn`, no auto-rejoin. Token persistence is the SpacetimeDB SDK's own `AuthToken` helper (there is no first-party `AuthToken.cs`); `--pN` launch args (exact `^--p\d+$` match — a prefix match also caught Godot's own `--path`) suffix the token key for parallel run instances.
- `TableSubscriber.cs` — subscription waves (base/lobby/game) as the static `BaseTables`/`LobbyTables`/`GameTables` name lists — the single source of truth for "what is subscribed", built into SQL via the generated `From` API. Also exposes `LapQ`/`LapR` torus lap vectors from `MapConfig` as **statics** (read directly by `InterpolationComponent` per entity per frame; reset to zero in `_ExitTree`). `_ExitTree` unhooks `Connected` + the `MapConfig` row handlers and unsubscribes both wave handles (skipped when the connection is already dead — the hooks die with the old `DbConnection`).
- `TableBinderComponent.cs` — `[Tool]` node binding one subscribed table (`TableName` dropdown from `TableSubscriber.AllSubscribedTables`) and re-exposing its row events as editor-wireable Godot signals (`RowInserted`/`RowUpdated`/`RowDeleted`). Signals carry no args (rows aren't Variant-compatible) — handlers read `LastRow`/`LastOldRow`/`LastDeletedRow` and cast. `ReplayExistingRows` replays cached rows through `RowInserted` on bind — **never enable it on event tables** (`BulletPatternEvent`/`BulletControlEvent`): no last-seen-id tracking exists, so replay would re-fire the table's whole history on scene entry.

**This is the standard way every component consumes table row events** — place one binder child per table on the consuming component and wire its signals in the `.tscn`; no direct `conn.Db.*.OnInsert/OnUpdate/OnDelete` hooks outside this folder. See the inline binder declarations and signal connections in `game.tscn` (Catalog/EntitySpawner/Terrain components) and `local_player.tscn`. Only infrastructure keeps internal hooks: `TableSubscriber` (`MapConfig` lap vectors) and `DatabaseConnector` (`LocalLobbyPlayer`).

## Module Map (`Scripts/`)

### `Components/` + `Entities/` (entity/component framework)

Server-authoritative rule: components never mutate health/stats locally. They *mirror* server rows (`SetFromServer(...)`) and emit signals for observers, and they *report* hits via reducers — the server computes damage and the updated row flows back into the mirror.

- `IComponent.cs` — the whole contract is one member: an `Entity` back-reference to the owning `IEntity` (null before `_Ready`, null again after `_ExitTree`).
- **The lifecycle lives in the base classes, not in `ComponentRegistration`.** One base per native root type, because C# has single inheritance: `Component.cs` (`Node`), `AreaComponent.cs` (`Area2D` — hitboxes/hurtboxes), `Node2DComponent.cs` (`Node2D`), `Node3DComponent.cs` (`Node3D`), `ControlComponent.cs` (`Control`), `VisualComponent.cs` (`AnimatedSprite2D`). Each one's `_Ready` registers with the nearest `IEntity` ancestor, runs `OnRegistered()`, then `CallDeferred`s a pass that validates `GetRequiredComponents()` and runs `OnEntityReady()` — deferred so every sibling has finished its own `_Ready`. `_ExitTree` unregisters, so dynamically spawned components (e.g. `HitZone`) don't leak in the registry. Override points: `OnRegistered`, `OnEntityReady`, `GetRequiredComponents`; sibling access via `GetSibling<T>()`.
- `ComponentRegistration.cs` — only two static helpers those bases share: `Register(node, component)` (walks ancestors for the nearest `IEntity`, `PushError` if there is none) and `ValidateRequired(node, entity, types)` (`PushWarning` per missing sibling).
- `Entities/IEntity.cs` / `Entity.cs` / `EntityRegistry.cs` — the entity side. `IEntity` declares `RegisterComponent`/`UnregisterComponent`/`GetComponent(Type)` plus a default-implemented generic `GetComponent<T>()`. Roots needing a native base (`LocalPlayer`/`Enemy : CharacterBody2D`) implement `IEntity` directly with an `EntityRegistry` field; plain-`Node` roots can derive from `Entity`. `EntityRegistry` itself is a flat `List<IComponent>` with `Register`/`Unregister`/`Get(Type)`, and `Get` returns the first component the type `IsInstanceOfType` — i.e. lookups are subclass-friendly and **order-dependent** when two components share a base. Results are memoized per query type in a cache cleared on Register/Unregister, so repeated `Get` calls are O(1) with identical semantics.
- `NodeExtensions.cs` — `GetAncestor<T>()` (works across instanced sub-scene boundaries, unlike `Node.Owner`).

### `Components/Combat/` (scenes in `Scenes/Components/Combat/`)
- `HealthComponent.cs` (`health_component.tscn`) — owns the entity's `Health` Stat as a mirror of server hp/max_hp; `SetFromServer(hp, maxHp)` emits `HealthDidDecrease`/`HealthDidIncrease`/`HealthDidZero`. Deliberately no `Damage()`/`Heal()`.
- `FactionComponent.cs` — `[Flags] Factions { Neutral, Players, Enemies }`; `CheckOpposition` = no shared flag (missing component ⇒ Neutral ⇒ opposed to everything). Static per scene; not server-synced.
- `DamageReceivingComponent.cs` (`damage_receiving_component.tscn`) — victim hurtbox (`Area2D`, no in-scene shape; each entity adds its own shape child). `ProcessHit` emits `DidReceiveDamage`; `ProcessBulletHit` routes BlastBullets2D overlaps to `ReportHit` (via `BulletHitRouterComponent`).
- `RemoteHitWitnessComponent.cs` (declared inline in `non_local_player.tscn`) — remote player puppet's bullet hurtbox (`Area2D`, layer 2 / mask 0). Makes enemy bullets collide with other players on every client; `BulletHitRouterComponent` applies the elevation band check before forwarding here and disables the bullet manually on a reported hit (enemy spawn data is piercing, so despawns stay deterministic across clients). Forwards the overlap to the `FlagPlayerHit` anti-cheat reducer (witness corroboration only; damage stays reported by the victim's own client).
- `HitZone.cs` (`Scenes/Components/hit_zone.tscn`) — attacker hitbox (`AreaComponent`) with a lifetime fuse; on expiry `ReportHits()` finds faction-opposed `DamageReceivingComponent`s in contact and reports them (`ReportEnemyHit` for enemy victims); never computes damage. Spawned by `CombatComponent` along bullet paths, which stamps the zone's `Elevation` from the firing player's hex — `ReportHits` gates receivers to the [band − `BulletElevationDrop`, band + `BulletElevationClimb`] hit window around it.

### `Components/Data/` + `Resources/Stats/`
- `StatsComponent.cs` (`Scenes/Components/Data/stats_component.tscn`) — `Stat` set keyed by `StatKind`; `SetFromServer(kind, value)`, `StatChanged` signal. Shared-Stat pattern: the entity registers `HealthComponent.Health` under `StatKind.Hp` so all observers see one instance. Carried by `LocalPlayer` only.
- `LocalPlayerDataComponent.cs` — `LocalPlayerData`/`LocalPlayerStats`/`LocalPlayerStatAllocation` rows → the `HealthComponent`/`StatsComponent` mirrors; owns `Level`, `Defense` and `BaseSpeed` (modifier-only — they live on the data row like max_hp), and `UnspentPoints`.
- `Resources/Stats/Stat.cs` — `[GlobalClass] Resource`: clamped `MinValue`/`MaxValue`/`Value`, `ValueChanged` signal. Data only.
- `Resources/Stats/StatKind.cs` — mirrors the server's `StatKind`: the six allocatable stats (Strength/Wisdom/Dexterity/DamageDealer/Supporter/Artisan) + modifier-only Hp/Defense/BaseSpeed. Note the generated bindings also define `SpacetimeDB.Types.StatKind` — qualify when you need that one (e.g. the `AllocateStat` reducer).

### `Components/Weapon/`
- `CombatComponent.cs` — `Component`; weapon firing from the **effective weapon** (fire rate/pattern/range/effective shot count), cursor aiming (shots fire toward `LocalPlayer.GetCursorWorldPosition()`), aim assist/lock-on from `LocalPlayerActiveProfile` (aim-assist cone is relative to the cursor direction, lock-on snaps to the nearest enemy in range), spawns `HitZone`s along bullet paths. Holds fire while an ability charge is held (P4 — firing is client-authoritative, so charge fire-suppression lives here, driven by `AbilityChargeComponent.Charging`). Polls the `weapon_toggle` input action (T) to cycle the weapon slot's `active_toggle` via `SetSlotToggle`. Re-resolves on `InventoryChanged` or `CatalogComponent.CatalogChanged` only when the resolver fingerprint changes (item, toggle index, equipped enchantments, catalog version — a catalog row edit re-resolves without any inventory change). Nearest-enemy invalidation comes from a child `NearbyEnemies` binder (`RowDeleted` wired in `local_player.tscn`).
- `EffectiveWeaponResolver.cs` — static client mirror of the server's `resolve_effective_weapon`: toggle options (item's own `Weapon` behaviors + `WeaponToggle` enchantment grants) indexed by `active_toggle`, with `AddShots`/`ShotCountMult` folded into the shot count and the true-damage/flat mods summed. Fold order (slot index ascending, innate before socketed) must match the server. Also owns the `Fingerprint` cache key. Never mutates the catalog's shared `WeaponBehavior` — copies it.

### `Game/` — GameManager + its decomposition (component scenes in `Scenes/Components/`)
- `GameManager.cs` — `Node2D, IEntity`, root node of `Scenes/game.tscn` (named `game`); **not an autoload**. Thin entity glue plus a facade delegating to its child components: `Conn`, `Username`, `IsLocal` → the `DatabaseConnector` autoload; `LapQ`/`LapR` → `TableSubscriber` (direct passthrough to its statics); `GetItem`, `GetEnchantment(s)`, `EnchantmentsChanged`, `GetResPath2D`/`GetResPath3D` → `CatalogComponent`; `GetEnemy`, `EnemyCount` → `EntitySpawnerComponent`. Reach anything else on it via its `GetComponent<T>()` instance method. Its `_Ready` also applies the menu-picked `GameVisuals.Mode`: in 3D mode it instantiates `Scenes/world_3d.tscn` into the `3D` CanvasLayer's SubViewport (declared in game.tscn but intentionally empty; the CanvasLayer is `layer = -1`, a backdrop below every UI CanvasLayer) and hides `BulletManager` — the 2D bullet simulation stays alive (hit reporting + the `Bullets3DComponent` mirror read it), only its rendering/textures are suppressed. TerrainComponent and every entity/drop/chest sprite also gate on `GameVisuals.Is3D`, so 3D mode loads **no res_path2d world asset at all** (inventory/sidebar UI icons still use res_path2d). In 2D mode it frees the whole `3D` CanvasLayer, so no 3D asset ever loads and every `GetComponent<World3DComponent>()` null-guard skips 3D model creation.
- `Components/Catalog/CatalogComponent.cs` (declared inline in `game.tscn`) — the `AllItems`/`AllEnchantments`/`AllTextures` views as caches (`GetItem`, `GetEnchantment(s)`, `GetResPath2D`/`GetResPath3D`, `EnchantmentsChanged`), fed by three child `TableBinderComponent`s with `ReplayExistingRows`. Each `TextureEntry` carries both a `res_path2d` (sprites/icons) and a `res_path3d` (FBX model; empty = no 3D representation, normalized to null by `GetResPath3D`). Also owns `CatalogVersion` (bumped on any item/enchantment row change) + the `CatalogChanged` event, both forwarded through the `GameManager` facade for catalog-derived caches (`CombatComponent`).
- `Components/Spawning/EntitySpawnerComponent.cs` (declared inline in `game.tscn`) — row insert/delete signals from five child binders (`LocalPlayer`/`NearbyRemotePlayers`/`NearbyEnemies`/`NearbyLootDrops`/`NearbyChests`, all replaying) → spawn/despawn of `LocalPlayer`/`RemotePlayer`/`Enemy`/`Drop`/`Chest`, plus the tracking dictionaries (`GetEnemy`, `EnemyCount`). Adds are deferred and tracked (`pendingAdds`): a row delete arriving before the deferred add fires cancels the add instead of `QueueFree`ing a not-yet-parented node, and the parent scene is resolved at deferred-execution time. `DespawnAll()` (frees tracked entities + cancels pending adds) runs on subscription-wave swap and `_ExitTree`, so stale ids can't wedge respawn.
- `Components/Zones/ZoneRendererComponent.cs` (declared inline in `game.tscn`) — renders every `GroundZone` row (P3) as a code-created `Polygon2D` circle colored per `ZoneKind`, deleted on row delete. Its child `GroundZoneBinder` keeps `ReplayExistingRows = true` — GroundZone is a persistent table, so replay shows late joiners still-live zones (the opposite of the event-table rule).
- `Components/Lobby/LobbyComponent.cs` (declared under `UI` in `game.tscn`) — CharSlots UI and profile panels (tracked in a `Dictionary<ulong, Control>` keyed by profile id), fed by a child `LocalPlayerProfiles` binder (inserts only; panel removal stays local via the Delete button). Join flow: the lobby stays up until the `JoinWorld` reducer callback reports success — on failure or a `JoinTimeoutSeconds` (5 s) timeout the attempt aborts and the lobby re-shows with the `JoinError` label.
- `BulletManager.cs` — `Node2D, IEntity`, declared inline in `game.tscn` (not row-driven, so no code spawn; `z_index = 1` keeps bullets drawn above the dynamically spawned entities). Children: `BlastBullets`, the BlastBullets2D `BulletFactory2D` GDExtension node, typed only as `[Export] public Node` (reached via NodePath, not `GetChild(0)`); `Components/Bullets/BulletSpawnerComponent.cs` (`BulletPatternEvent` → per-`PatternType` dispatch through ONE child `BulletPatternEventBinder` declared in `bullet_spawner_component.tscn` — bound before any enemy spawns, and the event rows are self-contained (absolute origin stamped server-side), so there is no per-enemy binder fan-out and no lost volley during a puppet's deferred-spawn window; reaching the factory through **untyped `BlastBullets.Call(…)`** — no compile-time checking on those calls or their `.tres` spawn-data resources, so typos surface only at runtime; Ring renders the `Line`/`LineSpeedStep` speed ladder as one spawn call per stack level and Volley batches each stack level as ONE instance of Count bullets via per-index transforms + exact per-index speed data, while Shotgun/Explosion stay one-instance-per-pellet (per-pellet lifetime jitter, and the plugin's `max_life_time` is scalar per instance); `ApplyMotion` maps event `AngularSpeed`/`SpeedAcceleration` to BlastBullets2D rotation/speed data (`adjust_direction_based_on_rotation` is what makes rotation actually curve the trajectory — re-set per event since the spawner resource is shared, and a size-0 rotation array clears it for straight events); `bullet_max_collision_count = 0` (piercing) is pinned explicitly on the enemy spawn data — a bullet must survive overlapping off-elevation-band players, so single-hit enforcement moved to the router's manual `disable_bullet`; enemy bullets spawn via `spawn_controllable_directional_bullets` and the returned `DirectionalBullets2D` instances are tracked in `LiveEnemyBullets` (a `Dictionary<GodotObject, int>` stamping each instance's elevation band — its origin hex's level — alongside player bullets in `LivePlayerBullets`; band = elevation at the spawn origin via `GameManager.ElevationMap`), pruned on a 1 s timer and a 256-instance threshold (never per event), because the factory cannot enumerate active instances); `Components/Bullets/BulletHitRouterComponent.cs` (overlap → band check (victim hex elevation must be within [band − `BulletElevationDrop`, band + `BulletElevationClimb`] of the bullet instance's band, out-of-window overlaps fly through) → `ReportHit` routing through the victim's `DamageReceivingComponent` + manual `disable_bullet` via `call_deferred` (the plugin's collision counting no longer despawns — piercing); remote-player hits route to `RemoteHitWitnessComponent` → `FlagPlayerHit` instead; an unrecognized layer-2 area is warned about and ignored, never reported); `Components/Bullets/BulletCliffComponent.cs` (declared inline in `game.tscn` under `BulletManager`; on a 0.15 s timer sweeps `LiveEnemyBullets`/`LivePlayerBullets` via `all_bullets_get_transforms` and disables (call_deferred) any enabled bullet over a hex more than `BulletElevationClimb` above its band — bullets fly over lower ground freely); `Components/Bullets/BulletControllerComponent.cs` (player abilities that manipulate live enemy bullets — `DeleteNear`/`SplitNear`/`AttractNear` near a point, `DeleteInRect` (deletes) and `SplitInRect` (splits) as a rectangle from the caster toward the cursor, `SlashInRect` (deletes only bullets whose `BulletData.Damage` ≤ the threshold — stamped from `BulletPatternEvent.Damage` at spawn), plus `SpawnAttractZone`, a lingering black hole that re-attracts bullets for its duration, and `SpawnWallZone`, a lingering delete-rect that re-sweeps for its duration, over the spawner's `LiveEnemyBullets`; **driven by the ability system**: `LocalPlayerInventoryComponent.TryActivateAbility` applies the cast optimistically for bullet-control `AbilityEffect`s, and `activate_ability` appends the `BulletControlEvent` server-side with the item's radius/dims — event rows arrive via the child `BulletControlEventBinder` (wired in `game.tscn`), own echoes skipped via `cast_by`; each client resolves the proximity query locally, so edge-of-radius results can differ slightly. Slash events encode the rect as origin + far end + width; every client draws the black slash `Polygon2D` flash under BulletManager, so the visual replicates with the cast). Keeps a static `Instance` + spawn pass-throughs (`CombatComponent` has no registry path to it). `BulletData.cs` — small `Resource` carried through the bullet pipeline.
- `LobbyGui.cs` — lobby/menu UI, root of `Scenes/main_menu.tscn` (the menu/game scene-naming swap is covered in the root `AGENTS.md`). The **2D**/**3D** buttons set `GameVisuals.Mode` (see `VisualMode.cs` below) and enter `game.tscn`; Server List / Settings are panel toggles. Not yet wired to the `create_profile`/`join_world` reducers.
- `VisualMode.cs` — the `VisualMode` enum + static `GameVisuals.Mode`/`Is3D`, set by the main menu's 2D/3D buttons before `ChangeSceneToFile` and read by `GameManager._Ready` plus every 2D-visual gate (TerrainComponent, BulletSpawnerComponent textures, entity/drop/chest sprites). Static because the choice must survive the menu→game scene swap.
- `DebugOverlay.cs` — debug HUD (declared inline in `game.tscn`); paired with server `main/debug.rs`.

### `Components/Camera/` (+ `Scenes/world_3d.tscn`)
- `CameraRigComponent.cs` and `Camera2DPresenterComponent.cs` — 2D camera rig/presenter, children of `game.tscn`.
- `World3DComponent.cs` — root of `world_3d.tscn` (the 3D backdrop viewport). Not declared in `game.tscn` — `GameManager._Ready` instantiates it into the `3D` CanvasLayer's SubViewport only when `GameVisuals.Is3D`, so its assets (hex tiles, `hex_bullet.tscn`) never load in 2D mode. Also owns `CursorGroundIntersection(groundY)` — the cursor ray from its Camera3D intersected with the ground plane at a given elevation height, mapped back to world 2D (root-window mouse coords are scaled into the stretched SubViewport manually; input never reaches it). Its declared children: `HexGridOverlay3DComponent` (debug), `Bullets3DComponent`, `TerrainComponent3D` (the runtime MST terrain — see `Components/Terrain/`), and the PhantomCamera3D/Camera3D rig. The PhantomCamera3D's `collision_mask` is pinned to 0: its third-person SpringArm3D defaults to mask 1, and MST chunk collision sits on layer 1, so an enabled mask would let terrain hexes shorten the arm and fight the arcball controls.
- `HexGridOverlayComponent.cs` — hex grid debug overlay, `MapConfig` rows via a child binder; `HexGridOverlay3DComponent.cs` — its 3D sibling, declared with its own binder in `world_3d.tscn`, Y-stretches tile columns by their hex's elevation level (`GameManager.ElevationMap`, re-applied on `ElevationChanged`; `HeightScalePerLevel` export = extra Y scale per level) and floats the coord labels (hex/chunk/spiral index + elevation level) above the column tops (native mesh AABB top × Y scale).
- `Components/Bullets/Bullets3DComponent.cs` — 3D mirror of ALL live bullets (enemy and player), declared in `world_3d.tscn` with `BulletScene` = `hex_bullet.tscn`. On a throttled sync tick (`SyncHz` = 30, not every frame — each tick costs an untyped interop Call per bullet plus a full transform-array alloc per instance, and the plugin offers no caller-buffer overload) it reads the enabled bullet transforms of every `DirectionalBullets2D` in the cached `BulletSpawnerComponent.LiveEnemyBullets`/`LivePlayerBullets` and lays pooled bullet instances over them. Every volley's model is catalog-driven: the instance's stamped `TrackedBulletInfo` (band + texture id) resolves to the texture's `res_path3d` (cached per texture id, `BulletScene` fallback), and each model scene gets its own pool (a weapon swap never rebuilds another volley's pool). A bullet's Y is its instance's elevation band × `WorldHeightPerLevel` + `BulletHeight`. Liveness uses per-index `is_bullet_status_enabled` — the bulk `get_all_bullets_status` array is buggy in the plugin (its index is never incremented, so only slot 0 is ever written).

### `Components/Terrain/` (scenes in `Scenes/Components/Terrain/`)
- `ElevationMapComponent.cs` (`Component`, declared inline in `game.tscn` with `MapConfigBinder` + `NearbyBuildingTilesBinder` children, both replay on) — per-hex elevation levels from the AOI-filtered `NearbyBuildingTiles` view rows as a `(q, r) → level` dictionary (`GetElevation(q, r)` default 0, `GetElevationAt(Vector2)` via `HexMath.WorldToHex` with the MapConfig outer radius). Raises `ElevationChanged` on any row change; reached via the `GameManager.ElevationMap` facade by `LocalPlayer` (movement prediction/fall tween), the bullet components (band rule) and `TerrainComponent` (tint).
- `TerrainComponent3D.cs` (`Node3DComponent`, declared in `world_3d.tscn` with a `MarchingSquaresTerrain` child — the MST plugin node, `storage_mode` RUNTIME, runtime texture baking off — and a replaying `MapConfigBinder`) — the runtime MST hex terrain of the 3D world. Builds the whole canonical lap of chunks (`ChunkCols × ChunkRows` from MapConfig) and feeds per-hex elevation levels from the `GameManager.ElevationMap` facade into `chunk.draw_elevation` (re-applied on `ElevationChanged`, one `regenerate_mesh` per dirty chunk; border-wall neighbor chunks regen too). `level_height` is locked to `ElevationMapComponent.WorldHeightPerLevel` so mesh tops land exactly where `GetWorldHeightAt` puts characters and cursor raycasts. Reaches the plugin through untyped `Call`/`Set` interop (the `BulletSpawnerComponent` caveat applies — typos surface only at runtime), and calls `force_batch_update` itself after building because `add_new_chunk`'s dirty marks make the terrain's deferred enter-tree skip it. Only the canonical lap is built (torus-seam edge chunks read void neighbors); distant chunks render flat at level 0 until they enter the AOI — same data scope as the 2D terrain.
- `TerrainComponent.cs` (`Node2DComponent`, declared inline in `game.tscn`) — receives `MapConfig`/`NearbyTerrainTiles`/`NearbyHexDecor` rows through three child binders, stores rows, dirty-flag one-rebuild-per-frame with the camera path throttled to chunk crossings (pixel motion within a chunk doesn't rebuild; zoom changes still do), pooled clear-and-reused grouping buffers (no per-rebuild dictionary/list allocation), shared wedge/decor mesh + texture caches, per-hex torus wrap + camera cull. Minimal cosmetic elevation cue (2D only): ground/overlay grouping buffers carry a per-hex tint (dark→bright lerp by `elevation / (ELEVATION_LEVELS - 1)`, constant mirrored in `ServerConstants.cs`), applied as per-instance colors on the ground/overlay MultiMeshes (`use_colors` on — decor layers untouched); `ElevationMapComponent.ElevationChanged` sets the dirty flag for a re-tint rebuild. Owns a pool of `TileComponent` instances pre-warmed to the AOI ring count (`1+3R(R+1)`; `[Export] AoiChunkRadius = 2` matching the server's `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS`), growing on demand. **3D mode:** `_Ready` hides the component and stops processing, the pool pre-warm is skipped, and `RebuildVisibleInstances` returns early (it's also called straight from `OnMapConfigRow` → `InvalidateMeshes`, so the `_Process` gate alone is not enough) — no 2D tile or ground/decor texture is ever built.
- `TileComponent.cs` (`tile_component.tscn`, `Node2D, IEntity`) — per-chunk scaffolding with four declared layer children: `GroundComponent` (z=0), `OverlayComponent` (z=1, centroid-scaled), `DecorShadowComponent` (z=2), `DecorComponent` (z=3). `Populate(chunkIndex, rows…)` fills the layers per frame; `Clear()` parks it back in the pool.
- `TerrainLayerComponent.cs` — base for the four layers; each owns pooled `MultiMeshInstance2D` batch leaves. The leaves stay code-created (data-driven count, deliberate perf design); z-order/scaffolding is declared in the `.tscn`. `DecorLayerComponent.cs` — shared base for the two decor layers (per-texture batches sorted by hex row).

### `Components/Movement/` + `Components/Visual/` + `Components/Interaction/`
- `Movement/InterpolationComponent.cs` (`interpolation_component.tscn`) — shared position/rotation lerp toward server targets, torus-aware via `TorusMath.NearestCandidate`; exposes `Moving`. Position+velocity targets via `SetTarget(position, velocity)` (velocity drives dead-reckoning), screen rotation separately via `SetScreenRotationTarget` (it arrives from its own table). Used by `RemotePlayer` + `Enemy`; both reconstruct velocity from the row's `movement_direction`/`movement_speed` angle+scalar pair.
- `Movement/PositionSyncComponent.cs` — local player's `LocalPlayerPosition` rows, the 10Hz `ReportMovement` timer (`ReportInterval` = 0.1 — this cadence is load-bearing, remotes rubber-band below it; `ReportInterval = -1` selects event-driven mode: report on movement-key edges and direction/speed changes only — sends **actual** movement as `movement_direction` angle + `movement_speed` scalar, speed zero when idle), and a faster `ReportScreenRotation` timer (~30Hz, only on facing change). Also owns the speed controls: `increase_move_speed`/`decrease_move_speed` (Ctrl+scroll, persistent 10% scale steps) and `self_slow` (hold R, ×0.4); `LocalPlayer` reads its `CurrentSpeed`. P4 additions: `SetExternalSlow(float?)` (cosmetic charge SelfSlow, driven by `AbilityChargeComponent` — the server clamps for real) and `RequestMovementReport()` (public report trigger the grapple tween calls at start and end only — timed/edge reports are suppressed while `ExternalMovementActive` so a mid-tween report can't burn the server's one-shot grapple displacement allowance).
- `Visual/RemoteVisualComponent.cs` — remote player sprite/texture; Walk/Idle driven by `InterpolationComponent.Moving`; in 3D mode `SetTexture` hides the sprite and loads nothing (RemotePlayer mirrors a catalog-driven 3D model instead). `Visual/LocalPlayerProfileComponent.cs` — `LocalPlayerActiveProfile` rows → SpriteFrames (2D mode only; in 3D mode the sprite stays hidden and the profile texture goes to `LocalPlayer.SetModel3DTexture`).
- `Visual/SpellVisualComponent.cs` (declared inline in `game.tscn` with a child `AbilityVisualEventBinder`, **ReplayExistingRows OFF** — event table, the BulletControlEvent rule) — renders P5 Spell casts as code-created Polygon2D flashes per `AbilityVisualKind` (Circle ring, Line rectangle, Cone wedge, Meteor/Converge visual-only streak variants — damage is the plain shape either way), fading/freeing after the event's duration. The caster renders optimistically via the same `Render` method and the echo skips own `cast_by` (the BulletControllerComponent pattern). Reached from inventory code via the `GameManager.SpellVisuals` facade.
- `Interaction/PickupComponent.cs` (`pickup_component.tscn`) — `AreaComponent` with declared `CollisionShape2D` + `PickupLockTimer` children; body-entered → `PickupDrop` reducer.
- `Interaction/InteractComponent.cs` (declared in `chest.tscn`) — `AreaComponent` interaction zone: tracks the local player inside and toggles the chest panel on the `interact` action (Shift+E), closing it when the player steps out.

### `Components/Inventory/` (UI declared inline in `local_player.tscn` — see the note below)
- `InventoryPanel.cs` — plain `Control` script (not a ControlComponent); hotbar/backpack/equipment slot UI, listens for `LocalPlayer.InventoryChanged`, calls `UseItem` reducer on hotbar key press, ability keys route through `LocalPlayerInventoryComponent.TryActivateAbility` — charge-capable items (P4) instead route key-down/key-up to `TryBeginCharge`/`TryReleaseCharge`. Hotbar/Backpack stay plain containers (zero behavior) inside the inline inventory UI in `local_player.tscn`.
- `LocalPlayerInventoryComponent.cs` — `LocalPlayerInventory` rows → slot state; owns slot resolution (`ResolveSlotAt`/`GetSlotItemId`), the shared `TryActivateAbility(player, cellIndex)` static (cooldown/charge pre-check → `ActivateAbility` reducer with the cursor's world position → optimistic local apply for bullet-control effects via `BulletControllerComponent` and spell flashes via `SpellVisualComponent`; passive and charge-capable ability items no-op), the P4 charge pair `TryBeginCharge`/`TryReleaseCharge` (charge-scaled spells render their flash optimistically on release too) + the `IsChargeCapable(At)` mirror of the server's `ability_is_charge_capable`, the client-tweened grapple pull (`StartGrappleTween` — reports at tween start/end only, suspends input movement via `LocalPlayer.ExternalMovementActive`). A per-slot optimistic-cast guard (`castPendingUntilMs`, set on cast, cleared early by the echoed slot row) rejects double-click recasts until the echo lands — one click, one optimistic bullet-delete. Mirrored ability constants (`AbilityPositionMultipliers`, `MaxAbilityTargetRange`) live in `World/ServerConstants.cs`.
- `AbilityChargeComponent.cs` (declared in `local_player.tscn` with a child `AbilityChargeBinder`, replay on) — the local player's P4 charge state from the server-echoed `AbilityCharge` row (echo-only, no optimistic flag, so timeout auto-releases and lifecycle purges clear it by themselves); applies the cosmetic charge SelfSlow to `PositionSyncComponent` and exposes `Charging`/`ChargedSlot` for `CombatComponent`'s fire suppression. The client mirrors of `CHARGE_SELF_SLOW_FACTOR`/`MAX_CHARGE_SECONDS` and the charge-range multiplier live in `World/ServerConstants.cs`.
- `SlotComponent.cs` — single inventory slot, still a `ControlComponent`: drag/drop (`SwapSlots` reducer), left-click on ability slots (`TryActivateAbility`), right-click drop in the backpack (`DropItem` reducer), hover shows `ItemSidebar` (reached via a cached `GetNode<ItemSidebar>("%ItemSidebar")` instead of `GetSibling`). Sets its `Icon`'s `mouse_filter` to Ignore in `OnRegistered` — the icon sits on top of the slot, and Godot asks the *hovered* control for drag data, so a hit-testable icon silently kills drag start. For the same reason the full-screen `Menu` Control in the `local_player.tscn` inventory UI is `mouse_filter = 2` (Ignore): it renders above the always-visible Equipment panel and would otherwise swallow all input over the equipment slots whenever the Tab menu is open.
- `ChestSlotComponent.cs` (`Scenes/UI/chest_slot.tscn`) — plain `Control` script; one item entry in an open chest panel, drag source only (drag data is a `{"chest_item_id": …}` Dictionary → `SlotComponent` reports `TakeFromChest`). Icon `mouse_filter` Ignore for the same drag-start reason as `SlotComponent`.
- `StatsSidebar.cs` — plain `Control` script; player stat panel: the six allocatable stats (STR/WIS/DEX/DPS/SUP/ART) + DEF and unspent-points lines, with a `+` Button per allocatable stat (visible only while `UnspentPoints > 0`) calling the `AllocateStat` reducer.
- `ItemSidebar.cs` — plain `Control` script (its node has `unique_name_in_owner = true`); hovered slot's item name/icon/description plus full composition: base stat modifiers, stat requirements (red when unmet), behavior summary (equipped weapon shows its toggle-pattern list with the active one marked; abilities show effect/cooldown/charges), innate enchantments (no Remove button), socketed enchantments (`N / MaxEnchantments`), and — for enchantable items in equipment slots — applicable enchantments with Socket/Remove buttons calling the `ApplyEnchantment`/`RemoveEnchantment` reducers. Enchantment rows are instantiated from `Scenes/UI/enchantment_row.tscn`. Refreshes on `InventoryChanged` and `EnchantmentsChanged`; stays open while the mouse is over it.
- The three plain scripts reach the player via `GetAncestor<LocalPlayer>()` in `_Ready` — NOT `LocalPlayer.Local`, which is still null when children ready. The whole inventory UI is **declared inline in `local_player.tscn`** under its `InventoryCanvas` child — that inline copy is what the game actually runs (`game.tscn` spawns `local_player.tscn`), and the only copy, so UI edits go to `local_player.tscn`. It holds **39 `SlotComponent` nodes**: a 5-slot `Hotbar` (indices 0–4, the weapon + four consumables), a 9-slot `Equipment` panel (Weapon 0, Accessory 5, Armor 6, Ability 32–37), and a 25-slot `Backpack` (indices 7–30 across six 4-slot rows, plus Bag 31). Several indices therefore appear in more than one visible slot. Every slot's `[Export] SlotIndex` is authored in the scene; check the export before assuming a layout.

### `Components/Status/` (P6 status UI)
- `StatusBarComponent.cs` — `ControlComponent` declared under `InventoryCanvas/InventoryPanel` in `local_player.tscn` (an always-visible strip above the hotbar): the LOCAL player's `ActiveStatusEffect` rows as "Kind N.Ns" labels, fed by a child `ActiveStatusEffectBinder` (replay on — persistent table), filtered to the local profile (the `AbilityChargeComponent` pattern). Labels count down locally between the server's 1 Hz row updates; row insert/update/delete is the source of truth.
- `EnemyDebuffIndicatorComponent.cs` — `Node2DComponent` at the `DebuffAttach` point in `default_enemy.tscn` (counter-scaled against the enemy root's 0.5 scale): colored chips per `EnemyStatusKind` (DoT green, Slow blue, Vulnerability purple, ArmorBreak orange, Stunned yellow) plus the 0–100 stagger bar (`Enemy.Stagger`), fed by a child `ActiveEnemyStatusEffectBinder` (replay on) filtered per enemy instance in code — fine at co-op scale.

### `Players/`
- `Local/LocalPlayer.cs` — `CharacterBody2D, IEntity`; WASD movement at the server-resolved `BaseSpeed`, with per-hex elevation prediction in `_PhysicsProcess` (via a cached `ElevationMapComponent`): steps within ±`MaxWalkableUpDelta`/`MaxWalkableDownDelta` are walked normally, steeper rises are blocked with an axis-separated slide, steeper drops start a client-tweened fall (~0.75 hex past the boundary along velocity over `FallSecondsPerLevel` × Δ, cosmetic modulate dip, `ExternalMovementActive` during, one `RequestMovementReport` at landing — the grapple-tween pattern; the server re-validates and applies fall damage) (item-only `PlayerData.base_speed`, via `PositionSyncComponent.CurrentSpeed` for the player's speed-scale/self-slow settings), twin-stick cursor facing (`Rotation` always tracks `GetCursorWorldPosition()` — 2D mode: `GetGlobalMousePosition`; 3D mode: `World3DComponent.CursorGroundIntersection` at the terrain's elevation height via `ElevationMapComponent.GetWorldHeightAt`, refined once against the hit hex), sprite Walk/Idle, 3D-model sync, camera registration. The 3D model is catalog-driven: `LocalPlayerProfileComponent` passes the profile's `TextureId` to `SetModel3DTexture`, which loads the `res_path3d` FBX in code (no scene export — 2D mode never loads it) and wires the PhantomCamera follow target. Server-table concerns live in child components, each fed by its own binder with signals wired in `local_player.tscn`: `PositionSyncComponent`, `LocalPlayerDataComponent`, `LocalPlayerInventoryComponent`, `LocalPlayerProfileComponent`. Other children: `StatsComponent`, `HealthComponent`, `FactionComponent`, `DamageReceivingComponent`, `CombatComponent`. `LocalPlayer` keeps the `InventoryChanged`/`AimSettingsChanged`/`StatsChanged` signals (components raise them via `Raise*Changed()`) and pass-through properties (`Hp`, `MaxHp`, the six stats, `Defense`, `UnspentPoints`…) so UI readers stay stable.
- `Remote/RemotePlayer.cs` — `Node2D, IEntity` root of `non_local_player.tscn` (EntityRegistry boilerplate + thin glue). `NearbyRemotePlayers` position updates (`movement_direction`/`movement_speed` reconstructed into velocity) and `NearbyRemotePlayerRotations` screen-rotation updates arrive via two child binders (`RowUpdated` wired in the `.tscn`); the one-shot profile lookup stays a direct `Iter()` read. The work lives in `InterpolationComponent` + `RemoteVisualComponent`. In 3D mode it mirrors a `CharacterModel3D` into the World3DComponent viewport from the profile texture's catalog `res_path3d` (same pattern as Enemy), synced per frame. Also carries a `RemoteHitWitnessComponent` hurtbox child so enemy bullets collide with the puppet on every client (see `Components/Combat/`).
- `Enemies/Enemy.cs` — `CharacterBody2D, IEntity`; server-driven puppet. `NearbyEnemies` rows arrive via a child binder (signals wired in `default_enemy.tscn`; the binder replays so late-spawned instances still initialize). Bullet patterns bypass the puppet: one shared `BulletPatternEventBinder` lives on `BulletSpawnerComponent`. Feeds row hp + `EnemyTemplate` max_hp into its `HealthComponent` and mirrors the 0–100 `stagger` row field onto `Enemy.Stagger`. Mirrors a 3D model into the World3DComponent viewport via `CharacterModel3D`, loaded in code from the template texture's catalog `res_path3d` in `OnEnemyRowInserted` (no scene-declared FBX export — 2D mode must not load it; no-op when `world3D` is null) — same pattern as `LocalPlayer`. In 3D mode the 2D sprite is hidden and its SpriteFrames never load. `default_enemy.tscn` children: `HealthComponent`, `FactionComponent` (Enemies), `DamageReceivingComponent` (Enemy collision layer — what `HitZone`s detect instead of the physics body), `InterpolationComponent`, and the `DebuffAttach` Node2D (above the sprite) holding `EnemyDebuffIndicatorComponent` + its `ActiveEnemyStatusEffectBinder`.
- `CharacterModel3D.cs` — the 3D character model mirroring 2D entity state. Not present in any `.tscn`; its consumers are `LocalPlayer.cs`, `Enemy.cs` and `RemotePlayer.cs`. `SyncFrom2D(pos, yaw, groundY)` (and the constructor) take an optional `groundY` — every consumer passes `GetWorldHeightAt(GlobalPosition)` so models stand on the terrain surface instead of floating at Y=0.

- `Items/Drop.cs` — `Node2D, IEntity` root of `drop.tscn` (EntityRegistry boilerplate; sets the plain `Sprite2D` child's texture from the catalog itself; 3D mode hides the sprite and loads nothing — no 3D drop model yet, but PickupComponent still works). ## MCP-driven playtesting (open-godot-mcp)

Run/publish flow and the always-start-from-`main_menu.tscn` rule are in the root `AGENTS.md`; **the full click/hover/drag/key recipe repository and UI node-path map live in the `playtest` skill** (`../.kimi-code/skills/playtest/`) — use it instead of taking screenshots to find buttons. Bridge: port **6970** (`godot_instance list` → adopt the running instance, `godot_health check` to verify). The gotchas that bite hardest, kept here because they invalidate silent assumptions:

- Pass `coords: "viewport"` with `get_global_rect().get_center()` coordinates so window-size/stretch mismatches can't silently move the click.
- Verify hover with `get_tree().root.gui_get_hovered_control()` — `get_viewport().get_mouse_position()` reads the real OS cursor and never reflects injected positions.
- Keep `godot_exec eval` bodies loop-free — any `for`/`while` loop times out. Injected input dispatches on the next frame, so check state in a follow-up call.
- The editor runs **2 game instances** (`--p1`/`--p2` per-instance args). Runtime tools default to instance 1; pass `"instance": 2` in `params` to target the second. `godot_game` action `instances` lists live instances (pid, args, ready).
