# client/AGENTS.md

Per-file map of the Godot client. See the root `AGENTS.md` for the project-wide domain map, folders to skip, and run/publish commands.

100% C# (Godot 4.7, .NET 8) and fully compositional, modeled on the **Comedot** component framework.

## Naming convention

Every high-level parent node's children are **components named `<Role>Component`** — node name = class name = file name (the `HealthComponent` node in a `.tscn` is an instance of `HealthComponent.cs`). Exceptions:

- Pure data nodes with zero behavior: `CollisionShape2D` inside Area components, `SpriteFrames`, the BlastBullets GDExtension node, phantom_camera addon nodes.
- `TableBinderComponent` children: node name is `<Table>Binder` (e.g. `NearbyEnemiesBinder`), not the class name — one per consumed table, signals wired in the `.tscn`.
- Code-instantiated scenes whose count is data-driven: server-row entities, `HitZone`s, enchantment rows, profile panels, terrain MultiMesh batch leaves + the chunk pool.

Nodes are declared in the `.tscn`, not built in code, wherever feasible.

## `client/sstdbsdk/` — connection + subscription layer (first-party)

Everything else here depends on these three. Not under `addons/`, despite the name.

- `DatabaseConnector.cs` — **autoload singleton** (`DatabaseConnector.Instance`, declared in `project.godot` as `res://sstdbsdk/DatabaseConnector.cs`, *not* a child of Main). Owns the `DbConnection` (`Conn`), pumps `FrameTick()` every frame, does the `IsLocal` identity check, exports `Host`/`DbName`. Consumers wire table callbacks from its `Connected` signal — guard with `Conn?.IsActive` first, since the autoload can finish connecting before Main loads. `AuthToken.cs` handles token persistence.
- `TableSubscriber.cs` — subscription waves (base/lobby/game) as the static `BaseTables`/`LobbyTables`/`GameTables` name lists — the single source of truth for "what is subscribed", built into SQL via the generated `From` API. Also exposes `LapQ`/`LapR` torus lap vectors from `MapConfig`.
- `TableBinderComponent.cs` — `[Tool]` node binding one subscribed table (`TableName` dropdown from `TableSubscriber.AllSubscribedTables`) and re-exposing its row events as editor-wireable Godot signals (`RowInserted`/`RowUpdated`/`RowDeleted`). Signals carry no args (rows aren't Variant-compatible) — handlers read `LastRow`/`LastOldRow`/`LastDeletedRow` and cast. `ReplayExistingRows` replays cached rows through `RowInserted` on bind.

**This is the standard way every component consumes table row events** — place one binder child per table on the consuming component and wire its signals in the `.tscn`; no direct `conn.Db.*.OnInsert/OnUpdate/OnDelete` hooks outside this folder. See the inline binder declarations and signal connections in `main.tscn` (Catalog/EntitySpawner/Terrain components) and `local_player.tscn`. Only infrastructure keeps internal hooks: `TableSubscriber` (`MapConfig` lap vectors) and `DatabaseConnector` (`LocalLobbyPlayer`).

## Module Map (`Scripts/`)

### `Components/` + `Entities/` (entity/component framework)

Server-authoritative rule: components never mutate health/stats locally. They *mirror* server rows (`SetFromServer(...)`) and emit signals for observers, and they *report* hits via reducers — the server computes damage and the updated row flows back into the mirror.

- `IComponent.cs` — the whole contract is one member: an `Entity` back-reference to the owning `IEntity` (null before `_Ready`, null again after `_ExitTree`).
- **The lifecycle lives in the base classes, not in `ComponentRegistration`.** One base per native root type, because C# has single inheritance: `Component.cs` (`Node`), `AreaComponent.cs` (`Area2D` — hitboxes/hurtboxes), `Node2DComponent.cs` (`Node2D`), `Node3DComponent.cs` (`Node3D`), `ControlComponent.cs` (`Control`), `VisualComponent.cs` (`AnimatedSprite2D`). Each one's `_Ready` registers with the nearest `IEntity` ancestor, runs `OnRegistered()`, then `CallDeferred`s a pass that validates `GetRequiredComponents()` and runs `OnEntityReady()` — deferred so every sibling has finished its own `_Ready`. `_ExitTree` unregisters, so dynamically spawned components (e.g. `HitZone`) don't leak in the registry. Override points: `OnRegistered`, `OnEntityReady`, `GetRequiredComponents`; sibling access via `GetSibling<T>()`.
- `ComponentRegistration.cs` — only two static helpers those bases share: `Register(node, component)` (walks ancestors for the nearest `IEntity`, `PushError` if there is none) and `ValidateRequired(node, entity, types)` (`PushWarning` per missing sibling).
- `Entities/IEntity.cs` / `Entity.cs` / `EntityRegistry.cs` — the entity side. `IEntity` declares `RegisterComponent`/`UnregisterComponent`/`GetComponent(Type)` plus a default-implemented generic `GetComponent<T>()`. Roots needing a native base (`LocalPlayer`/`Enemy : CharacterBody2D`) implement `IEntity` directly with an `EntityRegistry` field; plain-`Node` roots can derive from `Entity`. `EntityRegistry` itself is a flat `List<IComponent>` with `Register`/`Unregister`/`Get(Type)`, and `Get` returns the first component the type `IsInstanceOfType` — i.e. lookups are subclass-friendly and **order-dependent** when two components share a base.
- `NodeExtensions.cs` — `GetAncestor<T>()` (works across instanced sub-scene boundaries, unlike `Node.Owner`).

### `Components/Combat/` (scenes in `Scenes/Components/Combat/`)
- `HealthComponent.cs` (`health_component.tscn`) — owns the entity's `Health` Stat as a mirror of server hp/max_hp; `SetFromServer(hp, maxHp)` emits `HealthDidDecrease`/`HealthDidIncrease`/`HealthDidZero`. Deliberately no `Damage()`/`Heal()`.
- `FactionComponent.cs` — `[Flags] Factions { Neutral, Players, Enemies }`; `CheckOpposition` = no shared flag (missing component ⇒ Neutral ⇒ opposed to everything). Static per scene; not server-synced.
- `DamageComponent.cs` (`damage_component.tscn` — an unreferenced scene; the only live use of `DamageComponent` is as `HitZone`'s base class) — attacker hitbox (`Area2D`). `ReportHits()` finds faction-opposed `DamageReceivingComponent`s in contact and reports them (`ReportEnemyHit` for enemy victims); never computes damage.
- `DamageReceivingComponent.cs` (`damage_receiving_component.tscn`) — victim hurtbox (`Area2D`, no in-scene shape; each entity adds its own shape child). `ProcessHit` emits `DidReceiveDamage`; `ProcessBulletHit` routes BlastBullets2D overlaps to `ReportHit` (via `BulletHitRouterComponent`).
- `RemoteHitWitnessComponent.cs` (declared inline in `non_local_player.tscn`) — remote player puppet's bullet hurtbox (`Area2D`, layer 2 / mask 0). Makes enemy bullets collide with other players on every client — the plugin's own collision counting despawns the bullet at `bullet_max_collision_count` (0 = piercing, never despawned) — and forwards the overlap to the `FlagPlayerHit` anti-cheat reducer (witness corroboration only; damage stays reported by the victim's own client).
- `HitZone.cs` (`Scenes/Components/hit_zone.tscn`) — `DamageComponent` with a lifetime fuse; spawned by `CombatComponent` along bullet paths.

### `Components/Data/` + `Resources/Stats/`
- `StatsComponent.cs` (`Scenes/Components/Data/stats_component.tscn`) — `Stat` set keyed by `StatKind`; `SetFromServer(kind, value)`, `StatChanged` signal. Shared-Stat pattern: the entity registers `HealthComponent.Health` under `StatKind.Hp` so all observers see one instance.
- `LocalPlayerDataComponent.cs` — `LocalPlayerData`/`LocalPlayerStats`/`LocalPlayerStatAllocation` rows → the `HealthComponent`/`StatsComponent` mirrors; owns `Level`, `Defense` (modifier-only — lives on the data row like max_hp), and `UnspentPoints`.
- `Resources/Stats/Stat.cs` — `[GlobalClass] Resource`: clamped `MinValue`/`MaxValue`/`Value`, `ValueChanged` signal. Data only.
- `Resources/Stats/StatKind.cs` — mirrors the server's `StatKind`: the six allocatable stats (Strength/Wisdom/Dexterity/DamageDealer/Supporter/Artisan) + modifier-only Hp/Defense. Note the generated bindings also define `SpacetimeDB.Types.StatKind` — qualify when you need that one (e.g. the `AllocateStat` reducer).

### `Components/Weapon/`
- `CombatComponent.cs` — `Component`; weapon firing from the **effective weapon** (fire rate/pattern/range/effective shot count), aim assist/lock-on from `LocalPlayerActiveProfile`, spawns `HitZone`s along bullet paths. Polls the `weapon_toggle` input action (T) to cycle the weapon slot's `active_toggle` via `SetSlotToggle`. Re-resolves on `InventoryChanged` only when the resolver fingerprint changes (item, toggle index, equipped enchantments). Nearest-enemy invalidation comes from a child `NearbyEnemies` binder (`RowDeleted` wired in `local_player.tscn`).
- `EffectiveWeaponResolver.cs` — static client mirror of the server's `resolve_effective_weapon`: toggle options (item's own `Weapon` behaviors + `WeaponToggle` enchantment grants) indexed by `active_toggle`, with `AddShots`/`ShotCountMult` folded into the shot count and the true-damage/flat mods summed. Fold order (slot index ascending, innate before socketed) must match the server. Also owns the `Fingerprint` cache key. Never mutates the catalog's shared `WeaponBehavior` — copies it.

### `Game/` — GameManager + its decomposition (component scenes in `Scenes/Components/`)
- `GameManager.cs` — `Node2D, IEntity`, root node ("Main") of `Scenes/main.tscn`; **not an autoload**. Thin entity glue plus a **static facade** delegating to its child components: `Conn`, `Username`, `IsLocal` → the `DatabaseConnector` autoload; `LapQ`/`LapR` → `TableSubscriber`; `GetItem`, `GetEnchantment(s)`, `EnchantmentsChanged`, `GetResPath` → `CatalogComponent`; `GetEnemy`, `EnemyCount` → `EntitySpawnerComponent`. Reach anything else on it via `GameManager.GetComponent<T>()` — the old camera/sidebar static singletons are gone.
- `Components/Catalog/CatalogComponent.cs` (declared inline in `main.tscn`) — the `AllItems`/`AllEnchantments`/`AllTextures` views as caches (`GetItem`, `GetEnchantment(s)`, `GetResPath`, `EnchantmentsChanged`), fed by three child `TableBinderComponent`s with `ReplayExistingRows`.
- `Components/Spawning/EntitySpawnerComponent.cs` (declared inline in `main.tscn`) — row insert/delete signals from four child binders (`LocalPlayer`/`NearbyRemotePlayers`/`NearbyEnemies`/`NearbyLootDrops`, all replaying) → spawn/despawn of `LocalPlayer`/`RemotePlayer`/`Enemy`/`Drop`, plus the tracking dictionaries (`GetEnemy`, `EnemyCount`).
- `Components/Lobby/LobbyComponent.cs` (`lobby_component.tscn`) — CharSlots UI and profile panels, fed by a child `LocalPlayerProfiles` binder (inserts only; panel removal stays local via the Delete button).
- `BulletManager.cs` — `Node2D, IEntity`, root of `Scenes/bullet_manager.tscn`, instanced directly in `main.tscn` (not row-driven, so no code spawn; `z_index = 1` keeps bullets drawn above the dynamically spawned entities). Children: `BlastBullets`, the BlastBullets2D `BulletFactory2D` GDExtension node, typed only as `[Export] public Node` (reached via NodePath, not `GetChild(0)`); `Components/Bullets/BulletSpawnerComponent.cs` (`BulletPatternEvent` → per-`PatternType` dispatch, reaching the factory through **untyped `BlastBullets.Call(…)`** — no compile-time checking on those calls or their `.tres` spawn-data resources, so typos surface only at runtime; enemy bullets spawn via `spawn_controllable_directional_bullets` and the returned `DirectionalBullets2D` instances are tracked in `LiveEnemyBullets`, pruned defensively, because the factory cannot enumerate active instances); `Components/Bullets/BulletHitRouterComponent.cs` (overlap → `ReportHit` routing through the victim's `DamageReceivingComponent`; remote-player hits route to `RemoteHitWitnessComponent` → `FlagPlayerHit` instead); `Components/Bullets/BulletControllerComponent.cs` (player abilities that manipulate live enemy bullets near a point — `DeleteNear`/`SplitNear`/`AttractNear` over the spawner's `LiveEnemyBullets`; **driven by the ability system**: `LocalPlayerInventoryComponent.TryActivateAbility` applies the cast optimistically for bullet-control `AbilityEffect`s, and `activate_ability` appends the `BulletControlEvent` server-side with the item's radius — event rows arrive via the child `BulletControlEventBinder` (wired in `main.tscn`), own echoes skipped via `cast_by`; each client resolves the proximity query locally, so edge-of-radius results can differ slightly). Keeps a static `Instance` + spawn pass-throughs (`CombatComponent`/`Enemy` have no registry path to it). `BulletData.cs` — small `Resource` carried through the bullet pipeline.
- `LobbyGui.cs` — lobby/menu UI (root of `Scenes/main.tscn`, the project's main scene — the file names are swapped: `main.tscn` is the menu, `characters.tscn` is gameplay). Currently scene navigation only — not yet wired to the `create_profile`/`join_world` reducers.
- `DebugOverlay.cs` — debug HUD (declared inline in `main.tscn`; the standalone `Scenes/UI/debug_overlay.tscn` is an unreferenced duplicate); paired with server `main/debug.rs`.

### `Components/Camera/` (scenes in `Scenes/Components/Camera/` + `Scenes/world_3d.tscn`)
- `CameraRigComponent.cs` and `Camera2DPresenterComponent.cs` — 2D camera rig/presenter, children of `main.tscn`.
- `World3DComponent.cs` — root of `world_3d.tscn` (the 3D backdrop viewport).
- `HexGridOverlayComponent.cs` — hex grid debug overlay, `MapConfig` rows via a child binder; `HexGridOverlay3DComponent.cs` — its 3D sibling, declared with its own binder in `world_3d.tscn`.
- `Components/Bullets/EnemyBullets3DComponent.cs` — 3D mirror of live enemy bullets, declared in `world_3d.tscn` with `BulletScene` = `hex_bullet.tscn`. Each frame it reads the enabled bullet transforms of every `DirectionalBullets2D` in `BulletSpawnerComponent.LiveEnemyBullets` (untyped `Call("all_bullets_get_transforms")` etc., same as the other bullet components) and lays a pooled set of bullet instances over them. Liveness uses per-index `is_bullet_status_enabled` — the bulk `get_all_bullets_status` array only ever reports index 0 as enabled.

### `Components/Terrain/` (scenes in `Scenes/Components/Terrain/`)
- `TerrainComponent.cs` (`Node2DComponent`, declared inline in `main.tscn`) — receives `MapConfig`/`NearbyTerrainTiles`/`NearbyHexDecor` rows through three child binders, stores rows, dirty-flag one-rebuild-per-frame, shared wedge/decor mesh + texture caches, per-hex torus wrap + camera cull. Owns a pool of `TileComponent` instances pre-warmed to the AOI ring count (`1+3R(R+1)`; `[Export] AoiChunkRadius = 2` matching the server's `DEFAULT_TERRAIN_AOI_CHUNK_RADIUS`), growing on demand.
- `TileComponent.cs` (`tile_component.tscn`, `Node2D, IEntity`) — per-chunk scaffolding with four declared layer children: `GroundComponent` (z=0), `OverlayComponent` (z=1, centroid-scaled), `DecorShadowComponent` (z=2), `DecorComponent` (z=3). `Populate(chunkIndex, rows…)` fills the layers per frame; `Clear()` parks it back in the pool.
- `TerrainLayerComponent.cs` — base for the four layers; each owns pooled `MultiMeshInstance2D` batch leaves. The leaves stay code-created (data-driven count, deliberate perf design); z-order/scaffolding is declared in the `.tscn`. `DecorLayerComponent.cs` — shared base for the two decor layers (per-texture batches sorted by hex row).

### `Components/Movement/` + `Components/Visual/` + `Components/Interaction/`
- `Movement/InterpolationComponent.cs` (`interpolation_component.tscn`) — shared position/rotation lerp toward server targets, torus-aware via `TorusMath.NearestCandidate`; exposes `Moving`. Used by `RemotePlayer` + `Enemy`.
- `Movement/PositionSyncComponent.cs` — local player's `LocalPlayerPosition` rows + the `ReportMovement` timer.
- `Visual/RemoteVisualComponent.cs` — remote player sprite/texture; Walk/Idle driven by `InterpolationComponent.Moving`. `Visual/DropVisualComponent.cs` — drop item texture. `Visual/LocalPlayerProfileComponent.cs` — `LocalPlayerActiveProfile` rows → SpriteFrames.
- `Interaction/PickupComponent.cs` (`pickup_component.tscn`) — `AreaComponent` with declared `CollisionShape2D` + `PickupLockTimer` children; body-entered → `PickupDrop` reducer.

### `Components/Inventory/` (UI scene: `Scenes/UI/inventory_panel.tscn`)
- `InventoryComponent.cs` — `ControlComponent`; hotbar/backpack/equipment slot UI, listens for `LocalPlayer.InventoryChanged`, calls `UseItem` reducer on hotbar key press, ability keys route through `LocalPlayerInventoryComponent.TryActivateAbility`. Hotbar/Backpack stay plain containers (zero behavior) inside `inventory_panel.tscn`.
- `LocalPlayerInventoryComponent.cs` — `LocalPlayerInventory` rows → slot state; owns slot resolution (`ResolveSlotAt`/`GetSlotItemId`), the shared `TryActivateAbility(player, cellIndex)` static (cooldown/charge pre-check → `ActivateAbility` reducer with the cursor's world position → optimistic local apply for bullet-control effects via `BulletControllerComponent`; passive ability items no-op), and the `AbilityPositionMultipliers` mirror of the server's `ABILITY_POSITION_MULTIPLIERS` (both must change together).
- `SlotComponent.cs` — single inventory slot: drag/drop (`SwapSlots` reducer), left-click on ability slots (`TryActivateAbility`), right-click drop in the backpack (`DropItem` reducer), hover shows `ItemSidebarComponent`. Sets its `Icon`'s `mouse_filter` to Ignore in `OnRegistered` — the icon sits on top of the slot, and Godot asks the *hovered* control for drag data, so a hit-testable icon silently kills drag start. For the same reason the full-screen `Menu` Control in `inventory_panel.tscn` is `mouse_filter = 2` (Ignore): it renders above the always-visible Equipment panel and would otherwise swallow all input over the equipment slots whenever the Tab menu is open.
- `StatsSidebarComponent.cs` — player stat panel: the six allocatable stats (STR/WIS/DEX/DPS/SUP/ART) + DEF and unspent-points lines, with a `+` Button per allocatable stat (visible only while `UnspentPoints > 0`) calling the `AllocateStat` reducer.
- `ItemSidebarComponent.cs` — hovered slot's item name/icon/description plus full composition: base stat modifiers, stat requirements (red when unmet), behavior summary (equipped weapon shows its toggle-pattern list with the active one marked; abilities show effect/cooldown/charges), innate enchantments (no Remove button), socketed enchantments (`N / MaxEnchantments`), and — for enchantable items in equipment slots — applicable enchantments with Socket/Remove buttons calling the `ApplyEnchantment`/`RemoveEnchantment` reducers. Enchantment rows are instantiated from `Scenes/UI/enchantment_row.tscn`. Refreshes on `InventoryChanged` and `EnchantmentsChanged`; stays open while the mouse is over it.
- The whole inventory UI lives in `Scenes/UI/inventory_panel.tscn`, instanced into `local_player.tscn`. Scripts inside it reach the player via `GetAncestor<LocalPlayer>()`, not `Owner`. It holds **29 `SlotComponent` nodes**: a 5-slot `Hotbar` (indices 0–4, the weapon + four consumables) plus a `Backpack` of six 4-slot rows covering all 24 server slots — so indices 0–4 are shown twice. Every slot's `[Export] SlotIndex` is authored in the scene, and **row order is not index order** (Row 1 is armor 9–12, Row 2 accessories 5–8, Row 5 the hotbar 1–4); check the export before assuming a layout.

### `Players/`
- `Local/LocalPlayer.cs` — `CharacterBody2D, IEntity`; WASD movement at the flat `MoveSpeed` constant (there is no Speed stat), sprite Walk/Idle, 3D-model sync, camera registration. Server-table concerns live in child components, each fed by its own binder with signals wired in `local_player.tscn`: `PositionSyncComponent`, `LocalPlayerDataComponent`, `LocalPlayerInventoryComponent`, `LocalPlayerProfileComponent`. Other children: `StatsComponent`, `HealthComponent`, `FactionComponent`, `DamageReceivingComponent`, `CombatComponent`. `LocalPlayer` keeps the `InventoryChanged`/`AimSettingsChanged`/`StatsChanged` signals (components raise them via `Raise*Changed()`) and pass-through properties (`Hp`, `MaxHp`, the six stats, `Defense`, `UnspentPoints`…) so UI readers stay stable.
- `Remote/RemotePlayer.cs` — `Node2D, IEntity` root of `non_local_player.tscn` (EntityRegistry boilerplate + thin glue). `NearbyRemotePlayers` position updates arrive via a child binder (`RowUpdated` wired in the `.tscn`); the one-shot profile lookup stays a direct `Iter()` read. The work lives in `InterpolationComponent` + `RemoteVisualComponent`. Also carries a `RemoteHitWitnessComponent` hurtbox child so enemy bullets collide with the puppet on every client (see `Components/Combat/`).
- `Enemies/Enemy.cs` — `CharacterBody2D, IEntity`; server-driven puppet. `NearbyEnemies` and `BulletPatternEvent` rows arrive via two child binders (signals wired in `default_enemy.tscn`; the `NearbyEnemies` binder replays so late-spawned instances still initialize). Feeds row hp + `EnemyTemplate` max_hp into its `HealthComponent`/`StatsComponent` and forwards matching `BulletPatternEvent` rows to `BulletManager`. Mirrors a 3D model into the World3DComponent viewport via `CharacterModel3D` (exported `SkeletonScene`, wired to `Skeleton_Warrior.fbx` in the `.tscn`) — same pattern as `LocalPlayer`. `default_enemy.tscn` children: `StatsComponent`, `HealthComponent`, `FactionComponent` (Enemies), `DamageReceivingComponent` (Enemy collision layer — what `HitZone`s detect instead of the physics body), `InterpolationComponent`.
- `CharacterModel3D.cs` — the 3D character model mirroring 2D entity state. Not present in any `.tscn`; its consumers are `LocalPlayer.cs` and `Enemy.cs`.

### `Items/` + `World/`
- `Items/Drop.cs` — `Node2D, IEntity` root of `drop.tscn` (EntityRegistry boilerplate only). Children: `DropVisualComponent` + `PickupComponent`.
- `World/TorusMath.cs` — torus wrap / nearest-candidate math (`NearestCandidate`). The only file left in `World/`.

## MCP-driven playtesting (open-godot-mcp)

The editor's MCP bridge listens on port **6970** (`godot_instance list` → adopt the running instance, `godot_health check` to verify). **Only run the game while `characters.tscn` is open in the editor** (`godot_editor_edit open_scene res://Scenes/characters.tscn` first — remember `main.tscn` is the *menu*, not gameplay) — then `godot_game play`. The runtime scene root is `/root/Characters` (GameManager), with the lobby at `/root/Characters/UI/LobbyComponent`.

Manual flow that works (verified 2026-08-12):
1. `godot_screenshot game` → read the PNG to find buttons; lobby starts at Character Slots / Server List / Settings.
2. `godot_input mouse_button` (press + release) at the button's coords clicks buttons fine — including the per-profile `Join`. Pass `coords: "viewport"` with `get_global_rect().get_center()` coordinates so window-size/stretch mismatches can't silently move the click. Join succeeds when `lobby.visible == false` and a `LocalPlayer` node exists under the root.
3. `godot_input key` with `key: "Tab"` (press + release) toggles the inventory panel. Note the toggle cycles between hotbar-only and full-menu: with the menu open the `Hotbar` container is hidden, so hotbar slots can't be hovered/dragged.
4. `godot_log get/errors` reads editor+game output; `godot_exec eval` is the escape hatch for inspecting any live node (`get_tree().root.get_children()`, `find_child`, signal connection lists).
5. **Mouse injection works for hover, click, and drag** (fixed in the plugin 2026-08-12 — the runtime autoload now tracks a synthetic cursor and synthesizes `relative` on absolute `mouse_motion`, which the engine's drag-start threshold requires). Verify hover with `get_tree().root.gui_get_hovered_control()` — do NOT use `get_viewport().get_mouse_position()`, which reads the real OS cursor and never reflects injected positions. Injected events dispatch on the next frame (accumulated input), so check hover/drag state in a follow-up call. Drag recipe: `mouse_motion` to the source → `mouse_button` press → `mouse_motion` to the target with `button_mask: ["MOUSE_BUTTON_LEFT"]` (check `gui_is_dragging()`) → `mouse_button` release. Keep eval bodies loop-free — any `for`/`while` loop in eval times out.
